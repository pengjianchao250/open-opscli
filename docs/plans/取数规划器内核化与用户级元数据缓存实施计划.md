# 取数规划器内核化与用户级元数据缓存实施计划

> 分类：方案计划（docs/plans）
> 主题：将 `ops-dataset-query` Skill 取数规划器封装为 opscli 正式 CLI 命令与 MCP 工具（A 方案：单端点彻底解耦），并配套用户级元数据缓存
> 关联分析：`docs/analysis/取数规划器迁移可行性分析报告.md`
> 编写日期：2026-07-25

---

## 一、目标与路线

把取数规划器从 Skill 脚本迁入 opscli 内核，暴露为 `opscli query plan` / `opscli query flow` CLI 命令与 MCP `query_plan` / `query_flow` 工具。采用 **A 方案（彻底解耦）**：规划器只认后端 `query-metadata` 单一端点，不再依赖 Skill `data/` 缓存与 `skills upgrade`。

为避免每次取数都向后端拉全量元数据，配套一套**用户级元数据缓存**：CLI 与 MCP 共用，按用户隔离，带 TTL 与并发文件锁。

### 已确认的关键决策

| 项 | 决策 |
| --- | --- |
| 缓存 TTL | **1 小时**；登录时强制失效 |
| 后端拉取失败兜底 | **用过期缓存 + 披露 `stale=true`**，不硬失败 |
| 缓存文件命名 | 按 **email 哈希** 命名（`sha256(email)[:16]`），支持同机多账号 |

## 三、Phase 0：后端改造（data-metrics）

后端项目：`/Applications/MxSrvs/www/auto-scheduler/vendor/aukey/data-metrics`

数据本已查出、算进内存，仅被输出层白名单挡住，故改动小、无 DB migration、无需改底层查询。

### 0.1 补字段白名单（卡点 2）

- 文件：`src/Services/DatasetSkillService.php`
- 方法：`buildQueryMetadataForUser()`，`$fieldKeepKeys` 数组（约 120-124 行）
- 改动：加入 `snapshot_metric`（规划器强依赖，`dataset_guidance.py:168` 决定快照聚合口径）、`has_formula_config`（客户端 `manager._field_has_formula` 已在读）
- **暂缓（预留扩展点）**：`filter_config`（字段级默认条件）、`remarks`（字段级）本期不补——数据集级 `filter_configs` 已在 `datasetKeepKeys` 内，字段级暂无强需求。**实现时须在 `$fieldKeepKeys` 处加注释标明"如后续规划器需要字段级默认条件/备注，在此追加即可"**；客户端 `scoped_dataset_reader` 的字段解析同样预留这两列的读取扩展位并加注释，避免未来扩展时改动分散。
- 无需改：`loadColumns()`（452 行已 select `snapshot_metric`）、`buildFields()`（675 行已写入值）
- 可选：`buildFields()` 指标行（699-730 行）补 `'snapshot_metric' => 0` 以统一键集（`Arr::only` 遇缺键静默跳过，不补也不报错）

### 0.2 加全量字段参数（卡点 1）

- 文件：`src/Http/Controllers/DatasetSkillApiController.php`，`queryMetadata()`（73-99 行）：新增读取 `$request->query('include_all_fields')` 转 bool，作第 4 参传入
- 文件：`src/Services/DatasetSkillService.php`，`buildQueryMetadataForUser()`（111-173 行）：签名加 `bool $includeAll = false`；第 149 行 `if ($hasFilter)` 改为 `if ($hasFilter || $includeAll)`（无过滤且 `$includeAll` 时 `$allowedTableIds` 取全部授权数据集，fields 全量放行，即不执行 160 行 `$fields = collect()` 清空）
- 参数默认 false、显式 opt-in，保持现有裸调用"只列数据集"契约不变

### 0.3 权限与体积

- 权限天然安全：`loadAuthorizedMetadata()`（385-398 行）已按用户收敛，"全量"即"该用户授权范围内的全量"，无越权
- **体积（真实实测，2026-07-25，账号 66 数据集 / 2814 字段 / 953 select_columns）**：

  | 形态 | 体积 |
  | --- | --- |
  | 紧凑 JSON（UTF-8） | 1163.8 KB（约 1.14 MB） |
  | 紧凑 JSON（ensure_ascii） | 1268.7 KB |
  | 缩进 JSON | 1499.5 KB |
  | **紧凑 JSON gzip 后（上网体积）** | **93.2 KB** |

  结论：数据量小。gzip 后约 93 KB，一次请求亚秒级、稳在 30 秒命令窗口内，**一次全量拉完即可，无需分页/N 次调用**。由客户端缓存承接，同一用户 1 小时内不再重复拉。
- **传输必须开 gzip**：客户端带 `Accept-Encoding: gzip`（httpx 默认支持），1.14MB → 93KB 约 12 倍压缩，收益最高、成本为零。

### 0.4 验证

- `GET /v1/data-metrics/datasets/query-metadata?include_all_fields=1` 返回全部授权数据集的全部字段，且 field 对象含 `snapshot_metric` / `has_formula_config`
- 裸调用（不带参数）行为不变，仍 `fields=[]`
- 顺带核对：修复既有"客户端 fixture 假设含 `has_formula_config`/`filter_config`、后端白名单实际不下发"的契约漂移

## 五、Phase 2：用户级元数据缓存

### 5.1 模块与结构

- 新增：`opscli/query/services/metadata_cache.py`，结构镜像 `opscli/mcp/credential_cache.py`
- 核心类 `MetadataCache` + 模块级池 `get_metadata_cache(base_dir)` + `invalidate_metadata_cache(base_dir)`
- **身份无关设计（守铁律2，query 禁止 import mcp）**：缓存只接收 `(base_dir, user_email, fetch_fn)`，身份由调用方注入

### 5.2 两层缓存

- L1 内存：模块级池按 `base_dir` 键（复刻 `get_credential_cache()` 池化范式），服务 MCP 长驻进程高频读
- L2 磁盘：`<base_dir>/metadata/<sha256(email)[:16]>.json`，服务 CLI 短生命进程跨调用复用

### 5.3 磁盘信封格式

```json
{
  "cache_version": 1,
  "user_email": "<email>",
  "metadata_version": "<后端版本戳>",
  "fetched_at": "<ISO UTC>",
  "ttl_seconds": 3600,
  "payload": { "datasets": [...], "fields": [...], "select_columns": [...] }
}
```

### 5.4 读取/刷新流程（双重检查防惊群）

```
get_full_metadata(base_dir, email, fetch_fn):
  1. L1 命中且同 email 且未过期(1h) → 返回
  2. 读 L2，命中且同 email 且未过期 → 回填 L1 → 返回
  3. miss/过期 → with file_lock(base_dir/metadata/.lock_<email_hash>):
       重读 L2（双重检查：他进程可能刚刷完）
       仍过期 → fetch_fn()  # query-metadata?include_all_fields=1
                 成功 → 原子写 L2（TemporaryDirectory + Path.replace，照搬 updater 约定）
                 失败 → 若存在过期 L2 → 返回过期 payload 并标 stale=true
                        否则抛错（无任何缓存可用）
       回填 L1
  4. 返回 {payload, stale, fetched_at}
```

### 5.5 命中判定（同时满足才 HIT）

1. `user_email == 当前用户`（换账号即失效）
2. `now - fetched_at < 3600s`
3. （可选）`metadata_version` 与后端一致——本期先只靠 TTL

TTL 可经 `config.ini [query] metadata_cache_ttl` 覆盖，默认 3600。

### 5.6 验证

- 单测（铁律8：`tmp_path` + `respx` mock，不碰真实网络/Keychain）：
  - 首次 miss → 拉取并落盘；二次 HIT 不再拉取
  - 过期后自动刷新
  - 换 email → 旧缓存不命中，各自独立文件
  - `fetch_fn` 抛错 + 存在过期缓存 → 返回 `stale=true`
  - 并发（多线程模拟）只触发一次 `fetch_fn`（双重检查生效）

## 六、Phase 3：QueryClient / QueryManager 全量字段支持

- `opscli/query/transport/client.py`：`fetch_query_metadata()` 增加 `include_all_fields: bool` 参数，透传到 query string
- `opscli/query/services/manager.py`：新增 `metadata_all()`（或 `metadata(full=True)`），返回全量 payload；内部经 Phase 2 缓存（传入 base_dir + email + 以 `fetch_query_metadata(include_all_fields=True)` 为 `fetch_fn`）
- 验证：`respx` mock 全量响应，断言参数透传、缓存介入、`QueryMetadataResult` 承载全量 fields

### 6.1 解析策略：内存直接解析（不做流式落文件）

实测全量 payload 约 1.14 MB（gzip 93 KB），属小数据量，采用**内存直接解析**：`httpx` 拉回 → `json.loads` → 写 Phase 2 磁盘缓存（原子写）。

- **不引入"流式落文件 + 流式解析（ijson）"**：当前量级下与内存解析效果基本一致，属过度设计（铁律20）。且 Phase 2 的 L2 磁盘缓存已经把 payload 落成 JSON 文件，"下载成文件再解析"的诉求由缓存天然覆盖——拉一次、落一次、之后都读文件。
- **预留扩展点（加注释）**：若未来 payload 涨到几十 MB 级（数据集/字段数量数量级增长）导致内存峰值成顾虑，再改为从 L2 缓存文件用 `ijson` 流式解析。在 `metadata_all()` 解析处加注释标明此扩展方向。

## 七、Phase 4：规划器内核化

### 7.1 代码迁移

- 五文件迁入 `opscli/query/services/planner/`：`query_plan` / `agent_query_planner` / `dataset_guidance` / `typed_schema_linking` / `scoped_dataset_reader`（及 `time_scope` / `scoped_metadata_index` / `plan_integrity` / `evidence_contract` / `field_semantics` 等依赖库）
- 静态资源：`intent_rules.json` + `query_plan.schema.json` 打包为内核包内资源（`importlib.resources` 读取）

### 7.2 数据源改造（A 方案核心）

- `scoped_dataset_reader` 从"读 Skill `data/*.csv`"改为"读 Phase 2 缓存的 `metadata_all()` JSON"
- 在 JSON 形态上**重建** CSV reader 独有逻辑：同物理字段多 `global_alias` 合并去重、快照一致性、字段级 `filter_config` 解析
- 3 处 subprocess 换为内核内部调用：
  - 元数据刷新 → Phase 2 `invalidate + get_full_metadata`
  - 平台/部门权限枚举 → 复用 `QueryManager.build_simple_and_run`

### 7.3 对外入口

- CLI：`opscli query plan` / `opscli query flow`（`opscli/query/commands/cli.py` 注册，产出规划合同 JSON）
- MCP：`query_plan` / `query_flow` 工具（`opscli/mcp/tools/query.py` 加函数 + 入 `_ALL_TOOLS`），补上当前 MCP 侧最大能力缺口（无规划器）
- 身份注入：CLI 层读 `CredentialStore` 拿 email 传 `base_dir=CONFIG_DIR`；MCP 层用 `helpers._get_authenticated_user_email()` + `_get_credential_dir()` 传入

### 7.4 SKILL.md 契约承接

- 规划器产出的 `query_plan_model_contract_v2`（model_view / answer_contract / execution_ref）消费契约需在 CLI/MCP 边界表达；`ops-dataset-query` SKILL.md 入口从 `python3 scripts/query_flow.py` 改为 `opscli query flow`
- 验证：迁移前后同一批用户请求的规划合同关键字段（选表结果、时间窗、execution_ref）一致（回归对拍）

## 十、验收总标准（铁律22）

- 后端 `include_all_fields=1` 全量返回且含 `snapshot_metric`/`has_formula_config`，裸调用契约不变
- `opscli query flow "<请求>"` 与 MCP `query_flow` 产出与迁移前 Skill 规划器一致的规划合同（回归对拍通过）
- 同一用户在 1 小时内多次取数（无论 CLI 或 MCP）只拉取一次全量元数据（缓存命中日志/计数验证）
- 登录切换账号后强制重新拉取
- 后端故障时返回过期缓存并披露 `stale=true`
- 全量单元测试通过（`tmp_path` + `respx`，不依赖真实网络与 Keychain）
