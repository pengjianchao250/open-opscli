# OPS App 迁移运行兼容与发布门禁闭环需求

## 一、目标

源码复制迁移完成后必须同时满足：

1. 原项目的本地启动仍可正常运行；
2. 目标副本只增加一层薄 AppHub 适配，不以模板重构替代原业务源码；
3. 目标副本通过统一验证后可由 `opscli app push` 推送到远端 `master`，并具备进入 AppHub 线上构建的必要资产；
4. 用户在任务开始时已授权 `push_on_success` 且推送范围未变化时，验证通过后自动推送，不重复确认。

迁移改造本身允许因源项目不同而采用不同实现，但改造结果必须接受同一验证合同。验证失败时只修改目标副本，持续执行“定位失败项 → 最小修复 → 定向复验”，直到通过或遇到需要用户决策的外部阻塞。

## 二、范围边界

- 本需求只适用于 `.opscli/project.json.origin_type=migration_copy` 的源码复制迁移项目。
- 普通新建项目继续使用现有模板克隆、`app create`、`app init`、`app push` 流程，不读取迁移验证清单，不增加迁移合同门禁，不改变创建请求、目录结构或身份逻辑。
- 源目录始终只读；迁移适配、验证清单和修复只发生在独立目标目录。
- 自动修复限于薄适配、构建配置、入口、路径、健康检查和发布资产；涉及业务重写、数据删除、敏感权限变化或无法确认的运行语义时停止并向用户说明。

## 三、必须合同

仅保留三项顶层合同，不为 SPA、WebSocket、SQLite、后台任务等场景另建合同；这些能力只在项目实际使用时作为条件检查。

### 3.1 迁移完整性合同

验证源目录存在且未被迁移流程改写、源目标互相隔离、复制状态完整、最小适配文件已登记、本地敏感状态不会进入交付源码，并确认 `opscli app migrate verify` 已达到 `delivery_ready=true`。

### 3.2 运行兼容合同

验证清单字段继续使用 `dual_runtime` 保持兼容，但默认只执行两个快速冒烟：

- 原本地入口能够启动或完成最小健康检查，证明薄适配没有破坏本地运行；
- AppHub 薄适配入口能够启动并通过 `/__apphub_healthz`，按改动范围抽查必要页面、静态资源或一个核心只读接口。

完整业务一致性不再作为每次迁移的固定检查。只有出现下列任一风险时，才要求提供 `parity_check` 并启用 `require_parity`：

- 薄适配修改了原业务源码、API 路由、响应结构或鉴权语义；
- 修改了公共路径、SPA fallback、WebSocket 或前后端代理方式；
- 修改了 SQLite、`/data`、后台任务、进程模型或持久化行为；
- 本地入口与 AppHub 入口经过不同业务执行链路，无法由相同核心模块自然保证一致性。

未命中风险时，业务一致性记录为 `not_required`，不阻断交付。命中风险但未提供检查命令时记录为 `missing_required_command` 并阻断交付。

所有命令由项目证据确定，以参数数组执行，禁止 shell 字符串拼接。验证器记录退出码、标准输出和标准错误，但不虚构项目不存在的测试命令；同一次验证中完全相同的命令只执行一次，其他检查复用结果。

### 3.3 发布门禁合同

至少验证：

- `app.yaml`、`backend/app.py`、`Dockerfile`、`nixpacks.toml`、`.dockerignore`、`.gitignore` 和实际依赖清单存在；
- 存在前端目录时，`frontend/package.json` 与唯一锁文件存在；
- `app.yaml.app_id` 合法并与迁移应用身份一致，且不含废弃顶层 `name`；
- Dockerfile 与 Nixpacks 使用 `backend.app:app`、端口 `8000`，后端提供 `/__apphub_healthz`；
- 必要发布资产未被忽略，Corepack、动态访问前缀和运行时公开快照合同通过；
- 推送前没有默认禁止提交的环境文件、数据库和根运行数据。

## 四、验证结论与证据

```text
release_ready = migration_integrity && dual_runtime && release_gate
```

验证器将结果写入 `.opscli/migration/<migration-id>/validation-manifest.json`。清单必须包含三项合同、项目命令结果、`release_ready` 和排除本地状态后的交付源码指纹。

`opscli app push` 对迁移项目必须拒绝以下情况：

- 清单不存在或三项合同未全部通过；
- 发布资产当前已不满足门禁；
- 当前交付源码指纹与验证清单不一致，即验证后源码又发生变化。

普通项目不读取此清单。

### 4.1 耗时控制

- 默认验证不得主动安装依赖；优先复用项目已有 `.venv`、`node_modules`、pnpm store 和构建缓存。
- Python 与 Node 版本在迁移开始时按项目证据确定，验证过程中不得因试错反复重建环境。
- 锁文件和依赖声明未变化时不重复安装依赖；生产构建在同一轮验证中最多执行一次。
- 只有依赖环境缺失、锁文件变化或构建资产变化时，才执行对应安装或构建。
- 文件扫描默认排除 `.git`、`.opscli`、`.venv`、`node_modules`、`dist`、`build`、`.vinext`、`.next`、`.nuxt` 和缓存目录。
- 两个必需冒烟检查默认单项超时 180 秒；项目明确需要更长启动时间时才提高超时。

## 五、自动修复与推送闭环

1. 迁移适配前记录本地运行基线、可复用依赖环境和风险触发项；
2. 执行源码复制迁移和薄适配；
3. 执行 `opscli app migrate verify`；
4. 执行三项标准验证合同，其中 `dual_runtime` 默认只运行两个轻量冒烟，风险触发时再运行定向业务一致性检查；
5. 未通过时按失败项最小修改目标副本并重复第 3、4 步；
6. 仅当 `release_ready=true` 且用户已授权 `push_on_success` 时执行 `opscli app push`；
7. push 成功只表示源码已到达远端 `master`，不得在没有平台证据时声称已发布或线上运行成功。

## 六、验收标准

- 迁移项目缺少 `app.yaml` 等线上构建资产时验证失败；
- 本地或 AppHub 冒烟失败时验证失败；
- 风险触发后业务一致性命令缺失或失败时验证失败，未触发时记录 `not_required`；
- 同一检查命令被多个检查项引用时只实际执行一次；
- 锁文件和依赖声明未变化时，不因验证流程默认重新安装依赖；
- 验证通过后修改交付源码，push 因清单过期而失败；
- 普通新建项目不需要迁移验证清单，原有 create/init/push 回归保持通过。
