# 应用推送后构建状态回传需求与方案

- 日期：2026-10-29
- 状态：两份独立失败附件已在本地实现；`tests/app` 294 条通过，待部署到 QA 后联调
- 范围：`open-opscli` 的 `app` 命令与 Codex 使用规范、`ops-apphub` 的只读发布查询接口；不改变应用构建和自动发布机制。

## 1. 背景与目标

新建应用和源码复制迁移最终都通过 `opscli app push` 将源码推到绑定仓库的 `master`。目前命令只报告 Git 推送结果，AppHub 随后异步构建，用户要登录运营系统才能知道结果并查看构建日志。

目标是 Codex 在本次推送后每 15 秒查询一次**本次提交**的发布状态；成功时只返回完整的运营系统入口链接，失败时返回简短错误摘要，并分别提供完整构建日志和发布诊断两个可点击文件，供下一轮对话修复。等待结束、超时、取消或进程退出时，轮询立即停止并清理，不遗留后台任务。

## 2. 已核实的现状

| 能力 | 源码证据 | 结论 |
| --- | --- | --- |
| 推送身份 | `open-opscli/opscli/app/services/gitops.py` 的 `push_all` 返回 `commit_sha`、`remote_commit_sha`、`pushed`；`services/manager.py` 原样带入结果 | 可用完整 40 位 SHA 标识本次推送；`pushed=false` 不代表发生新的构建。 |
| 自动发布 | `ops-apphub/apphub/jobs.py` 的 `run_auto_publish_job` 每 15 秒扫描一次远端 `master`，按 SHA 创建或续跑 release | 推送与 release 建立之间存在空窗；15 秒客户端轮询可能先看到“未开始”。短时间连续推送时，中间提交可能未被扫描到。 |
| 发布事实 | `GET /api/v1/apps/{app_id}/deployments/latest` 返回最新 release 的状态、SHA、release ID、deployment ID、错误码，并分别返回最新尝试与当前线上版本 | 已有只读接口，但“最新”可能属于其他提交，不能直接作为本次推送的终态判断。`ready` 是最新状态和已有公开 URL 的组合，仍须核对 SHA 与当前线上 release ID。 |

| 应用直达 URL | AppHub `public_base + app_public_path(app_id, slug)`；按提交查询接口另返回完整的 `iframeEntry` 入口 | CLI 在本次 release 成为当前 healthy 版本时只展示 `entry_url`。 |

| 当前客户端边界 | `opscli app push --wait` 与 `app deployment wait` 按 SHA 查询终态；`AppHubClient` 复用运营 JWT Bearer 认证并读取完整日志及发布事件回放 | 失败时返回两个独立附件元数据；已同步 `ops-app-build-spec` 的 Codex 回复规范，不要求用户在浏览器登录后才能查看结果。 |

上述现状以本地源码与合同为准；两份附件的端到端链路尚未在 QA 验证，不能据此宣称线上可用。

## 3. 用户需求

1. 新建和迁移项目的 `app push` 成功且 `pushed=true` 后，Codex 自动进入本次 SHA 的发布等待；立即查一次，此后每 15 秒查一次。
2. `healthy` 且本次 release 已成为当前线上版本时，只返回可点击的完整运营系统入口，例如 `[https://ops.qa.aukeyit.com/iframeEntry?menuId=apphub:foZPp](https://ops.qa.aukeyit.com/iframeEntry?menuId=apphub:foZPp)`；不需要在成功消息中返回 AppHub 直达 URL 或其它内部字段。
3. `failed` 时在消息中输出 `error_code` 和简短失败摘要，并将本次 deployment 的**完整构建日志**与本次 release 的**发布诊断**分别保存为两个文件，提供两个独立、可点击的文件链接。没有 deployment ID 时仍返回发布诊断文件，不误取旧构建日志，也不伪造完整构建日志附件或链接。
4. 推送完成后先提示正在等待本次提交的发布结果。15 秒轮询由当前等待进程执行，不为每次“仍未完成”的查询向对话发送消息；仅在阶段发生变化时可更新进度，终态只发一次明确结果。不能把 Git push 成功、Coolify `finished` 或旧版本仍可访问当成新版本发布成功。
5. 发布查询失败、权限不足、超时、取消和被后续提交覆盖时给出明确状态和可重查的 SHA；不伪报构建失败或成功。20 分钟超时后提示用户登录运营系统“应用 → 我的应用管理”查看，或用本次 SHA 再启动一轮 15 秒一次、最长 20 分钟的查询。
6. 轮询仅在当前 CLI/Codex 等待进程内运行，不创建持久计划任务；任一终止路径及时结束定时器、关闭 HTTP 客户端并清空本次等待状态。

## 4. 建议实现

### 4.1 AppHub：按提交查询只读发布事实

新增成员可读的 `GET /api/v1/apps/{app_id}/deployments/by-commit/{commit_sha}`。复用现有 `find_release_by_commit(..., include_rollback=False)`，按应用 ID 和完整 SHA 定位，避免 `/latest` 在并发 push 或回滚后指向别的 release。响应建议包含：

```json
{
  "app_id": "RPsOE",
  "commit_sha": "<40位SHA>",
  "status": "not_started | received | validated | tagged | deploying | verifying | healthy | healthy_not_current | failed | superseded",
  "release_id": null,
  "deployment_id": null,
  "is_current_release": false,
  "error_code": null,
  "error_summary": null,
  "entry_url": null
}
```

- `not_started` 表示自动扫描尚未为该 SHA 建立 release，不返回 404。若仓库 `master` 已移到其他 SHA 且本 SHA 从未建 release，则返回 `superseded`，避免一直空等；已有 release 时继续跟踪原 release。
- `healthy` 仅在 `release.id == apps.current_release_id`、应用 active 时视作本次发布成功。若 release 是 healthy 但当前指针已经切向后续版本，返回 `status=healthy_not_current`，不声称链接指向本次版本。
- `failed` 返回现有 release 的 `error_code` 与经服务端裁剪、脱敏的 `error_summary`。部署前失败也必须有可用诊断；不将内部凭据、完整异常对象直接返回。
- `entry_url` 由 AppHub 按平台公开 origin 与已核实的运营前端路由生成，仅在本次版本已上线时返回。成功态 Codex 消息只使用该完整链接；QA 与生产分别使用各自 `public_base`，客户端不得硬编码域名。
- 继续沿统一 Bearer/Cookie 认证、成员权限、版本门禁与错误信封。无需新表或更改发布状态机；同步 `docs/contracts/cli-api.yaml` 与 OpenAPI 校验。

按 deployment ID 查日志的旧接口只返回尾部；已新增 `GET /api/v1/apps/{app_id}/deployments/{deployment_id}/logs/complete`，返回完整日志文本及 `redacted` 标记，客户端保存为 UTF-8 `.log` 附件。完整是指保留全部日志行，不是只取尾部；服务端对常见凭据、Cookie、Authorization、密码等敏感值脱敏。部署前失败没有 deployment ID 时不生成空日志附件。

发布诊断沿用现有 `GET /api/v1/apps/{app_id}/releases/{release_id}/events?since_seq=0`。客户端按 SSE 帧读取至 `event: done`，避免按提交查询已看到 `failed`、但失败终帧尚未写入事件表时漏掉错误码；单次读取限制为 10 秒无数据超时、30 秒总时长，超限只影响诊断附件。只保存前端可见事件的序号、级别、状态、说明、错误码、修复建议，以及 `detail` 中经白名单筛选的 `rule_id/file/line`；不保存 `hidden` 事件或未知原始 `detail`。诊断内容另存 UTF-8 文件，不与 Coolify 构建日志混合。

### 4.2 opscli：复用一次性等待器

- `AppHubClient` 增加按 SHA 查询和按 deployment ID 取构建日志的只读方法，继续用 `AuthClient.get_token("ops")`。
- 增加可复用的等待逻辑：第一次立即查询，之后以单调时钟每 15 秒查询；建议默认最长等待 20 分钟，可配置超时但设置合理上限。15 秒指两次请求**开始**的目标间隔，不并发叠加请求。
- `app push` 增加 `--wait` 选项，保持现有默认快速返回行为。Codex 的新建、迁移和后续推送规范统一使用 `opscli app push ... --wait --json`，从而在 Codex 流程中自动等待。另提供 `opscli app deployment wait <path> --commit <sha> --json` 供中断后续查，无需再次 push。
- `pushed=false` 时不自动等待；若用户明确使用 `deployment wait`，允许重查既有 SHA。启动等待前核对 `commit_sha == remote_commit_sha`，不一致则报告远端已被后续提交覆盖。
- JSON 结果保留现有 `data.pushed`、`data.commit_sha` 等推送字段；发布结果中的 `build_log_attachment` 与 `diagnosis_attachment` 分别记录两份文件的绝对路径、文件名和媒体类型。发布失败仍保留“推送已成功”的事实，不能把两种结果混为一个布尔值。成功态对话把 `entry_url` 渲染成可点击的 Markdown 链接；失败态消息输出摘要和两个独立的文件链接。`--json` 的 stdout 只输出一个最终 JSON 对象，不把完整文件内容复制到 JSON 字段。
- 发布失败时仅下载**同一 release 的**完整 deployment 日志，并按本次 `release_id` 读取发布诊断。两个请求独立处理：日志服务不可用时标注 `logs_unavailable`，仍返回可用的诊断文件；事件流不可用、未正常结束或无可见事件时标注 `diagnosis_unavailable`，仍返回可用的完整构建日志。部署前失败无 deployment ID 时只生成诊断文件，明确说明未产生构建日志。两份文件保存在当前用户可访问的稳定绝对路径，不随轮询任务清理而删除；构建日志不按行数截断，诊断事件不按前端 200 条窗口截断。写入诊断文件前对文本做敏感值脱敏。
- 用 `try/finally` 关闭 HTTP 连接；等待使用当前进程内的循环或可取消计时器，不注册 APScheduler、系统计划任务或常驻后台线程。终态、超时、Ctrl+C、异常和 Codex 工具会话取消都要停止下轮请求。超时结果为 `unknown_timeout`，不是构建失败。
- 超时回复给出 `opscli app deployment wait <project-root> --commit <sha> --json`，该命令重新开始一轮等待，不重复推送；同时提示登录运营系统“应用 → 我的应用管理”手动查看。

### 4.3 Codex 对话呈现

更新仓内 `ops-app-build-spec` 模板及安装版本的推送规范：仅当 `pushed=true` 且本次发布状态为 `healthy`、`is_current_release=true` 时返回完整 `entry_url`，成功消息不附其它地址；`failed` 时展示错误码、简短摘要、对应 SHA，并分别附上可点击查看的完整构建日志与发布诊断文件；缺失的文件只说明原因，不伪造链接。超时/中断只报告已推送、发布未确认和重查命令。分享链接仍需访问权限，不能暗示链接本身会授权。

对话只提示一次“正在等待本次提交的发布结果”，同一阶段的每次轮询不产生单独消息；阶段变化时可以更新进度，成功、失败、超时或中断时给出一次最终反馈。`--json` 的 stdout 同样只输出一次最终结果，不连续输出轮询快照。

**Codex 返回样式（示例值，非实际发布结果）**

成功态直接输出可点击的 Markdown 链接；链接文字使用完整 URL，链接目标与文字一致。不要放进代码块或反引号中，否则无法点击：

> 构建发布成功：[https://ops.qa.aukeyit.com/iframeEntry?menuId=apphub:foZPp](https://ops.qa.aukeyit.com/iframeEntry?menuId=apphub:foZPp)

失败态在消息中保留简短诊断，并用 Markdown 文件链接指向实际生成的 UTF-8 `.log` 附件：

> 构建发布失败。  
> 错误码：BUILD-FAILED  
> 提交 SHA：31baa40960044021d1c22cfd0ef60b6cd7031dc3  
> 失败摘要：前端依赖安装失败。  
> 完整构建日志：[查看完整构建日志](<构建日志文件的实际绝对路径>)  
> 发布诊断：[查看发布诊断](<发布诊断文件的实际绝对路径>)

上例中的路径是模板占位符，实际回复必须换成已存在的文件绝对路径；路径含空格时用尖括号包住 Markdown 链接目标。不能只显示文件名、把链接放在代码块中，或在文件不存在时输出可点击链接。点击后应能分别打开两份完整文件；轮询任务结束不删除文件。

超时态示例：

> 本次提交已推送，20 分钟内尚未确认发布结果（提交 SHA：`31baa40960044021d1c22cfd0ef60b6cd7031dc3`）。可登录运营系统“应用 → 我的应用管理”查看；也可执行 `opscli app deployment wait <项目目录> --commit 31baa40960044021d1c22cfd0ef60b6cd7031dc3 --json` 再等待一轮。超时不是构建失败。

## 5. 边界与风险

- AppHub 自动扫描周期为 15 秒，客户端按 15 秒查询不会加快发布。高频同时等待需要评估 AppHub 查询容量；按 SHA 查询应以数据库为主，不在每轮访问 Coolify。仅失败终态各查一次构建日志和发布事件回放。
- 当前 `/deployments/latest` 的测试允许“最新 healthy release ID 与当前 release ID 不同仍 `ready=true`”。新能力必须严格核对本次 SHA 和当前指针，不能复用这个 `ready` 布尔值作为唯一成功条件。
- 运营入口依赖运营前端的 `iframeEntry` 路由；应在 QA 用真实已发布应用验证链接、登录回跳和权限拒绝。服务端构造入口时保留直达 URL，以免运营入口集成故障掩盖发布事实。
- 发布前的 app.yaml 校验、密钥扫描、仓库错误等失败不会产生 Coolify deployment。其 `error_summary` 应来自 release 失败记录，并返回可获取的发布诊断文件，不虚构“构建日志”。
- 若 AppHub 自身查询持续不可用，客户端按有限重试与总超时收口，保留 SHA 以供后续重查；不能因为查询故障重新执行 push 或另行创建 release。

## 6. 验收标准

1. 新建与迁移项目 push 后，Codex 均每 15 秒查询对应 SHA；首查可在 AppHub 建立 release 前返回 `not_started`，最终按真实终态收口。
2. 旧版本 healthy、本次 failed 时返回失败和本次发布的两份独立文件；其他人随后 push 时不会把对方 release 认作本次结果；中间 SHA 未建 release 且被覆盖时返回 `superseded`。
3. 本次 healthy 且为当前版本时，Codex 只返回可点击的完整运营入口 `https://<ops-origin>/iframeEntry?menuId=apphub:<app_id>`；链接文字与目标 URL 一致、不在代码块中。QA 浏览器点击入口到正确应用，未授权访问仍按现有权限规则拒绝。
4. 部署前失败有错误摘要和发布诊断文件，且不生成伪构建日志；部署阶段失败有匹配 deployment 的完整构建日志文件及匹配 release 的发布诊断文件，分别提供可点击链接。事件流包含全部前端可见事件及失败终帧，不含 `hidden` 或未知 `detail`；日志包含全部构建日志行。轮询清理后两份链接仍可用；任一来源不可用时仍返回另一份并说明缺失项。
5. `pushed=false` 不启动自动等待；超时、Ctrl+C、网络故障、正常终态后无残留定时器、后台任务或重复请求。可用 SHA 独立续查。
6. AppHub 的路由权限/契约测试、opscli 客户端与等待器的假时钟测试、CLI JSON 合同测试通过；再以 QA 真实推送各验证一次成功与失败链路。QA 验证前不宣称线上可用。

## 7. 已确认的产品选择

`app push` 保留原有快速返回默认值，Codex 使用规范加 `--wait`；等待上限默认 20 分钟。超时后按 SHA 重新等待或到运营系统查看。成功态只返回完整 `iframeEntry` 链接；失败态将完整构建日志和发布诊断作为两个独立文件交付，缺失时分别说明。两份附件及本机两处已安装的 Codex Skill 均已更新，`tests/app` 294 条通过；QA 联调仍待实施。
