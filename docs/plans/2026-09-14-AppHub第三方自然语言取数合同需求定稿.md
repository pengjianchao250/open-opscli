# AppHub 第三方自然语言取数合同需求定稿

## 1. 背景

AppHub 页面需要把用户自然语言转换为 Keepa、SellerSprite 可接受的真实场景和参数。当前 AppHub 运行时路由已经定义 REST 端点、鉴权、同步/异步流程和结果存储规则，但两个来源 Skill 主要描述 CLI/MCP，缺少面向 AppHub 后端的交接合同。

缺少交接时，业务项目可能把页面字段直接当作上游字段，例如把 `asin`、`marketplace` 放在 REST 顶层，触发 `422 Extra inputs are not permitted`。

## 2. 目标

建立不改变既有查询行为的专用链路：

```text
用户自然语言
→ 来源 Skill 识别正式场景
→ 生成已验证的 AppHub REST 请求合同
→ ops-app-data-builder 消费合同
→ AppHub FastAPI /api
→ OPS、Keepa 或 SellerSprite
```

目标：

1. 明确自然语言到 `scenario`、`site`、`period`、`params` 的映射边界。
2. 明确 REST 路径、允许字段、响应数据路径和错误判断方式。
3. 明确 Keepa 同步查询与 SellerSprite 异步任务的差异。
4. 禁止业务项目猜测场景、字段、鉴权字段或内部运行参数。
5. 保持 OPS、Keepa、SellerSprite CLI/MCP 行为不变。

## 3. 现状与职责边界

### 3.1 OPS

OPS 已由 `ops-dataset-query` 和查询规划器提供完整查询合同：

```text
自然语言
→ 数据集与在线元数据
→ dimensions / metrics / filters / aggregation
→ query flow 或 query simple
→ execution_ref / answer_contract / evidence_contract
```

本需求不重写 OPS 查询规划器，也不修改 `ops-dataset-query` 或 `ops-query-wizard`。

### 3.2 AppHub 数据层

`ops-app-data-builder` 和 `references/runtime-source-routing.md` 已具备浏览器仅访问 FastAPI `/api`、统一 REST Base URL、Keepa 同步、SellerSprite 异步及用户隔离规则。本需求不新增统一模型或 AppHub 运行时端点。

## 4. 最小改动范围

### 4.1 必改

1. `opscli/skills/templates/ops-keepa/SKILL.md`
   - 追加 AppHub REST 请求、响应、错误和自然语言映射规则。
   - 明确只在 AppHub 数据层构建场景启用。
2. `opscli/skills/templates/ops-seller-sprite/SKILL.md`
   - 追加 AppHub REST 异步任务、Listing Analysis、任务复用和结果读取规则。
   - 明确只在 AppHub 数据层构建场景启用。
3. 本需求文档作为实现和评审基线。

### 4.2 暂不改

- `opscli/skills/templates/ops-dataset-query/SKILL.md`
- `opscli/skills/templates/ops-query-wizard/SKILL.md`
- `opscli/skills/templates/ops-app-build-spec/SKILL.md`
- `opscli/skills/templates/ops-app-data-builder/SKILL.md`
- `opscli/skills/templates/ops-app-data-builder/references/runtime-source-routing.md`
- OPS 查询规划器、第三方 REST 服务端、CLI/MCP Tool 实现

## 5. AppHub 合同要求

### 5.1 通用

- 只使用正式 REST 合同允许的字段，未知字段不得透传。
- 身份、Session、JWT、Cookie、内部 API Key 和本地路径不得进入业务请求体。
- 同时检查 HTTP 状态、响应 `success` 和业务状态。
- 业务分支依据稳定的 `error.code`，不解析错误文案。
- 页面字段必须先显式映射到上游字段；不确定场景或缺少必填参数时澄清或标记 `blocked`。

### 5.2 Keepa

- 端点：`POST /api/v1/keepa/run`。
- 页面数据优先使用 `scenario`、`site`、`params`、`export_format="json"`、`wait=true`。
- 成功业务数据读取 `data.data`，不读取 CLI/MCP 的 `export.url`。
- HTTP 200 且 `success=false` 仍为失败。
- 指定 ASIN 当前信息映射为 `scenario="product"` 和 `params.asin`；除非用户明确要求，不默认启用历史数据。
- 场景和参数沿用正式合同，不得自造 `marketplace` 等顶层字段。

### 5.3 SellerSprite

- 普通任务：`POST /api/v1/seller-sprite/jobs`，状态和结果分别使用对应 `job_id` 端点。
- HTTP 202 只表示已受理；保存并复用 `job_id`，不得重复提交。
- `queued`、`running`、`ready=false` 为处理中；只有 `succeeded` 才读取 `data.result`。
- `listing-analysis` 使用独立端点，不得提交到普通 jobs。
- 请求使用正式的 `scenario`、`site`、`period`、`page_size`、`params`；`月份`/`数据月份`/`YYYY-MM` 使用顶层 `period`。
- 场景和参数以正式场景合同及 `SCENARIO_PARAMS_ZH.md` 为准，不根据页面字段或旧项目猜测。

## 6. 兼容性原则

- 现有 CLI/MCP 章节原文保留。
- AppHub 章节只在 `ops-app-data-builder` 生成或维护站点数据层时生效。
- 不改变场景名称、参数含义、命令入口、MCP Tool 或服务端接口。
- 不让 AppHub 参数污染 CLI/MCP 参数，也不反向兼容猜测字段。

## 7. 验收标准

1. 两个来源 Skill 明确区分 CLI/MCP 与 AppHub REST 合同。
2. Keepa AppHub 请求不再把未声明页面字段放入 REST 顶层。
3. SellerSprite AppHub 调用正确区分 202 pending、成功结果和失败终态，并复用任务。
4. OPS 查询合同和 `ops-query-wizard` 行为不变。
5. `git diff --check` 通过；测试不访问真实第三方账号或提交真实业务数据。
