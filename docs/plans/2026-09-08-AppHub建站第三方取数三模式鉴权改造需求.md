# AppHub 建站第三方取数三模式鉴权改造需求

> 日期：2026-09-08  
> 状态：已实施，本次相关验证通过  
> 适用范围：Codex 基于 AppHub 最新模板构建的新项目  
> 兼容策略：不兼容旧模板项目，不保留旧鉴权配置兜底

## 1. 背景

AppHub 最新建站模板已经为 OPS 取数提供 `viewer`、`session`、`local` 三种鉴权模式，但当前 `ops-app-build-spec` 和 `ops-app-data-builder` 对 Keepa、SellerSprite 仍按共享后端 Secret 设计：

```env
OPSCLI_THIRD_PARTY_DATA_API_KEY=<backend-secret>
```

Keepa 和 SellerSprite 现已支持与 OPS 相同的三种身份模式，因此 Codex 建站规范和数据层生成规范需要同步调整，使新项目按当前访问用户身份调用第三方数据 API，并同步修正第三方数据的存储隔离模型。

本需求已确认，实施范围为 Skill、Reference、测试和评估用例，不修改 `opscli/app` 或最新模板仓库。

## 2. 模板基线

最新模板以以下仓库为唯一事实源：

```text
仓库：http://10.1.13.143:3000/aukeys-admin/template
分支：master
分析基线提交：3f2622ab3d0e67ab89ac281721d69f2ee8380a8a
提交时间：2026-09-08 12:26:26 +0800
提交说明：fix: 修复部署问题
```

本次需求只面向基于该最新模板创建的新项目。旧模板项目、历史数据层实现和已生成旧项目不在兼容范围内。

## 3. 已确认决策

1. 聚焦 AppHub 建站相关功能，不扩展为 opscli 通用第三方接口改造。
2. OPS 继续复用最新模板已有三模式鉴权和 `QueryGateway`，不新增第二套身份解析。
3. Keepa、SellerSprite 改为复用模板已有 `QueryCredentials`，按请求用户身份访问第三方数据 API。
4. 删除共享密钥 `OPSCLI_THIRD_PARTY_DATA_API_KEY` 的建站要求，不保留兼容读取或 Secret 回退。
5. 保留唯一的第三方数据服务地址变量 `OPSCLI_THIRD_PARTY_DATA_API_BASE_URL`，由部署环境显式注入。
6. 第三方原始快照和异步任务由站点共享改为用户私有，所有读写必须包含 `owner_user_id`。
7. 前端仍只访问当前站点同源 `/api`，不直接访问 OPS、Keepa、SellerSprite 或携带上游凭证。
8. 本次不修改 `opscli/app` 功能，也不修改最新模板仓库。
9. 实施范围集中在 `ops-app-build-spec` 和 `ops-app-data-builder` 的规范、测试、版本及评估用例。

## 4. OPS 当前鉴权机制

最新模板已经提供 `QueryCredentials`、`get_query_credentials()`、`get_query_gateway()` 和 `get_current_user()`，身份模式按以下优先级判定：

```text
viewer > session > local > 401
```

| 模式 | 站点收到的凭证 | OPS 取数行为 |
| --- | --- | --- |
| `viewer` | `X-Ops-Token`，以及可信的 `X-User-Email`、`X-User-Id`、`X-User-Name` | 使用 `ViewerQueryGateway`，访问 OPS viewer 接口时只向上游发送 `X-Ops-Token` |
| `session` | `X-Session-Id`，可选 `Authorization: Bearer <ops-jwt>` | 使用 `OpsQueryGateway`；缺少 JWT 时通过 `get_token_by_session()` 获取 |
| `local` | 请求无上述头，且 `LOCAL_AUTH_FALLBACK_ENABLED=true` | 使用 `LocalQueryGateway`，读取本机 opscli 登录状态 |
| 无有效身份 | 不满足以上模式 | 返回 HTTP 401，不跨模式回退 |

`opscli app create` 当前已经在应用 binding 中写入：

```json
{"opscli": {"auth_mode": "viewer", "datasets": []}}
```

因此 OPS 侧无需新增功能，只需保持现有模板合同不被 Skill 生成代码覆盖。

## 5. Keepa 与 SellerSprite 目标鉴权

### 5.1 总体方案

当新项目需要 Keepa 或 SellerSprite 时，由 `ops-app-data-builder` 在项目业务层生成一个请求级 `ThirdPartyApiClient`：

```text
浏览器请求
→ 模板 get_query_credentials()
→ 已校验的 QueryCredentials
→ ThirdPartyApiClient 重建上游鉴权头
→ OPS 第三方数据服务
```

`ThirdPartyApiClient` 复用 `QueryCredentials` 的身份判定结果，不自行重新解析浏览器请求头，不改变模板现有类名、依赖签名和优先级。

### 5.2 上游请求头映射

#### viewer 模式

```http
X-Ops-Token: <viewer-ticket>
X-User-Email: <trusted-email>
X-User-Id: <trusted-user-id>
X-User-Name: <trusted-user-name>
```

用户身份字段必须来自模板验证后的 `QueryCredentials`，不得直接透传浏览器提交的任意 Header。

#### session 模式

```http
X-Session-Id: <session-id>
Authorization: Bearer <ops-jwt>
```

`Authorization` 为可选项。存在经过验证的 JWT 时发送；缺失时允许上游依据 `X-Session-Id` 完成后续鉴权流程。

#### local 模式

本地模式只存在于站点后端，不向远端服务发送特殊的 `local` 标识。站点通过 `AuthClient` 把本机 opscli 登录状态转换为标准 session/JWT 请求头，优先复用：

- `build_session_headers("ops")`
- `build_request_auth("ops")`

远端最终收到的仍是标准 `X-Session-Id` 和可选 `Authorization`。

### 5.3 鉴权安全边界

- 只根据已校验的 `QueryCredentials` 重建允许的上游 Header。
- 不盲目代理浏览器传入的完整 Header 集合。
- 不在请求体中传递 Token、Session、JWT 或用户身份。
- 不把凭证写入前端、`VITE_*`、日志、SQLite、源码或生成文档。
- 不允许 `viewer`、`session`、`local` 之间自动降级或交叉回退。
- 身份不完整或不合法时快速失败，不能改用共享 Secret 绕过用户权限。

## 6. 第三方服务地址配置

删除以下旧配置合同：

```env
OPSCLI_THIRD_PARTY_DATA_API_KEY=<backend-secret>
```

保留且只保留：

```env
OPSCLI_THIRD_PARTY_DATA_API_BASE_URL=<environment-origin>
```

| 环境 | `OPSCLI_THIRD_PARTY_DATA_API_BASE_URL` |
| --- | --- |
| 生产 | `https://ops.mcp.xenkee.com` |
| 预发布 | `https://ops.api.qa.aukeyit.com` |

配置规则：

1. Base URL 由 AppHub 对应部署环境显式注入，应用不自行判断生产或预发布。
2. 鉴权模式与部署环境相互独立，不得通过 `viewer/session/local` 推断服务地址。
3. 配置值必须是纯 origin，不包含 `/api`、具体端点、查询参数或结尾 `/`。
4. 不新增 Keepa、SellerSprite 各自的 Base URL 变量。
5. 固定接口地址统一使用 `base_url.rstrip(/) + path` 构造。
6. Base URL 缺失或格式非法时启动或首次调用快速失败，不静默使用硬编码地址。

## 7. 运行时接口合同

### 7.1 Keepa

```text
POST /api/v1/keepa/run
```

- 场景发现和参数验证仍属于开发期 Skill 能力，不进入站点线上流程。
- 同时检查 HTTP 状态码和业务响应中的 `success`。
- 失败不得覆盖或清空同一用户最后一次有效快照。

### 7.2 SellerSprite 普通任务

```text
POST /api/v1/seller-sprite/jobs
GET  /api/v1/seller-sprite/jobs/{job_id}
POST /api/v1/seller-sprite/jobs/status
GET  /api/v1/seller-sprite/jobs/{job_id}/result
```

- HTTP 202 只表示任务已受理，不表示任务完成。
- `queued`、`running`：保存并复用当前用户的 pending `job_id`，继续轮询，不重复提交。
- `succeeded`：调用 result 接口读取 JSON 结果。
- `failed`、`cancelled`：停止轮询并返回稳定错误。

### 7.3 SellerSprite Listing Analysis

```text
POST /api/v1/seller-sprite/listing-analysis/jobs
GET  /api/v1/seller-sprite/listing-analysis/jobs/{job_id}
GET  /api/v1/seller-sprite/listing-analysis/jobs/{job_id}/result
```

Listing Analysis 必须使用专用接口，不能提交到 SellerSprite 普通 jobs 接口。

## 8. 用户数据隔离改造

### 8.1 改造原因

旧共享 Secret 模式下，第三方调用代表站点统一身份，因此原始快照和异步任务使用站点级唯一键：

```text
UNIQUE(provider, request_hash)
```

改为三模式鉴权后，同一业务参数可能由不同用户、不同权限或不同上游账号发起，继续共享快照或 pending 任务会造成越权复用和数据串读。

### 8.2 新唯一键

以下表统一改为用户私有：

- `third_party_source_snapshot`
- `third_party_async_job`

唯一约束改为：

```text
UNIQUE(owner_user_id, provider, request_hash)
```

所有查询、插入、更新、UPSERT、索引、任务轮询和 pending `job_id` 复用都必须包含 `owner_user_id`。

### 8.3 request_hash 边界

`request_hash` 只表达业务请求，不包含用户身份和凭证：

| 来源 | `request_hash` 业务组成 |
| --- | --- |
| Keepa | `scenario + site + params` |
| SellerSprite 普通任务 | `scenario + site + period + page_size + params` |
| Listing Analysis | `asin + station + site` |

用户身份属于数据库唯一键维度，不写入 `request_hash`；Token、Session、JWT 等凭证不得参与哈希或持久化。

## 10. 是否修改最新模板仓库

本次不需要修改最新模板仓库，原因如下：

1. 模板已经具备三模式身份识别所需的 `QueryCredentials`、依赖注入和当前用户解析能力。
2. OPS 取数路径已经验证可直接复用，无需改动模板的 `QueryGateway`。
3. `ThirdPartyApiClient` 只在页面实际需要 Keepa 或 SellerSprite 时生成，属于按业务需求构建的数据层代码，不应让所有模板项目默认携带第三方 client、表结构和轮询逻辑。
4. 用户私有快照表和异步任务表只属于使用第三方数据的项目，不适合作为模板公共基础设施。
5. 环境 Base URL 应由具体部署环境注入，模板只需遵守规范，不需要固化生产或预发布地址。

只有后续发现以下情况时，才重新评估模板修改：

- `QueryCredentials` 无法稳定提供第三方请求需要的已验证身份字段。
- 本地模式无法通过现有 `AuthClient` 转换为标准 session/JWT 请求头。
- 多个项目重复实现完全相同且稳定的第三方基础 client，需要平台统一下沉。

## 12. 验收标准

### 12.1 静态规范

- 两个 Skill 中不再要求或引用 `OPSCLI_THIRD_PARTY_DATA_API_KEY`。
- 生产和预发布 Base URL 均有明确配置说明，且没有通过鉴权模式推断环境。
- 三种模式的 Header 映射、失败边界和禁止透传规则一致。
- Keepa、SellerSprite 和 Listing Analysis 接口路径准确且职责分离。
- 第三方快照及异步任务唯一键均包含 `owner_user_id`。
- 所有版本、测试断言和 eval 用例与新规范一致。

### 12.2 生成项目行为

- `viewer` 请求使用当前访问者的 viewer ticket 和可信用户身份访问第三方服务。
- `session` 请求使用当前 session 和可用 JWT，不使用共享 Secret。
- `local` 请求通过 `AuthClient` 转换为标准 session/JWT Header，远端不感知 `local` 模式。
- 身份无效时返回 401/403 类稳定错误，不跨模式回退。
- 两个用户提交相同业务参数时，各自拥有独立快照和异步任务记录。
- 同一用户重复提交 SellerSprite pending 请求时复用原 `job_id`。
- HTTP 202 不被当作成功完成，`failed/cancelled` 不继续轮询。
- 前端始终只访问本站 `/api`，构建产物中不存在上游凭证。

### 12.3 回归验证

- 执行两个 Skill 的 `quick_validate.py`。
- 执行两个 Skill 的定向 pytest。
- 验证 manifest、Skill 打包和版本一致性。
- 静态搜索旧 Secret、共享唯一键、Header 盲目透传和 provider 专属 Base URL。
- 增加 viewer、session、local、未认证、用户隔离、pending 复用和环境 Base URL 的评估样例。
