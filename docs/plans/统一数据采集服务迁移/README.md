# 统一数据采集 MCP 服务迁移文档

> 状态：方案阶段
>
> 适用基线：`aukeys-opscli 0.0.112`，提交 `5e079a9`
>
> 首个迁移模块：SellerSprite（卖家精灵）
>
> 最后更新：2026-07-21

本目录维护将浏览器采集、第三方数据抓取等模块从通用 `opscli-mcp` 迁移到统一数据采集 MCP 服务的架构与实施规范。

统一数据采集服务不是新的代码仓库。业务代码继续保留在 `open-opscli`，通过共享 MCP App Factory、Collector Service Profile 和显式 Tool Bundle 注册表形成独立部署单元。

## 1. 目标形态

```text
open-opscli 仓库
├── opscli-mcp                  # 通用 MCP 部署入口
└── opscli-collector-mcp          # 统一数据采集 MCP 部署入口
    ├── seller_sprite_*         # 首个迁移 Tool Bundle
    ├── scrape_do_*             # 后续评审后接入
    ├── amazon_rufus_*          # 后续评审后接入
    └── 其他显式注册的数据采集 Tool Bundle
```

SellerSprite 只是首个迁移实例，不是通用服务的命名边界。后续模块必须按[新数据采集模块接入指南](08-新数据采集模块接入指南.md)评审，不能仅因模块含 HTTP 请求就自动归入数据采集服务。

## 4. 状态标记

- **当前已实现**：适用基线中已经存在，可从代码或测试核对。
- **迁移后要求**：统一数据采集服务正式上线前必须实现。
- **模块接入要求**：后续任一数据采集 Tool Bundle 接入前必须满足。
- **后续演进**：不阻塞首期 SellerSprite 单实例迁移。

当前尚未实现：

1. `opscli-collector-mcp` 统一数据采集服务入口。
2. 共享 MCP App Factory 和 Collector Service Profile。
3. 显式 Tool Bundle 注册表及模块生命周期契约。
4. 通用 MCP 到 Collector 的静默代理和内部路由。
5. 服务级和模块级健康检查。
6. SellerSprite 公开 `output_dir` 的服务端路径限制。

因此，完成这些代码改造前不能直接切换生产流量。

## 6. 维护约定

1. 新文档只在本目录维护，不复制一套模块专用部署框架。
2. 每个 Tool Bundle 保留业务前缀，例如 `seller_sprite_*`，禁止使用无模块边界的通用 Tool 名。
3. 模块依赖、Secret、状态、并发和回滚必须显式声明。
4. 管理员与 debug Tool 默认不进入公开 Bundle。
5. 示例仅使用 `example.com`、`mcp_xxx`、`user@example.com` 等占位值。
6. API Key、账号密码、Cookie、Session、JWT 和密钥不得进入文档、Git 或普通日志。
7. 任何架构变更先更新本文档集，再修改接入模板和代码。

## 7. 首期结论

首期在同一仓库增加一个统一 `opscli-collector-mcp` 部署入口，仅启用 SellerSprite Tool Bundle。由于 SellerSprite 当前使用 SQLite、进程内调度器和浏览器会话，整个数据采集服务首期固定单实例、单 Worker。后续模块接入必须接受该服务级约束，或先完成状态外置与隔离评审。
