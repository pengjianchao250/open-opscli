# 统一数据采集 MCP 服务运维手册

## 1. 运维边界

统一数据采集服务是一个进程级部署单元，内部运行多个显式 Tool Bundle。运维必须同时关注：

- 服务级传输、鉴权、权限、额度、遥测和资源；
- Bundle 级健康、队列、账号、浏览器、状态和结果；
- 模块间资源竞争和故障传播；
- 模块私有数据和回滚边界。

首期仅启用 SellerSprite，但操作方式应从一开始按“服务 + 模块”分层。

## 2. 首期部署限制

```text
服务实例 = 1
Uvicorn Worker = 1
SellerSprite 消费者 = 1
```

不得通过增加 systemd 实例、Uvicorn Worker 或共享卷 Pod 扩容。统一服务中任一 Bundle 要求单 Worker，整个服务都受限。

未来横向扩容前，必须外置需要共享的队列、锁、绑定和结果，并完成多实例一致性设计。

## 3. 服务管理

假设 systemd 单元为 `opscli-collector-mcp`：

```bash
sudo systemctl status opscli-collector-mcp
sudo systemctl start opscli-collector-mcp
sudo systemctl stop opscli-collector-mcp
sudo systemctl restart opscli-collector-mcp
sudo journalctl -u opscli-collector-mcp --since "30 minutes ago"
```

重启前：

1. 查看服务和所有 Bundle 健康；
2. 查看各 Bundle `queued/running`；
3. 将有状态 Bundle 设为 draining；
4. 等待或记录运行中任务；
5. 确认备份和磁盘正常；
6. 确认没有第二实例。

不要把 `kill -9` 作为常规重启。强制终止会同时影响所有 Bundle，并可能留下浏览器 Profile 锁和 stale running。

## 4. 分层健康检查

### 4.1 服务级

| 检查 | 内容 |
|---|---|
| 进程 | systemd active、单实例、单 Worker |
| HTTP | `/mcp` 可连接，未认证请求返回 401 |
| MCP | initialize、Tool Catalog、服务信息正常 |
| 鉴权 | `verify-key`、权限上下文和隔离凭证正常 |
| 公共状态 | quota、磁盘、文件上传和遥测正常 |
| Profile | 实际 Bundle 与批准清单一致 |
| 资源 | CPU、内存、FD、子进程、磁盘在预算内 |

### 4.2 模块级

目标 `collector_modules_health` 应分别返回：

```text
ready / degraded / draining / not_ready / failed
```

SellerSprite 检查：

- 队列可读写；
- 绑定库可访问；
- 公共账号来源可用；
- 浏览器 runtime 可启动；
- Profile 和结果目录可写；
- 调度器运行；
- 文件上传正常。

健康信息只返回脱敏摘要，不含路径、邮箱、账号和 Secret。

## 5. 日常巡检

### 每日服务级

- systemd、MCP initialize 和服务健康；
- API Key 校验和权限错误率；
- Profile 和 Tool Catalog 是否意外变化；
- CPU、内存、FD、子进程和磁盘；
- quota SQLite 和文件上传；
- API Key Query、Header 和异常日志脱敏；
- 是否误启动第二实例或 Worker。

### 每日模块级

每个 Bundle：

- 提交量、成功率、延迟和错误码；
- queued、running、最老等待和 stale running；
- 账号、验证码、第三方接口和浏览器异常；
- 状态目录、结果增长和上传积压；
- 当前模块是否 degraded/draining。

### 每周

- 按 Bundle 完成备份恢复抽查；
- 加密数据库与密钥配对检查；
- 浏览器和依赖版本兼容性；
- 结果保留和清理策略；
- 模块资源预算与峰值；
- Tool 权限白名单与实际 Catalog 对比；
- 模块级回滚资料是否仍可用。

## 6. 模块级停写

模块维护优先使用 draining，不应先停止整个服务。

SellerSprite draining：

```text
禁止：seller_sprite_run
禁止：seller_sprite_listing_analysis_submit
允许：状态、结果和导出 Tool
```

要求：

- 服务端强制执行；
- 状态写入健康和运维记录；
- 不影响其他 Bundle；
- 客户端不得回退旧入口或重复提交；
- 完成维护后先验证，再恢复提交。

当前代码尚未实现通用模块 drain，这是统一服务上线前置项。

## 7. SellerSprite 队列运维

管理员命令在服务主机、相同 `HOME/CONFIG_DIR` 执行。

### 7.1 摘要

```bash
opscli seller-sprite queue status
opscli seller-sprite queue worker-health --stale-running-seconds 1800
```

当前 `worker-health` 没有持久 heartbeat，只根据 stale running 判断。`healthy=true` 不证明 Worker 正在消费，还要查看：

- `oldest_queued_at`；
- 调度器和账号工作槽日志；
- 服务进程；
- 受控测试任务状态变化。

### 7.2 列表

```bash
opscli seller-sprite queue list --state queued --limit 100
opscli seller-sprite queue list --state running --limit 100
opscli seller-sprite queue list --state failed --limit 100
```

重点关注 job ID、任务类型、时间、账号槽、failover、错误码和结果。对外共享前移除邮箱、账号和内部路径。

### 7.3 终止 queued

```bash
opscli seller-sprite queue fail \
  --state queued \
  --job-id <job-id> \
  --reason "维护窗口终止"
```

批量操作使用明确 job ID、时间或显式 `--all`，执行前保存清单并确认影响。

### 7.4 stale running

1. 确认原服务和浏览器是否仍执行；
2. 检查第三方外部副作用；
3. 确认不存在第二消费者；
4. 判断任务是否幂等；
5. 再执行：

```bash
opscli seller-sprite queue requeue-running --older-than-minutes 30
```

Listing Analysis 优先续查，不盲目重排。

## 8. SellerSprite 专属账号

绑定或更新：

```bash
opscli seller-sprite account-binding bind \
  --user-email user@example.com \
  --account-name account-a \
  --username seller@example.com
```

查看：

```bash
opscli seller-sprite account-binding list
```

解绑：

```bash
opscli seller-sprite account-binding unbind \
  --user-email user@example.com
```

密码使用隐藏提示输入。绑定库与 `.account_bindings.key` 成对备份。解绑会使未领取的专属 queued 任务失败，running 继续使用领取时账号；专属账号异常不回退公共账号池。

详见[卖家精灵专属账号绑定指南](../../guide/卖家精灵专属账号绑定指南.md)。

## 9. 资源与故障域

统一进程需要建立服务级预算和模块级归因：

| 资源 | 服务级 | 模块级 |
|---|---|---|
| CPU | 总使用和限额 | 每类任务耗时、浏览器峰值 |
| 内存 | 主进程和全部子进程 | Bundle worker、Chrome 会话 |
| 磁盘 | 持久卷总量 | 各模块状态、结果、临时文件 |
| 并发 | Worker 和请求总量 | 模块队列、账号和任务并发 |
| 网络 | 总出入流量 | 第三方域名、上传和超时 |

单模块持续超限时：

1. 将该模块设为 degraded 或 draining；
2. 保留其他模块查询和提交；
3. 降低模块并发或暂停工作槽；
4. 排查资源泄露、结果积压或第三方超时；
5. 若无法逻辑隔离，评估从统一 Profile 拆出独立部署。

进程崩溃会影响全部 Bundle，这是统一服务无法消除的故障域。

## 10. 备份与恢复

### 10.1 公共状态

```text
credentials_by_key/
mcp_quota/quota.sqlite3
```

公共状态可能服务多个 Bundle。恢复时不能用一个模块的旧备份覆盖其他模块新数据。长期应按服务/模块拆分 quota，或提供事务级导入导出。

### 10.2 模块私有状态

SellerSprite：

```text
seller_sprite/task_queue.sqlite3
seller_sprite/account_bindings.sqlite3
seller_sprite/.account_bindings.key
seller_sprite/browser_profiles/
seller_sprite/api_runs/
```

后续 Bundle 在 `collector/<bundle_id>/` 使用独立目录。

### 10.3 恢复要求

- 停止目标 Bundle 写入；
- 确认没有第二消费者；
- SQLite 使用一致性备份；
- 校验哈希、权限和 `PRAGMA integrity_check`；
- 验证密钥解密、历史结果和新任务；
- 只恢复目标模块私有数据；
- 公共状态按最新权威版本或事务迁移处理。

完整步骤见[状态数据迁移方案](04-状态数据迁移方案.md)。

## 11. 常见服务级故障

### 11.1 服务无法 ready

- 检查 Profile 和 Bundle ID；
- 检查 Tool 重名和前缀校验；
- 检查关键 Bundle 初始化；
- 检查 OPS 鉴权配置和持久卷；
- 不通过删除 Bundle 状态或放宽注册白名单强行启动。

### 11.2 API Key 或权限异常

- 检查 `verify-key` 连通和响应；
- 检查配置中心 URL 和 Tool 白名单；
- 检查 Agent `clientInfo.name`；
- 检查 Query/Header 是否被代理剥离；
- 身份无法确认时失败关闭。

### 11.3 Tool Catalog 异常

- 对比 Profile、注册表和后端权限清单；
- 检查是否意外注册 debug/admin Tool；
- 未知 Tool 立即停止发布；
- 不用后端放开全量权限规避 Catalog 不一致。

### 11.4 多实例或 SQLite 锁

- 检查 systemd、容器副本和 Uvicorn Worker；
- 立即停止多余实例；
- 检查 SQLite 完整性；
- 逐模块确认 running 任务所有权；
- 不通过增加 SQLite timeout 掩盖架构错误。

## 12. SellerSprite 常见故障

### 12.1 长期 queued

- 调度器是否运行；
- 公共账号接口和加密密钥；
- 专属绑定解密；
- 账号是否冷却或登录失败；
- Chrome/Xvfb 和 Profile 权限；
- 第二实例或 SQLite 锁。

账号接口短暂失败时任务可能保留 queued 等待刷新，不要让用户重复提交。

### 12.2 凭证作用域错误

- 检查 `credentials_by_key` 和各自 `.key`；
- 检查配置根目录；
- 检查 `clientInfo.name` 是否变化；
- 用对应 API Key 重新执行 `auth_mcp_login`；
- 不复制其他用户凭证目录。

### 12.3 专属账号不可用

- 检查绑定库与密钥配对；
- 使用列表核对摘要；
- 以原 `account-name` 更新凭证；
- 检查解绑或改绑；
- 不降级公共账号。

### 12.4 浏览器或验证码失败

- 用服务用户验证 Patchright/Chrome；
- 检查 Xvfb、字体、共享内存和磁盘；
- 检查 Profile 锁和浏览器版本；
- 检查 OCR 配置；
- 不上传含 Cookie 或账号的完整 Profile。

### 12.5 导出无 HTTPS URL

- 检查文件上传和 OPS 凭证；
- 检查本地结果是否保留；
- 安排补传并告警；
- 不把 `file://` 或服务器路径发送用户。

## 13. 日志与安全

禁止记录：

- 完整 MCP URL Query API Key；
- Authorization、Cookie、Session、JWT；
- 第三方账号密码；
- 密文和加密密钥；
- 浏览器 Profile 内容；
- 未脱敏邮箱、任务参数和内部路径。

要求：

- Nginx 使用 `$uri`；
- APM 和 tracing 脱敏 Query/Header；
- 日志含 `service_id`、`bundle_id`、Tool 和稳定错误码；
- 不用真实账号做普通健康探针；
- 备份和日志按最小权限访问；
- Secret 泄露后停写、吊销、轮换并保留审计证据。

## 14. 升级流程

1. 读取发布说明和各 Bundle schema 变化；
2. 在恢复副本验证升级、降级和 Tool Catalog；
3. 按 Bundle 进入 draining 并排空；
4. 创建公共状态和模块私有状态备份；
5. 停止统一服务并安装固定版本；
6. 验证 Profile、Tool、健康、状态和导出；
7. 按 Bundle 逐个灰度恢复提交；
8. 失败时按模块或服务级回滚，不只降级代码而忽略数据兼容性。

上线清单见[上线验证与回滚清单](06-上线验证与回滚清单.md)。
