# 统一数据采集 MCP 服务迁移总体方案

## 1. 背景

当前 `opscli-mcp` 是全量 MCP 部署入口，认证、查询、数据抓取和其他业务 Tool 运行在同一进程。随着浏览器采集和第三方数据采集模块增加，会出现以下问题：

- 浏览器崩溃、内存增长和验证码阻塞可能影响通用 MCP Tool；
- 数据采集模块依赖 Chrome、Xvfb、OCR 等重型运行环境，通用 MCP 镜像被动膨胀；
- 数据采集任务通常具有异步队列、本地结果和账号状态，部署约束不同于无状态 Tool；
- 任一数据采集模块升级都可能扩大通用 MCP 发布风险；
- 通用 MCP 本地执行重型采集 Tool，无法隔离运行资源和故障域。

本方案建立一个统一数据采集 MCP 部署边界。业务实现仍保留在当前仓库，通过显式 Tool Bundle 组合到数据采集服务中。

## 2. 当前调用链

### 2.1 通用 MCP

```text
MCP Host
  → opscli-mcp
  → 全部已注册 Tool
```

当前 `opscli/mcp/server.py` 直接注册各业务 Tool 模块，SellerSprite 也在其中。

### 2.2 SellerSprite 正式 CLI

```text
opscli seller-sprite ...
  → 本机 OPS 登录态
  → GET /api/v1/mcp-api-keys/config
  → SellerSpriteRemoteAdapter
  → 默认选择“BI运营系统”
  → 远端 opscli-mcp
  → seller_sprite_* Tool
  → SQLite 队列 + 进程内调度器 + 浏览器/API 执行器
```

当前公开 SellerSprite CLI 已经通过 OPS 配置访问通用 MCP。迁移不改变客户端入口，只把 SellerSprite 的实际执行转移到 Collector。

## 3. 目标架构

```text
CLI / MCP Host
  → OPS 配置中心下发“BI运营系统”通用 MCP URL 和用户 API Key
  → opscli-mcp
      ├── auth/query/skills/... 本地执行
      └── seller_sprite_* 静默代理
            → OPSCLI_COLLECTOR_MCP_URL（内部地址，不含共享 API Key）
            → opscli-collector-mcp
            → SellerSprite Bundle / 后续数据采集 Bundle
```

外部客户端只访问 OPS 配置中心下发的 `BI运营系统`。Collector 使用内部域名或内网 IP，由通用 MCP 配置和访问，不进入客户端远端 MCP 配置。

## 4. 仓库与发布关系

代码继续在 `open-opscli` 仓库：

```text
opscli/
├── mcp/                         # 共享 MCP 基础设施
├── collector_mcp/                 # 目标统一数据采集服务入口与注册表
├── seller_sprite/               # SellerSprite 领域实现
├── scrape_do/                   # 其他业务模块，是否接入另行评审
└── amazon_rufus/                # 其他业务模块，是否接入另行评审
```

同一个 Wheel 提供不同部署入口：

```toml
opscli-mcp = "opscli.mcp.server:run"
opscli-collector-mcp = "opscli.collector_mcp.server:run"
```

这样可以共享版本、测试和基础设施，同时让通用 MCP 与数据采集 MCP 独立部署、升级和回滚。

## 5. 为什么选择统一数据采集服务

### 5.1 收益

- 只维护一套数据采集服务入口、鉴权、遥测、健康检查和反向代理模板；
- 后续模块通过 Tool Bundle 注册，无需复制 MCP Server；
- 浏览器、字体、OCR 等运行依赖集中维护；
- 客户端继续只使用 `BI运营系统`，Collector 内部地址由通用 MCP 统一维护；
- 用户仍使用各自业务 CLI 和 Tool 名称，不感知部署变化；
- 可以统一治理并发、磁盘、日志脱敏和文件上传。

### 5.2 代价

- 任一模块的进程级故障可能影响全部数据采集 Tool；
- 模块共享 CPU、内存、浏览器和磁盘，需要资源预算；
- 一个模块升级可能触发整个数据采集服务发布；
- 只要任一已启用模块要求单实例，整个服务就不能直接横向扩容；
- Tool 注册和模块生命周期必须显式管理，否则容易暴露不应公开的能力。

本方案通过显式 Bundle、模块私有状态、分层健康检查和模块级停写降低耦合，但不能消除统一进程的故障域。

## 6. 迁移目标

1. 增加统一 `opscli-collector-mcp`，与通用 MCP 分离部署。
2. 复用 API Key 鉴权、用户身份、隔离凭证、额度、遥测和错误信封。
3. 通过显式注册表加载经过批准的 Tool Bundle。
4. 数据采集模块的公开 Tool 由通用 MCP 静默代理到 Collector。
5. 每个模块独立声明依赖、Secret、状态目录、并发和生命周期。
6. 首期迁移 SellerSprite，保持其 CLI、Tool 名称和任务协议兼容。
7. 状态、文件和密钥按模块隔离，支持模块级备份与回滚。
8. 生产导出提供 HTTPS URL，不向用户暴露服务器本地路径。

## 7. 非目标

本期不包含：

- 拆分独立 Git 仓库；
- 一次性把所有抓取模块迁入数据采集服务；
- 自动扫描包并注册 Tool；
- 修改各模块业务场景、参数和导出字段；
- 把管理员或 debug 命令暴露为 MCP Tool；
- 立即引入 PostgreSQL、Redis 或分布式队列；
- 首期多实例、高可用和自动伸缩。

## 8. 服务与模块边界

### 8.1 服务级公共能力

由统一入口提供：

- Streamable HTTP/SSE 传输；
- API Key 认证和权限校验；
- API Key + Agent 名称凭证隔离；
- Tool 权限、额度和遥测包装；
- 统一错误信封和日志脱敏；
- Tool Bundle 注册与冲突检查；
- 服务级和模块级健康检查；
- 优雅启动、停写和关闭编排。

### 8.2 模块私有能力

每个 Bundle 自己负责：

- Tool 名称、Schema 和业务实现；
- 第三方账号和 Secret；
- 队列、数据库、Profile 和结果目录；
- 模块并发和超时；
- 启动、恢复和关闭生命周期；
- 模块健康和业务探针；
- 模块级迁移、灰度和回滚。

共享服务不意味着共享数据库、密钥、账号池或浏览器 Profile。

## 9. 首期 SellerSprite 实例

SellerSprite 当前包含：

- `seller_sprite_*` MCP Tool；
- SQLite 任务队列；
- SQLite quota；
- 专属账号绑定库和 AES 密钥；
- API Key 隔离 CredentialStore；
- 浏览器 Profile；
- 任务结果目录；
- 进程内 scheduler 和最多三个账号工作槽。

因此首期要求整个数据采集服务：

```text
实例数 = 1
Uvicorn Worker = 1
SellerSprite 队列消费者 = 1
持久卷 = 1
```

后续轻量数据采集模块接入时必须接受这个服务级限制。若某模块需要独立扩容，应先外置状态，或评审是否从统一框架派生独立部署 Profile。

## 10. 分阶段迁移

| 阶段 | 工作 | 完成标志 |
|---|---|---|
| 1. 架构冻结 | 评审本目录和 Bundle 契约 | 服务、模块、状态边界明确 |
| 2. 通用框架 | App Factory、Profile、注册表、静默代理 | 框架测试通过 |
| 3. SellerSprite Bundle | 迁移 Tool 注册和生命周期 | 专用 Profile 只暴露允许 Tool |
| 4. 环境准备 | 安装浏览器依赖、Secret、持久卷和 HTTPS | 新服务无流量可运行 |
| 5. 状态迁移 | 停写、排空、备份、恢复 SellerSprite | 新服务读取历史状态正常 |
| 6. SellerSprite 灰度 | 通用 MCP 的 SellerSprite 代理指向 Collector | 提交、状态、导出、额度通过 |
| 7. 全量切流 | 全量通用 MCP 实例启用 Collector 内部路由 | 通用 MCP 不再本地执行 SellerSprite |
| 8. 后续模块接入 | 按接入指南逐模块评审和灰度 | 不与 SellerSprite 数据和回滚耦合 |

首次切流只迁移 SellerSprite，不要求其他数据采集模块同时迁移。

## 11. 验收标准

### 服务级

- `opscli-collector-mcp` 只注册 Profile 允许的 Bundle；
- Bundle Tool 名称无冲突，管理员/debug Tool 不公开；
- API Key、权限、额度、遥测和隔离凭证保持现有语义；
- 未配置或无法连接 Collector 时通用 MCP 明确失败，不回退本地执行；
- 服务和模块健康可分别判断；
- 单模块停写不影响其他模块状态查询；
- 日志不泄露 Query API Key、Session、JWT 或账号密码。

### SellerSprite 模块级

- 现有 CLI 命令和 `seller_sprite_*` Tool 名称不变；
- 用户只能查询自己的任务；
- 普通任务两段式和 Listing Analysis 三段式保持兼容；
- 专属账号、公共账号池和额度语义不变；
- 队列和历史结果重启后可读取；
- 导出返回 HTTPS URL；
- 新旧服务不同时消费 SellerSprite 队列；
- 模块级回滚演练通过。

## 12. 关键风险

| 风险 | 处置 |
|---|---|
| 单模块拖垮统一进程 | 资源限制、超时、模块健康和发布准入 |
| Tool 意外暴露 | 显式 Bundle 白名单，禁止自动扫描 |
| Tool 名称冲突 | 注册时全局唯一校验，保留模块前缀 |
| SQLite 多实例写入 | 首期整个服务单实例单 Worker |
| 模块状态混放 | 独立目录、独立数据库、独立密钥和备份清单 |
| 一个模块回滚覆盖其他数据 | 按模块停写、备份、恢复和路由回滚 |
| Collector 路由缺失或不可用 | 返回稳定代理错误，禁止本地回退 |
| 浏览器依赖膨胀 | Profile 显式声明依赖，统一镜像版本和容量预算 |

通用代码边界见[通用服务端架构设计](02-通用服务端架构设计.md)。
