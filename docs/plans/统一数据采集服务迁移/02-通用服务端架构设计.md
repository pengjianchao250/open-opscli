# 统一数据采集 MCP 服务端架构设计

> 本文描述迁移后目标，当前基线尚未实现这些通用抽象。

## 1. 设计原则

1. 同一仓库、同一发布包、不同部署入口。
2. 共享 MCP 基础设施，不复制认证、额度、遥测和传输层。
3. Tool Bundle 必须显式注册，禁止运行时自动扫描。
4. Tool 名保留模块前缀，注册时进行全局冲突检查。
5. 服务公共状态与模块业务状态分离。
6. 每个模块独立声明生命周期、健康、依赖和持久化。
7. 管理员和 debug 能力默认不公开。
8. 一个模块的业务错误不能改变其他模块状态。
9. 统一进程的故障域和最严格并发约束必须被明确接受。

## 2. 目标模块结构

建议新增：

```text
opscli/
├── mcp/
│   ├── app_factory.py                 # 共享 MCP App Factory
│   └── ...                            # 现有鉴权、权限、额度、遥测
├── collector_mcp/
│   ├── __init__.py
│   ├── server.py                      # opscli-collector-mcp 启动入口
│   ├── profile.py                     # Collector Service Profile
│   ├── registry.py                    # Tool Bundle 显式注册表
│   ├── health.py                      # 服务级和模块级健康聚合
│   └── bundles.py                     # 生产允许 Bundle 清单
├── seller_sprite/
│   ├── mcp_bundle.py                  # SellerSprite Bundle 定义
│   └── ...
└── 其他模块/
    ├── mcp_bundle.py                  # 通过评审后新增
    └── ...
```

脚本入口：

```toml
[project.scripts]
opscli = "opscli.cli:app"
opscli-mcp = "opscli.mcp.server:run"
opscli-collector-mcp = "opscli.collector_mcp.server:run"
```

## 3. MCP App Factory

当前 `opscli/mcp/server.py` 同时负责 Tool 注册、传输、鉴权和服务启动。建议提取共享 App Factory，由通用 MCP 和数据采集 MCP 共同使用。

### 3.1 输入

```python
@dataclass(frozen=True)
class McpServiceDefinition:
    service_id: str
    display_name: str
    register_tools: Callable[[FastMCP], None]
    lifespan: AsyncContextManager
    health_provider: Callable[[], Awaitable[dict]]
```

实际类型可按项目风格调整，契约至少应包含：

- 稳定服务 ID；
- 对外显示名称；
- 明确 Tool 注册函数；
- 服务生命周期；
- 健康提供器。

### 3.2 统一处理

App Factory 负责：

1. 创建 FastMCP 实例；
2. 注册 ToolPermission、quota 和 telemetry 包装；
3. 构建 stdio、SSE、Streamable HTTP 或 both 传输；
4. 包裹 `ApiKeyAuthMiddleware`；
5. 聚合服务 lifespan；
6. 暴露统一健康信息；
7. 启动前冻结 Tool 清单并检测重名；
8. 启动时上报实际 Tool Catalog。

App Factory 不负责：

- 选择具体业务 Bundle；
- 读取业务账号；
- 创建业务 SQLite；
- 决定模块并发；
- 自动扫描代码目录。

## 4. Collector Service Profile

Profile 定义一次部署启用哪些 Bundle 以及服务级策略。

目标生产 Profile 示例：

```python
COLLECTOR_SERVICE_PROFILE = CollectorServiceProfile(
    service_id="collector",
    display_name="数据采集服务",
    bundles=(
        "seller_sprite",
    ),
    critical_bundles=(
        "seller_sprite",
    ),
)
```

首期只启用 SellerSprite。后续模块经过评审后显式追加，不通过环境变量随意导入 Python 路径。

Profile 建议包含：

| 字段 | 用途 |
|---|---|
| `service_id` | 日志、指标和部署的稳定标识 |
| `display_name` | Collector 内部服务显示名，固定为 `数据采集服务`；不作为外部 CLI 配置项 |
| `bundles` | 允许注册的 Bundle ID 白名单 |
| `critical_bundles` | 初始化失败时阻止服务就绪的 Bundle |
| `transport` | 允许的远端传输模式 |
| `single_worker_required` | 是否强制单 Worker |
| `health_policy` | 服务 ready 如何聚合模块状态 |

生产 Profile 应由版本控制管理。临时环境可选择子集，但必须输出实际 Bundle 清单并通过配置校验。

## 5. Tool Bundle 契约

建议定义结构化契约，而不是只暴露 `register(mcp)`：

```python
@dataclass(frozen=True)
class CollectorToolBundle:
    bundle_id: str
    tool_prefix: str
    register: Callable[[FastMCP], None]
    lifespan_factory: Callable[[], AsyncContextManager]
    health_check: Callable[[], Awaitable[dict]]
    required_env: tuple[str, ...]
    persistent_paths: Callable[[], tuple[Path, ...]]
    single_worker_required: bool = False
```

### 5.1 必填语义

- `bundle_id`：内部稳定 ID，例如 `seller_sprite`；
- `tool_prefix`：公开 Tool 前缀，例如 `seller_sprite_`；
- `register`：只注册公开 Tool；
- `lifespan_factory`：启动和关闭模块后台资源；
- `health_check`：只返回脱敏状态；
- `required_env`：启动前校验的环境变量名；
- `persistent_paths`：备份和容量检查所需目录；
- `single_worker_required`：模块是否限制整个服务单 Worker。

### 5.2 禁止内容

Bundle 不得：

- 注册不带业务前缀的 Tool；
- 注册账号绑定、删除、重排、debug 等管理员 Tool；
- 在模块 import 阶段创建 SQLite、浏览器或网络连接；
- 把明文 Secret 放入元数据或健康结果；
- 依赖另一个业务 Bundle 的内部对象；
- 隐式修改其他 Bundle 的配置或状态目录。

## 6. 显式注册表

生产注册表使用静态白名单：

```python
BUNDLE_REGISTRY = {
    "seller_sprite": build_seller_sprite_bundle,
    # 后续经过评审再增加
}
```

注册流程：

1. Profile 提供 Bundle ID；
2. 注册表解析对应 factory；
3. 校验 ID、Tool 前缀和依赖；
4. 创建 Bundle 元数据，不立即启动后台任务；
5. 向 FastMCP 注册公开 Tool；
6. 比较注册前后 Tool 集合；
7. 检测重名、越界前缀和禁止 Tool；
8. 冻结实际 Tool Catalog；
9. lifespan 启动各 Bundle。

未知 Bundle、重复 ID 或 Tool 重名必须阻止服务启动。

禁止使用 `pkgutil`、入口点扫描或文件名遍历自动发现生产 Tool，避免新模块被安装后未经授权直接公开。

## 7. Tool 注册边界

### 7.1 服务公共 Tool

统一数据采集服务建议公开最小公共能力：

```text
auth_mcp_login
auth_is_authenticated
ops_health_check
collector_service_info
collector_modules_health
```

其中：

- `collector_service_info` 返回版本、服务 ID 和已启用 Bundle，不含路径和 Secret；
- `collector_modules_health` 需要鉴权，返回模块级脱敏健康；
- 其他 auth 管理 Tool 是否公开按最小权限评审。

### 7.2 SellerSprite Tool Bundle

首期包含：

```text
seller_sprite_spec_must_read
seller_sprite_scenarios
seller_sprite_quota_status
seller_sprite_run
seller_sprite_listing_analysis_submit
seller_sprite_listing_analysis_status
seller_sprite_listing_analysis_result
seller_sprite_job_status
seller_sprite_jobs_status
seller_sprite_export
```

不包含：

```text
seller_sprite_start               # 内部 helper
account-binding ...               # 本地管理员命令
queue ...                         # 本地管理员命令
seller_sprite_debug_*             # debug 能力
```

### 7.3 通用 MCP 清理

SellerSprite 全量切流并度过回滚窗口后，通用 `opscli-mcp` 停止注册 SellerSprite Bundle，避免双入口。后续模块同样遵循“先新增数据采集入口、切流、观察、再移除旧入口”。

## 8. 模块生命周期

统一服务 lifespan 建议顺序：

### 启动

1. 校验 Profile 和 Tool Catalog；
2. 校验公共认证配置；
3. 按稳定顺序进入 Bundle lifespan；
4. 关键 Bundle 全部 ready 后服务才 ready；
5. 非关键 Bundle 失败时根据 Profile 标记 degraded，但不得留下半初始化资源；
6. 开始接受业务请求。

### 关闭

1. 全局停止新提交；
2. 逆序通知 Bundle 停止领取新任务；
3. 有界等待业务任务；
4. 关闭浏览器、连接和后台协程；
5. 退出传输层；
6. 保留持久状态。

### SellerSprite 生命周期

SellerSprite Bundle 应在启动时主动启动调度器，使重启后持久 `queued` 能恢复消费；关闭时调用调度器 `close()`。跨服务器迁移仍必须提前排空 `running`，生命周期不是跨机恢复协议。

## 9. 健康模型

每个 Bundle 返回统一结构：

```json
{
  "bundle_id": "seller_sprite",
  "status": "ready",
  "checks": {
    "queue": "ok",
    "accounts": "ok",
    "browser": "ok",
    "storage": "ok"
  }
}
```

允许状态：

- `ready`：可接受提交；
- `degraded`：部分非关键能力异常，是否接受提交由模块策略决定；
- `draining`：禁止新提交，允许状态和结果查询；
- `not_ready`：不可接受业务调用；
- `failed`：初始化或关键依赖失败。

服务级状态由 Profile 聚合，不能只用 HTTP 200 代表所有模块可用。

健康结果不得返回：

- API Key、Session、JWT、Cookie；
- 账号用户名或密码；
- 加密密钥；
- 完整内部路径；
- 用户邮箱和具体任务参数。

## 10. 模块级停写

统一服务必须支持按 Bundle 停写：

```text
seller_sprite: draining
```

SellerSprite draining 时禁止：

```text
seller_sprite_run
seller_sprite_listing_analysis_submit
```

仍允许：

```text
seller_sprite_job_status
seller_sprite_jobs_status
seller_sprite_listing_analysis_status
seller_sprite_listing_analysis_result
seller_sprite_export
```

一个 Bundle 停写不应阻止其他健康 Bundle 接受请求。停写状态需要服务端强制执行，不能只依赖客户端或通知。

## 11. 通用 MCP 静默路由

CLI 和 MCP Host 继续选择 OPS 配置中心中的 `BI运营系统`。通用 MCP 对已迁移的数据采集 Tool 注册同名代理：

```text
用户请求（用户 API Key）
  → BI运营系统 / opscli-mcp
  → seller_sprite_* 代理
  → OPSCLI_COLLECTOR_MCP_URL
  → Authorization: Bearer <当前用户 API Key>
  → opscli-collector-mcp 同名 Tool
```

严格模式：

- `OPSCLI_COLLECTOR_MCP_URL` 只允许 HTTP(S) 内部地址，不得包含共享 `api_key`；
- 当前请求必须存在已验证的用户 API Key；
- 不向 Collector 透传 `session_id` 或 JWT；
- Collector 再次通过 OPS `verify-key` 校验用户身份和 Tool 权限；
- Collector 缺失或不可用时返回稳定错误，禁止回退通用 MCP 本地执行；
- 通用 MCP 只记录入口遥测，业务额度由 Collector 统一扣减。

## 12. 配置中心契约

外部客户端配置保持为通用 MCP：

```json
{
  "success": true,
  "data": {
    "http": {
      "mcpServers": {
        "BI运营系统": {
          "type": "http",
          "url": "https://ops-mcp.example.com/mcp?api_key=mcp_xxx"
        }
      }
    }
  }
}
```

Collector 地址由通用 MCP 的部署环境配置，不下发给 CLI 或 MCP Host。用户 API Key 在通用 MCP 和 Collector 分别校验，Tool 白名单必须覆盖对应代理 Tool。

## 13. 认证、额度和凭证隔离

统一服务继续复用：

1. `ApiKeyAuthMiddleware` 校验 Bearer 或 Query API Key；
2. OPS `verify-key` 恢复用户邮箱、用户 ID 和允许 Tool；
3. 请求上下文保存已验证身份；
4. 模块 Tool 按需调用 `ensure_ops_credentials()`；
5. `API Key + clientInfo.name` 定位隔离 CredentialStore；
6. 缺失或过期时执行一步登录；
7. 后台任务只持久化非敏感凭证作用域。

额度规则由各 Bundle 声明并接入共享 quota 包装，不应使用一个全局“数据采集次数”覆盖不同业务口径。

## 14. 状态和目录隔离

建议统一根目录：

```text
CONFIG_DIR/
├── credentials_by_key/           # 服务公共隔离凭证
├── mcp_quota/                    # 共享额度仓储，key 中保留工具/服务维度
└── collector/
    ├── seller_sprite/
    │   ├── task_queue.sqlite3
    │   ├── account_bindings.sqlite3
    │   ├── .account_bindings.key
    │   ├── browser_profiles/
    │   └── api_runs/
    └── <future_bundle>/
        └── 模块私有状态
```

兼容迁移期可保留 SellerSprite 当前 `CONFIG_DIR/seller_sprite/` 路径，不应为了目录美观同时引入未经验证的路径改写。新模块直接使用 `collector/<bundle_id>/`。

规则：

- 不同 Bundle 不共享 SQLite；
- 不同加密用途不共享密钥；
- 不同模块 Profile 不混用；
- 结果路径只能位于模块输出根目录；
- 模块删除前先完成状态归档和路由清理。

## 15. 故障隔离

统一进程只能做到逻辑隔离，不能做到完整进程隔离。最低要求：

- Tool 调用使用模块级超时；
- 后台协程异常被模块 supervisor 捕获并记录；
- 浏览器子进程由所属 Bundle 管理；
- CPU、内存、并发和磁盘设置服务级预算；
- 模块失败不得修改其他模块健康和状态；
- 关键模块失败时服务 not ready；
- 非关键模块失败时服务 degraded，并拒绝该模块提交；
- 进程崩溃仍会影响所有 Bundle，这是统一部署接受的代价。

## 16. 单 Worker 约束聚合

Profile 的服务并发约束取所有启用 Bundle 的最严格值。只要 SellerSprite `single_worker_required=true`：

```text
整个 opscli-collector-mcp = 单实例、单 Worker
```

不能让其他 Bundle 启动多个服务实例却共享 SellerSprite SQLite。未来解除约束前，需要外置 SellerSprite 队列、锁、绑定和结果，并完成并发一致性设计。

## 17. 输出和文件访问

统一服务应提供公共输出安全策略：

- 客户端不得指定服务器绝对输出路径；
- 相对路径必须约束在 Bundle 输出根目录内；
- API 响应不向普通用户展示内部绝对路径；
- 生产结果上传文件服务并返回 HTTPS URL；
- 上传失败保留模块本地文件并告警；
- 每个 Bundle 声明结果保留和清理策略。

SellerSprite 当前公开 `output_dir` 的兼容处理是首期代码改造项。

## 18. 管理员命令

管理员命令继续使用本地 CLI，不注册公共 MCP：

```text
opscli seller-sprite account-binding ...
opscli seller-sprite queue ...
```

命令必须在数据采集服务主机、相同服务用户和相同配置目录执行。长期可建立统一 `opscli collector-admin <bundle> ...` 命令组，但不作为首期必要改造。

## 20. 测试要求

### 框架测试

- Profile 只加载白名单 Bundle；
- 未知 Bundle、重复 ID、Tool 重名和越界前缀阻止启动；
- 管理员/debug Tool 不公开；
- 生命周期按顺序启动、逆序关闭；
- 关键与非关键 Bundle 健康聚合正确；
- 模块停写只阻止提交 Tool；
- 单 Worker 约束正确聚合；
- API Key、权限、额度和遥测包装保持有效；
- Collector URL 缺失或服务不可用时不回退本地实现；
- API Key 不出现在错误和日志。

### SellerSprite 实例测试

- Bundle Tool 集合与当前公开集合一致；
- 启动后恢复已有 `queued`；
- 关闭时释放所属浏览器资源；
- API Key 用户隔离和任务所有权保持不变；
- 专属账号、公共账号池和 quota 语义不变；
- 绝对 `output_dir` 被拒绝或忽略；
- 普通任务和 Listing Analysis 全流程通过；
- 导出成功返回 HTTPS URL。

部署配置见[部署与环境配置](03-部署与环境配置.md)，后续模块必须遵循[新数据采集模块接入指南](08-新数据采集模块接入指南.md)。
