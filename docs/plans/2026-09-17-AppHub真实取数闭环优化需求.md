# AppHub 真实取数闭环优化需求

> 日期：2026-09-17  
> 状态：已确认，进入实施  
> 范围：`opscli app migrate`、`ops-app-build-spec`、`ops-app-data-builder` 及其 AppHub 专项测试  

## 1. 背景

AppHub 看板生成流程已经能够识别 OPS、Keepa 和 SellerSprite 数据需求，也明确要求在线验证数据合同。但现行流程允许 Agent 在没有实际调用数据源的情况下，直接把数据产品标记为 `blocked`，随后生成固定返回“尚未完成在线验证”的 API 和页面。

这种结果满足了“不伪造字段”的安全要求，却没有完成用户要求的真实业务取数。用户提供部门、ASIN、时间、币种、指标和展示方式后，不应继续承担数据集别名、字段名、查询场景、轮询方式等技术细节。

## 2. 目标

1. 对已存在正式查询能力且业务需求明确的数据源，必须实际发起合同验证，不能从候选状态直接落到“未验证阻塞”。
2. 区分“尚未验证”“正在验证”“验证成功”“服务临时降级”和“结构性阻塞”，避免用一个 `blocked` 覆盖所有情况。
3. 查询成功但零行时仍确认技术合同有效，页面按“暂无数据”处理。
4. 数据服务临时失败时继续完成其他模块和不依赖未知字段的业务代码，不把单个来源失败扩散为整站阻塞。
5. 通过机器可读的 AppHub 数据合同凭证和可执行校验器，阻止固定 `blocked` API 被当成完整交付。
6. 开发诊断保留在项目合同、日志和交付报告中，业务页面只显示简单可理解的错误提示。
7. 区分数据合同验证与站点数据层实现，阻止 `contract_verified_only`、`layout_only` 或前端占位页面进入最终交付。

## 3. 非目标

- 不修改 `opscli query flow`、查询规划器、OPS SDK、MCP、认证或元数据内核。
- 不修改 `ops-dataset-query`、`ops-query-wizard`、`ops-keepa`、`ops-seller-sprite` 或其他业务 Skill。
- 不改变 `opscli app create/init/dev/push` 的现有行为。
- 不允许根据关键词、显示名、相似度或历史字段目录猜测正式字段。
- 不把真实查询行、导出文件、凭证、完整 Header 或临时下载 URL 提交到源码。
- 不让前端直连 OPS、Keepa、SellerSprite 或 opscli REST。

## 4. 术语与状态

每个数据产品独立维护合同状态：

| 状态 | 含义 | 交付要求 |
| --- | --- | --- |
| `candidate` | 已识别业务需求或候选来源，尚未发起在线验证 | 仅允许开发中间态 |
| `verifying` | 正在调用正式数据源或执行恢复流程 | 仅允许开发中间态 |
| `verified` | 当前身份下的元数据、正式参数和少量真实查询已确认 | 可以生成正式业务调用 |
| `degraded` | 已实际调用，但认证外的临时服务错误、超时或上游异常导致本轮未完成 | 继续其他模块，保留重试与失败证据 |
| `blocked` | 正式能力不支持、权限缺失、业务口径无法确认或运行时硬前置缺失 | 必须给出结构化阻塞证据 |
| `mock-only` | 只用于测试或前端联调 | 不得描述为真实接入 |

以下原因不得作为最终 `blocked` 的依据：

- 尚未在线验证；
- 还没有尝试查询；
- 服务暂时异常或超时；
- 先完成页面以后再接数据。

每个真实数据产品还必须独立维护 `implementation_status`：

| 状态 | 含义 | 最终交付 |
| --- | --- | --- |
| `not_started` | 尚未开始站点数据层实现 | 不允许 |
| `in_progress` | 正在实现后端、前端或测试 | 不允许 |
| `implemented` | 代码已存在但尚未完成验证 | 不允许 |
| `contract_verified_only` | 只验证了上游合同 | 不允许 |
| `layout_only` | 只有页面布局或占位内容 | 不允许 |
| `verified` | 后端 API、Schema、前端消费、测试和 OpenAPI 证据完整 | 允许 |

## 5. AppHub 真实取数闭环

### 5.1 清晰需求

当部门、时间、指标、筛选和币种等业务范围足以构造查询时：

1. `ops-app-data-builder` 进入 `verifying`。
2. OPS 复用 `$ops-dataset-query` 的正式流程；Keepa 和 SellerSprite 复用各自现有 Skill。
3. 只获取足以验证合同的少量样本。
4. 成功后固化精确技术合同并进入 `verified`。
5. 零行结果记录为 `outcome=zero_rows`，合同仍进入 `verified`。
6. 生成 FastAPI service、站点 API、前端类型、测试和 `app.yaml.opscli.datasets` 白名单。

### 5.2 需要澄清

只有会改变业务语义、权限或存储方案的问题才询问用户。例如“订单量”同时可能表示订单数和商品件数时，可以询问业务口径；不得要求用户选择 `orders` 或 `order_qty` 等技术字段。

### 5.3 自动恢复

- 查询合同给出正式 `recovery_command` 时，按原合同执行一次恢复并重新验证。
- 认证未完成时提示用户完成认证，不把认证问题误判为字段或场景不支持。
- 认证外的 CLI/MCP 失败按 `ops-feedback` 规范提交反馈。
- HTTP 502、503、超时和临时上游异常进入 `degraded`，不进入“未验证阻塞”。

### 5.4 部分交付

单个来源进入 `degraded` 或 `blocked` 时：

- 继续完成其他已验证数据产品；
- 继续完成通用页面状态、独立加载、错误提示和测试结构；
- 不凭未知字段生成正式查询；
- 不把静态 `blocked` 响应描述为完整业务实现；
- 最终报告明确区分已完成、降级和阻塞模块。

## 6. 数据合同凭证

有真实数据需求的 AppHub 项目生成：

```text
docs/ops-app/data-contracts.json
```

该文件是开发期验证凭证，不是运行时配置权威源。它只保存：

- 数据产品标识、来源和状态；
- 验证方式、时间、结果和行数摘要；
- 精确数据集、表、字段角色、聚合、筛选和稳定结果别名；
- 降级失败码、是否可重试和反馈 UUID；
- 结构性阻塞原因。

不得保存真实查询行、原始响应、Token、Cookie、JWT、Session ID、密码、Secret、API Key 或下载 URL。

## 7. 可执行交付门禁

`ops-app-data-builder` 提供独立校验器：

```text
scripts/validate_data_contracts.py
```

交付模式至少校验：

- `candidate` 和 `verifying` 不能进入最终交付；
- `verified` 必须存在真实验证尝试和技术合同；
- OPS 的 `verified` 合同必须包含 `dataset_alias`、`table_id` 和字段映射；
- OPS 合同必须声明用户点名的全部业务角色，并保证字段映射逐项覆盖，不能只实现部分指标；
- `degraded` 必须存在实际失败尝试、失败码和可重试说明；
- `blocked` 必须是结构性阻塞，禁止使用“尚未验证”“未尝试”“服务异常”充当阻塞理由；
- 真实数据产品不能以 `mock-only` 冒充完成；
- 合同文件不得包含敏感字段或真实结果载荷。
- `delivery` 模式要求 `implementation_status=verified`。
- `delivery` 模式检查后端 API、service、Pydantic Schema、前端消费者、测试和 OpenAPI 工件实际存在。
- 前端实现工件不得保留“等待真实数据合同”或“仅用于布局验证”等占位文本。

## 8. Skill 职责

### 8.1 `ops-app-data-builder`

- 执行真实合同验证闭环；
- 维护数据产品状态；
- 生成 `data-spec.md` 和 `data-contracts.json`；
- 生成或修改站点业务数据层；
- 在交付前执行合同校验器。

### 8.2 `ops-app-build-spec`

- 识别真实数据需求并委托 `ops-app-data-builder`；
- 不选择或猜测数据集和字段；
- 在页面/API 完成前检查真实取数闭环是否执行；
- 禁止把固定 `blocked` 路由描述成完整交付；
- 要求业务页面隐藏内部合同诊断文本。

### 8.3 `opscli app`

只修改 `app migrate` 子命令，不改变应用创建、模板、本地开发和源码推送：

- 迁移状态返回 `data_ready`、`release_ready`、`delivery_ready`、未完成项和下一门禁。
- `verify-data` 自动校验 `data-contracts.json`、实现状态和项目工件。
- 覆盖矩阵升级为 Schema v2，并兼容读取现有 Schema v1。
- 门禁失败时保持原阶段，不提前推进到后续阶段。
- 导出的验收报告明确显示当前是否可交付以及全部未完成问题。

## 9. 验收标准

1. 清晰 OPS 页面需求必须触发真实查询验证要求。
2. 未执行真实查询时，合同校验器在交付模式返回失败。
3. 零行结果可以通过 `verified + zero_rows` 合同校验。
4. 临时服务失败使用 `degraded`，并允许其他模块继续交付。
5. `blocked` 不能使用 `not_attempted`、`not_validated`、`service_error`、`timeout` 等理由。
6. OPS 已验证合同缺少数据集、表或字段映射时校验失败。
7. 合同中出现 Token、Cookie、JWT、Session ID、Secret 或真实结果行时校验失败。
8. 两个 Skill 的安装、打包和静态契约测试通过。
9. 合同已验证但实现状态为 `contract_verified_only` 时交付校验失败。
10. 前端仍有布局占位文字时交付校验失败。
11. 门禁失败时迁移阶段不变化。
12. 不修改查询内核、其他业务 Skill和 `opscli app create/init/dev/push` 行为。

## 10. 实施顺序

1. 增加本需求文档。
2. 在 `opscli app migrate` 增加 Schema v2、交付状态和数据实现门禁。
3. 在 `ops-app-data-builder` 增加合同与实现双状态及 delivery 校验器。
4. 在 `ops-app-build-spec` 增加最终回复和交付门禁。
5. 更新两个 Skill 的版本、默认提示和静态 eval。
6. 增加迁移状态机、校验器和两个 Skill 的契约回归。
7. 运行定向测试、打包检查和静态扫描。

## 11. 回滚

本需求不修改运行期查询内核和 `opscli app create/init/dev/push`。出现兼容问题时，可以分别回滚迁移门禁、两个 Skill 版本、合同校验器和对应测试，不影响其他查询、认证、MCP 或业务 Skill。
