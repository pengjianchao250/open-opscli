# Ops App 迁移业务入口识别与完整运行需求

## 一、背景

源码复制迁移的目标不是尽快找到一个可执行命令，而是保留原项目真实业务入口，在 AppHub 薄适配后仍能运行完整业务。

现有迁移实现按 `Dockerfile -> Python -> Node` 选择首个运行时，Node 包内固定按 `start -> preview -> dev` 选择脚本。该方式适合单入口项目，但会把以下项目误判为普通单进程应用：

- README 或 DEPLOY 明确使用 `dashboard`、`dev:lan` 等业务入口；
- `run_local.py` 等入口负责启动网关、页面、采集器或后台进程；
- 前端和后端需要由迁移启动器同时运行。

## 二、目标

1. 单入口项目继续使用现有快速路径，不增加依赖安装、构建或完整 E2E；
2. 多候选 Node 项目优先使用 README、DEPLOY 和入口脚本提供的业务证据；
3. 迁移启动器支持单进程、前后端双进程和项目自带编排器；
4. 能从明确的命令参数或入口脚本环境变量中形成 AppHub 端口 `8000` 的薄适配证据；
5. 选择结果写入 `startup-manifest.json`，供后续 Dockerfile 和运行验证复用；
6. 全部改动只作用于 `opscli app migrate`，不得改变普通 `app create/init/push` 和模板克隆流程。

## 三、非目标

- 不建设通用微服务拓扑引擎；
- 不扫描整个仓库的抽象语法树；
- 不自动改写业务 API、数据库或鉴权逻辑；
- 不默认执行完整 E2E 或重新安装依赖；
- 不为证据不足的项目生成猜测性 Dockerfile；
- 不改变普通新建项目的目录、模板、发布资产或门禁。

## 四、业务入口选择

### 4.1 证据范围

迁移服务只读取低成本、高确定性的证据：

- 根目录或包目录的 `README.md`、`DEPLOY.md`、`DEPLOYMENT.md`；
- `package.json` 中存在的脚本；
- 脚本命令直接引用的 `.py`、`.js`、`.mjs`、`.cjs`、`.ts` 文件；
- 已有 Dockerfile 的 `CMD` 或 `ENTRYPOINT`；
- 固定位置的 FastAPI 或 Starlette 入口。

不递归分析未被候选命令引用的业务源码。

### 4.2 Node 脚本优先级

1. 文档明确列出的编排入口；
2. 文档明确列出的 Web 入口；
3. 能确认存在子进程编排行为的入口；
4. `start:prod`、`start:production`、`serve`、`dashboard`；
5. `start`、`preview`、`dev`。

安装、构建、测试、刷新、校验和数据维护脚本不因出现在文档中自动成为运行入口。

### 4.3 启动模式

- `single`：单个 Docker、Python 或 Node Web 入口；
- `dual`：没有统一编排器，但后端与前端都必须运行；
- `orchestrator`：项目已有入口负责启动和回收全部必要子进程。

编排器存在时只启动编排器一次；不得再次单独启动其内部服务。

## 五、端口薄适配

- 脚本命令明确包含非 `8000` 的 `--port` 时，在迁移运行命令中追加 `8000` 参数覆盖；
- 入口脚本明确读取 `PORT` 或项目公共端口变量时，在迁移启动器中注入值 `8000`；
- 存在多个端口变量时，优先公共、非 internal、非 worker、非 dashboard 的变量；
- 内部服务端口保持原值；
- 端口证据不足时不猜测修改业务源码，由目标副本继续做项目专属薄适配。

## 六、迁移清单

`startup-manifest.json` 增加以下兼容字段：

```json
{
  "runtime_candidates": [],
  "runtime": {},
  "launch_mode": "single|dual|orchestrator",
  "selection_reason": "documented_command|documented_orchestrator|docker_entry|backend_frontend_pair"
}
```

现有 `runtime`、`docker`、`backend`、`frontend` 字段继续保留，旧迁移状态仍可读取。

## 七、效率约束

- 单入口项目不读取入口脚本以外的业务文件；
- 不安装依赖、不启动服务、不构建镜像；
- README 和 DEPLOY 只在包脚本存在多个运行候选时参与评分；
- 同一入口文件只读取一次；
- 后续生产构建仍遵循同一轮最多一次的迁移验证约束。

## 八、新建流程隔离

本需求只修改 `MigrationService`、迁移规范和迁移专项测试。普通新建流程不得：

- 生成 `startup-manifest.json`；
- 读取 README 或 DEPLOY 选择启动脚本；
- 注入迁移端口环境变量；
- 改变模板 clone、`app create`、`app init` 或普通 `app push` 行为。

## 九、验收标准

1. 文档明确使用 `pnpm dashboard` 时，迁移选择 `dashboard`，不选择同包的普通 `start`；
2. 文档明确使用 `pnpm dev:lan` 且入口存在子进程编排时，启动模式为 `orchestrator`；
3. 编排入口读取公共端口环境变量时，迁移启动器注入 `8000`，内部端口不修改；
4. 同时存在独立后端和前端且没有编排器时，启动模式为 `dual`，两个进程都被启动和回收；
5. 只有一个明确入口时保持原选择结果和执行效率；
6. 迁移测试、App 服务测试和普通新建流程回归全部通过。

## 十、验证命令

```bash
python -m pytest tests/app/test_migration.py tests/app/test_migration_contract.py -q
python -m pytest tests/app -q
```
