# ops-app 源码复制迁移适配层优化需求

## 1. 背景

现有 `opscli app migrate` 已能把已有项目复制到独立目录并创建 AppHub 应用，但迁移来源字段被加入了服务端创建请求，迁移项目又在推送时跳过普通 `app.yaml` 身份门禁。复制后的生成文件会干扰复制校验，未知启动方式仍可能进入 Git 初始化状态，失败后也缺少可恢复入口。

本需求把迁移定义为“源项目只读复制 + 目标副本最小适配”。平台继续使用一套创建、身份、推送和生产发布合同；迁移差异由本地适配层消化，不修改 AppHub 后端，也不为迁移项目开辟第二套生产门禁。

## 2. 决策

1. `POST /api/v1/apps` 使用普通创建合同，不发送 `origin_type`、`migration_id`。
2. `origin_type=migration_copy` 与 `migration_id` 只保存在 `.opscli/project.json` 和 `.opscli/migration/<migration-id>/migration.json`。
3. 普通新建项目维持模板克隆、默认 SQLite 创建参数和原有 `create/init/push` 行为。
4. 迁移创建不猜测数据库类型，创建请求省略 `database`；数据库与运行资产由实际项目适配结果决定。
5. 迁移项目推送前既要通过本地迁移门禁，也要通过普通项目的 `app.yaml` 身份门禁。

## 3. 范围

本期包含通用迁移命令、迁移状态与清单、最小适配层、恢复机制、推送门禁、Skill 规范和自动化测试。

本期不包含：具体业务项目适配、任意运行时的自动改写、AppHub 后端字段或接口变更、自动推送和部署。

## 4. 状态机

迁移按阶段持久化，成功一步写入一步：

`target_resolved -> copied -> startup_ready | startup_manual_required -> registered -> adaptation_ready | adaptation_manual_required -> initialized -> push_ready`

- `startup_manual_required`：无法可靠识别所需启动入口，停止创建与 Git 初始化。
- `adaptation_manual_required`：应用已经登记，但 `app.yaml` 身份或最小适配资产不满足要求，停止 Git 初始化。
- `push_ready`：复制、启动、适配、身份、binding 与 Git 检查全部通过，`delivery_ready=true`。
- 异常保留最后成功 `phase`，另写 `status=failed`、`failed_phase` 和结构化错误；`migrate resume` 从该阶段继续。

`resume` 不重新复制源目录；已有 `app_id` 时不重复创建应用；已有 Git 仓库时不重复初始化。

## 5. 本地文件与数据分层

| 分类 | 文件或数据 | 规则 |
| --- | --- | --- |
| 源码副本 | 原项目源码、配置、文档、测试与资源 | 记录逐文件摘要，适配前后可独立验证 |
| 适配资产 | `.gitignore`、`scripts/start_app.py`、`app.yaml` | 记录在 `adaptation-manifest.json`，不作为复制漂移 |
| 本地迁移元数据 | `.opscli/project.json`、迁移目录下四类清单 | 只在本地保存并由 `.gitignore` 排除 |
| 本地敏感与运行数据 | `.env*`、数据库文件、`data/`、日志 | 复制到目标供本地使用，但默认禁止进入 Git |
| 排除项 | `.git`、旧 `.opscli`、依赖、缓存、构建与临时目录 | 不复制，清单记录原因 |

迁移目录至少包含：

- `migration.json`：阶段、状态、错误、`app_id`、`adaptation_status`、`delivery_ready`。
- `copy-manifest.json`：复制文件、排除文件、逐文件摘要、源与目标摘要。
- `startup-manifest.json`：前后端启动证据、命令与人工处理状态。
- `adaptation-manifest.json`：受管适配文件、生成或修改文件、检查项与适配状态。

## 6. 最小适配层

自动适配只处理可确定的内容：

1. 补充本地忽略规则，确保 `.opscli/`、`.env*`、数据库和 `data/` 默认不提交。
2. 根据明确证据生成 `scripts/start_app.py`；不确定时标记人工处理，不猜测命令。
3. AppHub 创建成功后生成或同步 `app.yaml`，写入真实五位 `app_id`，禁止保留旧顶层 `name`。
4. 核对 `backend/app.py`、`frontend/package.json`、`Dockerfile` 和 `nixpacks.toml` 等最低生产适配资产；缺失时转人工适配，不自动生成猜测性构建配置。
5. 生成 `adaptation-manifest.json`，明确自动生成、修改和本地专用文件。

不得生成无法从项目证据确定的通用 Dockerfile、依赖文件或业务代码，也不得把任意旧框架自动宣称为符合 AppHub 生产合同。

## 7. 启动识别与人工处理

启动识别只接受仓库内可审计证据。当前确定性自动路径为可识别的 FastAPI 后端入口和具有明确 package script 的前端入口。任一必要入口缺失或冲突时写入 `startup_manual_required`，保留目标副本供人工补齐。

人工补齐后先执行 `migrate scan-startup` 更新证据，再执行 `migrate resume` 继续登记、身份同步和 Git 初始化。不得直接编辑 JSON 把状态改成 ready。

## 8. 推送门禁

迁移推送必须同时满足：

1. 迁移来源与目标相互隔离，迁移标识和四类清单存在。
2. `startup_status=ready`、`adaptation_status=ready`、`delivery_ready=true`。
3. 复制文件校验通过；适配层受管文件不被误判为复制漂移。
4. `.opscli/app.json` 与 `app.yaml.app_id` 一致，且 `app.yaml` 满足普通 AppHub 身份合同。
5. 默认敏感和运行数据未被 Git 跟踪。

迁移门禁只验证迁移过程与适配状态，不降低后端生产构建、发布和安全门禁。

## 9. 兼容性

- `app create` 的默认请求保持现有 SQLite 行为。
- 模板克隆、新建、已有合规模板项目和普通推送流程不变。
- `origin_type`、`migration_id` 从服务端请求模型移除，但本地迁移状态继续保留。
- 旧迁移重构状态继续通过 `convert-legacy` 显式转换，不静默覆盖。

## 10. 验收标准

1. 服务端迁移创建 payload 不含 `origin_type`、`migration_id` 和默认 `database`；普通创建仍含默认 SQLite。
2. 本地项目标识与迁移状态仍包含两个迁移字段。
3. 已存在的空目标目录可直接迁移。
4. `.gitignore`、启动包装器和 `app.yaml` 的生成或修改不导致复制校验失败。
5. `app.yaml` 写入真实 `app_id`；身份缺失或不一致时禁止推送。
6. 未知运行时停在人工状态，不创建 Git 仓库，`delivery_ready=false`。
7. 中断后 `migrate resume` 不重新复制、不重复创建应用。
8. 正常迁移、未知运行时、恢复流程、普通创建和统一推送门禁均有自动化回归测试。
