# 意图管理闭环 · 总体规划

> 本文是三份实施计划的总纲：锁定跨端契约与依赖顺序。执行任一子计划前必读本文。

**目标**：为 `dm_dataset_query_intents` 意图体系补上「命中归因 → 效果统计 → 后台可见」的闭环，回答"新增的意图是否有效、被命中多少次"。

**背景分析**（2026-08-17 会话结论）：
- 意图匹配发生在客户端（opscli 内核 `intent_matcher.py` + Skill `local_fallback.py`），服务端无感知，命中数据目前完全不存在
- 服务端已有意图 CRUD（auto-scheduler_debug `QueryIntentController`）与逐查询记录表 `dm_dataset_query_records`，但 records 只到 dataset 粒度
- 已确认决策：① 未命中上报**携带查询原文（截断 500 字符）+ 分词**；② 命中→执行转化用 **match_record_id 强关联**（opscli 透传）

## 跨端契约（改动任何一侧必须同步更新此处）

### 契约 1：上报端点

```
POST /api/v1/data-metrics/datasets/skill/intent-match-report
认证：JWT（与 /skill/catalog 同路由组）
请求体：
{
  "matched": true,                    // 必填 bool
  "intent_code": "ads_overall",       // matched=false 时为 null 或省略
  "score": 123,                       // int，匹配得分
  "ask_required": false,              // bool，是否多候选需澄清
  "fallback_reason": "",              // "" | "empty_catalog" | "no_intent_match"
  "match_source": "cli_intent",       // "cli_intent" | "mcp_intent" | "local_fallback"
  "query_text": "看下各平台广告费",     // 原文，服务端截断 500 字符
  "query_keywords": ["广告费"],        // 分词数组
  "catalog_version": "v1.1.26"        // 本次匹配所用 catalog 版本
}
响应：{ "code": 200, "data": { "match_record_id": 123 } }
```

### 契约 2：执行归因（HTTP Header，不污染查询 payload）

opscli 调 `POST /cli-query` 与 `/cli-query/simple` 时附加可选请求头：

```
X-Intent-Code:      ads_overall        # 本次查询归因的意图编码
X-Selection-Source: intent_route       # planner | intent_route | local_fallback | user_specified
X-Match-Record-Id:  123                # 契约 1 返回的 match_record_id
```

服务端 `DatasetQueryRecordService::record()` 从 `request()->header()` 读取落列。选 Header 而非 payload 字段的原因：cli-query 的 body 会透传给 Python 取数服务，塞额外字段有被下游校验拒绝的风险。

### 契约 3：数据表

**新表 `dm_intent_match_records`**（`ops_metrics` 连接）：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| id | bigIncrements | 主键 |
| request_id | varchar(64) default '' | LogRequest UUID，可关联请求日志 |
| intent_code | varchar(80) default '' | 命中的意图编码，未命中为空串 |
| matched | bool default 0 | 是否命中 |
| fallback_reason | varchar(32) default '' | empty_catalog / no_intent_match |
| match_source | varchar(32) default '' | cli_intent / mcp_intent / local_fallback |
| score | int default 0 | 匹配得分 |
| ask_required | bool default 0 | 是否需澄清 |
| query_text | varchar(500) default '' | 查询原文（截断） |
| query_keywords | json nullable | 分词数组 |
| catalog_version | varchar(32) default '' | catalog 版本 |
| user_id | int default 0 | 登录用户 |
| called_date | date | 冗余日期，聚合与清理用 |
| created_at | timestamp useCurrent | |

索引：`(intent_code, called_date)`、`(matched, called_date)`、`called_date`、`user_id`。

**`dm_dataset_query_records` 追加列**：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| intent_code | varchar(80) default '' | 归因意图 |
| selection_source | varchar(32) default '' | planner / intent_route / local_fallback / user_specified |
| intent_match_record_id | bigint unsigned nullable | 强关联 dm_intent_match_records.id |

追加索引：`(intent_code, called_date)`。

### 契约 4：有效性指标口径（后台展示）

| 指标 | 计算 |
| --- | --- |
| 命中次数 | `dm_intent_match_records` 按 intent_code + 时间窗计数（matched=1） |
| 执行转化数 | `dm_dataset_query_records` 中 intent_match_record_id 非空按 intent_code 计数 |
| 查询成功率 | 上一项中 is_success=1 占比 |
| 最近命中时间 | match_records 按 intent_code 取 max(created_at) |
| 未命中查询榜 | match_records 中 matched=0 按 query_text 分组计数 |

**口径注记（executed-only 意图）**：执行转化数按 `dm_dataset_query_records` 的
`intent_match_record_id` 强关联反查 `intent_code`，与命中数按 `dm_intent_match_records`
的 `matched=1` 独立聚合，两者统计口径不同。多候选场景用户最终选择了非首位候选（首位候选才计入
matched=1 的命中数），或匹配事件与执行事件恰好跨了统计时间窗边界，都会出现某个 intent_code
只有 executed、没有 hits 的一行（`hits=0, last_hit_at=''`，`executed`/`success`/`success_rate`
为真实值）。这属于正常口径，不是数据错误；后台展示层不应把 `hits=0` 的行当异常剔除。

## 明确不在本期范围（防止被误认为遗漏）

- **planner 主链路的 `selection_source=planner` 打标**：契约 2 预留了该枚举值，但本期只有意图路由（`intent_route`）与降级路径（`local_fallback`）打标。给规划器主链路的 plan 加 `selection_source=planner` 需要动 `query_plan.py` 的合同输出，价值是"选表来源分布"对照组，留待闭环跑通、确有分析需求时再做。
- **match→执行的跨事件超时清理**：命中后用户放弃、match_record_id 永不出现在 records 表，这本身就是"命中未转化"信号，无需清理任务。

## 部署顺序（强制）

1. **`aukey/data-metrics` 包迁移先行**（A1/A2）。注意该 QA 环境需按迁移文件级
   `--path`/`--realpath` 指定执行，绕开预存的 `dm_field_groups` 迁移状态不一致问题，不能直接跑
   全量 `migrate`。
2. **再上服务端代码**（包 A3 + 主仓库 A4）。**顺序颠倒的后果必须写明**：若 A4 代码先于 A2 迁移
   上线，`dm_dataset_query_records` 的 insert 会因目标表缺少新增列而失败，且该失败被
   try/catch 静默吞掉——不只是本次写入失败，整张表（含此前一直在写入的既有遥测）会停止写入，
   唯一线索是 `Log::warning`，界面和调用方都不会报错，非常隐蔽。
3. **再上 debug 后台**（C 侧）。C 侧对统计查询有失败隔离，顺序颠倒时后果较轻，仅统计页面降级为
   零值展示，不影响主链路数据写入。
4. **最后升级 opscli 客户端**。双向兼容已核实：旧客户端 + 新服务端、新客户端 + 旧服务端两种组合
   均安全，因此客户端升级可以放在最后，不阻塞前三步。

## 前提与风险

1. **catalog 当前返回 0 条意图**（2026-08-14 起，v1.1.26）。根因候选已定位到 `loadDatasetQueryIntents` 的三个过滤条件：`dm_dataset_query_intents.status=1`、`dm_tables.is_cli_enabled=1`、用户数据集权限。**开工前先连库确认并修复**，否则闭环建好也没有数据流。
2. `vendor/aukey/data-metrics` 是以 git 仓库形式直接在 vendor 里开发的（composer git 源），提交前确认当前分支与远端 `gitlab.aukeyit.com` 的关系。
3. opscli 仓库遵循项目 CLAUDE.md 全部铁律（中文注释/变更记录/GBK 输出安全等）；两个 PHP 仓库各有自己的 CLAUDE.md，执行前先读。
