# 取数规划器澄清增强方案（clarification assist）

> 版本：v1（草案）
> 日期：2026-07-26
> 范围：`opscli/query/services/planner/**`、`opscli/mcp/tools/query.py`、`opscli/query/commands/cli.py`、`opscli/skills/templates/ops-dataset-query/SKILL.md`，以及 ops-agent 侧取数提示词
> 前置阅读：`docs/analysis/ops-dataset-query规划器实现逻辑深度分析报告.md`、`docs/plans/取数规划器内核化与用户级元数据缓存实施计划.md`

---

## 1. 背景与问题

`query_flow` / `query_plan` 的选表依赖确定性规则：

| 阶段 | 依据 | 位置 |
|---|---|---|
| 1 | 显式 `dataset_alias` / 英文 `dataset_name` | `agent_query_planner.py:658` |
| 2 | 中文说明完整命中 | `agent_query_planner.py:699` |
| 3 | `intent_rules.json` 的 domain/slot 覆盖 + 打分，前两名分差 < `CLARIFY_SCORE_GAP=8` 则澄清 | `agent_query_planner.py:857` |

领域词表（`resources/intent_rules.json`，当前 8 个 domain）与业务别名表（`field_semantics.FIELD_QUERY_TERMS`，当前 5 组）是**静态维护**的，必然滞后于：

- 新数据集上线（中文说明未进 `description_patterns`）；
- 业务方新造的说法、部门黑话、指标缩写。

结果是用户描述明明清晰，却收到 `status=clarify_required`，且澄清文案只能给出"需要先确认要查询的数据集"这类空泛提示——**规划器知道自己不知道，但给不出有价值的选项**。

### 1.1 已否决的替代方案

「规则未命中 → 自动把全量元数据交给模型自选并直接执行」**不采纳**，原因：

1. 把 fail-loud 变成 fail-silent。取数场景下错表返回的是"看起来合理的错数"，用户无从察觉；
2. 破坏确定性与可审计性，`scripts/regression/planner_parity.py` 对拍安全网直接失效；
3. `plan_integrity` 封存的"规划不可被改写"语义被削弱；
4. 澄清事件本身是改进词表的最佳语料，自动兜底会让这个信号永久消失，技术债由显性转隐性。

### 1.2 本方案的定位

**只增强"怎么问"，不改变"谁来定"。** 模型基于全量授权目录生成**更准的澄清选项**，最终仍由用户确认；确认结果写回 `request` / `requested_fields` 后**重新走完整规划器**执行。规划器的选表算法、执行链路、完整性校验一律不变。

## 2. 目标与非目标

### 2.1 目标

- G1：`clarify_required` 且规划器给不出有效候选时，能向用户呈现**具名的、带理由的**数据集选项，而非空泛提示；
- G2：模型看到的信息**不弱于**规划器自身的决策卡片（否则增强无意义，见 §4）；
- G3：新增上下文开销可控，目录投影硬上限 **8 KB**；
- G4：产出"规则缺口"结构化语料，闭环反哺 `intent_rules.json` / `FIELD_QUERY_TERMS`；
- G5：全链路可开关、可回滚，关闭后行为与当前完全一致。

### 2.2 非目标（明确不做）

- ✗ 不改 `plan_query` 选表算法与任何打分常量；
- ✗ 不改 `plan_integrity`、`MAX_OUTPUT_BYTES` 守卫、执行链路；
- ✗ 不引入自动执行——用户未确认则不查；
- ✗ 不新增数据源，目录投影与规划器**同源** `QueryManager.metadata_all()`；
- ✗ 不恢复被屏蔽的 `query_catalog` / `query_intent_match`（远端 catalog 是另一套数据源，双源会不一致）。

## 3. 前置门槛（Phase 0，未通过则不实施）

本方案的收益面仅覆盖"词表未覆盖"一类澄清。先量化，再决定是否投入。

对 `clarify_required` 按 `missing_information` / `clarification_reason_codes` 分类统计：

| 类别 | reason code | 本方案能否改善 |
|---|---|---|
| **A. 词表未覆盖** | `business_scope`、`dataset_selection`、`dataset_constraints` | ✅ 目标场景 |
| B. 用户信息真缺失 | `business_dataset`（多候选） | ⚠️ 仅改善提问质量 |
| C. 真歧义 / 无权限 | `field_identity`、`dataset_not_available_in_current_scope`、`incompatible_scope` | ❌ 不触发 |
| D. 确认类（非失败） | `time_scope_confirmation`、`recommended_fields_confirmation`、`default_dataset_confirmation` | ❌ 不触发，接入有害 |

**门槛：A 类占全部 `clarify_required` 的比例 ≥ 20% 才继续。** 低于该比例时，直接增补 `intent_rules.json` 与 `FIELD_QUERY_TERMS` 的性价比更高。

统计口径：优先取 ops-agent 侧 `dm_execution_logs`；opscli 侧从 `feedback` 记录中按工具名 `query_flow`/`query_plan` + 合同 `status` 抽取。

### 3.1 附带修复（低成本，建议同期做）

`CLARIFICATION_MESSAGES`（`query_plan.py`）缺少 `business_scope`、`business_dataset`、`dataset_selection`、`dataset_not_available_in_current_scope`、`incompatible_scope` 五个 code 的中文文案，当前全部 fallback 成 `"需要补充查询条件。"`——这是澄清质量差的直接原因之一，**补齐文案本身就能吃掉一部分收益**，且零风险。

## 4. 核心设计：相关性排序的目录投影

### 4.1 要解决的矛盾

- 投影 `dataset_summaries_zh`（现有实现：`{N 个维度、M 个指标；代表字段：前 3 个}`，`query_plan.py:1536`）→ 信息**比规划器卡片更少**（卡片携带全部字段中文名+技术名参与打分），模型凭什么选得更准？
- 投影全字段 → 撞 `MAX_OUTPUT_BYTES` 设计意图与上下文成本。

### 4.2 解法

**投影时就做检索**：字段样例不取"前 3 个"，而是**按与用户请求的相关性排序**取 TopN——直接复用现有 `dataset_guidance._field_score()`。模型看到的是"这张表里与你的问题最相关的字段"，信息密度远高于盲取，同时体积恒定。

### 4.3 数据结构

新增模块 `opscli/query/services/planner/clarify_catalog.py`（纯函数，无 IO）：

```python
def build_clarify_catalog(
    adapter: MetadataAdapter,
    query: str,
    *,
    top_datasets: int = 12,
    top_fields: int = 8,
    max_bytes: int = 8000,
) -> dict:
    """为澄清增强投影当前账号的授权数据集目录。

    与规划器同源（同一个 MetadataAdapter），只做投影不做决策。
    字段样例按 dataset_guidance._field_score 与 query 的相关性排序，
    保证模型看到的字段证据不弱于规划器决策卡片。
    """
```

返回形态：

```json
{
  "contract": "clarify_catalog_v1",
  "query": "<原始请求，供模型对照>",
  "dataset_total": 63,
  "datasets_shown": 12,
  "truncated": true,
  "datasets": [
    {
      "dataset_alias": "ds_xxx",
      "name_zh": "即时综合数据集",
      "category": "normal",
      "dimension_count": 42,
      "metric_count": 18,
      "has_date_field": true,
      "relevant_fields_zh": ["渠道名称", "平台", "订单量", "销售额"],
      "relevance_score": 187
    }
  ],
  "usage_zh": "从 datasets 中选出与请求最匹配的一个，把其 dataset_alias 原样写入 request 后重新调用 query_flow；不要据此自行拼装 query_simple。"
}
```

### 4.4 排序与截断规则

1. 过滤 `dataset_category == "query_component"`（权限组件表不是业务数据集）；
2. 每个数据集的 `relevance_score` = 该表所有字段 `_field_score(field, normalized_query, query_tokens)` 的 **Top3 之和** + 数据集 `description` 命中加权；
3. 按 `relevance_score` 降序取 `top_datasets`，得分为 0 的表**不进列表**，只计入 `dataset_total` 与 `truncated`；
4. 全部得分为 0 时（请求完全无字段证据）→ 退化为按 `dimension_count + metric_count` 降序取前 `top_datasets`，并置 `"relevance_basis": "size_fallback"`，让模型知道排序不可信；
5. **体积硬守卫**：序列化超 `max_bytes` 时逐步降 `top_fields`（8→5→3）再降 `top_datasets`（12→8），仍超则 `raise RuntimeError("clarify_catalog_output_too_large")`——与规划器守卫同风格，不静默截断。

体积估算：单条约 100~140 字节（中文按 UTF-8 3 字节计约 300~400 B），12 条约 4~5 KB，留足余量。

## 5. 触发条件

**由调用方（Agent/Skill）判定并主动调用**，规划器不自动串联——保持规划器单一职责与确定性。

判定条件（全部满足）：

```
contract.status == "clarify_required"
AND contract.query_mode == "dataset_query"
AND clarification_reason_codes ∩ {business_scope, dataset_selection, dataset_constraints, business_dataset} ≠ ∅
AND clarification_reason_codes ∩ {field_identity, time_scope_confirmation,
        recommended_fields_confirmation, default_dataset_confirmation,
        dataset_not_available_in_current_scope, incompatible_scope} == ∅
AND model_view.dataset_candidates_zh 为空或长度 < 2
```

最后一条很关键：**规划器已给出 ≥2 张候选卡片时不触发**——那种情况规划器的判断优于目录投影，直接按卡片提问即可。

为降低模型误判，同时在合同侧内嵌显式信号（见 §7），让模型无需自行推理触发条件。

## 6. 接口设计

### 6.1 MCP 工具（主路径）

`opscli/mcp/tools/query.py` 新增，并注册进 `_ALL_TOOLS`：

```python
async def query_clarify_catalog(
    request: str,
    top_datasets: int = 12,
    session_id: str | None = None,
    jwt: str | None = None,
) -> dict:
    """【仅澄清态使用】返回当前账号授权数据集目录（按与请求的相关性排序）。

    仅当 query_plan/query_flow 返回 status=clarify_required 且合同内含
```

## 7. 合同侧信号

`build_model_contract`（`query_plan.py:1180`）在 `status == "clarify_required"` 时追加：

```json
"clarification_assist": {
  "eligible": true,
  "reason_codes": ["business_scope"],
  "next_tool": "query_clarify_catalog",
  "hint_zh": "规划器无法从当前请求定位数据集。可调用 query_clarify_catalog 获取授权数据集目录，向用户给出具名选项；用户确认后把 dataset_alias 写回请求重新规划。"
}
```

`eligible` 由 §5 的条件在服务端算好，**模型不需要自己判断**。不满足条件时该键不出现（沿用现有"缺省即不适用"的合同风格）。

体积影响：约 200 B，且仅澄清态出现，不影响 `planned` 主路径。

## 8. 回灌协议（易错点）

⚠️ **必须写 `dataset_alias`，不能只写中文名。**

- 阶段 1 `_explicit_candidates` 匹配的是 `dataset_alias` 或**英文** `dataset_name`，命中得 100/90 分；
- 中文名走阶段 2 `_description_candidates`，要求数据集中文说明**完整**出现在查询中，长说明极易不命中。

因此：

1. 投影里必须带 `dataset_alias`，`usage_zh` 明确要求"原样写入 request"；
2. 用户点选字段时，走 `query_flow(requested_fields=[...])`（`_select_fields` 给 1000 分必选，`dataset_guidance.py:222`），**不要**把字段名硬塞进 `request` 文本；
3. 回灌后重新调用 `query_flow`，走完整规划链路——时间口径、公式/快照聚合、默认条件、权限枚举、`plan_integrity` 封存全部照常。

回灌示例：

```
query_flow(
  request="查询各渠道的销量 昨天 环比，使用数据集 ds_xxx",
  requested_fields=["order_qty", "channel_name"]
)
```

## 9. 审计与闭环

### 9.1 采纳标记

回灌后的规划合同追加（不参与 `plan_integrity` 摘要之外的语义）：

```json
"model_view": {
  "selection_source_zh": "本次数据集由澄清增强目录提供选项、经用户确认选定"
}
```

并写入 `answer_contract.required_disclosures_zh`——**用户有权知道这次选表不是规则直接命中的**。

### 9.2 规则缺口语料

澄清增强被触发并最终成功回灌时，通过既有 `feedback_submit` 提交一条结构化记录：

| 字段 | 内容 |
|---|---|
| `scene` | `planner_rule_gap` |
| `request` | 用户原始请求 |
| `reason_codes` | 触发时的 `clarification_reason_codes` |
| `resolved_alias` | 用户最终选定的 `dataset_alias` |
| `resolved_fields` | 最终采用的字段 |
| `metadata_fingerprint` | 规划时的元数据指纹 |

这批数据是 `intent_rules.json` 的 `description_patterns`、`terms` 与 `FIELD_QUERY_TERMS` 的**直接增补依据**。建议每月盘一次：命中同一 `resolved_alias` ≥3 次的请求模式，就该进词表。

**这是本方案区别于"自动兜底"的核心价值——不是掩盖规则缺口，而是把它变成可量化的待办。**

## 10. 提示词改动

### 10.1 ops-agent 侧（`dm_agent_prompts`，取数提示词 v4）

在现有第 2 条 `status=clarify_required` 处置分支内追加：

> 若合同含 `clarification_assist.eligible=true`：先调用一次 `query_clarify_catalog(request=<同一句请求原文>)`，把返回的 `datasets` 转成 2~4 个具名选项（中文名 + 相关字段）向用户提问；用户确认后，把选定的 `dataset_alias` 原样写入 request、点名字段放进 `requested_fields`，重新调用一次 `query_flow`。

按提示词 DB 化范式（见 `project_prompt_v9_merge` 经验）：**全量快照迁移**，不做局部 patch，逐字守卫只加在最新版。

第 46 行 `status=clarify_required` 处置段追加同语义说明，CLI 形态为 `opscli query clarify-catalog`。

## 12. 验收标准

| 编号 | 标准 | 度量 |
|---|---|---|
| A1 | A 类 `clarify_required` 的**二次规划成功率**提升 | 触发澄清增强后，回灌重规划得到 `status=planned` 的比例 ≥ 70% |
| A2 | 不引入静默错表 | 抽样 20 次触发，人工核对用户确认的数据集与真实意图一致率 100%（不一致必须能追溯到用户选错，而非系统替选） |
| A3 | 体积可控 | `clarify_catalog_v1` 序列化 P99 ≤ 8 KB |
| A4 | 主路径零影响 | `status=planned` 合同的字节数、`planner_parity.py` 对拍结果与改动前**逐字段一致** |
| A5 | 闭环有效 | 灰度期产出 ≥20 条 `planner_rule_gap` 语料，并据此完成一次词表增补 |

**A4 是硬门槛**：本方案若对 `planned` 主路径产生任何合同差异，说明设计走偏，必须回退重做。

## 14. 测试策略

### 14.1 单元测试（`tests/query/planner/test_clarify_catalog.py`）

- 相关性排序正确性：构造字段命中/不命中的假 payload，断言顺序；
- `query_component` 被过滤；
- 全 0 分退化到 `size_fallback` 且标记正确；
- 体积守卫：构造超大 payload，断言逐级降级路径与最终 `raise`；
- 与 `_field_score` 的一致性：同一 query 下投影里的 `relevant_fields_zh` 顺序 == `dataset_guidance` 选出的顺序。

### 14.2 契约测试

- `status=planned` 合同不含 `clarification_assist`；
- §5 各触发条件的真值表覆盖（尤其 D 类确认场景必须 `eligible=false`）。

### 14.3 回归

- `scripts/regression/planner_parity.py` 原样跑通（A4 硬门槛）；
- CASES 增补两条：`rule_gap_clarify`（词表未覆盖的真实请求）、`confirm_only`（仅默认时间口径待确认，断言不触发）。

### 14.4 e2e

QA 账号跑 3 条：词表未覆盖请求 → 触发 → 回灌 → `planned` → 取数成功；确认类澄清 → 不触发；`planned` 直查 → 全程无额外调用。

## 15. 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| 模型不经用户确认直接采用目录第一项 | 🔴 | 提示词显式禁止 + `usage_zh` 内嵌约束 + 回灌合同强制披露（§9.1），灰度期人工抽检 |
| 目录排序质量差，选项还不如规划器候选 | 🟠 | §5 最后一条：规划器已有 ≥2 候选时不触发；`size_fallback` 显式标记排序不可信 |
