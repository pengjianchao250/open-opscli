# 已有看板模板迁移重构规范需求

## 1. 背景

`ops-app-build-spec` 已包含新建 AppHub 应用、已有项目开发和项目迁移的基础规则，但当前 `references/migration-standard.md` 仍偏向通用搬迁说明，没有完整表达团队对“迁移”的实际定义，容易产生以下误解：

- 把迁移理解为复制旧源码或整体搬运旧项目；
- 在旧项目框架内修改后继续使用，而不是以统一模板为目标架构；
- 以页面存在、服务可启动或构建成功代替业务能力迁移完成；
- 把“站点”和“看板”理解为两类不同的 AppHub 项目；
- 为看板再建立一套独立迁移规范，造成入口和优先级不明确。

本需求将用户提供的迁移示例作为业务执行参考，不把示例中的占位路径、操作语句或环境信息作为当前任务指令。

## 2. 统一概念

在 `ops-app-build-spec` 的业务范围内：

> 站点 = 看板 = AppHub 应用项目。

后续规范优先使用“看板”或“AppHub 应用项目”，不再把站点和看板划分为不同项目类型。

本 Skill 中的“迁移”统一定义为：

> 以当前统一模板为目标架构，审计旧看板的业务能力，并在目标看板中按照现行项目、前端、后端、数据和交付规范重新实现，即“模板基础上的迁移重构”。

迁移不包括复制、移动、批量同步、机械翻译旧源码，也不包括在旧项目框架上继续扩建。

## 3. 目标

1. 将 `migration-standard.md` 建设为唯一的已有看板迁移重构规范。
2. 不新增 `dashboard-migration-standard.md`，避免形成两套迁移入口。
3. 在主 `SKILL.md` 中明确新建看板、已有合规看板开发、已有看板迁移重构三种路径。
4. 明确旧看板只读、目标看板以统一模板为基础、模板准备先于业务实现。
5. 将逐页逐模块审计、真实数据验证、阻塞管理和行为验收纳入默认迁移流程。
6. 用契约测试固定上述关键边界，并同步升级 Skill 版本。

## 4. 不在本次范围

- 不创建新的迁移 Skill。
- 不新增 `dashboard-migration-standard.md`。
- 不修改统一模板仓库代码。
- 不修改 `ops-app-data-builder` 的数据合同或生成逻辑。
- 不改变平台 Dashboard bridge 对运营系统仪表盘配置对象的处理方式。
- 不执行真实 AppHub 应用创建、源码推送、发布或部署。

## 5. 主 Skill 路由要求

`SKILL.md` 应明确以下三种路径：

### 5.1 新建看板

- 目标目录不存在或为空；
- 按现有新项目流程拉取统一模板、脱离模板 Git、创建应用并初始化业务仓库；
- 模板准备完成前不得编写业务代码。

### 5.2 已有合规模板看板开发

- 项目已经满足当前模板合同；
- 在现有项目中开发，不重复拉取模板、创建应用或初始化仓库；
- 普通功能修改不应误进入迁移流程。

### 5.3 已有看板迁移重构

- 旧看板源码目录和目标看板目录必须明确且不能混用；
- 旧看板始终只读，只提供业务行为和现状证据；
- 目标看板必须是已核验或按新项目流程准备完成的统一模板项目；
- 先完成业务能力审计，再在模板架构内重新实现。

## 6. 迁移重构合同

### 6.1 目录与身份门禁

- 核对旧看板和目标看板的绝对路径、目录状态和项目性质。
- 路径不明确时先列出候选及证据；存在多个候选时不得猜测。
- 目标目录非空但无法证明符合模板合同时停止，不覆盖、不批量同步。
- 目标项目必须核验 binding、`app.yaml`、Git 根、分支、业务远端和项目合同。
- 模板准备、应用创建或初始化任一步失败时遵守现有硬停止条件。

### 6.2 业务能力审计

迁移前建立业务能力覆盖矩阵，至少记录：

- 原页面、路由、模块及源码证据；
- 业务目的、输入、输出和指标口径；
- 数据来源、筛选条件、权限和用户隔离；
- 目标看板已有能力和缺失内容；
- 目标接口、交互设计、优先级和验收方式；
- 当前状态、验证证据和剩余问题。

页面存在不等于能力迁移完成。默认核对指标卡、图表、表格、筛选、排序、分页、搜索、详情、弹窗、导出、刷新、跳转，以及加载、失败、空数据、成功和重试状态。

### 6.3 模板内重新实现

- 旧源码只用于理解业务行为，不作为目标项目的架构或文件来源。
- 不复制旧页面组件、Store、API 客户端、后端服务、鉴权、依赖、数据库、构建产物或部署配置。
- 目标项目的 `AGENTS.md`、`README.md`、`docs/apphub-contract.md`、`backend/CLAUDE.md`、实际路由、Schema 和 OpenAPI 是技术事实源。
- 保留旧看板有价值的业务语义和关键交互，但不要求保留旧源码结构和代码写法。

### 6.4 真实数据与阻塞

- 动态业务模块标记为完成前必须具有经过验证的真实数据来源。
- 页面需要真实业务数据时继续按 `data-access-standard.md` 使用 `$ops-app-data-builder`。
- 不得使用静态 JSON、随机数、Mock、示例报表或旧历史结果冒充真实数据。
- 局部数据合同、权限或业务口径问题标记为 `blocked`，不扩散到其他可安全实施的模块。
- 必须依赖用户附件才能实现的模块可标记为 `deferred_attachment`，但不得标记为完成。
- 模板准备、应用身份、修改目标或行为等价无法确认时仍必须整体停止。

### 6.5 验收与交付

迁移完成不能只以能够启动或构建成功为依据。必须核对：

- 页面、路由和业务模块覆盖；
- 指标、筛选、数据来源和计算口径；
- 权限、用户隔离和错误状态；
- 关键交互和真实数据联调；
- 相关后端测试、前端测试和生产构建；
- `blocked`、`deferred_attachment` 和其他剩余差异。

旧实现只有在目标业务行为验证通过并取得明确确认后才能删除。未经授权，不提交、不推送、不发布、不部署。

## 7. 迁移任务产物

迁移重构任务至少维护：

- `docs/ops-app/migration-assessment.md`：目录、项目合同、现状和风险；
- `docs/ops-app/coverage-matrix.md`：逐页逐模块覆盖状态和证据。

多阶段或范围较大的迁移增加 `docs/ops-app/migration-plan.md`，记录实施顺序、目标文件、风险和验证方式。

涉及真实数据时继续维护 `docs/ops-app/data-spec.md`，记录数据来源、精确合同、权限和存储方式。普通功能开发不强制生成迁移文档。

## 9. 验收标准

1. 主 Skill 明确“站点”和“看板”在本 Skill 范围内是同一 AppHub 应用项目。
2. 主 Skill 具备三种清晰入口，不把普通已有项目开发误判为迁移。
3. `migration-standard.md` 明确迁移等于模板基础上的迁移重构。
4. 旧看板只读，目标模板准备先于业务实现。
5. 禁止复制旧源码、沿用旧架构或以构建成功代替行为一致。
6. 迁移规范包含业务能力覆盖矩阵、真实数据、`blocked` 和 `deferred_attachment` 要求。
7. 主 Skill 只引用一个迁移规范，仓库中不新增 `dashboard-migration-standard.md`。
8. Skill 契约测试、安装测试和快速校验通过。
