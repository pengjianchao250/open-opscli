# AppHub 应用迁移重构需求

## 1. 背景

现有 AppHub 看板迁移重构主要依赖 Skill 中的文字规范和 Agent 自行维护的 Markdown 记录，存在两个稳定复现的问题：

1. 迁移后页面能够运行，但导航、页面区域、模块顺序、父子层级和空间关系与旧看板差异较大。
2. 迁移步骤缺少机器可读状态、阶段门禁和逐项覆盖检查，页面、交互、异常状态或数据模块容易遗漏。
3. 真实数据合同验证与站点数据层实现没有机器区分，导致 `contract_status=verified` 被误解为 FastAPI、前端消费和测试已经完成。

本需求在 `opscli app` 下新增迁移工作流，并同步强化 `ops-app-build-spec` 与 `ops-app-data-builder`。命令负责状态和门禁，Skill 负责执行规则，项目文档负责业务证据。

## 2. 目标

- 迁移开始前明确旧看板与目标看板身份，保证旧看板只读、目标看板符合统一模板合同。
- 先完成导航、路由、页面区域和模块布局的一比一结构还原，再接入真实业务数据。
- 使用逐页逐模块覆盖矩阵记录迁移范围、状态、证据、阻塞原因和解除条件。
- 使用阶段门禁阻止跳过 UI 结构、真实数据合同或最终验收。
- 提供稳定 JSON 输出，供 Agent、CI 或其他自动化工具消费。
- 将迁移状态沉淀在目标项目中，支持中断后恢复和持续更新。
- 明确区分合同就绪、数据层就绪、发布就绪和最终可交付，任何中间态都不能被描述为完整交付。

## 3. 非目标

- 不自动复制旧项目源码、组件、Store、API 客户端、数据库、凭证或构建产物。
- 不通过截图像素比较替代业务结构验收。
- 不自动猜测 OPS 数据集、字段、聚合口径或第三方场景参数。
- 不把 Mock、随机数据、静态 JSON 或历史报表判定为真实数据接入完成。
- 不负责创建或发布 AppHub 应用；继续复用现有 `create`、`clone-template`、`init`、`push` 命令。

## 4. 角色与事实源

- **旧看板目录**：只读业务证据，只允许扫描文件清单和读取 Git 元信息。
- **目标看板目录**：标准模板项目，是迁移代码、状态和文档的唯一写入位置。
- **目标项目合同**：`AGENTS.md`、`README.md`、`docs/apphub-contract.md`、`backend/CLAUDE.md`、实际路由、Schema 和 OpenAPI。
- **迁移状态事实源**：目标项目 `.opscli/migration/<migration-id>/` 下的 JSON 文件。
- **人类可读证据**：目标项目 `docs/ops-app/` 下的迁移文档。

## 5. 标准阶段

迁移必须按以下顺序执行：

1. `audit`：确认路径和模板边界，盘点旧项目文件、路由、页面、导航、API 与测试候选证据。
2. `ui_blueprint`：建立导航、路由、页面区域、模块顺序、父子层级和尺寸约束。
3. `ui_skeleton`：在目标模板内完成 UI 骨架，不接入未经验证的真实数据合同。
4. `data_integration`：逐模块验证并接入真实数据。
5. `behavior_verification`：补齐筛选、排序、分页、搜索、详情、导出、刷新和页面状态。
6. `release_verification`：执行逐页逐模块验收、测试、构建和交付检查。
7. `complete`：所有交付门禁通过。

禁止从 `audit` 直接跳到数据接入或完成态。

## 6. 命令需求

在 `opscli app migrate` 下提供以下命令：

| 命令 | 职责 |
| --- | --- |
| `init` | 校验路径和目标模板，创建迁移任务、审计快照、覆盖矩阵、UI 蓝图和项目文档 |
| `audit` | 重新扫描旧项目只读证据并更新审计快照 |
| `plan` | 根据机器可读状态生成迁移计划、UI 规格和数据规格 |
| `status` | 输出当前阶段、覆盖数量、状态计数、动态数据模块、阻塞项、门禁问题和 `delivery_ready` |
| `check` | 只读检查指定门禁，不推进阶段 |
| `verify-ui` | 校验 UI 门禁，通过后推进到 `data_integration` |
| `verify-data` | 校验真实数据门禁，通过后推进到 `behavior_verification` |
| `verify-release` | 校验最终交付门禁，通过后推进到 `complete` |
| `export` | 重新生成全部人类可读迁移文档和验收报告 |

所有命令使用统一信封：

```json
{
  "success": true,
  "command": "app migrate status",
  "data": {},
  "error": null
}
```

## 7. 目录和文件

目标项目保存以下机器可读文件：

```text
.opscli/migration/current.json
.opscli/migration/<migration-id>/migration.json
.opscli/migration/<migration-id>/audit-snapshot.json
.opscli/migration/<migration-id>/coverage-matrix.json
.opscli/migration/<migration-id>/ui-blueprint.json
```

目标项目保存以下人类可读文件：

```text
docs/ops-app/migration-plan.md
docs/ops-app/ui-spec.md
docs/ops-app/data-spec.md
docs/ops-app/migration-acceptance.md
```

其中 `data-spec.md` 可能同时包含 `ops-app-data-builder` 维护的业务口径。迁移命令只能更新 `<!-- opscli:migration-data:start -->` 与 `<!-- opscli:migration-data:end -->` 之间的受管区块，不得覆盖区块外的人工或数据 Builder 内容。

## 8. 覆盖矩阵合同

新建迁移任务使用 Schema v2；现有 Schema v1 允许只读兼容，但 `status` 必须返回 `schema_upgrade_required=true`。Schema v2 固定使用 `remaining_issues` 和 `unblock_conditions` 数组，不再接受自由命名。

覆盖项至少包含：

```json
{
  "id": "MODULE-003-02",
  "kind": "module",
  "source": {"route": "/sales/trend", "evidence": ["frontend/src/views/SalesTrend.vue"]},
  "target": {"route": "/sales/trend", "files": ["frontend/src/views/SalesTrendView.vue"]},
  "status": "待实施",
  "dynamic": true,
  "layout": {"parent_id": "PAGE-003", "order": 2, "region": "main", "columns": 1},
  "data_contract": {
    "product_key": "sales_trend",
    "status": "candidate",
    "implementation_status": "not_started",
    "evidence": []
  },
  "acceptance": {"checks": [], "evidence": []},
  "remaining_issues": ["真实数据合同和业务 API 尚未完成"],
  "unblock_conditions": []
}
```

允许的迁移状态为：`待实施`、`部分完成`、`已完成`、`blocked`、`deferred_attachment`。

数据合同状态至少支持：`candidate`、`verified`、`degraded`、`blocked`、`deferred_attachment`。

数据层实现状态至少支持：`not_started`、`in_progress`、`implemented`、`verified`、`contract_verified_only`、`layout_only`、`blocked`。合同状态与实现状态必须独立维护；合同 `verified` 不代表数据层已经交付。

## 9. UI 蓝图合同

UI 蓝图必须表达结构而非仅表达视觉主题：应用壳层、导航顺序、路由、页面区域、模块层级、上下顺序、栅格列数、主要高度、响应式折叠关系，以及加载、成功、空数据、失败和重试状态所在区域。字体、颜色、阴影和图标细节可以后置，但不得改变模块层级和页面结构。

## 10. 门禁规则

### 10.1 初始化门禁

- 旧项目与目标项目必须存在且为目录。
- 两者不能相同，也不能互相包含。
- 目标项目必须包含标准模板关键文件。
- 命令不得在旧项目中创建或修改任何文件。

### 10.2 UI 门禁

- 覆盖矩阵至少存在一个导航、页面、模块或页面状态项。
- 所有 UI 项必须为 `已完成`。
- 每个 UI 项必须存在目标路由或目标文件，并包含布局验收证据。
- UI 蓝图必须至少包含一个页面。

### 10.3 数据门禁

- 所有 `dynamic=true` 的模块必须存在数据合同。
- 所有真实数据模块的数据合同和数据层实现状态都必须为 `verified`。
- 项目必须存在符合固定 Schema 的 `docs/ops-app/data-contracts.json`，并通过 `delivery` 模式校验。
- `data-contracts.json` 与覆盖矩阵中的 `product_key`、合同状态和实现状态必须一致。
- 最终实现必须登记并实际存在后端 API、service、Pydantic Schema、前端消费者、测试和 OpenAPI 工件。
- 前端实现工件不得继续包含“等待真实数据合同”“仅用于布局验证”等未交付占位文本。
- `degraded`、`blocked` 和 `deferred_attachment` 必须保留证据及解除条件，且模块不能标记为 `已完成`。

### 10.4 发布门禁

- 覆盖矩阵不得存在未完成、部分完成、阻塞或待附件项。
- 每个覆盖项必须存在验收检查和验收证据。
- UI 与数据门禁必须同时通过。
- 验收报告必须由当前机器可读状态重新生成。
- 只有迁移阶段为 `complete` 且发布门禁无问题时，`delivery_ready` 才能为 `true`。

## 11. 审计要求

- 自动审计只生成候选证据，不宣称理解全部业务语义。
- 扫描常见前端、后端、配置、文档和测试文件，排除依赖、缓存、构建产物、本地数据库和临时目录。
- 按路径特征分类路由、页面、导航、API、测试和配置候选文件。
- 记录 Git 分支、提交、工作区状态和文件清单指纹。
- Agent 必须把候选证据转换为覆盖矩阵，不能把候选文件数量当成迁移完成度。

## 12. Skill 协作要求

### 12.1 `ops-app-build-spec`

- 迁移任务必须先执行 `opscli app migrate init`。
- UI 骨架完成前不得开始真实数据接入。
- 每完成一个模块立即更新覆盖矩阵和证据。
- 交付前依次执行 `verify-ui`、`verify-data` 和 `verify-release`。

### 12.2 `ops-app-data-builder`

- 从当前迁移覆盖矩阵读取 `dynamic=true` 的模块。
- 一个动态模块对应一个明确的数据产品合同。
- 验证结果回写 `data_contract.status` 和证据。
- 同时回写 `data_contract.implementation_status`；只有合同、后端、前端和测试闭环完成后才能写为 `verified`。
- 合同样例、FakeGateway 测试和真实线上联调必须分别记录，不得互相替代。
- 一个数据产品合同验证成功后继续处理全部未阻塞动态项，不得提前结束迁移任务。

## 13. 错误码

| 错误码 | 含义 |
| --- | --- |
| `APP-MIGRATION-PATH` | 源路径或目标路径无效、相同或互相包含 |
| `APP-MIGRATION-TARGET` | 目标项目不满足模板合同 |
| `APP-MIGRATION-EXISTS` | 迁移任务已存在 |
| `APP-MIGRATION-NOT-FOUND` | 没有可读取的迁移任务 |
| `APP-MIGRATION-STATE` | 迁移状态文件损坏或不符合合同 |
| `APP-MIGRATION-GATE` | 阶段门禁未通过 |

## 14. 验收标准

- CLI 中能够发现完整 `app migrate` 命令树。
- 初始化不会写入旧项目，并能在目标项目生成完整状态与文档。
- 相同路径、嵌套路径和非模板目标会被拒绝。
- 空覆盖矩阵无法通过 UI 门禁。
- 动态模块未验证真实数据合同时无法通过数据门禁。
- 合同已验证但业务 API、Schema、前端消费或测试缺失时无法通过数据门禁。
- 前端仍显示待接入占位文本时无法通过数据门禁。
- 门禁失败不会修改当前迁移阶段。
- 任何未完成覆盖项都无法通过发布门禁。
- `status` 在未完成阶段明确返回 `delivery_ready=false` 和下一项必须完成的门禁。
- 门禁失败返回稳定错误码、非零退出码和可执行修复建议。
- 两个 Skill 明确使用迁移状态与阶段门禁。
- App 模块和两个 Skill 的定向测试全部通过。
