# 迁移项目本地开发启动增量支持

日期：2026-10-20。范围：`opscli app dev` 与 `opscli app dev-status`。需求已确认，实施与验证结果见本文末尾。

## 背景与问题

源码复制迁移允许保留原项目结构，不要求拉取模板、FastAPI、`backend/app.py` 或 `frontend/`。当前迁移扫描器已支持 Node Web 入口，但开发启动器仍要求 backend/frontend 两项，随后固定准备 Python、安装后端依赖、构建 frontend，导致合法的 Vinext 单服务迁移项目无法启动。

复现项目为 `项目new-product-prev-050` 的迁移目标副本。其 startup-manifest 为 `backend=null`、`frontend.kind=node_web`、`frontend.cwd=.`、`frontend.command=[pnpm,run,dev]`，真实开发脚本为 `node scripts/run_vinext.mjs dev`。生产 runtime 来自 Dockerfile，不应直接用作本地热更新入口。

## 目标与边界

1. 增量支持已交付的 Node 单服务迁移项目，通过统一的 `opscli app dev <project-root>` 启动本地开发。
2. 仅当 `.opscli/project.json` 标记 `origin_type=migration_copy`，且迁移状态 `delivery_ready=true`、启动清单 `status=ready` 时进入迁移分支。
3. 普通新建、模板拉取、模板环境准备和原有双进程启动逻辑保持不变；已有 FastAPI 迁移启动逻辑保持不变。
4. 不修改迁移项目业务源码，不补造 backend，不拉取模板，不修改 Dockerfile、AppHub 生产入口、迁移交付或推送门禁。
5. 本轮支持能够从清单及 package.json 确认的 Vinext、Vite、Next 开发入口。不新增任意编排器、多服务运行时或 Docker 本地编排支持；证据不明确时明确阻止启动并提供重新扫描指引。

## 启动分流与命令

| 结构 | 行为 |
| --- | --- |
| 无迁移标记或非 migration_copy | 沿用标准模板启动 |
| 迁移 backend/frontend 均存在 | 沿用已有 FastAPI 迁移启动 |
| 迁移 backend 为空，frontend 为 node_web | 新增 Node 单服务启动 |
| 其他缺失或不支持的结构 | 返回 APP-DEV-MIGRATION，说明入口问题 |

Node 分支使用迁移扫描选出的开发项；清单选中生产 start 时，仅从已有 candidate_scripts 中选择明确的 dev 项。不从 Docker 生产 runtime 猜测开发方式，不把所有包含 Node 包装脚本的项目都视为可自动编排。

启动前校验 command、相对 cwd、项目目录边界、package.json 脚本与扫描记录一致。入口漂移、缺少开发脚本或不支持的端口参数应报可操作错误，提示 `opscli app migrate scan-startup --target <project-root> --json` 后重试。

复用清单中的 pnpm/npm/yarn 及实际工作目录，不使用模板专用的 frontend/packageManager 限制。声明了 packageManager 时应与命令匹配并遵守版本约束；未声明时保留清单已识别的包管理器。已有 node_modules 时不重装；缺失时使用对应锁文件执行冻结安装，缺少锁文件时不擅自生成锁或切换包管理器。不执行 Python 环境准备、模板 init_env/check_startup 或生产 build。

## 端口与生命周期

Node 单服务默认从 5173 起寻找空闲端口。`--frontend-port` 指定服务端口；`--backend-port` 可作为单服务端口别名。两者同时传入时必须一致。显式端口被占用时失败，不停止其他项目、不静默更换用户指定端口。

Vinext/Next 使用 `--hostname 127.0.0.1 --port <port>`；Vite 使用 `--host 127.0.0.1 --port <port> --strictPort`。npm run 透传参数使用 `--`，pnpm/yarn 使用其脚本参数规则。服务仍由项目自己的开发脚本负责环境加载与热更新。

单服务启动就绪后只输出一个访问地址；记录真实单服务进程，不把同一 PID 伪装成 backend/frontend 两个进程。启动失败、等待超时、用户中断或服务异常退出时清理本次启动的进程树与本次监督进程写入的状态。

## 状态兼容

已有 schema 1 双进程状态读写保持兼容。Node 单服务使用 schema 2，保存 `launch_mode=single`、`project_root`、`supervisor_pid`、`app_pid`、`app_port`、`started_at`，以进程与 TCP 就绪联合判断状态，不要求开发入口暴露生产健康路由。

`dev-status` 保留通用字段 `running`、`active`、`identity_verified`、`ports_reused`，单服务额外返回 `app_url`，并让 `frontend_url` 指向同一真实地址以兼容现有预览调用方；`backend_url=null`。状态缺失、损坏、目录不匹配或记录进程已退出时不得认领占用原端口的其他服务。该身份校验沿用现有 PID/目录/端口模型，不声称具备进程实例密码学证明。

## 验收标准

- 使用当前 Node/Vinext 清单结构可复现修复前错误，修复后无需 backend/frontend 目录即可启动。
- 覆盖入口漂移、目录越界、迁移门禁未通过、未知入口、包管理器/锁文件和端口冲突的失败分支。
- 覆盖依赖复用、缺失依赖安装、npm 参数分隔、Vinext/Next/Vite 端口参数。
- 覆盖单服务状态、旧状态兼容、重复启动阻止、进程退出后的端口复用与失败清理。
- 原有模板启动、FastAPI 迁移启动及相关 CLI、迁移和新建流程测试通过。
- 在当前迁移副本执行真实 `opscli app dev`，再执行 `dev-status --json`，核实 running、identity_verified、项目路径和实际访问地址，并请求页面与健康路由。
