## 2. 背景

Collector 内部的 SellerSprite 任务已经使用 SQLite 队列、执行租约和长运行调度器。现有状态能够回答任务是否为 `queued`、`running`、`succeeded` 或 `failed`，但仍不能可靠回答以下问题：

1. `running` 任务是否仍有真实业务进展，而不只是进程继续续租。
2. 排队任务是否正被正常消费，还是队列已经无人处理。
3. 调度器、Worker 与任务之间是否出现“进程看似存活、任务实际停滞”的断层。
4. 服务重启后，异常提醒是否会重复轰炸，恢复是否能形成闭环。
5. 运维人员能否在不接触业务写入口、不控制浏览器的前提下快速定位问题。

因此一期在 opscli 内新增一个**独立、长运行、只读业务数据**的 Collector Monitor 服务。它与 Collector MCP 分进程部署，持续读取 SellerSprite 的持久监督数据，计算健康状态，通过 Starlette 提供只读网页和 API，并可向企业微信群机器人发送去重、冷却和恢复提醒。

## 3. 目标与非目标

### 3.1 一期目标

1. 在 opscli 发行包内提供独立的 `collector_monitor` 长运行服务。
2. 对 SellerSprite 任务进度和调度器运行状态建立可跨进程、跨重启读取的持久监督信号。
3. 将任务健康归类为 `healthy`、`slow`、`stalled`、`orphaned`。
4. 将队列与消费能力异常归类为 `queue_starved`、`worker_unavailable`。
5. 对业务 SQLite 保持严格只读，不迁移、不修复、不更新业务状态。
6. 提供 Starlette 网页和只读 HTTP API，以及本地 CLI 查询与服务启动命令。
7. 通过受保护文件读取企业微信 Webhook，不把密钥放入命令行或普通配置输出。
8. 提供告警去重、冷却、重启延续和恢复通知。
9. 对用户、账号、参数、凭证、内部路径和原始错误实施最小披露与统一脱敏。

### 3.2 一期明确不做

Collector Monitor v1 不提供也不暗含以下能力：

- 取消任务；
- 重试任务；
- 重新入队或调整队列顺序；
- 修改任务、租约、进度、调度器或账号状态；
- 启动、停止、接管或操作浏览器；
- 登录卖家精灵、处理验证码或刷新浏览器 Profile；
- 自动恢复 Collector、Worker 或业务任务；
- 飞书通知；
- 面向公网的完整身份认证系统；
- 替代系统级进程管理、日志平台或指标平台。

即使 SellerSprite 现有运维 CLI 中存在 `queue fail` 或 `requeue-running`，Monitor 的 UI、API 和 CLI 也不得代理、包装或调用这些写操作。

## 4. 总体架构

```text
SellerSprite 提交与调度进程
  ├─ 写任务状态、进度检查点、执行租约
  └─ 写调度器/Worker 运行时心跳
                 │
                 ▼
~/.config/opscli/seller_sprite/task_queue.sqlite3
                 │  SQLite URI mode=ro + query_only
                 ▼
独立 Collector Monitor 进程
  ├─ 只读快照采集器
  ├─ 健康判定器
  ├─ 事件与恢复状态机
  ├─ 监控私有状态库（唯一允许写入）
  ├─ 企业微信通知器
  └─ Starlette UI / 只读 API
                 │
                 ├─ 浏览器 / 反向代理
                 └─ opscli collector-monitor status|tasks|show|incidents
```

### 4.1 进程边界

- Collector MCP 继续负责业务任务提交和执行。
- SellerSprite 调度器继续是任务、租约、进度和运行时监督字段的唯一业务写入方。
- Collector Monitor 作为独立进程运行，Collector MCP 停止或阻塞时仍应能够读取最后的持久状态并报警。
- Monitor 不导入或启动 SellerSprite 调度器，不调用 `get_task_scheduler()`，避免查询动作意外初始化业务库或启动消费者。
- Monitor 的退出、故障或升级不得阻断任务提交与执行。

### 4.2 模块职责

一期建议将 `opscli/collector_monitor` 组织为以下职责边界，具体文件名可按实现调整：

| 组件 | 职责 | 禁止职责 |
|---|---|---|
| 配置加载 | 校验路径文本、阈值和监听地址；读取受保护文件时在 POSIX 拒绝组/其他用户权限 | 输出密钥原文；Windows 下不得假称已验证 ACL |
| 业务只读仓储 | 读取任务、进度、租约和调度器运行时快照 | 建表、迁移、更新、修复业务库 |
| 健康判定器 | 依据同一时刻快照计算健康分类与事故候选 | 依据单一 PID 或单一心跳直接断言健康 |
| 事件状态机 | 以 `(rule, subject)` 去重，持久化冷却、恢复和连续孤儿观测 | 修改业务任务 |
| 通知器 | 每次发送时从受保护文件读取 Webhook，发送脱敏 Markdown V2 | 支持飞书或泄露 Webhook |
| Web 应用 | 提供单页仪表盘、探针和只读 JSON API | 提供 POST/PUT/PATCH/DELETE 业务操作 |
| CLI | 启动服务；通过 HTTP API 查询 JSON 状态 | 暴露取消、重试、重排、浏览器控制 |

## 5. 持久监督模型

### 5.1 任务进度

任务状态变化粒度太粗。SellerSprite 执行方必须在业务步骤完成或进入可辨识的新阶段时持久化以下字段：

| 字段 | 状态 | 含义 |
|---|---|---|
| `progress_stage` | 已确认 | 稳定、低基数的业务阶段。运行阶段白名单为 `claimed`、`resolving`、`requesting`、`browser_wait`、`remote_poll`、`processing`、`exporting`、`uploading`、`finalizing`；另有排队、重派与终态阶段 `queued`、`reassigned`、`succeeded`、`failed`。`finished` 只用于旧数据迁移兼容，新写入使用 `succeeded` |
| `progress_at` | 已确认 | 最近一次真实进度发生时间，带时区 ISO 8601 |
| `progress_sequence` | 已确认 | 每次真实进度递增的单调序号；同一阶段内部有实际推进时也可递增 |
| `seller_sprite_task_progress_events.metadata_json` | 已确认 | 仅允许白名单键 `poll_attempt`、`poll_status`、`poll_total`、`outcome`；Monitor 默认详情只公开阶段、时间与序号 |

约束：

1. Worker 心跳续租不得自动更新 `progress_at` 或 `progress_sequence`。
2. 只有任务真正跨阶段或取得可验证成果时才记录进度。
3. 历史任务升级回填可使用 `created_at` 或 `started_at` 作为初始 `progress_at`，但不得伪造后续推进。
4. 终态必须写入稳定阶段；终态任务不参与 `stalled` 或 `orphaned` 告警。
5. 进度事件的 `metadata_json` 即使来自白名单，也不进入默认任务详情、企业微信或普通日志；需要排查轮询时只在受控入口按最小字段开放。

### 5.2 调度器与 Worker 运行时

只有任务租约心跳不足以证明调度器能够继续领取新任务。SellerSprite 已确认通过 `seller_sprite_runtime_heartbeats` 持久化调度器运行时记录：

- 每个调度器实例一行，以随机生成的 `execution_owner` 为主键，不使用可复用 PID。
- 调度器周期性 upsert 心跳与能力摘要。
- 优雅退出时将 `lifecycle_state` 写为 `stopped`，并把活跃 Worker 与可用容量清零；非优雅退出由心跳过期识别。

已确认字段：

| 字段 | 含义 |
|---|---|
| `execution_owner` | 调度器实例及任务租约 owner 的关联键 |
| `lifecycle_state` | 运行生命周期；分类器将 `running`、`ready`、`healthy` 视为可存活状态，停止时写 `stopped` |
| `heartbeat_at` | 调度器运行态最近心跳时间 |
| `generic_workers_alive` | 存活的通用账号工作槽数量 |
| `listing_worker_alive` | 存活的 Listing Analysis 工作槽数量 |
| `generic_available_capacity` | 当前可领取普通任务的通用 Worker 容量；基于同一队列范围内 SQLite 全局 `running` 账号占用与本实例活跃尝试的并集，扣除 Generic、Listing、专属任务及其他调度器产生的共享账号互斥占用 |
| `listing_available_capacity` | 当前可领取 Listing Analysis 的专属 Worker 容量；基于同一队列范围内 SQLite 全局 `running` 账号占用与本实例活跃尝试的并集，扣除 Generic、Listing、专属任务及其他调度器产生的共享账号互斥占用 |
| `available_capacity` | 两类可用容量之和，仅用于兼容和展示，不参与任务类型匹配 |
| `standby_capacity` | 冷备用容量摘要 |
| `last_claim_at` | 最近一次成功领取任务时间 |
| `last_progress_at` | 当前实例最近一次推动任一任务进度的时间 |

SellerSprite 队列 schema 当前为 v6；从 v5 升级到 v6 时为两类精确容量增量加列，历史运行时行默认填 0，等待下一次真实 heartbeat 覆盖。运行时记录只能由 SellerSprite 调度器写入。Monitor 只读取，不“代打心跳”。

多调度器或滚动部署期间，容量不能只依据本进程 `_active_attempts`：调度器会读取同一 `queue_scope` 下全部 `running` 任务的账号键，并与本实例刚登记的活跃尝试取并集后计算容量。普通任务发生账号认证故障时，备用账号改绑使用任务代际 CAS，并明确区分 `reassigned`、`replacement_busy` 和 `stale_attempt`：只有备用账号被占用时才按接口顺序继续枚举；旧代际立即停止，不能耗尽账号池、关闭可能已被新代际复用的会话或覆盖新执行跟踪。每个内存执行跟踪还携带独立令牌，旧 worker 收尾只能删除自己的令牌。所有候选均不可改绑时按当前账号和代际原子结束任务，不允许工作槽退出后遗留无人续租的 `running`。

### 5.3 业务库与监控私有库

业务库仍为：

```text
~/.config/opscli/seller_sprite/task_queue.sqlite3
```

Monitor 使用独立的私有状态库保存告警状态；已确认默认路径：

```text
~/.config/opscli/collector_monitor/state.sqlite3
```

当前监控私有库 schema 版本为 2，包含：

- `incidents`：以 `(rule, subject)` 为主键，保存严重度、脱敏消息、`opened_at`、`last_seen_at`、`resolved_at`、opening/escalation/reminder/recovery 投递状态与时间，以及脱敏 `delivery_error_class`、固定 `delivery_result`；
- `consecutive_observations`：以 `(rule, subject)` 为主键保存连续观测次数，目前用于 `orphaned` 确认；
- `scan_state`：单行保存最近扫描、最近成功扫描与安全错误码；轮询服务在成功和失败扫描后持久化更新，API 公开 `last_scan_at`、`last_success_at` 与稳定 `error_code`；
- `PRAGMA user_version = 2`。

任务详情只保存在进程内缓存。当前没有通知次数、显式冷却截止时间、连续健康恢复观测或事件保留表。

配置加载和 Monitor 每次建立状态库写连接时都必须复核物理文件身份：业务库与私有库不得是相同解析路径，不得通过符号链接或硬链接指向同一文件；写连接还需读取 SQLite `main` 实际打开路径后再次比较，避免路径检查与连接建立之间发生替换。身份无法可靠确认时应拒绝启动或写入，而不是冒险继续。

监控私有库不得复制以下内容：

- `request_json`、`params_json` 或结果正文；
- 用户邮箱原文；
- 卖家精灵用户名、密码、Cookie、JWT、Session、Authorization；
- 企业微信 Webhook；
- 浏览器 Profile、页面 HTML、截图或网络请求；
- 完整内部文件路径或第三方错误响应。

## 6. 严格只读业务 SQLite 边界

### 6.1 连接要求

业务仓储必须满足以下全部条件：

1. 使用 SQLite URI 的 `mode=ro` 打开业务库。
2. 连接后设置 `PRAGMA query_only = ON`。
3. 不执行业务仓储的 `_ensure_schema()` 或任何初始化逻辑。
4. 不执行 `CREATE`、`ALTER`、`DROP`、`INSERT`、`UPDATE`、`DELETE`、`REPLACE`、`VACUUM`、写事务或用户版本更新。
5. 不执行会修改业务 WAL 状态的检查点命令。
6. 不把业务库 `ATTACH` 到可写连接；不允许触发器或用户自定义函数产生副作用。
7. 查询连接使用 2 秒超时并保持稳定排序；活动任务用主键游标每批 500 条完整读取以保证分类不漏项，公开快照最多展示 1000 条任务，运行时最多读取 100 条，单时间线默认 200、上限 500 条。
8. 一轮任务、运行时和生命周期计数在同一只读连接与显式读事务中获取；时间线按任务集合分批查询，避免逐任务重扫全表。
9. 业务扫描、分类所需状态事务、事故对账、时间线读取和通知结果写回均通过工作线程执行，不阻塞 Uvicorn 事件循环；首次扫描在 ASGI lifespan 完成后后台启动，使 `/health/live` 可立即响应。
10. 业务库不存在、不可读、锁等待超时或 schema 不兼容时，Monitor 返回未就绪快照并通过 `/health/ready` 报告失败；当前不会创建监控自身事故记录，也不得尝试创建空库或修复。

不能使用 `immutable=1`，因为业务库会持续变化，且需要正确观察 WAL 中的新提交。

### 6.2 进程权限

推荐使用独立系统账号运行 Monitor：

- 对业务 SQLite 主文件及读取 WAL/SHM 所需目录仅授予读取和目录遍历权限；
- 对监控私有状态目录授予读写权限；
- 对企业微信 Webhook 文件仅授予读取权限；
- 不授予 SellerSprite 账号绑定库、密钥文件或浏览器 Profile 的访问权限。

文件权限是第一道防线，`mode=ro` 与 `query_only` 是第二道防线，API/CLI 无写命令是第三道防线。

## 7. 健康模型

### 7.1 数据时钟与共同原则

- 所有时间都解析为带时区时间，再统一转换为 UTC 比较。
- 仓储使用同一个只读连接并显式执行 `BEGIN`，在同一 SQLite 读事务中取得生命周期计数、全部活动任务、有界终态历史和运行时；分类基于该轮固定快照。
- 时间字段解析失败时年龄为未知，未来时间年龄钳制为 0；当前没有系统时钟回拨或数据质量事故，运维必须依赖主机时钟同步。
- 阈值使用“达到或超过”语义，即 `age >= threshold` 生效。
- 健康分类不改变业务状态；`running + stalled` 仍然是业务 `running`。

### 7.2 任务健康分类

优先级从高到低为：`orphaned` → `stalled` → `slow` → `healthy`。同一任务对外只展示最高优先级主分类，同时保留判定证据。

| 分类 | 适用任务 | 已确认判定 | 主要证据 |
|---|---|---|---|
| `healthy` | 全部生命周期 | 未达到适用于该生命周期的异常条件；排队年龄低于 `QUEUE_THRESHOLD / 2` 的 `queued`、进度新鲜的 `running` 和终态任务均归为此类 | 生命周期、排队年龄、进度年龄、租约、运行时心跳 |
| `slow` | `running`、`queued` | `running`：owner/运行时或租约不可信但尚未达到孤儿连续观测次数，或进度年龄达到 `STALLED_THRESHOLD / 2`；`queued`：排队年龄达到 `QUEUE_THRESHOLD / 2`，但尚未形成无匹配容量或无近期活动的队列事故 | 连续孤儿观测数、进度年龄、排队年龄、匹配容量、近期领取/进度 |
| `stalled` | `running` | owner 对应运行时新鲜、租约未过期，但进度时间缺失或年龄达到 `STALLED_THRESHOLD`；说明“调度器活着且租约有效，但业务进度不可证明或不推进” | `progress_at`、`started_at`、运行时 `heartbeat_at`、`lease_expires_at` |
| `orphaned` | `running` | owner 缺失、关联运行时不新鲜/不存在，或租约为空/过期，并已连续满足 `ORPHAN_REQUIRED_SCANS` 轮 | `execution_owner`、`lease_expires_at`、运行时 `heartbeat_at`、连续观测数 |

已确认的分类关系：

```text
slow 起点 = STALLED_THRESHOLD / 2
stalled 起点 = STALLED_THRESHOLD
运行时新鲜窗口 = RUNTIME_STALE_THRESHOLD
orphaned 需要 ORPHAN_REQUIRED_SCANS 次连续观测
```

终态 `succeeded`、`failed` 不产生任务事故；公开快照最多保留 1000 条任务，先完整保留全部活动任务，再用最近终态补足。任务 API 支持按 `status` 过滤，但没有时间窗口或 offset 分页。

排队任务低于 `QUEUE_THRESHOLD / 2` 为 `healthy`；达到一半但未达到完整阈值为 `slow`。达到完整阈值后：无匹配容量为 `worker_unavailable`，有匹配容量但无近期活动为 `queue_starved`，有近期领取或进度则仍为 `slow`。

### 7.3 `queue_starved`

`queue_starved` 既是老排队任务的健康分类，也是按 `queue_scope:task_kind` 去重的队列事故。当前实现同时满足以下条件时成立：

1. 任务生命周期为 `queued`，且 `created_at` 年龄达到 `QUEUE_THRESHOLD`；
2. 至少一个运行时生命周期为 `running`、`ready` 或 `healthy`，且心跳年龄严格小于 `RUNTIME_STALE_THRESHOLD`；达到阈值即视为失联；
3. 该运行时按任务类型存在真实可领取容量：`listing_analysis` 要求 `listing_available_capacity > 0`，其他任务要求 `generic_available_capacity > 0`；两类容量已扣除共享账号互斥占用，不得用 Worker 存活数或聚合 `available_capacity` 猜测；
4. 所有匹配运行时的 `last_claim_at` 和 `last_progress_at` 均无可解析值，或最近一次活动年龄也达到 `QUEUE_THRESHOLD`。

它表达“匹配 Worker 和容量存在，但在完整队列观察窗口内没有领取或任务进度”。

### 7.4 `worker_unavailable`

`worker_unavailable` 也是老排队任务的健康分类和按 `queue_scope:task_kind` 去重的事故。任务排队年龄达到 `QUEUE_THRESHOLD` 后，如果 scheduler 失联，或不存在同时满足新鲜心跳与该 `task_kind` 精确可用容量大于 0 的运行时，即归为此类。

分类器在同一任务上只会选择 `queue_starved` 或 `worker_unavailable` 之一；同一 `queue_scope` 和 `task_kind` 的多条老任务共享一条事故候选。

### 7.5 服务自身健康

HTTP 探针与业务健康分离：

- `liveness`：Monitor 事件循环可响应；不要求业务库健康。
- `readiness`：当前仅取决于缓存快照的 `source.ready`，即本地业务库最近一轮扫描成功；配置或私有状态库初始化失败通常使进程无法启动，Collector MCP 探测失败不影响 readiness。
- 业务异常：任务 `stalled`、`orphaned` 或队列事件不应令 Monitor 的 liveness 失败；它们通过摘要与事件表达。

## 8. 事件、去重、冷却与恢复

### 8.1 事故身份

当前事故以稳定、脱敏的复合主键 `(rule, subject)` 去重，不额外计算哈希指纹：

```text
任务事故：rule = stalled | orphaned，subject = job_id
队列事故：rule = queue_starved | worker_unavailable，subject = queue_scope:task_kind
```

事故身份不得包含错误正文、用户邮箱、账号名、Webhook、时间戳或其他每轮变化的值。当前数据源不可用只进入快照 `source.error`，不会写成事故记录。

### 8.2 状态机

```text
未出现
  → 首次满足：status=active，alert_status=pending，产生 opening 动作
  → 投递成功：alert_status=delivered，记录 last_alert_at
  → 冷却期内仍满足：只更新 last_seen_at，不重复通知
  → 冷却到期仍满足：产生 reminder 动作
  → opening/escalation/reminder 投递失败：alert_status=failed；下一次扫描按 pending_alert_kind 重试同类动作
  → 通知未配置：对应投递状态写为 disabled，作为终态 no-op，不再重试
  → 严重度升高：产生 escalation，可绕过普通提醒冷却
  → 一次可信扫描中候选消失：status=resolved，recovery_status=pending，产生 recovery 动作
  → 恢复投递失败：recovery_status=failed；恢复冷却到期后重试 recovery
  → 恢复投递成功或通知禁用：recovery_status=delivered 或 disabled；后续扫描不重复恢复通知
  → 同一身份再次出现：重新打开，并重置告警/恢复投递状态
```

已恢复事故当前不会按保留期归档或清理。

### 8.3 重启延续

- 去重、冷却、恢复投递状态和孤儿连续观测计数写入监控私有库，不能只放在内存。
- Monitor 重启后读取旧事故状态；仍在冷却期的同一事故不得重新发送首发告警。
- 业务库不可读或 schema 不兼容时，服务保留私有库中的既有事故并返回未就绪快照，不调用 `reconcile()`，因此不会把既有事故批量恢复。
- 数据源恢复后的第一次可信扫描会正常执行事故对账；当前没有额外恢复宽限。

### 8.4 恢复条件

事故恢复的实际条件是：某个 `(rule, subject)` 在本次可信分类结果中不再出现。

- `slow` 本身不生成事故，因此没有 `slow` 恢复通知。
- `stalled`：任务进入终态、进度年龄回到阈值内，或转为其他分类时，原 `stalled` 事故即恢复。
- `orphaned`：任务进入终态，或 owner、租约和运行时重新可信而不再满足孤儿条件时恢复。
- `queue_starved` / `worker_unavailable`：同一 `queue_scope:task_kind` 不再存在该规则对应的老排队任务时恢复；两种规则互相切换会表现为旧事故恢复并开启新事故。
- 恢复候选只需一轮可信扫描；恢复投递成功后不重复发送，投递失败按 `ALERT_COOLDOWN` 冷却后重投，直到成功或同一事故重新打开。

| 环境变量 | 当前默认值 | 与 Monitor 的关系 |
|---|---:|---|
| `OPSCLI_SELLER_SPRITE_TASK_TIMEOUT_SECONDS` | `600` | `stalled` 阈值不应无依据地高于任务超时；长轮询场景需结合真实进度调整 |
| `OPSCLI_SELLER_SPRITE_TASK_LEASE_SECONDS` | `60` | `RUNTIME_STALE_THRESHOLD` 与 `orphaned` 连续观测策略必须考虑租约长度 |
| `OPSCLI_SELLER_SPRITE_TASK_HEARTBEAT_SECONDS` | `20` | `RUNTIME_STALE_THRESHOLD` 建议至少覆盖 3 次正常心跳 |
| `OPSCLI_SELLER_SPRITE_ACCOUNT_CACHE_TTL_SECONDS` | `600` | 无账号期间的 `worker_unavailable` 解释与恢复观察依据 |

阈值建议：

```text
POLL_INTERVAL < RUNTIME_STALE_THRESHOLD
RUNTIME_STALE_THRESHOLD >= 3 × OPSCLI_SELLER_SPRITE_TASK_HEARTBEAT_SECONDS
ORPHAN_REQUIRED_SCANS × POLL_INTERVAL 应覆盖短时租约与扫描抖动
slow 起点 = STALLED_THRESHOLD / 2
STALLED_THRESHOLD <= OPSCLI_SELLER_SPRITE_TASK_TIMEOUT_SECONDS（常规短任务）
ALERT_COOLDOWN > POLL_INTERVAL
```

当前实现没有独立的 `slow`、孤儿秒数、恢复宽限或事件保留期环境变量；`slow` 由停滞阈值的一半派生，`orphaned` 由连续扫描次数确认。事故候选一次消失即恢复，已恢复事故持续保存在私有库。

CLI 已确认始终输出 JSON；查询命令通过 `OPSCLI_COLLECTOR_MONITOR_URL` 调用只读 HTTP API，没有额外 `--json` 开关。

```bash
opscli collector-monitor serve --host 127.0.0.1 --port 8767
```

独立入口直接调用 `server.run()`，用 `argparse` 解析 `--host`、`--port` 和 `--help`；省略监听参数时读取环境配置。两种入口只启动 Monitor 扫描、事故状态机和 Starlette 服务，不启动 Collector MCP 或 SellerSprite 调度器。

### 10.2 查询命令

| 命令 | 已确认行为 |

## 11. Starlette UI 与 API 合同

### 11.1 网页

| 方法 | 路径 | 内容 |
|---|---|---|
| `GET` | `/` | 无外部资源的嵌入式单页只读仪表盘，以 7 秒间隔刷新状态 |

任务、分类容量、Collector MCP 状态、活动与已恢复事故历史、进度时间线均在首页展示；当前没有独立 `/tasks` 或 `/incidents` HTML 路由。网页默认仅用于内网或本机，经反向代理暴露时必须在代理层实施认证、TLS、访问控制和访问日志脱敏。

### 11.2 探针与 API

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/health/live` | 进程存活探针，固定返回 `status=live` |
| `GET` | `/health/ready` | 首次本地队列扫描成功时返回 200；未就绪返回 503 和脱敏数据源错误 |
| `GET` | `/api/v1/status` | 完整脱敏缓存快照 |
| `GET` | `/api/v1/tasks?health=<值>&status=<值>&task_kind=<值>&limit=<1..500>` | 有界任务列表；过滤参数均可选，默认 100 条，非法或未知参数返回 400 |
| `GET` | `/api/v1/tasks/{job_id}` | 缓存中的单任务脱敏监督详情与时间线；不存在返回 404 |
| `GET` | `/api/v1/incidents?status=<值>&rule=<值>&limit=<1..500>` | 有界事故列表；过滤参数均可选，默认 100 条 |
| `POST` | `/api/v1/probes/collector` | 手动探测配置中的 Collector MCP，硬超时 5 秒 |
| `POST` | `/api/v1/probes/queue-source` | 手动只读探测配置中的业务队列源，硬超时 5 秒 |

约束：

1. 不提供任何业务写端点；两个 `POST` 仅执行固定目标的只读探测，不接受调用方 URL、路径、Header 或命令。
2. 普通 API 和 UI 刷新只读取轮询服务内存缓存；只有显式 `queue-source` 手动探测会只读查询业务 SQLite。
3. 任务详情由当前缓存映射按 `job_id` 查找，不拼接 SQL；当前没有单事故详情路由。
4. 任务 API 的 `status` 允许 `queued|running|succeeded|failed`，`task_kind` 允许 `generic|listing_analysis`；事故 API 的 `status` 允许 `active|resolved`，`rule` 允许四种事故规则。两个列表的 `limit` 均默认为 100、最大 500，拒绝未知参数。注意轮询快照最多缓存 1000 条任务和最近 500 条事故，因此 API 上限不会扩大已缓存集合。
5. API 错误只返回稳定错误码与安全摘要，不返回堆栈、SQL、Webhook、路径或第三方原文。
6. 所有响应设置 `Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、CSP、`X-Frame-Options: DENY` 和 `Referrer-Policy: no-referrer`。
7. UI 无外部 CDN/脚本，不把业务数据发送给外部分析服务；响应层还会递归剔除敏感键、`*_path` 和 `*_json`。

## 12. 企业微信通知

### 12.1 密钥读取

- `OPSCLI_COLLECTOR_MONITOR_WEBHOOK_FILE` 只保存文件路径，不保存 Webhook URL。
- 通知器每次发送时重新读取文件并去除首尾空白，不缓存密钥。
- 文件只支持一行纯文本完整 Webhook；不接受 JSON 对象或多行内容。
- 通用企业微信客户端严格要求 HTTPS、主机 `qyapi.weixin.qq.com`、路径 `/cgi-bin/webhook/send`、无端口/用户信息/fragment，且唯一查询键为非空 `key`。
- POSIX 环境要求文件为普通文件，且不得授予 group/other 任何权限，通常使用 `0600`；Windows 标准库无法可靠验证 ACL，仍依赖部署侧限制为服务账号只读。
- 文件为空、不可读、权限过宽或格式不合法时，本次通知返回安全异常类，监控轮询继续；不得回退到硬编码或普通环境变量中的 Webhook。
- Webhook 不得出现在日志、异常、API、UI、CLI、进程参数、systemd unit 明文或监控私有库。

### 12.2 通知内容

当前通知内容固定包含：

- `Collector Monitor` 与动作标题（告警、提醒、恢复）；
- 事故 `rule`、`subject`；
- 告警/提醒时的严重度，或恢复状态；
- 分类器生成的固定低敏消息。

当前通知不包含环境名、场景、任务参数、首次发现时间、持续时长或 Monitor 页面链接。若后续增加这些字段，必须继续遵守下述禁止清单。

禁止包含：

- Webhook、Authorization、API Key、JWT、Session、Cookie、账号密码；
- 用户邮箱原文、卖家精灵用户名；
- 请求参数、关键词、ASIN 列表或第三方响应正文；
- 业务数据库、结果文件、浏览器 Profile 的完整路径；
- 页面 HTML、截图或浏览器网络数据；
- 未脱敏错误堆栈。

一期通知渠道只有企业微信，不实现飞书适配器或多渠道抽象的公开配置。

## 13. 安全与脱敏边界

### 13.1 默认不读取的数据

Monitor 查询应使用字段白名单，默认不读取：

- `request_json`；
- `params_json`；
- `session_id`、`jwt`、`credential_scope`；
- 账号绑定库及其密钥；
- `result_path`、`root_dir` 的完整值；
- `error_json` 原文；
- 浏览器 Profile 与采集产物。

如判定需要错误信息，只读取稳定 `last_error_code`；如 UI 需要路径定位，只展示预先生成的非敏感运行标识或文件名，不展示绝对路径。

### 13.2 标识脱敏

- 用户邮箱不进入默认快照；确需关联时只使用不可逆、带部署盐的摘要，且盐不写业务库。
- 账号只使用现有稳定账号键或遮罩名称，不展示用户名。
- `job_id` 默认可在受控内网完整显示；企业微信仍显示完整事故 `subject`，但发送前会移除控制字符、折叠换行并转义 Markdown 控制字符，避免动态标识改变消息结构。若 `job_id` 未来包含业务信息，必须先统一改为摘要。
- 错误消息只允许稳定错误码与白名单运维说明。

### 13.3 网络边界

- 默认监听 `127.0.0.1`。
- 若监听非回环地址，必须通过受控内网、防火墙和带认证的反向代理。
- v1 不宣称内置应用认证；不能因“只读”而直接暴露公网。
- 企业微信出站请求只允许官方 HTTPS 地址，HTTP 超时固定 5 秒。当前网络客户端不自动重试；opening/escalation/reminder 失败后下一轮按原动作重试，recovery 失败按事故冷却时间重投。
- Collector MCP 配置 API Key 文件时，密钥读取在线程中执行，并与远端健康调用共用 `COLLECTOR_PROBE_TIMEOUT` 总时限；携带 `X-MCP-API-Key` 的探测禁止自动跟随重定向，避免跨源或 HTTPS 降级转发密钥。未配置自定义密钥的既有 Remote MCP 调用仍保持兼容的重定向行为。

## 14. 可靠性与失败模式

| 故障 | 行为 |
|---|---|
| 业务库不存在 | `/health/ready` 返回 503；快照使用 `queue_source_unavailable`；不创建空业务库 |
| 业务库读取失败 | 当前轮替换为安全未就绪快照并清空任务/运行时缓存；保留私有库既有事故且不执行恢复对账 |
| schema 不兼容 | `/health/ready` 返回 503，并在安全消息中列出缺失表/列；不迁移业务库 |
| 私有状态库不可写或无法初始化 | 当前未提供降级模式，异常可使启动或轮询失败；不会在无法完成事故事务后继续通知 |
| Webhook 未配置 | 监控继续运行；本次通知返回 disabled，投递状态记为 `disabled` 终态 no-op，不再重试 |
| Webhook 文件缺失/权限过宽 | 监控继续运行；只记录安全异常类和 failed；告警类下一轮重试，恢复类冷却后重试 |
| 企业微信请求失败 | 通知通过工作线程执行，最多 4 条并发；只记录清洗后的异常类和固定投递结果；本轮不中断监控；按动作类型重试且不输出 URL 或响应原文 |
| 系统时间异常 | 解析失败的时间年龄为未知，未来时间年龄钳制为 0；当前没有独立数据质量事故 |
| Monitor 重启 | 从私有库恢复事故、冷却、恢复投递和连续孤儿观测状态 |
| Collector MCP 探测失败 | 标记 `collector.status=unavailable`，不阻断本地队列扫描、分类和通知 |
| Collector/SellerSprite 重启 | 依据持久进度、租约和调度器运行时重新判定，不自动写业务状态 |

## 15. 可观测性

当前实现主要通过脱敏快照和事故状态提供可观测性：

- `/api/v1/status` 中的 `generated_at`、`source.last_scan_at`、`source.last_success_at`、`source.error_code`、`collector`、`summary`、任务、运行时和事故；
- 事故中的 `alert_status`、`last_alert_at`、`recovery_status`、`last_recovery_at` 和安全 `delivery_error_class`；
- Uvicorn 默认服务/访问日志。

禁止记录 SQL 参数、业务 JSON、用户邮箱、账号、绝对路径、Webhook 和 HTTP Authorization。当前尚未实现结构化扫描日志、扫描耗时、读取行数、通知抑制计数、读取失败计数或 Prometheus 指标；若后续加入，应继续使用低敏字段和路径模板，不记录查询参数值。

## 16. 验收标准

### 16.1 只读安全

- 使用操作系统权限、SQLite authorizer 或等价测试证明 Monitor 不能修改业务库。
- 业务库缺失时不会生成新的 `task_queue.sqlite3`。
- 启动 Monitor 不会初始化 SellerSprite 调度器、账号仓储或浏览器。
- API、CLI 和 UI 中不存在取消、重试、重排或浏览器控制入口。

### 16.2 健康判定

- 覆盖 `healthy`、`slow`、`stalled`、`orphaned` 的阈值边界。
- 覆盖 `queue_starved`、`worker_unavailable` 及二者优先级。
- Worker 心跳持续但 `progress_sequence` 不变时能判定 `stalled`。
- 任务租约/owner 失效时能判定 `orphaned`。
- 终态任务不会继续触发活动异常。

### 16.3 通知闭环

- 同一 `(rule, subject)` 事故首次出现产生一次 opening；投递成功后冷却期内不重复通知。
- 冷却到期仍活动时产生 reminder。
- Monitor 重启后仍遵守原冷却。
- 一次可信扫描确认候选消失后发送恢复通知；成功恢复只发送一次。
- 通知失败只落安全异常类和固定投递结果；opening/escalation/reminder 下一次扫描重试原动作，recovery 失败在冷却到期后补投；Webhook 未配置记为 `disabled` 终态且不重试；Webhook 原文不进入任何输出或状态库。
- Webhook 在每次发送时从受保护文件读取，支持安全轮换。

### 16.4 服务面

- `opscli collector-monitor serve|status|tasks|show|incidents --help` 可用。
- `opscli-collector-monitor` 能独立启动。
- Starlette UI/API 只读，探针语义符合第 7.5 节。
- API 返回值符合脱敏边界与 `Cache-Control: no-store` 要求。

## 17. 发布与回滚边界

发布顺序建议：

1. 先发布 SellerSprite 持久进度与运行时监督写入；
2. 验证字段可持续更新且不含敏感信息；
3. 再部署 Monitor，但先禁用企业微信，仅观察判定；
4. 依据真实运行时间校准阈值；
5. 最后配置受保护 Webhook 文件并启用通知。

回滚 Monitor 时只需停止独立服务并保留或归档其私有状态库。不得删除、回写或降级业务 SQLite。SellerSprite 新增的非敏感监督字段可以保留，不影响旧版本读取；如需回退 SellerSprite，必须由业务模块自己的迁移策略处理，Monitor 不参与。

## 18. 已知实现差异与后续对齐清单

一期组件均已落盘，以下项目仍与批准目标存在差异，需由实现与产品/运维共同确认，而不是在文档中假定已具备：

1. **恢复去抖**：当前事故候选一次消失即恢复，没有连续健康宽限或 `recovery_grace` 配置。
2. **事件保留**：当前没有保留期、归档或清理策略；已恢复事故会长期留在私有库。
3. **告警类投递失败节流**：Webhook 已配置但发送失败时，opening/escalation/reminder 下一轮立即重试原动作，没有退避或独立重试预算；Webhook 未配置记为 `disabled` 终态且不重试。recovery 失败按 `ALERT_COOLDOWN` 冷却后重投。
4. **企业微信超时**：通用客户端固定 5 秒且不做网络级重试，没有 Monitor 专用配置；同步网络调用已从事件循环卸载到线程，单轮最多并发 4 条。业务扫描、Monitor 状态事务和通知结果写回也已卸载到工作线程。
5. **事故身份与详情**：以 `(rule, subject)` 为主键，没有独立哈希 `fingerprint` 或单事故详情路由；事故列表已支持 `status`、`rule` 和有界 `limit`。
6. **阈值粒度**：只支持全局阈值，不支持按场景或进度阶段覆盖；运行任务和排队任务的 `slow` 起点均由对应完整阈值的一半派生。
7. **活动任务规模**：为保证事故分类不漏项，每轮必须读取全部 `queued` / `running` 任务；虽然采用 500 条游标批次、显式读事务、1000 条公开上限和批量时间线查询，但没有活动任务总量硬上限或时间分片，极端积压时仍需关注扫描耗时与 SQLite 读取压力。
8. **Monitor URL 与监听覆盖**：`OPSCLI_COLLECTOR_MONITOR_URL` 只供 CLI 查询，当前企业微信通知不附监控页链接；两个入口的 `--host/--port` 只覆盖监听参数，不同步改写 URL，查询 CLI 必须另行配置匹配地址。
9. **Collector 与数据源故障告警**：Collector 只在 UI、CLI 或固定 POST 端点显式触发时调用 `collector_modules_health`；自动页面刷新不会发起远端探测。响应进入缓存前仅保留 module、queue、scheduler、稳定错误码和固定 runtime 白名单。探测失败只进入缓存摘要，业务 SQLite 扫描失败进入 `source.ready=false`；两类故障当前都不形成事故或企业微信告警。
10. **生产构建平台**：生产 sdist 会携带业务 `.c` 并在二次构建时注册相同扩展集合；Typer/FastMCP 反射模块保留纯 Python。Windows 构建 Cython wheel 仍要求可用 MSVC，缺少编译器时只能用 `SKIP_CYTHON=1` 验证非生产 wheel，不得当作正式二进制产物。

已确认、不应无理由改名的合同包括：`opscli collector-monitor` 及 `serve`、`status`、`tasks`、`show`、`incidents`、`probe`；`opscli-collector-monitor`；第 9.1 节全部配置；第 11 节全部路由；SellerSprite 默认业务库路径、任务进度字段和事件表；`seller_sprite_runtime_heartbeats` 运行时表。若实现改变这些合同，必须同时更新本文和《Collector Monitor运维说明》。
