# 模块目录分层规范

## 1. 目标

为了避免每个模块都把 `cli.py`、`manager.py`、`client.py`、`models.py`、`exceptions.py` 平铺在同一级目录，`opscli` 后续模块统一采用“按职责分层、根目录保留兼容入口”的方式组织。

## 2. 推荐目录结构

### 2.1 通用模块

适用于 `query`、`skills`、未来的 `deploy`、`notify` 等：

```text
opscli/<module>/
├── __init__.py
├── cli.py                # 兼容导出
├── manager.py            # 兼容导出
├── client.py             # 兼容导出（如有）
├── models.py             # 兼容导出（如有）
├── exceptions.py         # 兼容导出（如有）
├── commands/
│   └── cli.py            # 真正的 CLI 实现
├── services/
│   └── manager.py        # 业务编排
├── transport/
│   └── client.py         # HTTP / RPC / API 调用
└── domain/
    ├── models.py
    └── exceptions.py
```

### 2.2 有抓取/解析逻辑的模块

适用于 `amazon` 这类具备本地采集链路的模块：

```text
opscli/amazon/
├── commands/
├── services/
├── transport/
├── domain/
└── scraping/
    ├── scraper.py
    └── parser.py
```

### 2.3 已有成熟底座的模块

适用于 `auth` 这类已经具备明确底座层的模块：

```text
opscli/auth/
├── commands/
├── domain/
├── core/
└── storage/
```

这里不强求再拆 `services/transport`，因为 `auth` 的现有 `core/` 与 `storage/` 已经足够表达职责。

## 3. 兼容策略

为了避免重构一次就打断所有外部导入，根目录文件继续保留，但只做薄封装：

- `opscli.query.cli -> opscli.query.commands.cli`
- `opscli.skills.manager -> opscli.skills.services.manager`
- `opscli.amazon.client -> opscli.amazon.transport.client`
- `opscli.auth.exceptions -> opscli.auth.domain.exceptions`

也就是说：

1. 新代码优先导入新路径
2. 旧路径继续可用
3. 对外 API 稳定优先于内部目录纯粹性

## 4. 当前项目落地结果

### 已完成分层

- `query`
- `skills`
- `amazon`

### 已做轻量统一

- `auth`

保留 `core/`、`storage/`，只补 `commands/` 和 `domain/` 的一致化入口。

## 5. 后续新增模块要求

后续新增模块时：

1. 不要再把所有实现文件直接放在模块根目录
2. 优先按 `commands/services/transport/domain` 组织
3. 如有明显特殊职责，可以新增专用层目录，例如 `scraping/`、`discovery/`
4. 根目录仅保留兼容导出文件，不承载复杂实现
