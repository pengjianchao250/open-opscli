> 适用场景：为 `opscli` 的可安装模块定义统一接入协议、元数据约束、插件发现机制、兼容校验与错误处理规范。

## 3. 核心对象定义

### 3.1 模块术语

| 术语 | 含义 |
|------|------|
| 核心 | `opscli` CLI 容器及公共基础设施 |
| 模块 | 一个可独立安装的 `opscli` 扩展包 |
| 插件入口 | 模块在安装后供核心发现的注册函数 |
| 模块规范 | 模块对自身元数据、命令名、兼容范围的声明 |
| 模块状态 | 模块在当前环境中的可用性、兼容性和加载结果 |

### 3.2 核心数据模型

建议在后续实现中定义以下核心数据结构：

```python
from __future__ import annotations

from dataclasses import dataclass, field


@dataclass(frozen=True)
class ModuleSpec:
    """模块自描述信息。"""

    name: str
    command_name: str
    version: str
    summary: str
    owner: str
    team: str | None = None
    homepage: str | None = None
    support_contact: str | None = None
    requires_core: str = ">=0.0.0"
    requires_python: str | None = None
    capabilities: tuple[str, ...] = ()
    dependencies: tuple[str, ...] = ()
    builtin: bool = False


@dataclass(frozen=True)
class ModuleRecord:
    """核心侧发现到的模块记录。"""

    entry_point_name: str
    entry_point_value: str
    dist_name: str | None
    spec: ModuleSpec | None
    load_error: str | None = None
    validation_errors: tuple[str, ...] = ()


@dataclass(frozen=True)
class ModuleLoadResult:
    """模块注册执行后的结果。"""

    module_name: str
    command_name: str | None
    registered: bool
    error_type: str | None = None
    error_message: str | None = None
```

说明：

- `ModuleSpec` 是模块自己的契约声明
- `ModuleRecord` 是核心在发现阶段记录的信息
- `ModuleLoadResult` 是实际执行注册后的结果

## 4. 模块元数据协议

### 4.1 必填字段

每个模块必须声明以下元数据：

| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | `str` | 包级模块名称，推荐 `opscli-xxx` |
| `command_name` | `str` | CLI 命令名，如 `query` |
| `version` | `str` | 模块自身版本 |
| `summary` | `str` | 一句话描述 |
| `owner` | `str` | 负责人或 owner 组 |
| `requires_core` | `str` | 与核心兼容的版本范围 |

### 4.2 推荐字段

建议声明以下字段，便于治理：

| 字段 | 说明 |
|------|------|
| `team` | 负责小组名称 |
| `homepage` | 项目主页或文档地址 |
| `support_contact` | 支持联系方式 |
| `requires_python` | 模块自身 Python 版本要求 |
| `capabilities` | 该模块提供的能力标签 |
| `dependencies` | 逻辑依赖的其他模块名 |
| `builtin` | 是否为内建模块 |

### 4.3 字段约束

必须遵守以下约束：

- `name` 必须全局唯一
- `command_name` 必须全局唯一
- `command_name` 必须匹配 `^[a-z][a-z0-9-]*$`
- `owner` 不能为空
- `version` 必须符合可解析的版本格式
- `requires_core` 必须为合法版本范围

### 4.4 推荐命名规范

建议统一采用：

- 包名：`opscli-<module>`
- Python import 名：`opscli_<module>`
- 命令名：`<module>`

示例：

| 包名 | import 名 | 命令名 |
|------|-----------|--------|
| `opscli-query` | `opscli_query` | `query` |
| `opscli-notify` | `opscli_notify` | `notify` |

## 5. 插件入口协议

### 5.1 入口点声明

模块必须在自己的 `pyproject.toml` 中声明 `entry_points`：

```toml
[project.entry-points."opscli.modules"]
query = "opscli_query.plugin:register"
```

约定：

- `group` 固定为 `opscli.modules`
- `name` 推荐与 `command_name` 保持一致
- `value` 指向模块的插件注册函数

### 5.2 注册函数签名

推荐统一使用以下签名：

```python
def register(app: typer.Typer) -> ModuleSpec:
    ...
```

返回 `ModuleSpec` 的原因：

- 核心可在注册完成后拿到最终元数据
- 避免元数据分散在多个文件中
- 便于后续 `module list / info` 复用

### 5.3 可选拆分方式

如果团队希望把“获取规范”和“执行注册”拆开，也可采用如下协议：

```python
def get_spec() -> ModuleSpec:
    ...


def register(app: typer.Typer) -> None:
    ...
```

但建议核心最终只支持一种主协议，避免接入成本上升。

本阶段推荐主协议：

```python
def register(app: typer.Typer) -> ModuleSpec:
    ...
```

### 5.4 模块侧示例

```python
import typer

from opscli_query.cli import app as query_app
from opscli.core.plugins import ModuleSpec


def register(app: typer.Typer) -> ModuleSpec:
    app.add_typer(query_app, name="query")
    return ModuleSpec(
        name="opscli-query",
        command_name="query",
        version="0.1.0",
        summary="数据查询模块",
        owner="@data-team",
        team="data-platform",
        requires_core=">=0.5,<0.7",
        capabilities=("query:metadata", "query:run"),
    )
```

## 6. 核心发现与注册流程

### 6.1 总体流程

核心启动时，推荐按如下顺序处理：

1. 加载内建模块列表
2. 扫描 `entry_points(group="opscli.modules")`
3. 读取每个 entry point 的分发信息
4. 逐个尝试加载注册函数
5. 执行基础校验
6. 若通过校验，则调用注册函数
7. 收集加载结果与错误
8. 将结果暴露给 `module list / doctor / info`

### 6.2 推荐伪代码

```python
from importlib.metadata import entry_points


def load_modules(app):
    records = []

    for ep in entry_points(group="opscli.modules"):
        record = discover_entry_point(ep)
        records.append(record)

    registered_commands = set()
    results = []

    for record in records:
        result = register_module(
            app=app,
            record=record,
            registered_commands=registered_commands,
        )
        results.append(result)

    return results
```

### 6.3 加载时机

建议模块加载发生在顶级 CLI 初始化期间，但应注意：

- 顶级 `--version` 应尽量不依赖模块加载
- 顶级 `--help` 可展示已成功注册的模块
- 模块加载失败不应导致整个 CLI 崩溃

## 7. 兼容性校验规则

### 7.1 校验清单

在调用模块 `register()` 前，核心至少应完成以下校验：

1. 是否存在可调用的注册函数
2. entry point 是否可导入
3. 是否能成功拿到模块分发信息
4. 命令名是否冲突
5. 核心版本是否满足 `requires_core`
6. Python 版本是否满足 `requires_python`
7. 模块名称是否重复

### 7.2 注册后校验

调用 `register()` 后，继续校验：

1. 返回值是否为 `ModuleSpec`
2. `spec.command_name` 与实际注册命令名是否一致
3. `spec.name` 与分发信息是否一致或兼容
4. `summary / owner / version` 是否为空

### 7.3 失败处理原则

模块校验失败时：

- 不注册该模块命令
- 记录失败原因
- 不影响其他模块继续加载
- 在 `opscli module doctor` 中可见

### 7.4 命令冲突处理

命令冲突规则建议为：

- 内建模块优先级高于外部模块
- 已加载成功的模块优先级高于后续冲突模块
- 冲突模块直接标记为 `conflict`

示例错误：

```text
模块 opscli-query-legacy 注册失败：命令名 query 已被 opscli-query 占用
```

## 8. 错误模型设计

### 8.1 核心异常类型

建议新增插件加载相关异常：

```python
class PluginError(Exception):
    """插件体系异常基类。"""


class PluginImportError(PluginError):
    """插件导入失败。"""


class PluginValidationError(PluginError):
    """插件元数据或兼容性校验失败。"""


class PluginConflictError(PluginError):
    """插件命令冲突。"""


class PluginRegistrationError(PluginError):
    """插件注册执行失败。"""
```

### 8.2 结构化错误输出

建议所有模块加载错误都可以序列化为统一结构：

```python
{
    "type": "PluginValidationError",
    "message": "模块 opscli-notify requires_core >=0.6,<0.7，当前核心版本为 0.5.1",
    "module": "opscli-notify",
    "command_name": "notify",
}
```

### 8.3 用户侧呈现原则

普通用户执行业务命令时：

- 只展示必要错误信息
- 不输出 Python traceback

执行 `opscli module doctor` 时：

- 可以展示完整的结构化诊断结果
- 应包含模块名、版本、owner、错误类型和建议动作

## 10. 对当前仓库的兼容落地方案

### 10.1 现状约束

当前仓库存在以下现实约束：

- [`opscli/cli.py`](/Users/mask/python3/opscli/opscli/cli.py) 采用静态 `add_typer(...)`
- AGENTS 中要求新增模块必须修改顶级 CLI
- 现有 `auth / query / skills` 尚未独立成包

因此，直接切到纯插件模式风险较高。

### 10.2 兼容方案

建议采用“双通道注册”：

1. 内建模块：
   继续静态注册，保证当前行为不变
2. 外部模块：
   通过 `entry_points` 动态注册

伪代码示意：

```python
def build_app() -> typer.Typer:
    app = typer.Typer(...)

    register_builtin_modules(app)
    load_external_modules(app)
    return app
```

这样可以做到：

- 不破坏当前 `auth / query / skills`
- 新模块无需继续修改核心 CLI
- 可以逐步把既有模块迁移到插件模式

### 10.3 内建模块元数据补齐

即使短期不拆包，也建议先为当前三模块补齐 `ModuleSpec`：

- `auth`
- `query`
- `skills`

好处：

- 先统一治理数据模型
- 后续切换为插件时，模块自身实现改动更小

## 14. 决策总结

这一层协议的关键结论有三个：

1. 模块接入统一通过 `entry_points("opscli.modules")`
2. 模块注册函数统一返回 `ModuleSpec`
3. 核心采用“静态内建 + 动态外部”的兼容加载模式

这三点一旦定下来，后续无论是继续单仓演进，还是逐步拆成多包、多团队协作，工程边界都会清晰很多。
