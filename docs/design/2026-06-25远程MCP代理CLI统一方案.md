# 2026-06-25 远程 MCP 代理 CLI 统一方案

> 本文档记录 2026-06-25 这一轮统一改造的最终落地事实，不再描述已被实现覆盖的旧假设。

## 1. 背景

改造前，`opscli` 内多类数据服务的 CLI 命令面对外行为不一致：

- `seller-sprite` 已切换为正式 CLI 代理远程 MCP，本地直连逻辑保留在 debug 路径。
- `keepa` 正式 CLI 仍直接调用本地 service。
- `google-trends` 正式 CLI 仍直接调用本地 service，且 MCP tool 一度未在 MCP Server 注册。
- `beta/canopy` 只有 beta MCP tool，对外命令面仍带有 beta 痕迹，未形成正式 CLI。

这种差异会带来以下问题：

- 用户侧命令体验不统一，不易理解哪些命令依赖本地配置，哪些走远程服务。
- 远程 MCP 配置获取、服务选择、调用重试逻辑已经在 `seller_sprite` 中沉淀，但尚未被其他模块复用。
- 本地调试能力和正式用户命令混在一起，容易把 API key、额度、账号等内部概念暴露给普通用户。

本轮已将 `seller-sprite`、`keepa`、`google-trends`、`canopy` 四组命令统一到同一正式 CLI 模型，并保留本地调试链路。

## 2. 目标与非目标

### 2.1 目标

1. 正式 CLI 统一走“本机登录态 + 远程 MCP 配置 + 远程 MCP tool 调用”链路。
2. 本地直连 service 保留，但只放在 `*-debug` 命令下。
3. 用户侧命令名和模块心智统一，不暴露额度、账号、API key、本地直连细节。
4. 抽取公共远程代理层，避免 `seller_sprite`、`keepa`、`google_trends`、`canopy` 重复实现同一套逻辑。
5. `beta` 对外命令名改为 `canopy`，形成正式模块。

### 2.2 非目标

1. 本轮不修改远程 MCP tool 名称。
2. 本轮不重命名远端 `beta_canopy_*` tool，也不迁移底层 `opscli/beta/canopy/` service 实现。
3. 本轮不扩展 Keepa、Google Trends、Canopy 的业务能力范围，只统一正式命令面与调试命令面。
4. 本轮不重写 Keepa、Google Trends、Canopy 的本地 service 实现。

## 3. 统一后的命令面

正式命令与调试命令按以下方式分轨：

| 模块 | 正式命令 | 调试命令 |
| --- | --- | --- |
| 卖家精灵 | `opscli seller-sprite ...` | `opscli seller-sprite-debug ...` |
| Keepa | `opscli keepa ...` | `opscli keepa-debug ...` |
| Google Trends | `opscli google-trends ...` | `opscli google-trends-debug ...` |
| Canopy | `opscli canopy ...` | `opscli canopy-debug ...` |

正式命令只负责远程 MCP 代理，不直接调用本地 service。

调试命令保留本地直连能力，用于：

- 联调本地实现
- 查看内部状态
- 验证本地配置
- 保留 token / 额度等仅开发和排障需要的命令

## 4. 核心设计

### 4.1 正式 CLI 统一代理远程 MCP

正式 CLI 的执行链路统一如下：

1. 使用本机 `opscli auth` 登录态构造 OPS 请求认证信息。
2. 调用远程 MCP 配置接口读取 `data.http.mcpServers`。
3. 优先选择 `BI运营系统` 对应的远程 HTTP MCP 服务。
4. 使用远程 MCP 客户端调用目标 tool。
5. 如果远程调用链路出现 `401`（兼容 `PermissionError`、`HTTPStatusError`、`ExceptionGroup` 等异常形态），重新拉取配置、重新构造客户端并重试一次。
6. 将远程 tool 返回的 JSON 结果直接透传给 CLI。

### 4.2 本地直连链路下沉到 debug 命令

`KeepaApiManager`、`GoogleTrendsApiManager`、`CanopyApiManager` 等本地 service 未删除，继续服务以下场景：

- MCP Server 内部执行
- 本地 debug 命令
- 现有 service 层单测

这样可以保证正式命令统一，同时不丢失本地调试和回归能力。

### 4.3 抽取公共远程代理基座

新增共享远程代理模块，例如：

`opscli/shared/remote_mcp_adapter.py`

该模块只负责通用职责：

- 读取远程 MCP 配置
- 校验并选择 HTTP server
- 调用远程 tool
- 对 `401` 做一次重试
- 过滤值为 `None` 的参数，避免把无意义字段透传到远程 tool

业务模块各自保留很薄的一层 adapter，只做“CLI 参数 -> MCP tool 参数”的映射。

### 4.4 远程 tool 名保持不变

本轮不变更远程 tool 名，避免扩大服务端和权限系统变更面：

- Keepa 继续调用 `keepa_*`
- Google Trends 继续调用 `google_trends_*`
- Canopy 继续调用 `beta_canopy_*`

即：

- 对外 CLI 名统一
- 对内远程 tool 契约暂时不动

这是本轮实际采用的最低风险路径。

## 5. 模块级改造边界

### 5.1 seller_sprite

`seller_sprite` 已是统一目标态，本轮只做一件事：

- 将 [opscli/seller_sprite/remote_adapter.py](opscli/seller_sprite/remote_adapter.py) 改为复用共享远程代理基座。

要求：

- 对外命令和参数口径不变
- 测试行为不回归

### 5.2 keepa

正式 `keepa` 已收敛为远端 MCP 正式命令面，保留：

- `scenarios`
- `run`
- `job-status`
- `export`

正式命令面移除：

- `token-status`

`token-status` 只保留到 `keepa-debug`，理由如下：

- 普通用户不应感知 Keepa 查询账号额度与 token 细节
- Keepa MCP 规范也不建议对普通用户暴露额度状态

本轮新增：

- `opscli/keepa/remote_adapter.py`
- `opscli/keepa_debug/cli.py`

当前事实：

- `opscli keepa` 走远程 `keepa_*` tools。
- `opscli keepa-debug` 继续使用本地 `KeepaApiManager`。
- 顶级 help 已只在 debug 命令面暴露 `token-status`。
- 正式 `keepa run` 已移除 `--output-dir`，该参数只保留给 `keepa-debug` 本地链路。
- Keepa public MCP 返回不再泄露本地 `file://` 或服务器路径；无远端上传 URL 时，`job-status` 追加 warning，`export` 返回结构化错误。

### 5.3 google_trends

正式 `google-trends` 已收敛为远端 MCP 正式命令面，保留：

- `scenarios`
- `run`
- `job-status`
- `export`

本轮新增：

- `opscli/google_trends/remote_adapter.py`
- `opscli/google_trends_debug/cli.py`

当前事实：

- `google_trends` tool 已恢复 MCP Server 注册。
- `opscli google-trends` 走远程 `google_trends_*` tools。
- `opscli google-trends-debug` 保留本地 pytrends/落盘调试链路。
- 正式 `google-trends run` 已移除 `--output-dir`，该参数只保留给 `google-trends-debug` 本地链路。
- Google Trends public MCP 返回不再泄露本地 `file://` 或服务器路径；无远端上传 URL 时，`job-status` 追加 warning，`export` 返回结构化错误。

### 5.4 canopy

对外正式命令名已正式化为：

- `opscli canopy ...`
- `opscli canopy-debug ...`

当前实现边界：

- 正式 CLI 入口位于 `opscli/canopy/`。
- debug CLI 入口位于 `opscli/canopy_debug/`。
- 本地 service 继续复用 `opscli/beta/canopy/`。
- 远端 tool 仍调用 `beta_canopy_*`。

正式 `canopy` 当前开放以下命令：

- `scenarios`
- `run`
- `job-status`
- `export`

为支撑统一正式命令面，本轮已扩展 beta MCP tool：

- `beta_canopy_job_status`
- `beta_canopy_export`

同时落地以下当前事实：

- 正式 `canopy` 不再暴露 `api_key_placeholder_used`。
- public beta MCP 不再回退 `file://`。
- 无远端上传 URL 时，`run` / `job-status` 会追加结构化 warning。
- 无远端上传 URL 时，`export` 直接返回结构化错误。
- 正式 `canopy run` 已移除 `--output-dir`。
- `canopy-debug run` 保留 `--output-dir`，且 `canopy-debug job-status` / `canopy-debug export` 也已补齐 `--output-dir`。

## 8. 风险与处理

### 8.1 远端导出 URL 依赖上传链路

风险：

- Keepa、Google Trends、Canopy 导出文件是否能给出公网 URL，取决于上传链路是否成功。

处理：

- 正式 public 返回不再泄露本地 `file://`。
- `run` / `job-status` 用 warning 暴露“当前无下载地址”的事实。
- `export` 在无可下载 URL 时直接返回结构化错误，避免调用方误以为导出可用。

### 8.2 Canopy 的外部命令名与内部远端 tool 名不一致

风险：

- 用户看到 `canopy`，但内部远端 tool 仍叫 `beta_canopy_*`。

处理：

- 当前已接受这一层命名不一致，并在文档中明确“对外命令已正式化，内部远端 tool 名暂不调整”。
- 后续如需彻底统一，再单独评估远端 tool 重命名与 service 目录收口。

### 8.3 正式 CLI 与 debug CLI 口径混淆

风险：

- 若 help 和文档未同步，用户仍可能误用 debug 命令。

处理：

- 顶级 help 与各子命令 help 统一使用“远端 MCP 正式命令面 / 本地调试命令面”口径。
- `keepa-debug`、`google-trends-debug`、`canopy`、`canopy-debug` 已出现在顶级命令树。

## 9. 实施结果

1. 新增共享远程代理基座，并让 `seller_sprite` 先复用公共层。
2. 改造 `keepa` 正式 CLI 与 `keepa-debug`。
3. 恢复 `google_trends` MCP 注册，并改造 `google-trends` / `google-trends-debug`。
4. 新增 `canopy` / `canopy-debug`，并补齐 `beta_canopy_job_status` / `beta_canopy_export`。
5. 补齐 CLI、adapter、MCP 回归测试。
6. 统一 help 文案与设计/变更记录口径。

1. `opscli keepa ...`、`opscli google-trends ...`、`opscli canopy ...` 均通过远程 MCP 执行。
2. `opscli keepa-debug ...`、`opscli google-trends-debug ...`、`opscli canopy-debug ...` 均保留本地直连能力。
3. `opscli keepa` 正式命令不再提供 `token-status`。

5. `canopy` 对外命令名已正式化，但内部仍沿用 `beta_canopy_*` tool。
6. `canopy` 正式命令面已具备 `scenarios/run/job-status/export` 四个命令。
