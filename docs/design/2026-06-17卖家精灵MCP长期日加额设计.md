# 2026-06-17 卖家精灵MCP长期日加额设计

## 1. 背景

当前 `seller_sprite_run` 已接入 MCP 每日调用限额，基础口径为全局默认额度加当日使用记录。现有实现只能通过配置文件控制全局默认值，不能针对某个用户做长期的个性化日加额。

运维侧的新需求是：

- 可以按用户长期增加某个 MCP 服务的每日额度
- 用户定位以邮箱为主，便于人工识别和运维操作
- 首期只覆盖 `seller_sprite` 服务
- 不新增公开 CLI 命令，避免污染现有 `opscli` 命令面
- 运维通过内部 SQL 直接维护数据

## 2. 目标

- 在不改动现有限额配置入口的前提下，支持“默认额度基础上长期追加 N 次”
- 运行时支持按邮箱读取长期日加额
- 保持 `mcp_quota_daily` 继续只承担“当日使用结果表”职责
- 首期不新增公开命令，仅新增内部数据结构和内部 SQL 操作文档

## 3. 非目标

- 不实现公开的 `opscli mcp quota` 命令组
- 不实现 Web 管理页或后台管理接口
- 不实现按时间段生效或到期失效的临时加额
- 不实现复杂审计字段和历史流水表
- 不将内部教程随 wheel 包或 MCP Skill 对外暴露

## 4. 当前实现现状

当前限额实现位于 `opscli/mcp/quota.py`，核心行为如下：

- 基础限额来自默认策略和 `mcp-quota.json`
- 当日使用记录落在 SQLite 表 `mcp_quota_daily`
- 当前身份解析优先级为 `user_id > email > api_key hash`
- `mcp_quota_daily` 保存的是某服务某天的已用次数、失败次数、重置时间等运行结果

现状问题是：

- 没有“用户长期日加额”数据层
- 没有按邮箱做长期额度覆盖的运行时逻辑
- 当日使用表不适合直接承载长期策略

## 5. 选定方案

采用“基础策略表述 + 长期日加额表 + 当日使用表”三层分离方案。

### 5.1 基础策略层

继续沿用当前全局默认限额配置，不修改其职责。

- `seller_sprite_run` 默认额度继续由代码默认值和配置文件决定
- 该层只描述“全局默认每天多少次”

### 5.2 长期日加额层

新增一张 SQLite 表，例如 `mcp_quota_bonus_daily`，用于保存某个邮箱在某个服务上的长期每日加额。

首版建议字段：

- `service`
- `email`
- `bonus_daily_limit`
- `created_at`
- `updated_at`

主键建议为：

- `(service, email)`

这样可以保证：

- 同一邮箱在不同服务上可以有不同长期日加额
- 同一服务下同一邮箱只保留一条当前生效记录

### 5.3 当日使用层

继续使用现有 `mcp_quota_daily`，不改变其核心职责。

- 记录当日已用次数
- 记录失败次数
- 记录下一个北京时间零点重置时间

该表不再承担任何长期策略语义。

## 6. 运行时口径

### 6.1 主身份口径

长期日加额和限额判断统一以 `email` 作为主匹配字段。

原因：

- 当前系统内邮箱可视为唯一且稳定
- 运维按邮箱识别用户最直观
- 后续人工查询、加额、撤销都更容易理解

### 6.2 邮箱获取顺序

运行时应按以下顺序获取邮箱：

1. 先读当前 MCP 请求上下文中的 `email`
2. 若缺失，则尝试从本地凭证恢复邮箱
3. 若仍缺失，可补一次获取动作

首期不再以 `user_id` 作为主键参与长期日加额匹配，但允许保留现有兼容代码结构，逐步把限额主身份收敛到邮箱。

### 6.3 实际额度计算

运行时实际每日额度公式为：

`effective_daily_limit = base_limit + bonus_daily_limit`

其中：

- `base_limit` 来自现有全局默认策略
- `bonus_daily_limit` 来自 `mcp_quota_bonus_daily`
- 查不到加额记录时，`bonus_daily_limit = 0`

示例：

- 默认额度为 `5`
- `a@example.com` 在 `seller_sprite` 上长期日加额为 `3`
- 则该用户实际每天可用额度为 `8`

### 6.4 当日重置行为

北京时间零点后：

- `mcp_quota_daily` 中的当日使用记录按现有逻辑切换到新日期
- `mcp_quota_bonus_daily` 不重置、不失效

这意味着“长期日加额”是永久日加额，而不是临时余额包。

## 7. 数据库变更建议

### 7.1 新增表

建议新增：

```sql
CREATE TABLE IF NOT EXISTS mcp_quota_bonus_daily (
    service TEXT NOT NULL,
    email TEXT NOT NULL,
    bonus_daily_limit INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    PRIMARY KEY (service, email)
);
```

约束建议：

- `bonus_daily_limit >= 0`
- `email` 写入前统一转小写并去掉首尾空白
- `service` 首期只允许 `seller_sprite`

### 7.2 现有表迁移策略

`mcp_quota_daily` 首期不做历史数据迁移，也不做重表。

原因：

- 该表职责仍然成立
- 当前需求只新增长期日加额语义
- 没必要为首版引入历史搬迁脚本和额外回滚复杂度

## 8. 运维操作方式

首期不新增任何公开 CLI 命令。

运维通过内部 SQL 直接维护 `mcp_quota_bonus_daily`：

- 新增或覆盖单个用户的长期日加额
- 批量维护多个用户的长期日加额
- 查询某服务下所有长期日加额记录
- 删除某邮箱记录，恢复默认额度

### 8.1 单用户 upsert 示例

```sql
INSERT INTO mcp_quota_bonus_daily (
    service, email, bonus_daily_limit, created_at, updated_at
)
VALUES (
    'seller_sprite',
    lower(trim('a@example.com')),
    3,
    datetime('now'),
    datetime('now')
)
ON CONFLICT(service, email) DO UPDATE SET
    bonus_daily_limit = excluded.bonus_daily_limit,
    updated_at = datetime('now');
```

### 8.2 查询示例

```sql
SELECT service, email, bonus_daily_limit, created_at, updated_at
FROM mcp_quota_bonus_daily
WHERE service = 'seller_sprite'
ORDER BY email;
```

### 8.3 删除示例

```sql
DELETE FROM mcp_quota_bonus_daily
WHERE service = 'seller_sprite'
  AND email = lower(trim('a@example.com'));
```

## 10. 风险与边界

### 10.1 邮箱缺失风险

若某些链路拿不到邮箱，而本地凭证恢复也失败，则限额系统需要明确返回受限错误，而不是静默回退到错误主键。

### 10.2 直接改库风险

运维直接执行 SQL 的方式简单，但也更依赖操作规范。因此内部教程中必须强调：

- 先备份 SQLite
- 所有邮箱统一标准化为小写
- 不允许写入负数加额

### 10.3 服务扩展边界

首期只覆盖 `seller_sprite`，但表结构按 `service + email` 设计，为后续扩展 `xiyou`、`sif` 预留空间。

## 11. 验收标准

设计完成后的实现应满足：

- 默认限额逻辑保持不变
- 对指定邮箱配置长期日加额后，实际每日额度变为 `默认额度 + 加额值`
- 当日使用记录继续按北京时间自然日重置
- 长期日加额不会因次日切日而失效
- 不新增公开 CLI 命令
- 内部教程不随打包对外暴露
