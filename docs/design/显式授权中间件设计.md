# 显式授权中间件设计

> 版本：v1.0（2026-07-23）
> 状态：已实现
> 关联需求：在任意子命令尾部显式传入授权凭证，一处中间件覆盖全部命令，支持 ops/polaris 双 JWT，并新增获取用户信息命令。

---

## 一、背景与目标

### 1.1 背景

opscli 原有认证依赖本机登录态：用户先 `opscli auth login`（Device Flow），凭证经 `CredentialStore`（Keychain / AES-256-GCM）持久化到本机，各命令通过 `AuthClient` 读取。

在脚本化、外部托管、CI 等场景下，调用方希望**直接携带已有凭证**执行命令，而不依赖本机登录态。

### 1.2 目标

1. 所有子命令支持在**尾部**追加三个全局参数：
   - `--session-id`：登录会话 ID（**必填**）
   - `--ops-jwt-token`：ops 系统 JWT（可选）
   - `--polaris-jwt-token`：polaris 系统 JWT（可选）
2. 提供了这些参数时，直接用其鉴权，覆盖本机登录态。
3. **一处中间件覆盖全部命令**，不逐个命令改造。
4. 支持 ops / polaris **两个** JWT，对应原有两个内置系统。
5. 新增 `opscli auth me`，调用 `/api/v1/auth/me` 获取当前用户信息。

---

## 二、关键设计决策

### 2.1 注入点选择：`AuthClient`（而非 `QueryClient` 等）

核查全部子模块后确认：**几乎所有模块都通过唯一的 `AuthClient` 取凭证**，
主流方式为 `self.auth_client.build_request_auth(alias)`，且都携带 `alias`（"ops"/"polaris"）。

因此在 `AuthClient` 一处注入即可覆盖 amazon / asin-data / calculator / feedback / query /
shopify / feedtask / xiyou / skills / shared 等所有命令，且 `alias` 天然区分双系统。

> 反例：`QueryClient` 的无状态分支只持有单个 jwt、忽略 alias，无法正确区分 ops/polaris，故不选它作为注入点。

### 2.2 参数捕获：argv 预解析（而非 Click 选项注入 / 顶层回调）

| 方案 | 语法 | 改每命令 | 健壮性 | 结论 |
|------|------|----------|--------|------|
| **argv 预解析** | `query simple ... --session-id=x`（尾部，符合需求） | 否 | 高 | **采用** |
| Click 命令注入 | 尾部 | 否（hack Click 内部） | 低（Typer 升级易碎） | 放弃 |
| 顶层回调 + envvar | `--session-id=x query simple`（前缀，不符合需求） | 否 | 高 | 放弃 |

Click 语法规则决定：尾部选项只能绑定叶子命令自身签名。要在**尾部**追加全局参数又不改每个命令，
唯一稳健方案是在 Typer 解析前从 `sys.argv` 预先摘除这三个参数。

代价：这三个参数不出现在各命令 `--help` 中（在顶层文档统一说明）。

### 2.3 存储：`contextvars`，请求级、进程内、**不落盘**

显式凭证**绝不写入** `CredentialStore`，避免污染当前登录用户的持久化凭证（安全要求）。
使用 `contextvars.ContextVar` 与 MCP 侧 `get_mcp_request_headers` 的上下文机制保持一致。

### 2.4 强制 `--session-id`

只要提供了任一 JWT，就必须同时提供 `--session-id`：
- 部分后端接口依赖 `polarisUserToken` session cookie；
- 仅有 session_id 时可用其向后端换取缺失的 JWT，是最稳健的凭证组合。

缺失时以退出码 2 直接终止，避免"看似成功实则鉴权不全"的隐性失败。

## 三、架构

```
┌─ 参数捕获层  opscli/cli.py : run()
│    _extract_explicit_credentials(sys.argv[1:])
│      · 支持 --flag=value 与 --flag value 两种写法
│      · 强制 session-id 校验
│      · 摘参后用清理过的 argv 覆盖 sys.argv
│         ↓ set_explicit_credentials(creds)
├─ 中间件核心  opscli/auth/context.py
│    ExplicitCredentials(session_id, ops_jwt, polaris_jwt)  +  ContextVar
│         ↓ 读取
├─ 单点注入   opscli/auth/__init__.py : AuthClient
│    get_token(alias):
│      1) 上下文有该 alias 的 jwt → 直接返回
│      2) 上下文有 session_id     → get_token_by_session(session_id, alias)（不落盘）
│      3) 否则                     → 本地 CredentialStore 常规流程（缓存 + 自动刷新）
│    get_session(alias): 上下文 session_id 优先
│    is_authenticated(): 上下文存在即 True
│    get_me(): GET {ops_system_url}/api/v1/auth/me
│         ↓ 自动流向
└─ 全部子模块  build_request_auth / get_token 一律自动生效（ops + polaris 双 token）
```

## 四、用法

```bash
# 直接携带 ops JWT + session
opscli query simple --table-id 35 --run \
    --ops-jwt-token=eyJ... --session-id=abc123

# 仅带 session（JWT 由后端换取）
opscli query simple --table-id 35 --run --session-id=abc123

# 同时带双系统 JWT
opscli asin-data bi ... --ops-jwt-token=eyJ... --polaris-jwt-token=eyJ... --session-id=abc123

# 获取当前用户信息（新命令）
opscli auth me --session-id=abc123 --ops-jwt-token=eyJ...
```

未提供任何显式参数时，行为与改造前完全一致（走本机登录态）。

## 五、影响范围与边界

| 项 | 说明 |
|----|------|
| 覆盖命令 | 所有经 `AuthClient` 取凭证的 CLI 命令 |
| MCP 入口 | `opscli-mcp` 不经 `cli.run()`，不受影响；MCP 有自己的按请求凭证机制 |
| `auth login/logout` | 管理本机登录态，不消费显式凭证，天然忽略 |
| 凭证持久化 | 显式凭证只存活当前进程，绝不落盘 |
| 过期刷新 | 显式 JWT 不自动刷新；仅有 session_id 时按需换取 |

## 八、MCP 侧对等（v1.1，2026-07-24）

### 8.1 为什么 MCP 与 CLI 形态不同

CLI 用 **argv 预解析 → 进程级 ContextVar**：一次进程、一次调用、全局生效。
MCP 是**长驻、异步、多用户**服务，进程级全局凭证会造成跨请求/跨用户串用，
**不可照搬**。MCP 的正确形态是**逐工具参数**（每个工具已有 `session_id` / `jwt`），
或逐请求 Header——这本就是 MCP 已有的"显式调用"机制。

### 8.2 本次补齐的两点差距

1. **`auth_me` MCP 工具**（`opscli/mcp/tools/auth.py`）：
   包装 `AuthClient.get_me()`，接 `session_id` / `jwt` 参数。为适配 MCP 无状态实例
   拿不到按 API Key 隔离的 session，`get_me` 扩展为 **session-aware**：
   有 `session_id` 走 `build_request_auth_with_session`，无则维持 `build_request_auth("ops")`
   （CLI `auth me` 无参调用行为不变）。工具先经 `_get_auth_pair("ops", …)` 解析隔离后的
   `(sid, jw)` 再传入。已加入 `_ALL_TOOLS`、`permissions.BASE_AUTH_TOOLS`（全模式可用）、
   `report_skill_usage` 映射。

2. **显式 `polaris_jwt` 参数**（`opscli/mcp/tools/asin_data.py`）：
   4 个 asin_data 工具新增 `polaris_jwt`；`_ProvidedAuthClient` 由
   `token = jwt if alias == "ops" else None` 改为
   `token = jwt if alias == "ops" else (polaris_jwt if alias == "polaris" else None)`，
   实现 per-alias 选 JWT。未显式提供时仍回退 session 换取（行为兼容）。

### 8.3 后端零变更

`permissions.py` 会本地无条件并入 `BASE_ALWAYS_ALLOWED_TOOLS`（`permissions.py:111`
`return frozenset(allowed) | BASE_ALWAYS_ALLOWED_TOOLS`），故 `auth_me` 加入 opscli
白名单后**全模式即可用，无需后端改动**。后端 auto-scheduler 的
`McpToolPermissionService::BASE_AUTH_TOOLS` 同步 `"auth_me"` 仅为可选一致性维护。

### 8.4 未触碰

shopify / feedtask 的 MCP 工具为未注册死代码（`server.py` 未注册、helpers 缺
`_shopify_manager` / `_feedtask_manager`），本次不涉及。
