# opscli 模块插件化与多团队治理方案

> 适用场景：`opscli` 未来从当前内建 `auth / query / skills` 三模块，演进为支持更多业务模块、可按需安装、由不同负责人或负责小组独立开发与发布的体系。
>
> 文档状态：设计提案
> 创建时间：2026-04-23
>
> 重要说明：本文描述的是未来插件化演进方向，属于**预留设计**。截至当前仓库版本，项目仍是单包分发、静态注册子模块，文中的独立模块包、按需安装、动态发现与治理机制**均未正式实现**。

---

## 1. 背景与目标

当前 `opscli` 采用单包分发、顶级 CLI 静态注册子模块的方式：

- 顶级入口 [`opscli/cli.py`](/Users/mask/python3/opscli/opscli/cli.py) 直接 `add_typer(...)`
- 所有模块位于同一 Python 包 `opscli`
- 模块默认随主包一起发布与安装

该模式在模块数量较少时简单稳定，但当后续出现更多模块，且这些模块满足以下条件时，会逐渐暴露治理问题：

- 模块数量持续增长
- 模块希望按需安装，而非全部随主包安装
- 模块由不同负责人或不同小组独立开发
- 模块发布节奏不一致
- 模块之间需要明确边界与兼容关系

因此，需要将 `opscli` 从“单体 CLI 工具集”演进为“核心 CLI + 可安装模块”的插件化架构。

本方案的目标：

1. 允许模块独立安装、独立发布、独立维护
2. 保持 `opscli` 命令体验统一，不增加用户理解成本
3. 让核心团队只维护底座能力，不承载所有业务模块研发
4. 为不同团队提供清晰的接入规范、版本治理和责任边界
5. 支持从当前仓库平滑迁移，不要求一次性重构

## 2. 设计原则

### 2.1 核心稳定，业务可插拔

核心只负责：

- CLI 容器
- 模块发现与注册
- 公共配置路径
- 公共鉴权 SDK
- 公共 HTTP/异常/日志/输出规范
- 模块兼容性校验

业务能力模块不应再通过修改核心仓库入口文件的方式接入。

### 2.2 公共接口前置，内部实现隔离

模块只能依赖：

- `opscli.core.*`
- `opscli.auth` 暴露的稳定公共 SDK
- 明确声明为公共接口的能力

模块禁止依赖其他模块内部实现细节，例如：

- 禁止 `opscli_notify` 直接 import `opscli_query.manager.QueryManager`
- 禁止直接读写其他模块私有配置文件
- 禁止跨模块访问未公开的 `core/` 私有实现

### 2.3 先单仓多包，后视情况多仓

优先推荐“单仓多包”作为第一阶段形态：

- 更容易统一规范、测试、CI、发布流程
- 更容易做兼容矩阵验证
- 更适合当前 `opscli` 仍在快速演进阶段

只有在以下场景成立时，再考虑拆分为多仓：

- 模块团队边界非常清晰
- 发布节奏差异很大
- 代码权限隔离要求强
- 模块体量已经足够独立

## 3. 推荐目标架构

### 3.1 包结构

推荐拆分为如下逻辑层：

```text
opscli-core                 # CLI 核心容器与公共基础设施
opscli-auth                 # 认证模块（或核心认证 SDK）
opscli-query                # 查询模块
opscli-skills               # Skill 管理模块
opscli-deploy               # 示例：发布/部署模块
opscli-notify               # 示例：通知模块
```

如果第一阶段仍保留单仓，则仓库结构可演进为：

```text
packages/
├── opscli-core/
├── opscli-auth/
├── opscli-query/
├── opscli-skills/
└── opscli-<module>/
```

### 3.2 命令模型

用户仍然使用统一入口：

```bash
opscli auth ...
opscli query ...
opscli skills ...
opscli deploy ...
opscli notify ...
```

但命令不再由核心静态写死，而由已安装模块在运行时动态注册。

### 3.3 模块发现机制

推荐使用 Python `entry_points` 做模块发现。

每个模块包在自己的 `pyproject.toml` 中声明：

```toml
[project.entry-points."opscli.modules"]
query = "opscli_query.plugin:register"
```

核心侧统一加载：

```python
from importlib.metadata import entry_points

for ep in entry_points(group="opscli.modules"):
    register = ep.load()
    register(app)
```

这样模块安装后即可自动出现在 `opscli` 命令树中，无需修改核心代码。

## 4. 模块协议设计

### 4.1 最小接入协议

每个模块必须提供一个注册入口，例如：

```python
def register(app: typer.Typer) -> None:
    ...
```

推荐同时暴露模块元信息：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class ModuleSpec:
    name: str
    command_name: str
    version: str
    owner: str
    requires_core: str
    summary: str
```

推荐模块插件文件结构：

```text
opscli_<module>/
├── __init__.py
├── cli.py
├── plugin.py        # 提供 register() / get_spec()
├── manager.py
├── client.py
├── exceptions.py
└── models.py
```

### 4.2 核心侧公共接口

核心需暴露稳定 API，供模块依赖：

- `opscli.core.config.CONFIG_DIR`
- `opscli.core.auth.AuthClient` 或兼容导出
- `opscli.core.http.create_client()`
- `opscli.core.output.print_json()`
- `opscli.core.errors.OpscliError`
- `opscli.core.plugins.ModuleSpec`

原则：

- 公共接口必须文档化
- 公共接口一旦对外发布，不得随意变更
- 若必须变更，需走兼容期和弃用通知

### 4.3 模块自描述信息

建议每个模块都带一份 `module.toml` 或等价元数据，用于 CLI 侧统一展示和健康检查，字段至少包括：

- `name`
- `command_name`
- `version`
- `owner`
- `team`
- `requires_core`
- `required_capabilities`
- `homepage`
- `support_contact`

## 5. 安装与分发策略

### 5.1 推荐安装方式

基础用户安装核心：

```bash
pip install opscli-core
```

按需安装模块：

```bash
pip install opscli-auth
pip install opscli-query
pip install opscli-skills
pip install opscli-deploy
```

也可提供聚合安装：

```bash
pip install "opscli-core[auth,query,skills]"
```

### 5.2 企业内部制品源

由于模块将进入可安装生态，必须收敛来源，推荐要求：

- 仅允许从公司内部 PyPI / 制品仓安装
- 不允许未审批模块进入官方模块组
- 发布前必须通过统一 CI 和安全检查

### 5.3 内建模块与外部模块

建议将模块分两类：

| 类型 | 定义 | 示例 |
|------|------|------|
| 核心模块 | 与 CLI 基础能力高度耦合，由核心团队托底维护 | `auth` |
| 业务模块 | 面向具体业务场景，可独立演进和安装 | `query`、`deploy`、`notify` |

其中：

- `auth` 可继续视为“核心依赖模块”
- `query`、`skills` 可优先作为插件化试点

## 6. 版本与兼容治理

### 6.1 双层版本

后续需要同时治理两类版本：

- 核心版本：`opscli-core`
- 模块版本：`opscli-<module>`

模块必须声明与核心的兼容关系，例如：

```toml
requires_core = ">=0.5,<0.7"
```

### 6.2 启动时兼容校验

核心启动加载模块时，应校验：

1. 模块是否声明 `requires_core`
2. 当前核心版本是否满足兼容范围
3. 模块命令名是否冲突
4. 模块是否缺少注册函数或必要依赖

若不兼容，应：

- 在 `opscli module doctor` 中标红显示
- 默认不注册有风险模块
- 给出明确错误提示和修复建议

### 6.3 版本治理规则

推荐规则：

- 核心公共接口新增能力：minor
- 核心公共接口不兼容变更：major
- 模块内部非破坏性改动：模块 minor / patch
- 模块命令参数不兼容变更：模块 major

### 6.4 兼容矩阵

建议维护一份兼容矩阵文档，至少记录：

- 核心版本
- 模块版本
- 最低支持 Python 版本
- 测试状态
- 发布状态

## 7. 多团队协作管控模型

### 7.1 责任边界

建议以“模块”为责任单元：

| 范围 | 责任方 |
|------|--------|
| 核心 CLI、插件协议、公共 SDK | 平台/基础团队 |
| 各业务模块代码与测试 | 各模块负责人或负责小组 |
| 模块接入评审与命名规范 | 平台/架构 owner |
| 发布审批与兼容验证 | 平台团队 + 模块 owner |

### 7.2 CODEOWNERS

建议为每个模块建立独立 owner：

```text
/packages/opscli-query/   @data-team
/packages/opscli-deploy/  @release-team
/packages/opscli-notify/  @ops-team
/packages/opscli-core/    @platform-team
```

### 7.3 模块准入机制

新模块接入前需满足以下门槛：

1. 命名符合规范：`opscli-<module>`
2. 命令名不冲突
3. 提供 `ModuleSpec`
4. 提供最小测试集
5. 提供 README / 使用说明
6. 提供 owner 与支持联系人
7. 通过核心兼容性检查

### 7.4 公共接口变更流程

只要变更涉及以下内容，必须走设计评审或 RFC：

- 核心公共 API
- 模块协议
- CLI 全局输出格式
- 认证 SDK 接口
- 配置目录结构

原因是这些变更会影响多个模块团队，不能由单一业务模块直接推动。

## 8. 目录与仓库治理建议

### 8.1 第一阶段：单仓多包

适合当前阶段，示意如下：

```text
opscli/
├── packages/
│   ├── opscli-core/
│   ├── opscli-auth/
│   ├── opscli-query/
│   ├── opscli-skills/
│   └── opscli-<module>/
├── tests/
│   ├── core/
│   ├── auth/
│   ├── query/
│   └── skills/
└── docs/
```

优点：

- 统一代码规范和工具链
- 一次 PR 可完成跨模块联调
- 更适合演进中的插件协议

### 8.2 第二阶段：多仓多包

只有当模块边界稳定、团队自治要求增强后，再考虑：

```text
opscli-core
opscli-auth
opscli-query
opscli-skills
opscli-deploy
```

多仓适用条件：

- 模块生命周期明显独立
- 团队权限和发布节奏必须隔离
- 平台团队已具备统一 SDK 与规范托管能力

## 9. CLI 治理能力建议

为方便运维与排障，建议后续补充统一模块治理命令：

```bash
opscli module list
opscli module doctor
opscli module info <name>
```

建议语义：

- `list`：查看当前已安装并成功注册的模块
- `doctor`：检查模块兼容性、依赖、命令冲突、注册状态
- `info`：查看模块版本、owner、支持团队、兼容范围

这会成为未来模块生态的统一治理入口。

## 10. 测试与 CI 管控

### 10.1 模块级测试

每个模块必须有自己的测试目录，例如：

```text
tests/query/
tests/deploy/
tests/notify/
```

### 10.2 核心兼容性测试

核心团队需要新增两类测试：

1. 插件发现测试
2. 兼容矩阵测试

示例：

- 某模块安装后是否能被正确加载
- 不兼容核心版本时是否能被拦截
- 重复命令名是否会被拒绝注册

### 10.3 发布前检查

建议在 CI 中强制执行：

- `pytest`
- `ruff` / `mypy`（如后续引入）
- 包构建校验
- entry point 注册校验
- 模块元数据校验
- owner/contact 字段完整性校验

## 11. 安全与权限边界

插件化后，风险不再只是代码复杂度，而是模块可信度问题。

建议约束：

- 只允许白名单模块参与自动发现
- 模块必须来自公司批准源
- 模块不得自行绕过 `AuthClient` 实现私有鉴权
- 模块不得自行定义新的全局配置根目录
- 模块不得向用户 home 目录写入未声明文件

如需更严格控制，可在后续引入：

- 模块签名校验
- 发布审批流
- 受限能力声明（例如网络访问、文件写入）

## 12. 从当前仓库到目标架构的迁移路径

### 阶段 0：保持现状，补设计与协议

本阶段目标：

- 不动现有命令行为
- 先定义模块协议、版本约束与治理规则

输出物：

- 本文档
- `ModuleSpec` 设计
- 核心公共接口清单

### 阶段 1：在当前仓库引入动态注册能力

本阶段目标：

- 保留现有 `auth / query / skills`
- 将 CLI 入口从纯静态注册改为“静态内建 + entry point 扩展”

建议做法：

- `opscli/cli.py` 保留内建模块兜底
- 新增 `load_external_modules()` 逻辑
- 增加重复命令名检测

这样可以兼容当前 AGENTS 中的“新增模块追加 `add_typer`”约束，同时为未来外部模块铺路。

### 阶段 2：选择一个模块做插件化试点

推荐优先级：

1. `query`
2. 新增业务模块
3. `skills`

不建议首个试点直接拆 `auth`，因为它是多数模块的基础依赖。

### 阶段 3：抽取核心公共包

本阶段将以下能力沉淀到核心：

- 配置目录
- 公共异常
- 输出工具
- 插件加载器
- 认证 SDK 接口层

### 阶段 4：形成正式模块生态

达到以下状态后，可认为插件体系成熟：

- 模块独立安装与发布
- 有统一 `module` 管理命令
- 有兼容矩阵与 owner 治理
- 有新模块准入标准

## 13. 对当前 AGENTS 规范的影响

当前规范中有一条铁律：

> 新增模块必须在 `opscli/cli.py` 中追加 `add_typer(...)`

该规则适用于当前“内建模块”模式，但不适合作为未来所有模块的统一规则。

建议后续拆分为两条：

1. 内建模块接入规范：
   继续允许在 `opscli/cli.py` 中静态注册
2. 外部可安装模块接入规范：
   必须通过 `entry_points` 与模块协议接入，禁止直接修改核心 CLI

这样既不破坏现有体系，也为未来插件化演进保留空间。

---

## 14. 推荐决策

结合当前 `opscli` 状态，推荐采用以下决策：

1. 先不急于多仓拆分，优先做“单仓多包 + 插件协议”
2. 先引入动态模块发现能力，再决定哪些模块独立发布
3. `auth` 继续保持核心地位，不作为首个外拆试点
4. `query` 或后续新增模块优先试点插件化
5. 建立模块 owner、兼容矩阵、发布准入机制

一句话总结：

`opscli` 后续最合理的治理模式，不是继续堆静态子模块，而是演进为“稳定核心 + 按需安装模块 + 明确责任边界 + 兼容矩阵治理”的插件式 CLI 平台。
