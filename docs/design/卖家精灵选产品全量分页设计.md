# 卖家精灵选产品全量分页设计

日期：2026-09-28。状态：首期本地实现与合成数据回归已完成；尚未部署，真实响应采样和真实20页端到端为发布门禁。

实际实现选择：all 暂停共享缓存读写；短页/重复/总数漂移直接失败并保留原始页，不交付易被误用的成功文件。仅502/503/504增加最多两次重试，429及业务错误交由既有worker处理后终止。恢复沿用首次绝对截止时间，停机也计入预算。实际字段与资源测试见 [开发验证](../analysis/卖家精灵选产品分页开发验证.md)。

## 1. 目标与范围

保留当前默认单页 100 条行为，新增选产品网页可访问范围的全量采集。默认仍快速返回；用户显式选择全量后，由现有异步任务执行多页请求、恢复中断页并导出文件。

首期只开放 `product-research`、`browser-route`、XLSX 文件结果。`xls` 继续沿用现有归一化为 XLSX 的兼容行为。其他场景、全量 JSON、前 N 条、自动拆分筛选条件、跨账号并发分页均不在首期。

关键来源约束：当前页面可访问前 **2000** 条。实际案例显示总数 4830，但只允许到第 20 页（每页 100）。产品文案使用“获取全部可访问结果（当前网页最多 2000 条）”，不能写成“获取全部 4830 条”。该数值属于有证据和版本的场景合同，来源变更后需重新核验，不能静默调大。

依据：[网页实测](../analysis/卖家精灵选产品分页网页实测.md)、[代码核查](../analysis/卖家精灵全量分页代码核查.md)。

## 2. 方案选择

| 方案 | 评估 | 决定 |
| --- | --- | --- |
| 翻页后全部 append 到列表，沿用导出 | 改动少，但保留多份数据、断点和部分结果问题；无法给出内存保证 | 不采用 |
| 调用官网批量导出任务 | 可能有独立导出额度、数量和异步合同，本轮未验证；不是当前列表分页的替代证明 | 本期不采用 |
| 逐页落盘、页检查点、逐行 XLSX | 复用现有队列和上传入库，对内存和恢复都有明确边界 | **采用** |
| 一次建立所有场景通用分页引擎 | 不同接口、页字段、HTML/文件任务、100 条截断语义尚未逐一核实 | 后续逐场景接入，再抽取确实相同的部分 |

2000 条的来源上限使首期无需建设百万行拆分或磁盘去重数据库。小型有界 ASIN 集合足够；保留逐页与流式结构，避免再依赖一份完整内存结果。

## 3. 对外参数合同

新增顶层 `collection_scope: "page" | "all"`，默认 `page`；CLI 对应 `--collection-scope`。CLI、远端适配器、MCP、请求模型、持久任务请求和缓存键同步透传。

| 参数 | page | all 首期 |
| --- | --- | --- |
| `page_size` | 保留现有行为，默认 100 | 固定有效值 100；不同值明确报参数错误，不静默覆盖 |
| `params.page/startPage` | 保留现有优先级 | 只允许省略或 1；统一归一化后从第 1 页开始 |
| `params.size/pageSize` | 保留现有兼容行为 | 只允许省略或 100；与顶层冲突时拒绝 |
| `export_format` | 保留 xls/xlsx/json | xls/xlsx；json 明确提示首期全量只支持文件导出 |
| `scenario` | 保留现有场景 | 仅 product-research |
| `mode` | 保留现有行为 | 仅 browser-route |

全量固定 100 是首期收敛决定，不是声称网页只支持 100。网页已验证支持 20/60/100；固定 100 可保证最多 20 个有效数据页，避免 60 条末页跨越 2000 边界和 20 条产生 100 次请求。失败重试与必要诊断请求另计，不算新增数据页。

请求示例（拟新增合同，当前版本尚不可调用）：

```json
{
  "scenario": "product-research",
  "site": "US",
  "period": "30d",
  "page_size": 100,
  "collection_scope": "all",
  "export_format": "xlsx",
  "params": {
    "keywords": "LOFT",
    "selectType": "2",
    "symbolFlag": false,
    "order": {"field": "total_units", "desc": true},
    "nodeIdPaths": [
      "1055398:1063306:1063308:3733101:3248801011",
      "1055398:1063306:1063308:3733101:3248804011"
    ]
  }
}
```

范围校验在排队前完成。无效 all 不创建后台任务；是否在 MCP 外层额度校验前拒绝，遵循现有 instrumentation 执行顺序，不声称能自动退还工具调用额度。

## 4. 请求与停止算法

1. 领取任务并绑定账号，解析站点、类目和周期。冻结规范化业务 payload；相对周期同时记录开始时间，不能承诺来源提供快照。
2. 恢复可信检查点，或发第一页。每页通过现有 worker 发送；复制基础 payload 后只修改 `page`，再用本场景 builder 重建 referer。保留前次修复中的 URL/POST 变体取反。
3. 校验 HTTP/业务成功以及 `data.items`、有效非负 `data.total`。如果返回页码、size 等辅助字段则校验；未返回不从别的场景捏造。具体可选字段以开发阶段脱敏响应 fixture 为准。
4. 首次计算 `planned_rows=min(total_reported, 2000)`、`planned_pages=max(1,ceil(planned_rows/100))`。首个请求同时用于确认零结果，因此空查询也记一次已完成页请求。总量 0 必须与空 items 一致；导出仅表头的有效 XLSX。
5. 每页验证后先落盘，再提交检查点，再推进页码。中途 raw total 变化单独记录；不无限追逐新增总量，不为重复行额外越过第 20 页。
6. 完成规划页数后做完整性核对，再生成导出与摘要。短页只有与可信总量、当前位置一致时才判定自然结束。

异常处理：

| 情况 | 处理 |
| --- | --- |
| 预期仍有结果却返回空页或短页 | 不能当自然结束；保留异常原始页及检查点，标记unverified并失败 |
| 响应页码错误、整页 ASIN 指纹重复 | 页码错位不推进检查点；重复页保留诊断页后标记unverified并失败，不继续翻页 |
| 实际 size 被压缩，或 total 字段缺失/无效 | 首期 fail closed，报告分页合同/权限异常，不静默改步长导致漏行 |
| 同一页重复 ASIN、跨页重复 | 按站点与子 ASIN 去重，统计重复；不按父 ASIN 合并。出现计数缺口不能宣称完整 |
| 总量在采集中变化 | 记录 first/last total，完成有界请求范围但 `coverage=unverified`，不进入完整结果缓存 |
| 到 2000 条来源边界且各页一致 | 约定范围完成；总量更大时标记 `coverage=source_limited` |
| 登录失效、网站额度/访问限制 | 保留已提交页并结束本轮；不得换账号续拼已采结果或绕过限制 |
| 502/503/504 | 每页最多2次额外重试，服从现有worker冷却和总预算；其他网络、429、认证、额度及业务错误不额外盲目重试 |

ASIN 缺失或业务行结构错误应作为合同异常处理，不能将多个缺失键去重成一条。原始响应不丢弃，以便定位错误。

没有服务端快照时，total 不变也不能数学证明零遗漏。结果声明 `consistency="best_effort"`，记录开始/结束时间；本轮 21 条网页比较是样本验证，不是对所有查询的全局保证。

## 5. 页文件、检查点与恢复

复用现有 SQLite 队列、账号占用、租约、heartbeat 和 assignment_generation。新增专用分页检查点表，不新建第二套队列或独立去重数据库。

检查点最小字段：job_id、查询指纹、冻结 payload 的文件引用及 hash、账号键、来源合同版本、effective_size、total_first/last、下一页、已提交页清单、计数、累计执行预算。最多 20 页，检查点 JSON 清单有明确上界。

页文件继续存于 `attempts/generation-N/pages/page-0001.json`，内容只包含业务请求/响应和安全元数据，不保存认证头。文件相对路径必须解析到任务根目录内。

提交顺序：写同目录临时文件 → flush/关闭并计算 hash → 原子替换为最终页文件 → 在 SQLite 事务中验证当前账号、generation 和租约后更新检查点。旧执行的条件更新失败时立即停止，不能覆盖新执行检查点。

恢复规则：

- 新 generation 可引用此前已提交、hash 正确的只读页文件，不依赖新 attempt 目录必须拥有全部旧文件。
- 写文件后、提交检查点前崩溃：忽略孤立文件，重取该页；提交检查点后崩溃：从下一页继续。
- 查询指纹、账号、size、来源版本不一致，不混合续取。已有页之后认证失败，首期禁用通用账号切换；第一页尚未成功时可沿用既有认证恢复策略。
- 已采齐后导出失败，复用页文件重新导出；上传失败只重传文件，不重新查询。
- 同一任务所有重启累计使用同一个时间与尝试预算，防止 lease 恢复导致无限重跑。单页重试次数一并记账。
- 首期不新增通用“任意失败任务重试”公网接口；自动续取覆盖现有进程退出/租约恢复。终态失败保留可诊断页文件，人工重试能力后续独立设计。

## 6. 内存与导出

```mermaid
flowchart LR
  A[绑定账号与恢复检查点] --> B[请求一页]
  B --> C[验证并落盘]
  C --> D[提交页检查点]
  D -->|有下一页| B
  D -->|范围结束| E[逐页读取与逐行格式化]
  E --> F[write_only XLSX]
  F --> G[上传与现有流式入库]
  G --> H[摘要与覆盖状态]
```

只在内存保留一页响应、最多 2000 个 ASIN、最多 20 个页摘要和有限预览。不能通过 `list(iterator)`、完整二维 worksheet.rows 或 `result.data` 再次收集全部数据。

抽取选产品单行格式化器供原路径和流式路径复用；保留已有列顺序、数字格式、币种、空值和父子体字段含义。使用 `Workbook(write_only=True)`，表头、列宽、冻结窗格在 append 前设置，最终只 save 一次。XLSX 不作为断点容器。

`raw.json` 在 all 路径使用显式版本的分页清单；完整响应保留在页文件。`result.json` 只保存摘要、导出引用及最多 10 行标明用途的 preview；`data=[]`，避免旧调用方把预览误当完整数据。默认 page 路径的文件结构与 `data` 行为不变。

既有上传是文件句柄 multipart，XLSX 沉淀是 read_only 逐行解析加批量写入，直接复用。禁止在 all 路径进入 JSON 缓存 fetchall、整份 JSON result 读取或返回全部行的 MCP 分支。

首期不需要 Excel 百万行分片；仍须检查磁盘可写、页文件大小、导出失败和上传失败。容量门禁先按本轮 2000 行范围测试，再根据峰值 RSS 给部署并发预算，不能以最终 XLSX 体积估算内存。

## 7. 结果、状态与缓存

成功的来源受限结果示例：

```json
{
  "row_count": 2000,
  "data": [],
  "collection": {
    "requested_scope": "all",
    "collection_complete": true,
    "coverage": "source_limited",
    "stop_reason": "source_limit",
    "total_reported_first": 4830,
    "total_reported_last": 4830,
    "access_limit": 2000,
    "effective_page_size": 100,
    "pages_completed": 20,
    "rows_received": 2000,
    "rows_exported": 2000,
    "duplicates": 0,
    "consistency": "best_effort"
  },
  "export": {"format": "xlsx", "filename": "Product-....xlsx"}
}
```

`collection_complete` 只表示规划的可访问页范围处理完毕；`coverage` 取 `matched_range`、`source_limited`、`partial` 或 `unverified`。导出与上传另有明确状态，不能用导出成功替代采集成功。

- 正常结束、来源边界：可使用现有 `succeeded`，响应文案必须披露来源限制。
- 网络错误、合同矛盾、超时：现有 `failed`，保留各attempt下raw.json分页清单；状态返回已提交页数、当前请求页和错误。远端接口不公开服务器路径；不自动把不完整文件作为正常成功数据沉淀。
- 范围处理完但 total 漂移或重复造成覆盖疑问：停止并返回failed，coverage=unverified，保留诊断页；首期不生成正常成功文件。
- 空结果确认：succeeded、row_count=0、matched_range，表头文件可读。

缓存键增加 collection_scope、来源访问合同版本及访问策略标识，page 与 all 不互相命中；默认 page 旧键兼容方式单独测试。缓存元数据白名单必须保留 collection 覆盖摘要，缓存命中仍提示“来源最多 2000 条”。

首期 all 禁用共享缓存查找及缓存身份写入沉淀，成功XLSX仍正常沉淀。page缓存策略不改。待账号访问策略核验后再考虑引入all缓存。

## 8. 时间、调度与额度

复用同账号串行和 worker 冷却。不建设页并发，不通过增加账号突破来源上限。最多 20 个数据页使首期可继续采用一任务占用一个账号槽位，无需先引入分片抢占调度。

新增进度白名单current_page、rows_received；完整collection摘要提供planned_pages、pages_completed、source_total、source_total_last、access_limit及请求/重试计数，仍避免写入 Token、账号密码和完整响应。心跳继续由现有执行机制维持，不能只在 HTTP 返回后续租。

保留当前默认任务总预算 600 秒作为首期起点，不宣称已经验证足够。各页、导出与上传共享有界总预算；超时应可靠停止请求并保留检查点。验收若证明 20 页正常路径不足，再仅针对 all 调整配置，不扩大所有场景超时。

内部 MCP quota 首期保持一次任务一次调用计量，与现有异步提交语义一致；后台重试不伪装成新的用户调用。额外记录 page_requests、retry_requests 供运营评估。网站自身额度和封控独立处理，逐页检查错误并停止；本轮未测得网站翻页扣费/扣额规则。

## 9. 未覆盖能力与发布门禁

本次网页没有抓到 HTTP 响应原文，故发布前必须补齐第一页、第二页、自然末页、零结果的脱敏响应 fixture，确定可选分页字段。这是实网验收前置事项，不影响已验证的 100 条可用、正常翻页和 2000 条网页边界。

全量 JSON、其他场景、自动筛选拆分、可配置任意页大小、通用失败任务续跑 API 均后续单独设计。全量 JSON 尤其要同时修改缓存、MCP 读取和沉淀路径，不能只把导出器换成流式。

上线前必须完成：20 页有界全流程、自然末页、空结果、故障恢复、账号/generation 隔离、缓存提示、现有格式一致性和峰值内存验收。详细清单见 [实施计划](../plans/卖家精灵选产品全量分页实施计划.md)。
