# opscli 模块安装分层与默认发行方案

> 适用场景：为 `opscli` 插件化演进后的安装方式、默认发行内容、必装模块与按需模块制定统一策略。
>
> 文档状态：设计提案
> 创建时间：2026-04-23

---

## 1. 目标

本文档解决三个实际问题：

1. 客户端如何“一条命令”默认安装常用模块
2. 哪些模块属于必装基础能力，哪些模块应该按需安装
3. 后续拆成 `core + modules` 后，如何避免默认安装越来越重

一句话结论：

`opscli` 应该是“官方默认发行版”，`opscli-core` 应该是“最小内核包”，业务模块则作为独立可安装包存在。

---

## 2. 推荐发行分层

建议将后续包分成四层：

| 层级 | 包名示例 | 面向对象 | 说明 |
|------|----------|----------|------|
| L1 核心层 | `opscli-core` | 平台团队、开发者、高级用户 | 只提供 CLI 容器与公共基础设施 |
| L2 默认发行层 | `opscli` | 普通用户 | 默认安装一组官方推荐模块 |
| L3 官方模块层 | `opscli-auth`、`opscli-query`、`opscli-skills` | 所有用户或部分用户 | 独立模块，可被默认发行版依赖 |
| L4 业务扩展层 | `opscli-deploy`、`opscli-notify` | 特定团队 | 按需安装，不应默认塞入所有环境 |

---

## 3. 默认安装策略

### 3.1 推荐安装入口

推荐保留三个用户入口：

```bash
pip install opscli
pip install opscli-core
pip install opscli-<module>
```

其含义分别是：

- `opscli`：默认标准安装，面向绝大多数用户
- `opscli-core`：极简安装，只装内核
- `opscli-<module>`：独立安装某个业务模块

### 3.2 默认发行版的职责

`opscli` 不应是所有模块的大杂烩，而应是“官方标准工作台”。

它的职责是：

- 提供开箱即用体验
- 覆盖公司内最常见场景
- 作为默认推荐安装命令

它不应该承担：

- 安装所有历史模块
- 安装所有实验性模块
- 安装所有团队私有模块

---

## 4. 必装模块与默认模块建议

### 4.1 必装模块

严格意义上的必装只有一个：

- `opscli-core`

原因：

- 所有命令入口、插件加载、公共配置、公共错误、公共输出都依赖核心
- 没有核心，模块无法统一挂载到 `opscli`

### 4.2 默认随 `opscli` 安装的模块

结合当前项目阶段，建议 `opscli` 默认依赖以下模块：

- `opscli-auth`
- `opscli-query`
- `opscli-skills`

原因分别是：

- `auth`：认证属于基础能力，未来多数业务模块都可能依赖它
- `query`：当前已是主功能之一，具备高频使用价值
- `skills`：是能力交付与升级入口，属于当前产品核心组成

### 4.3 按需安装模块

以下类型建议统一走按需安装：

- 面向特定业务线的模块
- 仅少数团队使用的模块
- 依赖重、安装慢的模块
- 发布频繁、变化快的实验性模块

示例：

- `opscli-deploy`
- `opscli-notify`
- `opscli-report`
- `opscli-warehouse`

## 5. 推荐的官方安装语义

### 5.1 面向普通用户

普通用户只需要记住一条命令：

```bash
pip install opscli
```

这条命令表示：

- 安装 `opscli-core`
- 安装默认官方模块
- 安装完成后即可直接使用最常见命令

### 5.2 面向平台团队或高级用户

如果只希望装一个极简底座：

```bash
pip install opscli-core
```

再手动按需安装：

```bash
pip install opscli-auth
pip install opscli-query
```

### 5.3 面向特定业务团队

如果某团队只需要额外能力，可以在默认发行版基础上增装：

```bash
pip install opscli
pip install opscli-deploy
```

## 6. 推荐依赖关系

### 6.1 包依赖模型

推荐依赖关系如下：

```text
opscli
├── depends on opscli-core
├── depends on opscli-auth
├── depends on opscli-query
└── depends on opscli-skills

opscli-auth
└── depends on opscli-core

opscli-query
└── depends on opscli-core

opscli-skills
└── depends on opscli-core

opscli-deploy
└── depends on opscli-core
```

如果某模块逻辑上需要认证，可以：

- 依赖 `opscli-core`
- 在运行时依赖公共 `AuthClient` 能力

是否让业务模块在打包依赖里直接依赖 `opscli-auth`，建议按实际耦合度判断：

- 若模块离开认证能力几乎不能工作，可直接依赖
- 若认证只是部分命令所需，可通过运行时检测能力并给出安装提示

### 6.2 `opscli` 聚合包建议

未来 `opscli` 这个包建议只扮演聚合分发角色，不承载过多业务实现。

其 `pyproject.toml` 可类似：

```toml
[project]
name = "opscli"
version = "0.1.0"
dependencies = [
    "opscli-core>=0.1",
    "opscli-auth>=0.1",
    "opscli-query>=0.1",
    "opscli-skills>=0.1",
]
```

这样做的好处是：

- 用户仍然只记一个安装命令
- 默认模块可以统一升级
- 业务扩展模块不会污染默认发行版

## 7. 为什么不建议“默认安装所有模块”

长期看，不建议让 `opscli` 默认安装全部模块，原因有五个：

1. 安装体积会持续膨胀
2. 不同业务模块依赖会互相污染
3. 某个冷门模块出问题会影响所有用户安装
4. 默认包会失去“稳定标准版”的定位
5. 多团队协作下，核心团队会被动背负所有模块的安装质量

换句话说：

“默认安装所有模块”适合作为初期权宜方案，不适合作为长期治理策略。

---

## 8. 如何判断一个模块是否应进入默认发行版

建议采用以下准入标准，满足大部分条件再进入 `opscli` 默认依赖：

1. 使用覆盖面广
2. 长期稳定维护
3. 与核心用户工作流强相关
4. 安装依赖较轻
5. 不会显著拖慢安装或升级
6. 有明确 owner 和稳定支持窗口

如果一个模块只满足其中少数条件，应优先作为按需模块，而不是默认模块。

---

## 9. 推荐的模块分级规则

建议以后在治理上把模块分成 A / B / C 三级：

| 级别 | 含义 | 安装策略 |
|------|------|----------|
| A 级 | 基础能力模块 | 默认进入 `opscli` |
| B 级 | 常用业务模块 | 可选进入扩展集合，但不默认全装 |
| C 级 | 团队专用或实验模块 | 仅按需安装 |

结合当前项目，建议先这样归类：

- A 级：
  - `auth`
  - `query`
  - `skills`
- B 级：
  - 后续通用但非全员必需模块
- C 级：
  - 团队专属、试验性、重依赖模块

## 10. 可选扩展方案

### 10.1 使用 extras 提供扩展安装

除了默认安装，也可以提供扩展安装组，例如：

```bash
pip install "opscli[full]"
pip install "opscli[data]"
pip install "opscli[release]"
```

对应语义示例：

- `full`：安装当前所有官方批准模块
- `data`：安装数据相关模块
- `release`：安装发布相关模块

这适合模块数量变多以后使用，但不建议一开始就把 extras 设计得太复杂。

### 10.2 是否需要 `opscli-all`

不建议优先增加 `opscli-all`。

因为：

- 与 `opscli[full]` 语义重复
- 会增加一个新的分发包维护成本
- 容易让“全量安装”变成误用默认项

只有当公司内部确实有明确“全家桶环境镜像”需求时，再考虑单独提供。

## 11. 对当前项目的推荐决策

结合你现在的项目现状，我建议：

1. 后续保留 `opscli` 作为默认推荐安装命令
2. 定义 `opscli-core` 作为未来的最小内核包
3. 默认模块先固定为：
   - `auth`
   - `query`
   - `skills`
4. 新增业务模块默认不进入 `opscli`
5. 是否纳入默认发行版，需要经过一次模块准入评审

一句话说，就是：

默认不是“全装所有模块”，而是“装一套公司官方基础工作台”。

---

## 12. 分阶段落地建议

### 阶段 1：先明确分层，不改用户安装命令

本阶段先在设计上确认：

- `opscli` 是默认发行版
- `opscli-core` 是未来核心包
- 默认模块为 `auth / query / skills`

### 阶段 2：插件化时保留默认体验

当模块改造成独立包后：

- `pip install opscli` 的体验保持不变
- 用户不需要知道内部已经拆包

### 阶段 3：新增模块统一按需安装

从某个时间点开始，所有新业务模块默认不进入 `opscli`，除非通过准入评审。
