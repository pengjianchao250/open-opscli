# 取数规划器迁移可行性分析报告

> 分类：分析调研报告（docs/analysis）
> 主题：将 `ops-dataset-query` Skill 的取数规划器脚本封装为 opscli 正式 CLI 命令与 MCP 工具的可行性评估
> 结论定位：**代码易迁移，命门在元数据来源；推荐"内核内化导出端点缓存"路线，可绕开最大风险点**
> 编写日期：2026-07-25

---

## 一、背景与问题

`opscli` 项目中的取数能力目前分布在两个层面：

- **opscli 正式模块**（`opscli/query/` + `opscli/mcp/tools/query.py`）：已提供取数原语层（metadata / build / run / chart / chart-doc / preferences），CLI 7 个命令 + MCP 9 个工具，全部复用 `QueryManager`。
- **`ops-dataset-query` Skill 脚本**（`opscli/skills/templates/ops-dataset-query/scripts/`，26 个脚本）：承载"自然语言→结构化查询计划"的规划智能层、图表异常分析、Excel 导出等治理与消费能力。

本报告聚焦其中价值最高、也最复杂的一块——**取数规划器**（`query_plan.py` 及其依赖库），评估能否将其封装成 opscli 正式指令与 MCP 工具迁移进内核，并给出实施路线与风险。

规划器涉及的核心文件：

| 文件 | 体量 | 职责 |
| --- | --- | --- |
| `query_plan.py` | 92KB | 规划器主入口，一次调用完成版本检查→规则校验→授权卡片→选表→字段/权限指导→平台枚举→产出规划合同 |
| `agent_query_planner.py` | 33KB | 选表引擎（库），带类型约束的 schema linking，三级优先选数据集 + 语义打分 |
| `dataset_guidance.py` | 27KB | 单数据集字段/权限指导（库），产出维度/指标、默认条件、权限范围 |
| `typed_schema_linking.py` | 14KB | 意图规则校验 + 语义抽取（库） |
| `scoped_dataset_reader.py` | 18KB | 授权元数据 CSV 统一读取层（库），含字段去重与快照一致性校验 |

---

## 二、总体判断

**代码本身极易迁移，真正的命门不在代码，而在"元数据从哪来"。而这个命门有一条风险最低的解法（下文路线 B）。**

分三个层次：

1. 规划器约 95% 是纯本地 Python 算法，可作为纯库直接平移进内核。
2. 唯一硬约束是"按账号动态元数据"的取得方式，存在两条路线，风险差异巨大。
3. 是否迁移本质上是产品决策（是否让规划能力脱离 Skill、被所有 opscli 用户与 MCP 复用），而非纯技术判断。

---

## 三、为什么代码易迁移

### 3.1 约 95% 是纯本地算法

以下逻辑全部无后端依赖，可直接平移：

- 选表打分（4 阶段匹配：授权外标识拦截 → 显式 alias/英文名精确命中 → 中文说明精确匹配 → 语义打分兜底 + 默认数据集推荐）
- 意图规则校验（`typed_schema_linking.validate_rules`，封闭式 fail-fast）与语义抽取
- 字段/权限指导（`dataset_guidance`，默认条件聚合、派生组件字段）
- 时间口径解析（`time_scope.parse`，纯 `datetime`，按 Asia/Shanghai 解析相对时间）
- 澄清阈值 / 确认门 / 合同投影 / 完整性封存（`plan_integrity`）

### 3.2 全流程仅 3 处 subprocess，且均可回退

规划器对外部的调用只有 3 处 `subprocess→opscli`，全部是**可选自愈/枚举**，任一失败都回退到"在合同里内嵌现成命令让 Agent 手动执行"，不阻塞主流程：

| # | 命令 | 触发阶段 | 用途 |
| --- | --- | --- | --- |
| 1 | `opscli skills upgrade ops-dataset-query --force` | 元数据未就绪时 | 刷新账号授权元数据 |
| 2 | `opscli query simple --table-id <组件>` | 平台筛选待权限枚举 | 自动枚举真实平台值并回灌重规划 |
| 3 | `opscli query simple` | 部门等组件筛选 | 服务端枚举消歧 |

迁入内核后，这 3 处替换为对 `QueryManager` 的内部函数调用即可（枚举可复用 `QueryManager.build_simple_and_run`）。

### 3.3 `intent_rules.json` 是包内静态资源

规划器的"NL 理解大脑" `data/intent_rules.json`（`schema_version:3`，含 domains / slots / platform_scope / compatibility / filter_fields / metric_terms）是**人工策展的账号无关领域知识库**，**不随 `skills upgrade` 从后端拉取**（不在 `updater.fetch_upgrade_data()` 清单内），随包分发。迁移时可直接打包成 opscli 内核静态资源，与后端完全无关。

### 3.4 输出合同分层清晰

产出的 `query_plan_model_contract_v2` 分层干净：

- `model_view`：仅中文、给用户看的结论（数据集中文名、维度、指标、时间口径、澄清消息等）
- `answer_contract`：回答必须遵守的披露与禁止项
- `execution_ref`（`user_visible:false`）：给 Agent 构造 `opscli query` 的物理引用（table_id、字段、时间窗、query_template + fill_rules 等）

**小结**：把这五个文件落成 `opscli query plan` / `query flow` 命令 + MCP `query_plan` / `query_flow` 工具，代码改造量小、逻辑几乎照搬。

## 四、真正的命门：元数据来源

### 4.1 关键事实——三张 CSV 不是从 query-metadata 派生

规划器需要的按账号动态元数据是三张 CSV，它们各有**专用后端导出端点**，由 `skills upgrade` 分别拉取：

| 本地文件 | 来源端点 |
| --- | --- |
| `datasets.csv` | `/v1/data-metrics/datasets/skill/export-datasets` |
| `dataset_fields.csv` | `/v1/data-metrics/datasets/skill/export` |
| `dataset_select_columns.csv` | `/v1/data-metrics/datasets/skill/export-select-columns` |
| `dataset_catalog.json` | `/v1/data-metrics/datasets/skill/catalog` |
| `query_metadata.json` | `/v1/data-metrics/datasets/query-metadata`（与 `QueryManager.metadata()` 同端点） |

后端设计上（`docs/plans/取数底座一期发布检查清单.md:39-40` 断言 `datasets payload == query-metadata == datasets.csv`、`fields payload == query-metadata == dataset_fields.csv`）这几套导出与 `query-metadata` **本就同源**（均出自服务端 `DatasetSkillService::buildExportPayloadForUser()`）。

### 4.2 元数据逐列等价性对照

**表① `datasets.csv` → query-metadata `datasets[]`**：全列可对齐（`select_column_count/names` 需从嵌套 `select_columns` 现算，Skill 侧现状本就是现算，无损）。

**表② `dataset_fields.csv` → query-metadata `fields[]`**：多数可对齐，但存在缺口：

| CSV 列 | query-metadata 等价 | 判定 |
| --- | --- | --- |
| field_name / verbose_name / global_alias / field_type / summary_expression / detail_expression / has_formula_config / filter_config | 有 | 能对上 |
| **snapshot_metric** | **无** | **对不上（主要卡点）** — 规划器 `dataset_guidance.py:168` 靠它决定快照聚合口径；后端二期只把它接进 CSV 导出，未接进 query-metadata JSON |
| description / remarks（字段级） | 无 | 对不上（规划器弱依赖，主要用数据集级 description/remarks） |
| dataset_name（field 行冗余） | 无（可 join 派生） | 可派生 |

**表③ `dataset_select_columns.csv` → query-metadata dataset 内嵌 `select_columns[]`**：全列可对齐。注意它对应的是 **`select_columns`（可筛选列→权限枚举组件的关系）**，不是 `filter_configs`（数据集默认过滤条件），两者结构相似但语义不同，勿混。

### 4.3 两条战略路线

#### 路线 A：把规划器改吃 `QueryManager.metadata()`（query-metadata 端点）

复用内核现成路径，但会**同时撞上两个后端级卡点**：

| 卡点 | 说明 | 需要 |
| --- | --- | --- |
| **snapshot_metric 不下发** | query-metadata 的 field 对象缺该键，规划器必需 | 后端改造（补下发） |
| **"全量 vs 按数据集"形态差异** | 规划器需一次性拿全部数据集全部字段建全局索引；`metadata()` 裸调用后端只回 `datasets` + `fields=[]`（实测 43 个数据集），字段仅在按 `dataset_alias` 过滤时逐个返回 | N 次 per-dataset 调用（撞 30 秒命令窗口/性能）或后端支持全量字段下发 |

→ **路线 A 无法纯客户端完成，必须后端配合。**

#### 路线 B（推荐）：opscli 内核内化导出端点 + 本地缓存

把今天 `skills upgrade` 干的事内化进内核——新增元数据缓存模块，调用 `skill/export-datasets` / `skill/export` / `skill/export-select-columns` / `catalog`，缓存到 `~/.config/opscli/`，按 TTL/按需刷新。规划器从该缓存读，**读的列与今天完全一致**（`snapshot_metric` 天然在内），`scoped_dataset_reader` 几乎不用改。

| 维度 | 路线 B 表现 |
| --- | --- |
| 后端改造 | 零（端点已存在且同源） |
| 等价性风险 | 零（数据完全一致，不存在 snapshot_metric 缺口） |
| `fields=[]` 全量问题 | 不存在（导出端点本就全量直出 CSV） |
| 代价 | opscli 从 Skill 接过"元数据缓存"职责；与现有 query-metadata 路径有一定重叠；需设计缓存失效策略 |

**元数据等价性这一最大风险点，在路线 B 下基本蒸发。**

## 五、路线 B 实施轮廓

1. 新增 `opscli/query/services/metadata_cache.py`：调 4 个导出端点、本地缓存、就绪/版本管理（接管 `skills upgrade` 对 ops-dataset-query 的元数据下发职责）。
2. 五个规划器文件落成 `opscli/query/services/planner/` 包；`scoped_dataset_reader` 的数据源从 Skill `data/` 改指向上一步的缓存。
3. `intent_rules.json` + `query_plan.schema.json` 作为内核静态资源打包。
4. 3 处 subprocess 换成内核内部调用（元数据刷新句柄 + 权限枚举查询句柄，后者复用 `QueryManager.build_simple_and_run`）。
5. 暴露 `opscli query plan` / `opscli query flow` CLI + MCP `query_plan` / `query_flow`（补上当前 MCP 侧最大的能力缺口——MCP 完全没有规划器）。
6. 将 CSV reader 独有逻辑一并迁入：字段去重（同物理字段多 global_alias 合并）、快照一致性指纹、filter_config JSON 解析；否则 `duplicate_dataset_field` 硬失败会复现。

## 六、待决策事项

以下三项属产品/架构决策，需相关负责人拍板后再进入实施设计：

1. **战略路线 A 还是 B**：B 零后端改造、零等价性风险，推荐 B；A 仅在"本就想统一到 query-metadata 单一端点、愿意推动后端补 `snapshot_metric` + 全量字段下发"时更优。
2. **规划器是否脱离 Skill 进内核**：迁入意味着自然语言规划从 Skill 用户专享变为所有 opscli 用户可用、且能纯 MCP 闭环；代价是 opscli 接手约 165KB 复杂治理逻辑的长期维护。
3. **SKILL.md 治理契约如何承接**：规划器今天嵌在 SKILL.md 的整套流程里（澄清、平台枚举、证据合同、命令预算）。只搬规划器、不搬编排，需在 CLI/MCP 边界重新表达该契约，否则规划器产出的合同无人按规矩消费。

## 七、附：与其他能力的迁移优先级定位

本报告聚焦规划器（此前评估中的"第三档，最高价值、最深耦合"）。完整迁移蓝图中另有两档更易落地、可先行：

- **第一档（立即可做）**：`time_scope.py` / `evidence_contract.py` / `plan_integrity.py` 等纯逻辑单元，零 `data/` 耦合，近乎"复制 + 改 import"。`time_scope` 可直接补上 `query` 模块"只吃显式日期、无自然语言时间解析"的现状缺口。
- **第二档（优先封装）**：`chart_analyze` / `excel_export` / `chart_map` 图表与导出支线，作者已按 `core / CLI / mcp` 三分、取数副作用隔离良好，数据源可复用现有 `query chart --run`；封装成 MCP 工具后即可实现"取数→异常分析→导出"纯 MCP 闭环。

规划器（第三档）建议单独立项，先定路线 A/B 再进入实施设计。
