## 一、给管理层的一页结论

**这次测试查出了 81 个真实缺陷，其中 50 个属于"不报错但答案是错的"，已全部修复并加了回归防护。**

规划器负责把一句中文（"看下上月各部门的销售额前 5"）翻译成一次数据库查询。它出问题时通常不会报错——查询照样跑通、数字照样返回，只是口径和你要的不是一回事。这类问题人是很难发现的：报表看起来完全正常。

本轮实测到的典型形态：

| 你说的 | 系统实际查的 | 后果 |
| --- | --- | --- |
| 8 月 15 日的销售额 | 整个 8 月的销售额 | 数字放大约 31 倍 |
| 今年第一季度 | 1 月 1 日至今天 | 窗口多了大半年 |
| 各平台的平台库存 | 全公司合计库存（平台分组被丢掉） | 拿不到分平台明细，且看不出被丢了 |
| 销售额最高的前 5 个平台 | 全部平台、不排序 | "Top 5"变成了没有排序的全量清单 |
| 排除「一部-B组」这个小组 | 排除整个一部 + 全公司所有 B 组 | 排除范围被放大了几十倍 |
| 各原产国/地区的数据 | 附带了一个恒不成立的品牌条件 | 稳定返回 0 行，容易被误读成"这段时间没有业务" |
| 有哪些渠道可选 | 查询固定失败 | 该功能此前 100% 不可用 |
| 各平台卖了多少钱 | 只查平台名，一个金额都不查 | 返回一列平台清单，看不出少了什么 |
| 各平台的销售量 | 平台×销售人员，仍然不带任何指标 | 结果与问题完全无关 |
| 近7天的销售额，同比去年同期 | 去年全年对比前年全年 | 要的 7 天一天都没查到 |
| 剔除亚马逊VC | 只看亚马逊VC | 查询语义被反转，返回的恰是要排除的数据 |
| 项目二部和项目六部的销售额 | 只认第一个部门，第二个被判无效 | 合法请求被拒 |
| 项目二部和项目六部分别的销售额 | 两个部门合起来一个数 | 看起来像单个部门的数字 |
| 综合数据，包括库存、广告、销售、退款 | 库存一类整体消失 | 报表里少一整类数据且无提示 |
| 二部-A组和一部-A组的销售额 | 部门=二部 且 小组=一部-A组 | 两个条件互斥，稳定返回 0 行 |
| 前天的销售额 | 最近 30 天的销售额 | 窗口错到 30 倍 |
| 卖得最好的 3 个平台 | 全部平台、无排序、无指标 | Top 3 完全失效 |
| 各平台销售额，剔除亚马逊VC（连后端执行） | 规划正确，但服务端只返回亚马逊VC 一行 | 结果与意图完全相反 |
| 各部门销售额，扣除九部 / 除了九部 | 只看九部 | 查询语义被反转 |
| 排除美国只看加拿大 | 美国、加拿大一起排除 | 要看的国家也被去掉 |
| 各品类销售额，剔除家居 | 全部品类，家居照样在内 | 排除条件被静默丢弃 |
| 排除九部，只看十部（十部无权限） | 九部以外的全部部门 | 范围被放大成几乎全公司 |
| 包括九部在内的各部门 | 只看九部 | 范围被收窄成一个部门 |
| 近7天各平台的CPC | 只查平台名，一个指标都不查 | CPC 对应好几个字段，系统没问就放行了 |
| 近7天各平台的TACOS | 查成了 ACOS | 两个口径分母不同，数字完全不是一回事 |

## 二、测试范围与方法

### 2.1 被测范围

| 维度 | 覆盖 |
| --- | ---: |
| 授权数据集 | 78（69 个业务数据集 + 9 个权限枚举组件），逐个覆盖 |
| 字段元数据 | 3312，逐个覆盖，每个字段至少点名两次 |
| 组件枚举实测取值 | 部门 25、平台 27、国家 38、销售小组 680、大组 185、开发小组 253、渠道 5000 |

### 2.2 六轮视角

**第一轮：领导汇报视角。** 按管理者真实提问方式，为每个数据集生成基线、多指标、按日趋势、TopN、环比、库存快照、快照与流量混查七类组合，再叠加时间口径、指标别名、平台语义、币种、组件筛选、排除极性等跨数据集语义用例。每条用例都带独立计算的预期：时间窗由测试脚本用 Python 单独算一遍再比对，指标、维度、排序、行数、筛选算子与取值逐项核对。

**第二轮：测试工程师视角。** 四种方法叠加：

- **不变量暴力测试**：全数据集随机组合上千条请求，不写逐条预期，改为校验 10 条任何输入下都必须成立的硬约束（投影字段必须属于该数据集、排序字段必须在本次投影里、澄清态不得下发可执行模板、模型可见层不得泄漏内部技术标识等）。
- **蜕变测试**：10 组语义等价改写（语序、动词、标点、全角半角、时间同义表述、TopN 同义表述、指标别名、币种表述、趋势表述、季度表述），组内必须产出完全相同的查询模板。
- **差分测试**：8 组语义不同的输入（换维度、换时间、换指标、正向与排除、不同行数、不同排序方向、不同币种、编号部门与项目部门），组内必须两两不同。
- **对抗与边界测试**：空输入、纯标点、超长输入、指令注入、SQL 注入片段、矛盾时间、非法行数、不存在的数据集与部门、中英混排、全角字符、跨年与闰年边界等 45 条。

**第三轮：初级业务视角。** 前两轮都用规范字段名提问，覆盖不到"业务同事嘴里的说法"。这一轮改成三件事：

- **全字段覆盖**：78 个数据集的每一个字段各点名一次，再换一种业务组合形态（Top N、按日趋势、环比、币种、排序）点名第二次。判据是"点名的字段必须真的进入合同和模板"，静默丢弃即判失败。
- **业务术语矩阵**：同一口径的多种叫法逐个核对，例如销售额的营业额、成交额、GMV、卖了多少钱，销量的销售量、订单量、出单量、卖了多少个、多少单。落不到字段的必须澄清，不得静默丢弃。
- **口语与模糊输入**：口语时间（前天、这周、上个月、今年以来）、口语分组（分平台看、按平台拆开看、逐个平台）、口语排序（卖得最好的、排名靠前的）、疑问句式、客气用语、中英混杂、半截词、代词指代。

**第四轮：特性交叉兼容。** 前三轮把每条修复单独验证过了，但它们分布在十余条互相重叠的代码路径上，单独通过不等于能同时成立。这一轮把每条修复抽象成一个可组合的语言片段（时间说法、指标说法、维度说法、筛选值、排序、对比、币种、趋势、排除），按两两、三重、四重叠加成请求，要求**所有片段的预期同时出现在同一份合同里**，任何一条被别的特性挤掉即判失败。另加 21 条槽位模板覆盖不到的高风险冲突用例，例如快照指标叠加趋势与 Top N、同一句里出现三个「销售」开头的词、单日日期叠加环比、含斜杠的字段标签叠加币种。

**第五轮：近义词、专业场景与多值组合。** 把同一个意思的不同说法系统铺开：指标、维度、时间、筛选、排除、排序、对比、趋势、动作词九类，每类列出业务同事真实会用的多种叫法，要求组内解析结果一致或安全澄清；再按真实场景补 30 条完整请求（周报、月度复盘、年同比、广告效率、库存健康、退款分析、人员绩效），以及多类目综合报表和多值组合（「项目二部和项目六部分别」「亚马逊和TEMU」）。这一轮还引入**行为快照**：先把当前行为落盘，修复后用同一语料重跑比对，任何非预期的行为变化都会被列出来，用来保证新修复不影响既有规划器。

**第六轮：排除与限定同义词复测（含端到端执行）。** 把"去掉某个值"和"只看某个值"两类说法按业务同事的真实口吻铺开：部门、平台、国家、品牌、销售小组、品类六个字段 × 二十种排除说法（扣除、刨除、排掉、拿掉、不算、除去、抛开、除了X、除X外、X以外、不包括X在内……），另加五个字段 × 二十种限定说法，再补 38 条多场景组合（「排除美国只看加拿大」「排除九部，只看十部」「户外品类和家居品类」「上个月，傲彼瑞-美国渠道」）。这一轮第一次把排除类请求**连后端实际执行**，并逐行检查被排除的值是否真的不在结果里——正是这一步发现了"模板正确、结果相反"的后端算子缺陷。最后再用专业运营的口吻补一组：MTD、YTD、上半年、近N个季度等经营汇报时间口径，以及 CPC、CTR、CVR、ROAS、TACOS 等广告缩写，要求要么正确落到字段，要么明确澄清，不得静默丢指标或替换口径。

## 三、缺陷统计

### 3.1 按严重级别

| 级别 | 数量 | 判定标准 |
| --- | ---: | --- |
| P0 | 12 | 静默产出错误结果，且错误方式让人倾向于做出错误业务判断 |
| P1 | 55 | 静默改变查询口径 / 丢弃用户诉求 / 合法请求被误拒 |
| P2 | 14 | 结果安全但提示误导、体验受损或审计信息缺失 |
| P3（未修复，已记录） | 12 | 多数为 fail-safe（会澄清或按字面执行）；少数属已知识别边界，见第五节 |

### 3.2 按失效形态

| 形态 | 数量 | 说明 |
| --- | ---: | --- |
| 静默改变查询口径 | 17 | 时间窗、分组维度、筛选范围与用户表述不一致 |
| 静默丢弃用户诉求 | 25 | 点名的指标、维度、排序或筛选值不出现在最终模板里 |
| 查询语义被反转 | 6 | 排除说法被读成只看该值，或模板正确但执行结果相反 |
| 条件导致恒空 | 2 | 查询稳定返回 0 行 |
| 误报澄清或阻断 | 28 | 合法请求被拒 |
| 功能完全不可用 | 1 | 权限枚举查询被后端固定拒绝 |
| 审计与可复现性 | 2 | 结果正确但审计信息缺失或摘要不稳定 |

### 3.3 P0 缺陷的实测证据

**P0-1：品牌枚举里存在一个名为「/」的取值。**
任何含斜杠的正常表述都会被它命中。实测「海运在途SKU明细上月各原产国/地区的包装长CM」，规划器附加了 `brand_name = '/'`，后端接受该条件并返回 **0 行**。整条链路没有任何错误或提示，使用者最可能得出的结论是"上月没有在途数据"。

**P0-2：点名了数据集里不存在的指标时，静默下发零指标模板。**
实测「近7天各平台的净推荐值」返回 `status=planned`，模板 `metrics` 为空数组。查询会成功执行并返回一列平台名称，核心诉求整个消失，且合同里没有任何澄清码。

**P0-3：初级业务用户最自然的问法整句丢失指标。**
实测「近7天各平台卖了多少钱」「各平台卖了多少个」「各平台有多少单」「各平台的销售量」全部返回 `status=planned` 且模板 `metrics` 为空。其中「销售量」还把「销售」误当成销售人员维度选了进来，结果是一张 平台 × 销售人员 的清单，一个数字都没有。这四种说法是业务同事口头提问的主力形态。

**P0-4：排除说法被读成只看该值。**
实测「近7天各平台的销售额，剔除亚马逊VC」下发 `platform_name = Amazon VC`，「亚马逊VC除外」「亚马逊VC以外」同样如此。查询返回的恰好是用户要求排除的那部分数据，状态为 planned、没有任何提示。「排除亚马逊VC」一直正常，所以之前的矩阵都没发现。

**P0-5：组件枚举分页截断。**
授权枚举默认只取 500 条，当前账号的销售小组有 681 个。落在首页之外的值校验不过，而服务端返回顺序不稳定，同一条请求时好时坏。它先前一直被当成服务抖动。单独对比 limit=500 与 limit=5000 后才定位：修复后同一请求并发 24 次全部命中，修复前约四成请求会被拆成更宽的部门加大组条件或转澄清。

**P0-6：未授权复合值的片段外溢，查询恒为 0 行。**
实测「近7天二部-A组和一部-A组的销售额」，二部-A组 不在授权范围内，它开头的「二部」被单独当成部门筛选，模板变成 `dept_name = 二部 AND team_name = 一部-A组`。两个条件互斥，查询稳定返回 0 行，最容易被读成"这个小组没有业务"。

**P0-7：模板正确，执行结果相反。**
「近7天各平台的销售额，剔除亚马逊VC」规划出 `platform_name != Amazon VC`，服务端却只返回 Amazon VC 一行。直连 simple 接口逐字段对照：`ne` 在平台、销售小组、大组、渠道、品牌、品类、SPU 上都只返回被排除的值，在部门、国家上正确；单元素 `not_in` 在全部字段上正确。此前各轮只验证到"模板正确"为止，因此一直没有暴露。执行器已把字符串单值排除改发单元素 `not_in` 规避，**后端缺陷需另行反馈修复**。

**P0-8：口语排除说法被反转成只看该值。**
「各部门销售额，扣除九部」「刨除九部」「不算九部」「除了九部」「除九部外」「九部以外的」全部下发 `dept_name = 九部`，平台、国家、品牌、销售小组同样如此（修复前 120 条排除说法只有 44 条正确）。

**P0-9：排除区间吞掉随后的正向限定。**
「排除美国只看加拿大」不带标点时下发 `country_name not_in [加拿大, 美国]`，用户要看的加拿大也被去掉，返回的是其余 30 多个国家。

**P0-10：片段字段名被当成认得，静默下发零指标模板。**
「近7天各平台的CPC」返回 `status=planned`，模板 `metrics` 为空。数据集里有「平均CPC」「CPC转化率」和 SP/SD/SB 各自的平均 CPC，CPC 只是这些名称的一部分，度量门禁把"是某个标签的片段"当成认得而放行。查询只会返回一列平台名。

## 五、遗留项

12 个 P3 观察项未纳入本轮修复。多数为 fail-safe 行为（会澄清或按用户字面执行），少数属于已知的识别边界（第 6～9 条）。原先记录的「近 N 个季度不支持」已在第六轮修复。明细与建议见配套的缺陷分析与修复报告第五节，摘要如下：

1. 白名单之外的冷门币种不识别，按账号默认币种执行；结果侧有币种披露兜底。
2. 同一句里出现两个互斥时间表述时静默取先匹配的一个。
3. 越界行数（前 0 个、前 999999 个）静默丢弃行数限制。
4. 完全位于未来的时间窗按字面执行。
5. 9 个数据集没有统一业务日期列，时间锚点落在其唯一业务时间字段上，合同未声明用的是哪个日期字段。
6. 品类、平台类目裸值的包含写法（「只看家居」「家居类的销售额」）仍不识别，按全部品类执行；排除写法与「家居品类」后置写法已支持。
7. 加合句式「除了九部以外，还要看十一部」仍按排除九部处理，建议识别到加合句式时澄清。
8. 指标口径类排除（「剔除退款后的销售额」「剔除今天」）按字面执行，排除意图被忽略。
9. 「九部对比十一部」只筛选两个部门、不补分组维度，返回合计。
10. 跨字段并列（「九部和一部-A组」）按 AND 组合，结果通常为空。
11. simple 接口 `ne` 反转缺陷已在客户端规避，需后端修复后移除规避。
12. 枚举自适应扩页让单次规划的中位延迟从约 3 秒升到约 4 秒，仍在 30 秒命令窗口内。

## 六、结论与建议

1. **本轮问题已闭环**：81 个缺陷全部修复，末轮各层验证全绿（领导矩阵 502、全字段 6486、交叉 1802、同义词/场景 273、暴力 649、同义词横向探测 258、专业口径探测 34、端到端 16、单元测试 849），全部缺陷已固化为回归用例。
2. **风险集中在"静默"而非"报错"**：81 个缺陷里只有 1 个会让查询失败，50 个会正常返回数据但答案是错的。建议今后对规划器的验收，以"不变量 + 蜕变 + 差分"这类不依赖逐条预期的方法为主，逐条预期为辅——本轮 3 个不变量违例和 1 组蜕变不一致，都是逐条预期的用例发现不了的。
3. **建议把两个测试脚本纳入发版前置检查**：领导视角矩阵约 444 条、暴力矩阵 1200 到 1500 条，10 到 12 并发下各约 3 到 10 分钟，成本可接受。
4. **单元测试基线未受影响**：`tests/skills/` 8 个、`tests/mcp/` 2 个失败与 1 个模块导入错误均为本轮之前既有，与规划器无关，修复前后计数一致。
5. **P3 观察项建议排期**，其中"最近 N 个季度"与"时间表述冲突澄清"对季度经营汇报场景的实用价值最高。
6. **排除与限定类的验收必须连后端执行**：第六轮的 P0-7 说明"模板正确"不等于"结果正确"。建议把端到端执行（检查被排除的值确实不在结果里）纳入发版前置检查，并尽快把 simple 接口 `ne` 的反转缺陷反馈给后端。
