## 二、授权流程对比

### 2.1 授权标准

两个项目均采用 **OAuth 2.0 Device Authorization Grant（RFC 8628）**，但实现完整度差异显著。

### 2.2 Lark CLI 完整授权流程

```
auth login [--scope] [--domain] [--recommend] [--no-wait] [--device-code]
    │
    ├─ 严格模式检查（StrictModeBot → 拒绝用户登录）
    │
    ├─ 是否有显式参数？
    │   ├─ 无参数 + TTY → 进入 TUI 交互模式
    │   │   ├─ Phase 1: 多选业务域（huh.MultiSelect）
    │   │   └─ Phase 2: 选择权限级别（common / all）
    │   └─ 有参数 → 直接解析 --scope / --domain / --recommend
    │
    ├─ Scope 展开
    │   ├─ 从 from_meta 元数据按域名收集 API scope
    │   ├─ 从 shortcuts 按 Service 名称收集 scope
    │   ├─ 展开 auth_domain 子域
    │   └─ 自动追加 offline_access（用于获取 refresh_token）
    │
    ├─ POST /oauth/v1/device_authorization
    │   └─ 响应：device_code, user_code, verification_uri, expires_in, interval
    │
    ├─ --no-wait 模式？
    │   └─ Yes → 保存 scope 到缓存文件，立即返回 device_code（异步）
    │
    ├─ 显示验证 URL，等待用户浏览器授权
    │
    ├─ 轮询 POST /open-apis/authen/v2/oauth/token
    │   ├─ authorization_pending → 继续（默认间隔 5s）
    │   ├─ slow_down → 增加间隔（最大 60s，最多 200 次）
    │   ├─ access_denied → 用户拒绝，终止
    │   └─ access_token 存在 → 成功！
    │
    ├─ GET /open-apis/authen/v1/user_info（获取 open_id + 用户名）
    │
    ├─ 存储 Token（系统 Keychain 优先）
    │   └─ key = "appId:userOpenId"
    │
    ├─ 同步 Profile 配置（更新 Users 列表，清理旧 Token）
    │
    └─ Scope 对比验证（已授予 vs. 请求的，输出 summary）
```

## 三、Token 生命周期管理

### 3.1 Token 体系架构差异

#### Lark CLI：标准 OAuth2 双 Token 体系

```
用户授权
    │
    └─ access_token（短期）+ refresh_token（长期）
            │
            ├─ access_token 用于 API 调用
            │   └─ 有效期：由后端决定（通常 2 小时）
            │
            └─ refresh_token 用于静默续期
                └─ 有效期：更长（通常 30 天）
                   └─ POST /oauth/token（grant_type=refresh_token）
                      → 获取新的 access_token（无需用户交互）
```

#### opscli auth：session_id 中间层体系

```
用户授权
    │
    └─ session_id（30 天）
            │
            └─ 每次需要 Token 时，用 session_id 换取 JWT
                └─ POST {system_url}/api/auth/cli-token
                   请求体：{"session_id": "..."}
                   → JWT（有效期最多 24 小时）
```

**核心差异**：当前项目无 `refresh_token`，每次 JWT 过期都需要消耗 session_id 向后端换取，session_id 失效则必须重走完整 Device Flow。Lark CLI 的 refresh_token 可在 access_token 过期后静默续期，无需用户参与。

### 3.2 Token 状态模型对比

#### Lark CLI：三态模型

```go
const refreshAheadMs = 5 * 60 * 1000  // 提前 5 分钟

func TokenStatus(token *StoredUAToken) string {
    now := time.Now().UnixMilli()
    if now < token.ExpiresAt - refreshAheadMs {
        return "valid"          // 距过期 > 5 分钟：直接使用
    }
    if now < token.RefreshExpiresAt {
        return "needs_refresh"  // access_token 近期过期，但 refresh_token 有效
    }
    return "expired"            // 完全过期，需要重新登录
}
```

#### opscli auth：两态模型

```python
REFRESH_THRESHOLD = 1800  # 30 分钟

def _is_valid(self, token_data: dict) -> bool:
    exp = datetime.fromisoformat(token_data["expires_at"])
    # 距过期 > 30 分钟：有效；否则：需要刷新
    return exp > datetime.now(timezone.utc) + timedelta(seconds=1800)
```

| 状态模型 | Lark CLI | opscli auth |
|----------|----------|-----------------|
| **状态数** | 3（valid / needs_refresh / expired） | 2（有效 / 需刷新） |
| **刷新阈值** | 提前 5 分钟 | 提前 30 分钟 |
| **过期后恢复** | 用 refresh_token 静默续期 | 重新换取 JWT（消耗 session） |
| **完全失效后** | 重新登录 | 重新走 Device Flow |

### 3.3 Token 有效期配置

| 配置项 | Lark CLI | opscli auth |
|--------|----------|-----------------|
| **access_token 有效期** | 由后端决定 | 最多 24h（MAX_JWT_TTL 限制） |
| **refresh_token 有效期** | 由后端决定（通常 30 天） | 无 refresh_token |
| **session 有效期** | 不适用（无 session 中间层）| 30 天 |
| **有效期上限限制** | 无客户端限制 | 客户端强制 ≤ 86400s |

## 四、Token 存储安全性

### 4.1 Lark CLI：分级存储方案

```
优先：系统 Keychain（OS 级安全保护）
  ├─ macOS  → Keychain Services（钥匙串）
  ├─ Linux  → Secret Service（GNOME Keyring / KWallet）
  └─ Windows → DPAPI（Data Protection API）

Fallback：本地 AES-256-GCM 加密文件
  └─ ~/Library/Application Support/lark-cli/<account>.enc
      ├─ 加密密钥存储在系统 Keychain
      └─ 格式：[IV(12B)] + [密文 + 认证标签(16B)]

存储键格式：
  Service = "lark-cli"
  Account = "{appId}:{userOpenId}"
```

**系统 Keychain 的安全优势**：
- 密钥由操作系统托管，其他进程无法直接访问
- macOS 上支持生物识别（Touch ID）保护
- 进程隔离：只有授权进程可读取
- 系统重启后密钥依然安全

### 4.2 opscli auth：自实现加密文件存储

```
~/.config/opscli auth/
├── credentials.bin   # AES-256-GCM 加密的 JSON（权限 600）
└── .key              # 256-bit AES 密钥（权限 600）
```

**加密实现**（`storage/crypto.py`）：
```python
class Crypto:
    def encrypt(self, plaintext: str) -> bytes:
        nonce = os.urandom(12)          # 随机 12 字节 nonce
        return nonce + AESGCM(self._key).encrypt(nonce, plaintext.encode(), None)

    def decrypt(self, ciphertext: bytes) -> str:
        return AESGCM(self._key).decrypt(
            ciphertext[:12],            # 前 12 字节为 nonce
            ciphertext[12:], None
        ).decode()
```

**安全性对比**：

| 安全维度 | Lark CLI | opscli auth |
|----------|----------|-----------------|
| **密钥保护** | OS 级（Keychain/DPAPI）| 文件系统（权限 600） |
| **跨进程隔离** | ✅ OS 强制隔离 | ❌ 任何有文件权限的进程可读 |
| **加密算法** | AES-256-GCM | AES-256-GCM |
| **Nonce 策略** | 每次随机 | 每次随机 |
| **密钥与数据同目录** | ❌ 分离（Keychain 保护密钥） | ⚠️ 同目录（.key 与 credentials.bin 同级） |
| **生物识别支持** | ✅（macOS Touch ID）| ❌ |
| **跨平台一致性** | ✅（各平台原生方案）| ✅（Python keyring 库，已引入未用）|

> ⚠️ **当前项目的安全隐患**：密钥文件 `.key` 与凭证文件 `credentials.bin` 位于同一目录。若攻击者获得该目录的文件系统读取权，可同时拿到密钥和密文，从而完全解密凭证。Lark CLI 通过将加密密钥存入系统 Keychain 避免了这一问题。

> ✅ **值得关注**：当前项目 `pyproject.toml` 已经声明了 `keyring 25+` 依赖，说明最初设计时曾考虑使用系统 Keychain，但实际未集成。

## 五、并发安全机制

### 5.1 Lark CLI：双层锁机制

Lark CLI 针对多进程/多协程同时刷新 token 的场景实现了完整的并发保护：

```go
// internal/auth/uat_client.go

// 层1：进程内锁（防止同进程多 goroutine 竞争）
var refreshLocks sync.Map

func refreshWithLock(ctx context.Context, ...) (*StoredUAToken, error) {
    key := accountKey(opts.AppId, opts.UserOpenId)
    done := make(chan struct{})

    if existing, loaded := refreshLocks.LoadOrStore(key, done); loaded {
        ch := existing.(chan struct{})
        select {
        case <-ch:
            // 其他 goroutine 已完成刷新，直接读取结果
            return GetStoredToken(opts.AppId, opts.UserOpenId), nil
        case <-ctx.Done():
            return nil, ctx.Err()
        }
    }
    defer func() {
        refreshLocks.Delete(key)
        close(done)
    }()

    // 层2：跨进程锁（防止多个 CLI 进程竞争，使用 flock 文件锁）
    lockFile := filepath.Join(cacheDir, "refresh_"+key+".lock")
    fileLock := flock.New(lockFile)
    locked, err := fileLock.TryLockContext(ctx, 500*time.Millisecond)
    if locked {
        defer fileLock.Unlock()
    }

    // 双重检查：另一进程可能已完成刷新
    freshStored := GetStoredToken(opts.AppId, opts.UserOpenId)
    if freshStored != nil && TokenStatus(freshStored) == "valid" {
        return freshStored, nil  // 使用已刷新的结果，跳过重复请求
    }

    // 执行实际刷新请求
    return doRefreshToken(httpClient, opts, stored)
}
```

### 5.2 opscli auth：无并发保护

当前项目没有任何并发保护机制：

```python
# core/token_manager.py
def get_token(self, alias: str) -> str:
    # 无锁保护，多进程并发调用会导致重复请求后端
    data = self._store.load() or {}
    td = data.get("tokens", {}).get(sys["system_key"])
    if td and self._is_valid(td):
        return td["jwt"]
    return self._fetch_token(...)  # 多进程可能同时执行到这里
```

**潜在问题**：在 CI/CD 或脚本并发场景下，多个进程同时调用 `get_token()` 且 token 均处于需要刷新状态时，会向后端发起多次重复换取请求，不必要地消耗 session 资源。

| 并发场景 | Lark CLI | opscli auth |
|----------|----------|-----------------|
| 同进程多协程并发刷新 | ✅ sync.Map 锁 | ❌ 无保护 |
| 跨进程并发刷新 | ✅ flock 文件锁 | ❌ 无保护 |
| 双重检查（避免重复刷新）| ✅ 有 | ❌ 无 |

Lark CLI 区分两种身份：**User（用户身份）** 和 **Bot（机器人身份）**，并提供管理员级别的严格模式控制：

```go
type StrictMode string

const (
    StrictModeOff  StrictMode = "off"   // 允许所有身份
    StrictModeBot  StrictMode = "bot"   // 仅允许 Bot 身份
    StrictModeUser StrictMode = "user"  // 仅允许 User 身份
)

func (m StrictMode) AllowsIdentity(id Identity) bool {
    switch m {
    case StrictModeBot:
        return id.IsBot()
    case StrictModeUser:
        return id == AsUser
    default:
        return true
    }
}
```

**应用场景**：Bot 严格模式下，`auth login` 命令被阻止，且错误信息明确说明"This setting is managed by the administrator and must not be modified by AI agents"——专门针对 AI Agent 的防护设计。

**配置层级**：
- 全局严格模式：`MultiAppConfig.StrictMode`
- 应用级严格模式：`AppConfig.StrictMode`（可独立覆盖）

### 8.2 opscli auth：无身份控制

当前项目无 User/Bot 身份区分，所有调用均以同一用户 session 身份执行。

**建议 1：集成系统 Keychain 存储**

当前项目已引入 `keyring 25+` 依赖但未使用，可直接集成：

```python
# 改造 CredentialStore，优先使用系统 Keychain
import keyring

class CredentialStore:
    SERVICE_NAME = "opscli auth"

    def save_session(self, session_id: str, email: str, expires_at: str):
        data = json.dumps({
            "session_id": session_id,
            "email": email,
            "session_expires_at": expires_at,
        })
        try:
            keyring.set_password(self.SERVICE_NAME, "session", data)
        except keyring.errors.NoKeyringError:
            self._save_to_encrypted_file(data)  # fallback：现有加密文件方案

    def load(self) -> dict | None:
        try:
            raw = keyring.get_password(self.SERVICE_NAME, "session")
            if raw:
                return json.loads(raw)
        except keyring.errors.NoKeyringError:
            return self._load_from_encrypted_file()
        return None
```

**收益**：密钥由 OS 托管，解决密钥和密文同目录的安全隐患。

**建议 2：添加并发安全锁**

```python
import fcntl
import threading

_refresh_locks: dict[str, threading.Event] = {}
_locks_mutex = threading.Lock()

def get_token(self, alias: str) -> str:
    sys_config = self._registry.get(alias)
    lock_key = sys_config["system_key"]

    with _locks_mutex:
        if lock_key in _refresh_locks:
            event = _refresh_locks[lock_key]
        else:
            event = None

    if event:
        event.wait()  # 等待其他线程完成刷新
        # 读取已刷新的 Token
        data = self._store.load() or {}
        td = data.get("tokens", {}).get(lock_key)
        if td and self._is_valid(td):
            return td["jwt"]

    # 使用文件锁防止跨进程竞争
    lock_file = self._store.base_dir / f".lock_{lock_key}"
    with open(lock_file, "w") as f:
        try:
            fcntl.flock(f, fcntl.LOCK_EX | fcntl.LOCK_NB)
            return self._fetch_token(...)
        except BlockingIOError:
            # 另一进程正在刷新，短暂等待后重试
            time.sleep(0.5)
            return self.get_token(alias)
        finally:
            fcntl.flock(f, fcntl.LOCK_UN)
```

**建议 3：三态 Token 状态模型 + 缩短刷新阈值**

```python
# 当前：提前 30 分钟刷新（过于保守，导致频繁换取）
REFRESH_THRESHOLD = 1800  # 30 分钟

# 建议：参考 Lark CLI，提前 5 分钟刷新
REFRESH_THRESHOLD = 300   # 5 分钟

def token_status(self, token_data: dict) -> str:
    """返回 valid / needs_refresh / expired 三态"""
    exp = datetime.fromisoformat(token_data["expires_at"])
    now = datetime.now(timezone.utc)
    remaining = (exp - now).total_seconds()

    if remaining > REFRESH_THRESHOLD:
        return "valid"
    if remaining > 0:
        return "needs_refresh"  # 距过期 ≤5 分钟，触发刷新
    return "expired"            # 完全过期，需重新 Device Flow
```
