# 跨境电商运营官方平台数据来源核对

> 核对日期：2026-07-21
> 范围：Amazon、Walmart Marketplace、TikTok Shop、Shopify、Google Ads、Google Trends、Meta Marketing API，以及内部 ERP/WMS/财务/客服系统。
> 说明：本文只引用平台官方文档或平台维护的一手开发者资料。第三方市场情报工具不在本文的事实核对范围内。

## 1. 结论摘要

### 1.1 数据源应按可信等级分层

| 层级 | 数据来源 | 最适合回答的问题 | 不能替代的数据 |
|---|---|---|---|
| L1 经营事实 | 平台官方 API、平台报表 | 自有店铺实际订单、流量、广告、库存、结算、退货发生了什么 | 完整成本、跨平台统一库存、竞品真实销量 |
| L1 内部事实 | ERP、OMS、WMS、TMS、财务、客服系统 | 实际采购成本、货权库存、可售库存、履约节点、费用、利润、客户问题 | 公域市场需求、平台搜索和竞品表现 |
| L2 外部市场情报 | 第三方选品、关键词、价格历史和趋势数据 | 市场规模、竞品、关键词和机会判断 | 自有店铺真实订单、真实广告归因、真实利润 |

**建议**：指标库必须记录 `source_system`、`source_account`、`marketplace`、`data_scope`、`grain`、`timezone`、`currency`、`freshness` 和 `is_estimated`。平台官方事实与第三方估算不得在没有标记的情况下直接拼接。

### 1.2 官方 API 的共同边界

- **官方事实**：Amazon、Walmart、TikTok Shop、Shopify、Google Ads 和 Meta Marketing API 都以授权账号、店铺或业务资产为主要数据边界。
- **官方事实**：Google Trends 提供的是经过抽样、匿名化、聚合和归一化的搜索兴趣，不是绝对搜索量。
- **建议**：竞品销量、竞品真实转化率、竞品广告花费和竞品利润应标记为“第三方估算或不可得”，不要用自有账号 API 推断为官方事实。
- **建议**：ERP/WMS/财务系统应承担跨渠道统一主数据和最终利润口径，平台 API 不应直接成为企业级利润事实表。

## 4. 推荐的数据归属设计

### 4.1 主题域与主数据源

| 主题域 | 首选事实源 | 补充源 | 推荐主键/粒度 |
|---|---|---|---|
| 市场需求 | Google Trends、平台 Brand/Insights 数据、第三方市场情报 | 内部销量和搜索词 | `marketplace + country + keyword/category + date` |
| 商品与 Listing | PIM/ERP 主档 + 各平台 Catalog/Listing API | 第三方竞品商品 | `internal_sku + marketplace + listing_id/asin + snapshot_at` |
| 流量与转化 | 平台官方流量/分析报表 | 第一方埋点/CDP | `account + listing/product + date + traffic_scope` |
| 广告 | 各广告平台官方 API | 内部素材标签和商品利润 | `ad_account + campaign/ad_group/ad/target + date` |
| 订单 | 平台订单 API；OMS 作为跨渠道汇总 | ERP 发货和财务状态 | `channel_order_id + order_line_id` |
| 库存 | WMS/ERP 货权库存；平台库存作渠道快照 | 3PL/FBA/WFS/FBT | `warehouse + internal_sku + inventory_status + snapshot_at` |
| 物流 | WMS/TMS/承运商 | 平台 Fulfillment 状态 | `shipment/package/tracking_number + event_time` |
| 售后/VOC | CRM/工单 + 平台退货/反馈接口 | 第三方合规评论数据 | `case/return/review_topic + sku/asin + event_time` |
| 结算与利润 | 财务总账/成本系统 | 平台结算、广告费用 | `settlement/transaction/order_line + accounting_period` |

### 4.2 必须保留的口径字段

**建议**每张事实表至少保留：

- `source_system`、`source_endpoint`、`source_account_id`
- `marketplace`、`marketplace_country`、`seller_type`（SC/VC/DTC 等）
- `source_grain`、`business_date`、`source_timezone`、`extracted_at`
- `currency`、`exchange_rate_type`、`tax_included`
- `attribution_window`、`conversion_definition`、`traffic_scope`
- `is_official`、`is_estimated`、`is_personal_data`
- `data_freshness_sla`、`backfill_window`、`retention_policy`

## 5. 接入优先级建议

### P0：先建立自有经营事实底座

1. 各平台订单、商品、库存、结算与退货。
2. Amazon `GET_SALES_AND_TRAFFIC_REPORT`、Brand Analytics/SQP。
3. Amazon Ads、Google Ads、Meta Ads 的官方账户报表。
4. ERP SKU/成本、WMS 库存、财务费用和利润映射。

验收标准：能按 `marketplace + seller/account + internal_sku + date` 对齐销售、流量、广告、库存和利润，并保留平台原始口径。

### P1：补齐运营优化数据

1. Amazon Customer Feedback topics、退货原因和 Listing 问题。
2. Walmart Insights/Pricing Insights。
3. TikTok Shop Finance、Customer Service（若满足审批条件）和 Analytics scope。
4. Shopify DTC 客户、营销、Fulfillment 和 payout 数据。

### P2：再接外部市场情报

用第三方工具补充竞品、关键词、价格历史、其他平台商品和内容趋势，但必须保留 `is_estimated=true`，并用平台官方经营结果做事后验证。

## 6. 主要实施风险

- **权限不是接口存在即有数据**：Brand Registry、SP-API roles、广告账户授权、TikTok custom scope、Shopify protected data、Meta Advanced Access 都可能形成审批门槛。
- **历史窗口不同**：Shopify 订单默认 60 天；Amazon 报表和 Orders API 各有历史及单次请求限制；平台报表应尽早持续落库。
- **口径会回补**：广告归因、无效流量过滤、取消/退款会让历史指标变化，应支持滚动重拉和版本化快照。
- **隐私和受限数据**：买家地址、邮箱、聊天和订单数据需最小权限、加密、审计、保留期和删除流程。
- **异步与限流**：Amazon/Walmart 报表、Bulk/Feed、Shopify Bulk Operations 均需要任务状态机，不能按同步查询设计。
- **平台数据不是利润事实**：订单收入、广告归因收入、结算和财务确认是不同事件，必须由财务规则完成最终对账。
