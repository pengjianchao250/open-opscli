# 反馈每日治理与工单闭环调研

> 调研日期：2026-07-21

## 一、结论

`ops-feedback-query` 可以接入每日任务，但它目前只是**只读查询适配器**，不是完整的日报或工单系统。推荐保持其职责不变，在外层增加“每日反馈治理任务”：

```text
GitLab 定时流水线
  -> 分页查询反馈
  -> 批量读取详情
  -> 脱敏与规则化指纹
  -> 聚合、分级、责任域识别
  -> 更新或创建 GitLab Issue
  -> 生成脱敏日报
  -> 推送企业微信/飞书消息与文档链接
```

推荐采用三层载体：

1. **反馈库**：保留原始提交、执行上下文和用户反馈状态，是事实源。
2. **GitLab Issue**：承载需要研发处理的问题、负责人、讨论、修复和验收，不按每条反馈一对一建单。
3. **企业微信/飞书**：承载通知和日报入口，不作为唯一状态源。

内部工单只用于跨部门、权限审批、运营操作或有明确 SLA 的事项；代码缺陷优先进入当前项目的 GitLab Issue。

## 二、当前能力与缺口

### 2.1 已具备能力

`ops-feedback-query` 已支持：

- 按类型、严重度、状态、来源、系统、用户和时间范围查询反馈；
- 按 `created_at/updated_at/severity/failed_call_count/id` 排序；
- 单页最多查询 100 条；
- 一次批量读取最多 100 个反馈详情；
- 将结果限制写入 `output/feedback-query/`，该目录已被 Git 忽略；
- 通过独立 `X-Feedback-Api-Key` 查询，避免混用用户 JWT；
- 查询结果可能包含邮箱、路径、调用参数和执行上下文，Skill 已明确要求最小必要使用。

项目还已有企业微信群机器人发送实现，可复用其以下经验：

- Webhook 配置与消息正文分离；
- HTTP 200 后继续检查企业微信 `errcode`；
- 本地去重状态；
- 超时与失败结果结构化返回。

### 2.2 尚缺能力

当前 Skill 不具备：

- 定时调度；
- 自动翻页和完整时间窗口采集；
- 跨反馈聚合、错误指纹、趋势和 SLA 计算；
- 企业微信/飞书文档发布；
- GitLab Issue 创建、更新、关闭和负责人映射；
- 对反馈状态进行分诊、处理中、解决等写回；
- “反馈 UUID/问题指纹/GitLab Issue IID”之间的持久映射。

当前开放接口仅包含反馈列表和批量详情查询。虽然列表支持 `new/triaged/processing/resolved/rejected` 状态，但仓库内未发现状态更新入口，因此只创建 GitLab Issue 会形成“双状态源不一致”。正式闭环前，应补充服务端反馈分诊写回 API，或明确 GitLab 是唯一执行状态、反馈库只保留关联链接和最终结果。

### 2.3 必须先处理的密钥风险

当前 `opscli/skills/templates/ops-feedback-query/data/credentials.json`：

- 已被 Git 跟踪；
- 当前不是占位值；
- Git 历史中存在该文件的提交记录。

这意味着独立查询密钥已进入版本历史。实施每日任务前应立即：

1. 轮换现有 Feedback API Key；
2. 将仓库文件恢复为占位模板；
3. 将真实密钥保存为 GitLab 受保护、掩码的 File 类型 CI/CD 变量或密钥管理系统；
4. Job 运行时临时写入 Skill 自身 `data/credentials.json`，任务结束后删除，以继续满足当前“密钥只能从 Skill 自身凭据文件读取”的安全约束；
5. 评估是否清理 Git 历史，并检查该密钥是否有异常调用。

不能把企微 Webhook、飞书应用 Secret、GitLab Access Token 一并写入 Skill 目录或日报内容。

## 三、每日任务怎么做

### 3.1 调度选择

当前远端是内部 GitLab，仓库没有 `.gitlab-ci.yml`。推荐新增 GitLab Scheduled Pipeline，而不是依赖某位开发者电脑的 Windows 任务计划：

- 服务端稳定运行，不依赖个人在线；
- Cron、时区、手动补跑和任务历史由 GitLab 管理；
- 凭据可放在受保护 CI/CD 变量中；
- 可限制 Job 权限和网络出口。

建议每日 `09:15 Asia/Shanghai` 执行，避开整点和半点通知高峰。计划所有者离职、被禁用或权限变化时，GitLab Schedule 可能失效，应使用团队维护的机器人身份或建立所有者巡检。

如果 GitLab Runner 无法访问内网反馈接口或外部企微/飞书 API，再改用内网常驻 Runner、Kubernetes CronJob 或统一调度平台；本地 Windows 任务计划仅适合短期验证。

### 3.2 采集策略

每日任务不能只请求第一页。建议：

1. 保存上次成功运行的水位时间；
2. 本次查询使用“上次水位前移 5～10 分钟”作为起点，容忍延迟入库和时钟误差；
3. `feedback_type=all`，按 `created_at asc` 分页，直到返回不足 100 条；
4. 按 100 个 UUID 分批读取详情；
5. 以 `feedback_uuid` 去重；
6. 只有整条流水线成功后才推进水位；
7. 首次运行限制回溯天数，避免无边界读取全量数据。

原始详情不应默认上传为公开 CI Artifact。仅保留脱敏汇总；确需保留排障样本时，应使用受限 Artifact、短保留期并记录访问权限。

### 3.3 报告内容

日报建议只包含：

- 新增反馈总数及与前一日/近 7 日均值对比；
- 按严重度、反馈类型、来源、系统、Skill/命令、版本聚合；
- Critical/High 未解决项；
- Top 问题指纹：今日次数、累计次数、首次/最后出现时间、受影响版本；
- 新建、更新、解决的 GitLab Issue；
- 超过分诊或处理 SLA 的问题；
- 数据质量提示，例如缺少错误码、调用参数或修复建议。

不要在群消息或普通文档中放：用户邮箱、原始 payload、完整调用参数、Cookie/Token、个人文件路径和未经处理的异常上下文。

## 四、如何从反馈形成工单或 GitLab Issue

### 4.1 不建议“一条反馈一个 Issue”

主流错误平台先把事件聚合成问题，再让人处理问题。Sentry 默认按显式 fingerprint、堆栈、异常类型/值或规范化消息分组；Prometheus Alertmanager 也先做 grouping 和 deduplication，再路由通知。直接一对一建单会产生重复工单和通知风暴。

建议先生成稳定的问题指纹：

```text
fingerprint = hash(
  system_alias
  + skill_name/mcp_tool_name/command_name
  + 标准化错误码
  + 去除动态 ID、时间、路径、数字后的错误模板
  + 可用时的首个业务代码帧
)
```

AI 可以生成摘要、归因建议和合并建议，但**不应作为唯一去重键**；指纹和创建阈值应保持确定性、可回放。

### 4.2 建单规则

建议先以规则运行两周，再根据噪声校准：

| 条件 | 动作 |
|---|---|
| Critical、安全/密钥泄露、数据破坏风险 | 立即创建 Confidential Incident/Issue，并即时通知 |
| High 且首次出现 | 进入当日日报并人工确认 |
| High 在 24 小时内重复，或影响多个用户/版本 | 自动创建或更新 Issue |
| Medium 达到频次阈值，或连续多日出现 | 自动创建或更新 Issue |
| Low、UX、Docs、Feature | 进入周报或产品需求池，不默认创建 Bug Issue |
| 已解决指纹再次出现 | 重新打开 Issue，标记 regression |

不要仅按提交者选择的 severity 建单，还应综合：频次、受影响用户数、失败调用次数、持续时长、回归、数据/安全影响和是否存在绕过方案。

### 4.3 Issue 幂等与结构

GitLab Issues API 没有原生创建幂等键。建议：

- 标签：`source::ops-feedback`、`severity::*`、`area::*`；
- 标题保留简洁问题摘要；
- 描述中写入稳定隐藏标记：`ops-feedback-fingerprint:<hash>`；
- 创建前按标签与标记查询，客户端精确比对；
- 已存在则更新 `last_seen/count/affected_versions/样本 UUID`，不存在才创建；
- 单任务串行执行，避免“先查后建”并发产生重复；
- 保留反馈 UUID 样本，但不复制敏感详情。

Issue 正文建议固定为：

```markdown
## 问题摘要
## 影响范围与严重度依据
## 首次/最后出现时间与趋势
## 代表性反馈 UUID
## 可能根因（事实与推测分开）
## 建议修复与负责人
## 验收标准
## 关联反馈与回归记录
```

代码问题可依据 `skill_name/command_name/mcp_tool_name/system_alias` 映射到 GitLab 标签和负责人，后续可借鉴 CODEOWNERS。GitLab API 支持 assignee、labels、due date、confidential、issue/incident 类型及状态更新。

Scheduled Job 调用 Issues API 时不能使用 `CI_JOB_TOKEN`，因为其官方允许的 API 范围不包含 Issues。应使用最小权限、短有效期的 Project Access Token，并将其保存在受保护变量中。

### 4.4 内部工单和 GitLab Issue 的边界

| 场景 | 推荐载体 |
|---|---|
| opscli 代码缺陷、测试、发布修复 | GitLab Issue |
| 新功能、体验和文档需求 | GitLab Issue/Epic 或产品需求池 |
| 数据修复、权限开通、运营补录 | 内部工单 |
| 跨系统事故、有值班/SLA/复盘要求 | Incident，并关联 GitLab Issue |
| 每日趋势和管理摘要 | 飞书/企微文档 + 群机器人消息 |

如果内部工单系统已有组织 SLA、审批和统计要求，可由一个“主问题”同步生成内部工单，但必须指定唯一主状态源，避免 GitLab 和工单互相覆盖。

## 五、企业微信与飞书怎么接

### 5.1 企业微信群机器人

这是最小成本入口。官方机器人支持 text、Markdown、图片、图文、文件和模板卡片，通过 Webhook POST 推送；每个机器人最多 20 条/分钟。Webhook Key 是凭据，必须放在 CI Secret 中。

建议发送一条脱敏摘要：

```text
反馈日报 2026-07-21
新增 23，Critical 0，High 3
聚合问题 8：新增 2、持续 5、回归 1
自动更新 GitLab Issue 4 个
详情：<文档链接>
待处理：<GitLab Issue 列表链接>
```

群机器人只负责通知，不负责状态和数据存储。

### 5.2 企业微信文档

企业微信官方提供应用级“新建文档”API，可创建文档、表格、智能表格或智能文档，返回 URL 和仅创建时返回的 `docid`。它使用应用 `access_token`，不是群机器人 Webhook。

因此“发消息”和“写文档”是两套认证与权限：

- 机器人：适合发送摘要和链接；
- 自建应用：适合创建/维护文档，需要配置可调用应用、Token 管理和文档权限。

当前调研已确认文档创建接口；正式选型前还需对企业微信正文写入/更新接口做一个最小 POC。若只需日报，可先每日新建一份文档，避免复杂的并发编辑和历史追加。

### 5.3 飞书机器人与飞书文档

飞书自定义机器人支持文本、富文本和卡片；支持关键词、IP 白名单和签名校验。建议至少启用签名校验，必要时叠加 IP 白名单。单机器人限制为每秒 5 次、每分钟 100 次，单次请求体不超过 20 KB。

飞书新版文档 API 已明确支持：

1. 创建文档；
2. 通过 block children API 写入正文；
3. 通过 `client_token` 实现写入幂等；
4. 给用户或群授予 view/edit 权限。

但创建文档时不能直接写正文，需要“创建文档 -> 写入块 -> 授权”三步；应用和单文档编辑均有限流，应串行写入并重试退避。

如果企业内部同时使用企微和飞书，建议只选一个文档平台作为日报事实源，另一侧只发送同一链接，避免维护两份内容和权限。

## 六、市面上错误日志如何生成、收集和处理

成熟体系通常分为六层，而不是直接“日志转工单”：

### 6.1 生成与采集

- 应用输出结构化日志，错误 SDK 捕获异常、堆栈、版本和环境；
- OpenTelemetry 统一 `Timestamp/Severity/Body/Resource/Attributes`；
- 在日志中写入 `TraceId/SpanId`，把错误与一次请求链路关联；
- 对密钥、Cookie、邮箱和业务数据在采集端脱敏。

### 6.2 传输与存储

- Agent/Collector 批量发送并处理重试、背压和采样；
- 日志平台负责搜索与留存；Sentry 一类平台负责错误事件及 Issue 聚合；
- 日志、指标、Trace、用户反馈可以互相关联，但保留周期和访问权限不同。

### 6.3 聚合与降噪

- Sentry 按 fingerprint 将同类事件聚合成 Issue；
- Alertmanager 做分组、去重、路由、静默和抑制；
- 维护窗口静默、上游故障抑制下游告警，避免一场故障产生大量重复通知。

### 6.4 分级与分派

- 综合严重度、频次、影响用户、持续时间、回归和业务影响排序；
- 按服务、文件路径、模块、Tag 或 CODEOWNERS 自动分派；
- Critical 实时值班响应，普通问题进入分诊队列或日报。

### 6.5 处理闭环

```text
New -> Triaged/Acknowledged -> Processing -> Resolved
                                  -> Rejected/Archived
Resolved 后再次出现 -> Regressed/Reopened
```

处理项应有 Owner、SLA、根因、修复版本、验收证据和回归监控。通知系统只传递状态变化，不替代 Issue/Incident。

### 6.6 复盘与改进

- 观察 MTTA、MTTR、重复率、回归率、超 SLA 数和高噪声规则；
- 将高频问题转化为测试、告警规则、运行手册和产品改进；
- 定期归档无行动价值的问题，调整指纹和阈值。

## 七、建议落地顺序

### 阶段 0：先消除风险

- 轮换已进入 Git 历史的 Feedback API Key；
- 建立 CI Secret 和最小权限；
- 明确日报文档平台与责任人。

### 阶段 1：只做日报，不自动建单

- GitLab 每日定时任务；
- 完整分页、批量详情、脱敏聚合；
- 输出 Markdown/HTML；
- 推送一个企微或飞书机器人；
- 人工验证两周指纹和阈值。

### 阶段 2：半自动 Issue

- 日报列出“建议创建/合并的 Issue”；
- 人工确认后建单；
- 建立 fingerprint 与 issue_iid 映射；
- 加入负责人、标签和 SLA。

### 阶段 3：自动闭环

- Critical/重复 High 自动建单或更新；
- 修复后自动写回反馈状态；
- 回归自动重新打开；
- 实时严重告警 + 每日汇总；
- 周期复盘规则质量。

这种顺序比一开始让 AI 自动总结并大量创建 Issue 更稳妥：先获得真实噪声率和聚合准确率，再逐步放开自动化动作。
