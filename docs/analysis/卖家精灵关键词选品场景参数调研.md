## 三、校验契约

### 3.1 所有范围字段的共性规则

1. 最小值和最大值都应为可选字段，空值时不传，不得自动补 `0`。
2. 只传一侧时应允许查询。
3. 同时传入两侧时，本地必须校验“最小值 ≤ 最大值”，避免把明显无效请求提交到远端。
4. 整数字段拒绝小数和布尔值；小数字段接受整数或有限小数。
5. 页面百分比显示值与服务端是传 `30` 还是 `0.30` 必须以抓包请求为准，不在 payload builder 中提前换算。

### 3.2 已确认的专项规则

| 字段 | 规则 | 证据 |
| --- | --- | --- |
| `minWordCount` | `1—5` 的整数 | HTML `type=number`、`min=1`、`max=5` |
| `maxWordCount` | `1—9` 的整数 | HTML `type=number`、`min=1`、`max=9` |
| `minAvgRating` | `0—5` 的数值 | 页面业务规则；控件为文本框，没有原生 `min/max` |
| `maxAvgRating` | `0—5` 的数值 | 页面业务规则；控件为文本框，没有原生 `min/max` |

评分值的 `0—5` 约束不能依赖浏览器原生验证，MCP/CLI 和远端适配层都应有至少一层可测试的显式校验。

### 3.3 前端属性已观察但仍需业务验证的上限

页面在部分整数最大值控件上配置了较大上限，例如月搜索量 `100000000`、商品数/购买量/展示量/SPR/标题密度 `30000000`、增长值和评分数 `40000000`。这些更像前端防御性上限，未抓包验证前不建议将其作为公开 MCP 参数手册的业务边界。

## 六、后续 MCP 场景设计建议

### 6.1 场景定位

- 场景 ID：`keyword-research`
- 中文名称：关键词选品
- 核心目标：按需求、增长、竞争、转化、成本和市场周期筛选关键词市场。
- 与 `keyword-miner` 的边界：`keyword-miner` 从种子词扩词；`keyword-research` 在更大关键词市场中做条件筛选和机会评估。

### 6.2 公共参数建议

1. 继续使用项目公共字段 `site`、`period`、`page_size`，由场景 payload builder 映射到最终请求契约。
2. 字段主名优先与实际服务契约一致，页面字段只作别名，避免 Web 页面改名导致公共 MCP 契约漂移。
3. Skill 中只记录面向用户的中文名称、主参数、默认值、必要校验和典型工作流；内部参数留在 manifest 和 payload builder。
4. 对于只在 Web 页面出现、开放 API 未记录的字段，本次先按页面原值透传用于本地 MCP 验收；未完成单字段 A/B 的参数必须标注为待验证，正式发布前再确认筛选是否生效。
5. 返回数据应标记为第三方市场估算或外部情报，不与自有账号的第一方搜索、订单和广告数据混同。

## 八、当前结论

1. “关键词选品”已有清晰的独立场景语义，不应与 `keyword-miner` 合并为同一个原子场景。
2. 页面参数可作为 Web 适配证据，但公共 MCP 契约应优先对齐已验证的服务契约，不直接暴露全部 URL 字段。
3. 单词个数和评分值的规则已落实本地校验；其他百分比和布尔参数已按页面原值透传，但筛选效果仍需本地 MCP 单字段 A/B 验收。
4. 可参考开放 API 与 Web 页面在字段名、筛选广度和分页默认上存在差异，实现前必须选定主契约并保留可观测的字段映射。
5. open-opscli 已以当前 Web GET 页面作为 `keyword-research` 主契约，复用现有 SellerSprite 普通任务队列；本地 MCP 活体验收仍需确认账号权限、远端页面响应和部署版本。
6. 默认任务只取第一页 100 条；官方异步导出的 2,000 条基线只用于工作簿结构和格式对齐，不代表本地查询需要自动汇总到 2,000 条。
