## 3. 本次新确认的 Quota 上线阻塞

### 3.1 撤销专属账号迁移后遗留失效导入

[迁移 quota.py:870](D:/Gitlab/open-opscli-worktrees/sqlite-to-mysql-migration/opscli/mcp/quota.py:870) 导入 `get_account_binding_store`，但 [account_bindings.py:88](D:/Gitlab/open-opscli-worktrees/sqlite-to-mysql-migration/opscli/seller_sprite/services/account_bindings.py:88) 只有原有 `SellerSpriteAccountBindingStore`，已不存在该工厂。

本次通过实际 `QuotaLimiter.before_call("seller_sprite_run")`、默认 `_resolve_service_access` 和注入测试邮箱复现：`binding_factory_exists=false`、`allowed=false`、`error_code=MCP_QUOTA_ACCESS_UNAVAILABLE`。未连接数据库、读取真实绑定或调用业务工具。公共账号用户也会经过此检查，并非只影响已绑定用户。应恢复原 Store 调用并增加默认组装路径回归，再上线。

### 3.2 最新策略未进入旧快照与迁移分支

主仓库新增 `ext_xydc_openapi_call`，默认归属 `xiyou` 服务、日额度 10，迁移标记为 `20260921_xydc_openapi_call`：[主仓库 quota.py:500](D:/Gitlab/open-opscli/opscli/mcp/quota.py:500)。9 月 20 日快照只有七条策略，不含该入口。

MySQL Store 的 `get_policy` 对不存在的策略返回 `None`，Limiter 对无策略入口放行：[MySQL Store:34](D:/Gitlab/open-opscli-worktrees/sqlite-to-mysql-migration/opscli/mcp/quota_mysql.py:34)、[主仓库 Limiter:670](D:/Gitlab/open-opscli/opscli/mcp/quota.py:670)。合入最新业务后如果直接沿用七条旧策略，新入口可能不受额度控制。需核对目标策略并幂等补新增策略，保留生产人工设置，不应覆盖为代码默认值。

### 3.3 schema 校验没有接入默认运行路径

`MySqlQuotaStore.check_schema()` 存在，但默认工厂只创建实例，没有调用它，仓库内相关调用仅见测试显式执行。当前建表 SQL 的 readiness 也只统计表数量，不比对全部列和索引。

证据：[schema 检查:194](D:/Gitlab/open-opscli-worktrees/sqlite-to-mysql-migration/opscli/mcp/quota_mysql.py:194)、[工厂:825](D:/Gitlab/open-opscli-worktrees/sqlite-to-mysql-migration/opscli/mcp/quota.py:825)、[DDL readiness:78](D:/Gitlab/open-opscli-worktrees/sqlite-to-mysql-migration/scripts/create_sqlite_runtime_mysql_tables_v1.sql:78)。旧文档中“schema 不匹配即失败关闭”尚未由默认启动链路完整保证，应补启动预检以及策略完整性核对。

### 3.4 导入成功不等于持续一致，重跑可能覆盖新计数

导入工具支持只读源、完整性检查、默认拒绝非空目标、事务写入和 SHA-256；输出只有源计数与 `target_counts_before`，没有导入后的逐键或聚合对账：[sqlite_runtime.py:248](D:/Gitlab/open-opscli-worktrees/sqlite-to-mysql-migration/opscli/migrations/sqlite_runtime.py:248)。

`--allow-nonempty` 使用 `calls = VALUES(calls)`、`failures = VALUES(failures)` 覆盖旧键：[sqlite_runtime.py:144](D:/Gitlab/open-opscli-worktrees/sqlite-to-mysql-migration/opscli/migrations/sqlite_runtime.py:144)。若目标已经产生真实新调用，重导旧快照会倒退计数。应先确认唯一权威写入源、切换窗口和差异策略，不能把该参数当作通用增量同步。

## 5. 迁移优先级

### P0：Quota 收尾

修复失效账号存储导入；同步主仓库最新策略；增加默认接入、MySQL schema/策略预检；补真实数据库失败退款、并发扣减、跨日及源目标对账；确认 MCP/Collector 各进程连接同一目标并完成切换观察。Monitor 的 quota 读取仍固定为 SQLite，必须同时适配数据源及 `day` 到 `quota_day` 的日期映射，否则可能继续读到旧值。此前测试成功不等于这些验收已经完成。

### P1：SellerSprite 任务队列及运行状态

这是下一项最有价值的 SQLite 迁移：领取任务、账号互斥、恢复和状态读取均依赖本地队列，多实例共享需要统一持久状态。

现有七张队列业务表草案需要对照最新主仓库重新核对；主仓库已新增 `seller_sprite_product_checkpoints`：[task_queue_store.py:2663](D:/Gitlab/open-opscli/opscli/seller_sprite/services/task_queue_store.py:2663)。它不在旧 DDL 中，不能把旧 SQL 的“表已建好”当作最新队列合同完整。

应一起处理任务、MCP 归属、成功事件、账号事件、隔离、进度、心跳及分页 checkpoint。最新任务领取 SQL 直接引用 checkpoint 表，遗漏该表会阻断通用领取。Monitor 对业务库的后端读取也属于切换依赖；它直接写入的是自己的状态库，不是 quota，不需要为此重做展示。细节见[队列与监控证据笔记](D:/Gitlab/open-opscli-worktrees/sqlite-to-mysql-migration/docs/analysis/SQLite迁移复核-队列与监控证据-2026-09-30.md)。

### P2：Collector Monitor 自有运行状态按部署需求决定

`collector_monitor/state.sqlite3` 是单独存储入口：[config.py:72](D:/Gitlab/open-opscli/opscli/collector_monitor/config.py:72)、[state.py:394](D:/Gitlab/open-opscli/opscli/collector_monitor/state.py:394)。应纳入数据库清单，按多实例与告警连续性需求评估，优先级低于业务队列。没有收到该生产库快照，不能认定其生产行数或已启用。

其三张表为 `incidents`、`consecutive_observations`、`scan_state`，承载告警生命周期、连续观测和扫描状态，不能按页面缓存直接丢弃。另外，browser worker 在未注入 listener 且 output_dir 非默认时会写 `.seller_sprite_session_events.sqlite3`，复用队列中的账号事件表。应确认生产是否启用该路径，再决定统一写入或历史归档；当前只有代码可达证据，没有生产活跃证据。默认 scheduler 已注入 listener，不会因此每次另建事件库。

### 保留并治理：在线采集 Outbox

`collection_storage/mcp.sqlite3`、`collection_storage/collector.sqlite3` 按 runtime 分库：[config.py:118](D:/Gitlab/open-opscli/opscli/shared/collection_storage/config.py:118)。MCP 和 Collector 启动时分别组装该在线能力，并非 Sorftime 离线链路。

启用沉淀后，Runtime 在 MySQL 就绪前先建立本地 Outbox；MySQL 恢复后再处理待办：[runtime.py:70](D:/Gitlab/open-opscli/opscli/shared/collection_storage/runtime.py:70)、[runtime.py:213](D:/Gitlab/open-opscli/opscli/shared/collection_storage/runtime.py:213)。若把它也搬到同一 MySQL，会改变数据库故障时的缓冲保障。因此建议先保留 SQLite，不以“去掉全部 SQLite”为目标。

建议另做清理功能：只处理已 completed 且 MySQL 持久化已核实、超过保留期的记录；保留 pending/processing/retrying/failed 的诊断与补偿能力。尤其要保留 `collection_outbox_meta` 的 `live_cutover_at` 和 `reconcile_cursor:*`，并验证删除完成行后的幂等去重及重复提交行为。[outbox.py:21](D:/Gitlab/open-opscli/opscli/shared/collection_storage/outbox.py:21)、[runtime.py:270](D:/Gitlab/open-opscli/opscli/shared/collection_storage/runtime.py:270)。
