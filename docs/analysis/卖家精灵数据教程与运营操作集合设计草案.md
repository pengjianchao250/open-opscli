# “如何使用卖家精灵数据”教程与运营操作集合设计草案

> 状态：第一版轻量案例方案已确定，本文已按当前实现修订
> 初稿：2026-09-01
> 修订：2026-09-03，代码基线 `e2cbfbb5`

## 1. 目标

当前 `opscli seller-sprite` 已解决“如何采集卖家精灵数据”，下一阶段应解决“拿到数据后应该做什么”。

建议交付物不是 16 篇孤立的工具说明，而是一套按运营问题组织的轻量案例：

1. 用户先选择要解决的问题，如找竞品、优化 Listing、建立关键词库、判断市场机会。
2. 系统说明需要哪些输入、依次查询哪些数据、重点看哪些字段。
3. 多个场景交叉验证，不用单一指标直接输出确定性结论。
4. 输出可执行的运营动作和证据表，同时披露数据范围、更新时间、分页与采样限制。

## 2. 当前资料基础

### 2.1 当前 opscli

- 当前 MCP 已注册 16 个卖家精灵场景，页面说明、温馨提示和官方教程已记录在 [`卖家精灵场景官方说明调研.md`](卖家精灵场景官方说明调研.md)。
- `ops-seller-sprite` 已解决自然语言到场景参数、任务状态、JSON/XLSX 导出和额度管理，但主要职责仍是采集与导出。
- `ops-amazon-listing-analysis` 已建立“问题定位—证据—优化方向—修改示例”的保守输出边界，但当前采集命令仍是早期的单一 Collector 口径，尚未充分利用现有 16 个场景。
- `ops-amazon-stylesnap` 提供一种低频、人工监督的视觉相似竞品发现方法，可补充关键词和类目无法发现的外观同质竞品。
- `ops-amazon-product-data` 可补充 Amazon 搜索结果、商品页、Offer、Buy Box 等结构化页面快照。
- `ops-amazon-rufus` 可从买家问答视角验证商品表达、适用场景、疑虑与信息缺口。

### 2.2 Sorftime 研究仓库

`D:\Gitlab\amazon-sorftime-research-MCP-skill` 当前已是远端 `main` 最新版本。仓库已有三层方法资产：

1. 综合工作流：竞品、关键词、流量、评论、市场、Listing、广告和定价分析。
2. 战术策略卡：新品爆发、低评分热销、标题密度缺口、自然流量验证、变体缺口等。
3. Listing Builder：先建立关键词库、问题库和证据库，再生成并校验文案。

这些方法可以作为业务问题和输出结构的参考，但不能直接照搬：

- 部分工具名和参数属于旧版卖家精灵 MCP，与当前 Collector 场景不一致。
- 一些战术卡使用固定阈值，阈值只适合作为示例或可配置条件，不应写成跨类目通用规律。
- 部分分析依赖评论、商品详情、Keepa、Google Trends、广告后台等卖家精灵 16 个场景以外的数据。
- 当前 MCP 的若干场景只返回第一页最多 100 条，教程必须披露，不能把结果描述为全量。

### 2.3 行业通用方案复核

行业资料的完整记录见 [`卖家精灵数据行业通用方案调研.md`](卖家精灵数据行业通用方案调研.md)。Amazon、Walmart、eBay、Etsy、TikTok Shop 及 Helium 10、Jungle Scout、DataHawk、Keepa 等平台虽然产品名称不同，但可归纳出同一条运营闭环：

1. 发现：用站内搜索行为和第三方市场数据发现需求、关键词、商品与竞品候选。
2. 验证：用用途、规格、价格、流量关系、口碑和趋势排除伪相关候选。
3. 构建：把关键词、买家问题、产品证据和视觉信息映射到 Listing 与广告结构。
4. 上线：一次只改变可解释的一组变量，并记录版本、日期与目标指标。
5. 测量：用 Seller Central、Brand Analytics、Amazon Ads、订单、退货和客服数据确认真实结果。
6. 迭代：保留有效动作，回滚或修正无效动作，更新竞品集和关键词资产。

卖家精灵在这条闭环中的定位应是“外部市场与竞争情报层”，而不是订单、广告、库存和财务事实的替代品：

| 数据层 | 主要来源 | 适合回答 | 边界 |
| --- | --- | --- | --- |
| 外部市场与竞争情报 | 卖家精灵、Helium 10、Jungle Scout、DataHawk、Keepa | 市场候选、竞品、关键词、趋势、价格与流量线索 | 多为估算、采样或公开页面信号 |
| 平台一方经营结果 | Seller Central、Brand Analytics、Amazon Ads、订单与库存报表 | 自己实际获得多少曝光、点击、订单、退货和利润 | 通常不能看到竞品未公开的真实经营结果 |
| 企业内部证据 | 成本、供应链、质检、认证、客服和退货原因 | 商品是否可做、卖点能否兑现、利润和风险 | 需要企业自己的数据治理与权限 |
| 开源与社区 | GitHub、Stack Overflow、V2EX | API 接入、自动化实现、工程陷阱和用户困惑 | 不能作为平台规则、指标定义或效果承诺 |

因此，教程中的每条重要结论都应区分“数据直接事实”“分析推断”“建议动作”，并说明来源、时间、站点、Parent/Child 层级、是否估算及验证方式。

## 3. 教程的信息架构

建议提供三个入口，而不是让用户先认识工具名。

### 3.1 按运营目标进入

| 运营目标 | 核心问题 | 首选卖家精灵场景 | 补充数据 |
| --- | --- | --- | --- |
| 找竞品 | 谁是真正可比的竞争对手？ | `keyword-reverse`、关键词模式的 `competitor-lookup`、`traffic-source`、`association-traffic` | Amazon 搜索结果、StyleSnap |
| Listing 优化 | 缺什么词、表达、图片或证据？ | `keyword-reverse`、`traffic-extend`、`keyword-comparison`、`keyword-miner`、`keyword-conversion-rate` | 商品页、评论、Rufus、StyleSnap |
| 建关键词库 | 哪些词应进入标题、五点、ST 或广告？ | `keyword-miner`、`traffic-extend`、`keyword-reverse`、`aba-reverse` | 广告搜索词报告、评论高频词 |
| 流量差距 | 为什么竞品有流量而我没有？ | `keyword-comparison`、`traffic-source`、`keyword-reverse` | 广告后台真实曝光与转化 |
| 广告选词与出价 | 哪些词值得测试，预算多少？ | `keyword-conversion-rate`、`real-time-bidding`、`aba-reverse` | 亚马逊广告报告 |
| 选产品 | 哪些具体产品值得继续研究？ | `product-research`、`competitor-lookup` | 成本、合规、供应链数据 |
| 选市场 | 市场容量、集中度和进入门槛如何？ | `market-research`、`keyword-research`、`aba-research` | Google Trends、利润测算 |
| 产品改良 | 买家不满意什么，怎么形成差异化？ | `listing-analysis` 中的口碑模块 | 评论全量样本、退货与客服数据 |
| 视觉竞品 | 哪些产品外观或使用场景最相似？ | `competitor-lookup` 大图模式 | `ops-amazon-stylesnap` |
| 商标初筛 | 品牌名称是否存在注册风险线索？ | `branddb` | 对应商标局官网、专业意见 |

`competitor-lookup` 按 ASIN 查询时只是筛选指定商品，并可能返回父子体或变体。它不能单独用于“从一个 ASIN 自动找竞品”；应先反查流量词，再用关键词搜索、关联关系和视觉搜索建立候选。

### 3.2 按手头输入进入

| 用户手头已有 | 可启动的流程 |
| --- | --- |
| 自己的 ASIN | Listing 诊断、流量差距、关键词覆盖、竞品发现 |
| 一个竞品 ASIN | 竞品拆解、反查关键词、关联竞品、视觉竞品 |
| 一组竞品 ASIN | 多竞品词库、流量词对比、共性词与差异词 |
| 一个种子关键词 | 扩词、搜索结果竞品、关键词市场分析 |
| 一个类目 | 市场分析、产品筛选、头部样本构建 |
| 品牌或卖家名称 | 品牌产品线、店铺结构、市场标杆研究 |
| 一张产品主图 | StyleSnap 视觉相似竞品搜索 |

### 3.3 按运营阶段进入

1. 市场发现：`keyword-research` / `aba-research` / `market-research`。
2. 产品立项：`product-research` / `competitor-lookup` / `branddb`。
3. 产品定义：竞品评论、变体、价格带、视觉与关联流量。
4. 上架准备：关键词库、Listing 表达、图片模块、合规证据。
5. 冷启动：出单词、转化率、实时竞价和广告测试词。
6. 稳定运营：流量差距、排名与词库变化、竞品与价格监控。

## 4. 每个运营案例的统一格式

每个教程案例建议固定包含以下字段：

```text
名称：例如“给现有 Listing 找流量缺口”
解决的问题：一句业务问题
适用条件：什么时候用
不适用条件：什么时候不能得出结论
输入：ASIN、关键词、站点、周期等
数据步骤：按顺序列场景和参数
关键字段：只列真正用于判断的字段
判断规则：如何交叉验证，不把示例阈值写成铁律
输出：表格、分类、优先级和下一步动作
证据要求：每条结论对应哪份数据
限制：数据范围、更新时间、分页、样本、估算或登录要求
```

案例可以提供两种阅读深度，但共用同一份 Markdown：

- 教学部分：解释为什么、怎么看和常见误区，适合新人学习。
- 执行部分：列出最少输入、现有 Skill、正式命令、输出和限制，供 Agent 直接调用既有能力。

第一版不为案例增加独立 JSON/YAML 协议、规划器或新的执行 CLI。

## 5. 核心案例一：如何找竞品

### 5.1 竞品不应只有一种

| 类型 | 定义 | 发现方式 |
| --- | --- | --- |
| 直接竞品 | 同类产品、相似价格、相似人群和用途 | 关键词搜索、类目、`competitor-lookup` |
| 流量竞品 | 与我争夺同一批搜索词 | `traffic-source`、`keyword-comparison` |
| 关联竞品 | 在商品详情页和推荐位与我争夺曝光 | `association-traffic` |
| 视觉竞品 | 外观、款式、颜色或构图相似 | StyleSnap、大图模式 |
| 标杆竞品 | 销量、排名、品牌或 Listing 表达值得学习 | 品牌/卖家查询、销量与趋势筛选 |
| 替代品 | 不同形态但解决相同任务 | 关键词、评论、Rufus 问题和跨类目搜索 |

### 5.2 推荐步骤

1. 建立候选池：按核心关键词使用 `competitor-lookup`；必要时按品牌、卖家或已知 ASIN 补充。
2. 补充流量竞品：用 `traffic-source` 查询核心关键词近 30 天进入搜索结果前 3 页的产品。
3. 补充关联竞品：对自己的 ASIN 或核心竞品使用 `association-traffic`。
4. 补充视觉竞品：对主图使用 `ops-amazon-stylesnap`，人工监督并串行执行。
5. 验证可比性：比较类目、价格带、产品功能、目标人群、评分数、销量、变体和上架时间。
6. 验证真实竞争关系：使用 `traffic-extend` 和 `keyword-comparison` 判断关键词重合与流量差距。
7. 分层保留：通常保留 3–5 个核心直接竞品，再保留少量标杆、视觉、关联或替代竞品；不把所有搜索结果都当直接竞品。

### 5.3 输出建议

输出“竞品关系表”，而不只是一列 ASIN：

| ASIN | 竞品类型 | 入选依据 | 共同关键词 | 价格带 | 销量/趋势 | 主要差异 | 用途 |
| --- | --- | --- | --- | --- | --- | --- | --- |

`用途` 可标记为：关键词学习、图片学习、定价参照、功能对比、广告对标、评论痛点或变体设计。

## 6. 核心案例二：Listing 优化应该查什么数据

Listing 优化建议拆成六个证据层，而不是直接让 AI 重写文案。

### 6.1 商品表达基线

- 当前标题、五点、描述、A+、图片、价格、评分、变体和类目。
- 来源可使用 Amazon 商品结构化数据；只有用户明确要求卖家精灵 AI 全景分析时才提交 `listing-analysis`。

### 6.2 关键词覆盖

1. `keyword-reverse`：现有 ASIN 近 30 天实际获得曝光的搜索流量词。
2. `traffic-extend`：3–10 个核心竞品的合并去重词库。
3. `keyword-miner`：从核心词扩展长尾、属性、场景和问题词。
4. `aba-reverse`：补充进入 ABA 点击前三的出单词线索。

输出应区分：已有核心词、竞品共同词、自己的缺失词、长尾机会词、品牌词、不相关词。

### 6.3 流量差距

- `keyword-comparison` 比较自己和竞品的默认流量占比视图。
- `traffic-source` 查看自然、广告和推荐来源结构。
- 当前 `keyword-comparison` Collector 首期只获取默认流量占比第一页最多 100 条，不能宣称已获取官网所有对比维度。

### 6.4 转化与广告价值

- `keyword-conversion-rate`：搜索/点击转化率、CPA、ACOS 和产品均价等市场参照。
- `real-time-bidding`：SP/SB/SBV 建议竞价，作为出价和成本估算参考，不等同于实际 CPC。
- 自有广告搜索词报告才是实际点击、订单、CPC 和 ACOS 的最终验证来源。

### 6.5 买家需求与证据

- 评论、退货原因、客服记录和 QA 用于识别购买动机、疑虑和痛点。
- Rufus 可补充“买家会问什么、页面能否回答”的验证视角。
- 供应链规格、测试、认证和实测结果是卖点证据；第三方估算数据不能替代产品证据。

### 6.6 图片与视觉

- StyleSnap 用于寻找视觉同质竞品，不用于批量抓取。
- 对比主图信息密度、使用场景、尺寸表达、结构细节和信任证明。
- 图片优化结论必须和关键词、评论痛点及产品证据对应，不能只评价“好不好看”。

### 6.7 Listing 优化最终输出

建议固定输出“问题—证据—动作”矩阵：

| 问题 | 数据证据 | 影响环节 | 优先级 | 优化方向 | 验证指标 |
| --- | --- | --- | --- | --- | --- |

文案生成是最后一步。在证据不足时，只给修改方向和示例，不生成声称可直接上线的完整文案。

## 8. 实现形态建议

第一版采用轻量 Skill，不再增加独立配方引擎：

1. 数据能力继续由 `ops-seller-sprite`、Amazon 商品数据、Rufus、StyleSnap、Keepa 和 Google Trends 等现有 Skill 提供。
2. `ops-commerce-playbooks/SKILL.md` 只负责识别运营问题，并把 Agent 路由到对应案例。
3. 每个案例使用一份 Markdown，描述适用条件、输入、数据步骤、判断、输出和限制。
4. Agent 读取案例后，直接调用各数据源已有的 MCP Tool 或正式 `opscli` 命令，不经过新的规划器或中间协议。
5. 最终报告统一区分事实、判断、动作和验证，并保留来源、站点、周期、Parent/Child 层级与数据限制。

当前没有非 Agent 调用方、跨会话状态恢复或强确定性工作流需求，因此不增加 Python 规划模块、JSON/YAML 配方模型、数据库表或新的 `commerce-playbook` CLI。

只有后续出现稳定的非 Agent API 调用、需要断点恢复的长流程，或必须由程序强制执行的审批和状态机时，才重新评估结构化工作流引擎。

## 9. 第一版边界与后续方向

第一版已经确定：

1. 以 Agent 可读取的 Markdown 案例为交付物，同时保留足够的教学解释。
2. 聚焦 Amazon 运营问题；Keepa 和 Google Trends 仅在案例确有需要时作为补充证据。
3. Listing 优化只提供诊断、修改方向和验证动作，不自动修改或发布 Listing。
4. 不把第三方估算当作自有广告、订单、退货、库存或利润事实。
5. 不把教程示例阈值写成跨类目强制规则。

后续优先根据真实运营反馈增加案例，再评估是否接入自有广告、销售、退货和客服数据。TikTok、1688 等跨平台验证应在 Amazon 案例稳定后独立设计，不提前放大第一版范围。
