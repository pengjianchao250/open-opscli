# 用户站点上传与构建发布方案调研

> 调研日期：2026-08-20
> 场景：类似 ChatGPT Sites/Artifacts 的 AI 站点与应用生成系统；用户可上传 HTML、JSON、SQLite、Python 等文件作为项目上下文，平台负责生成、版本、预览、发布与回滚。

## 一、结论先行

推荐把系统设计成“**上传入口与发布内核分离**”，而不是“FTP 目录即生产目录”，也不必把每个 ZIP 自动转换为 Git 提交。

```text
AI Chat/Agent / ZIP / CLI / Git Webhook / 可选 FTP 适配器
                    │
                    ▼
       上传 API（鉴权、配额、分片/断点续传）
                    │
                    ▼
   隔离区对象存储（原始 ZIP，不可变，按哈希寻址）
                    │
                    ▼
       校验与扫描（格式、路径、病毒、资源上限）
                    │
                    ▼
     构建队列 → 临时沙箱 → 静态制品 / OCI 镜像
                    │
                    ▼
      Release 记录 → 原子切换流量 → CDN / 容器
                    │
                    └── 运行数据：独立卷 / 数据库，不随发布覆盖
```

核心判断如下：

对 AI 站点生成产品，首先要分开 **Project 工作区、WorkspaceVersion 生成版本、PreviewSession 预览环境、Deployment 生产快照**。ChatGPT Sites、Replit、Bolt、Lovable 和 v0 的公开产品行为都体现了这种分层；Git 是可选协作/可移植通道，不是每次对话修改的必经步骤。

1. **默认入口用 ZIP 直传对象存储，不用 FTP。** 上传 API 更容易实现鉴权、配额、校验、审计、断点续传和状态机；FTP 可以保留为企业客户的兼容入口，但进入系统后仍应转换成同一个 `SourceRevision`，不能直接覆盖线上目录。
2. **Git 是技术用户的源码协作入口，不是上传系统的内部必选步骤。** Git 很适合 HTML、Python、配置和数据库迁移脚本；不适合不断变化的 SQLite 二进制、用户上传附件和构建制品。ZIP 自动入 Git 会制造无意义提交、大文件历史与二进制冲突，却没有提高发布可靠性。
3. **每次发布生成不可变制品。** 静态站点生成一个内容哈希目录/对象清单，Python 站点生成 OCI 镜像；发布只是把域名或路由从旧 `release_id` 原子指向新 `release_id`。Netlify 官方特别把这种整批切换与 FTP 逐文件覆盖作了对比，前者不会出现 HTML 已更新而 CSS/JS 尚未更新的中间状态。[Netlify：Atomic deploys][netlify-atomic]
4. **SQLite 必须区分“种子数据”和“运行数据”。** 只读/初始化用 `.sqlite` 可以随源码上传；线上可写 SQLite 必须放独立持久卷并备份，不能打进镜像或随回滚覆盖。SQLite 官方建议数据库与应用位于同一设备，并明确指出网络文件系统的锁与同步问题可能导致损坏；多实例或多写者应改 PostgreSQL/MySQL。[SQLite 适用场景][sqlite-when] [SQLite 网络文件系统注意事项][sqlite-network]
5. **允许 Python 就等于允许执行用户代码。** 这不是普通文件托管功能，必须有独立构建 worker、运行时沙箱、CPU/内存/磁盘/进程/时间/网络限制，且不得挂载 Docker Socket 或宿主敏感目录。普通容器是基线；真正的多租户不可信代码宜使用 gVisor、Kata 或 Firecracker 一类更强隔离。[Docker 安全][docker-security] [gVisor][gvisor] [Firecracker][firecracker]

## 二、不要在两个错误方案中二选一

### 2.1 “文件/压缩包传 FTP，再打包构建”

FTP/SFTP 只能解决文件传输，不能天然解决以下问题：

- 一次上传由哪些文件组成、是否已完整到达；
- 用户、项目、版本和构建之间的关系；
- 同名文件覆盖、并发上传与幂等；
- 恶意压缩包、配额、病毒扫描和审批；
- 构建日志、状态、取消、重试、回滚；
- 原子发布和审计追溯。

如果直接把 FTP 目录作为构建源或线上目录，还会出现半上传状态被读取、旧文件残留、断线后目录混合等问题。Netlify 官方文档指出，FTP/SSH/Rsync/S3 式逐文件推送可能让部分新文件先上线，连接中断后站点会长期处于不一致状态；其解决方式是先完成一个新 deploy，再整体切换。[Netlify：Atomic deploys][netlify-atomic]

**定位建议：** FTP/SFTP 只作为可选的输入适配器。服务监听“上传完成标记文件”或用户点击“提交版本”后，把目录快照成 ZIP/TAR、计算 SHA-256、写入对象存储，然后进入统一流水线。不要让 FTP 拥有生产目录写权限。

### 2.2 “ZIP 解压，自动上传 Git，再由 Git 构建”

这个方案可行，但只有在用户确实需要源码浏览、diff、分支、PR 和协作时才值得作为默认路径。

| 维度 | ZIP 直传对象存储 | ZIP 自动转 Git | 用户连接自己的 Git |
|---|---|---|---|
| 普通用户操作 | 最简单 | 简单 | 较复杂 |
| 版本与回滚 | 平台版本表 + 不可变对象 | Git commit + release | Git commit + release |
| 文本 diff / PR | 无或需额外实现 | 有 | 最完整 |
| 二进制/大文件 | 合适 | 历史膨胀 | 仍不合适 |
| SQLite 运行数据 | 不应随包发布 | 更不应提交 | 更不应提交 |
| 实现复杂度 | 低 | 中，需管理仓库和身份 | 中，需 OAuth/Webhook |
| 推荐定位 | 默认上传路径 | 合规/审计可选层 | 技术用户主路径 |

更合理的统一模型是：

- ZIP 上传产生 `source_revision(type=upload, object_key, sha256)`；
- Git push 产生 `source_revision(type=git, repo, commit_sha)`；
- 两者进入同一个 build/release 状态机；
- 若产品以后确实需要在线代码浏览，可把 ZIP 镜像到系统管理的 Git 仓库，但 Git commit 只是派生索引，原始上传对象和 `source_revision_id` 仍是审计源。

## 三、市场方案及其真实边界

### 3.1 AI 原生站点/应用生成产品

先区分两类产品：Artifact/Canvas 型强调在对话旁快速生成、预览、复制和分享，不一定是通用 PaaS；Project/App Builder 型则把项目作为长期工作区，保存代码和生成历史，提供开发预览，并把某个版本显式发布到稳定 URL。以下只记录厂商公开文档能确认的产品行为；未公开的内部 Git、对象存储、容器和沙箱实现均不作断言。

| 产品 | 官方公开工作流 | 对本系统的启示 |
|---|---|---|
| ChatGPT Sites | Site 是可重新打开、继续修改、配置和分享的持久托管输出。官方把发布拆成 **Save a version** 与 **Deploy a version** 两阶段；本地项目的保存版本会关联构建所用 Git commit。持久结构化数据和文件分别使用 D1、R2 绑定。[OpenAI Sites][openai-sites] | 最接近目标：Project、Version、Deployment、Data Binding 必须是不同对象；Git commit 可作为版本来源之一，但不是 Web 端生成项目的前提。 |
| ChatGPT 文件/HTML 预览 | 官方文档说明生成的 HTML 可在桌面应用中以交互预览打开，并可在渲染结果和 HTML 源码之间切换；这是文件审阅能力，不等同于公开托管。[OpenAI 文件预览][openai-artifacts] | “生成后立即预览”应先落为受限预览会话，不能把预览 URL 当生产发布。 |
| Claude Artifacts | Artifact 在对话之外的独立窗口展示可继续修改的独立内容；发布/分享时需确认具体 artifact version。个人计划可通过链接公开，组织计划可限组织内分享；复制代码后创建的是独立版本。[Claude Artifacts][claude-artifacts] [发布与分享][claude-artifacts-publish] | Artifact 是轻量、对话驱动的版本对象；“复制/Remix”应创建新 lineage，不能修改来源项目。官方未公开其底层容器/仓库实现。 |
| Replit Agent / Apps | Agent 从自然语言建立项目、创建应用、检查并修复，直到部署。Checkpoint 捕获项目文件、对话上下文、环境配置和 Agent memory，并可选择恢复数据库；每个 checkpoint 对应 Git commit。Publishing 单独管理域名、访问者、生产数据库、监控、安全和机器配置。[Replit Agent][replit-agent] [Checkpoints][replit-checkpoints] [Publishing][replit-publishing] | AI 产品的版本比源码 commit 更丰富，应关联 prompt/任务、构建配置和数据快照；数据恢复必须是显式可选动作。 |
| Bolt | 官方项目生命周期是设计/计划、生成、迭代、部署，再继续迭代。Version History 自动保存，可预览并恢复旧版本；GitHub 用于高级协作、分支和外部部署。发布后，编辑不会自动上线，需显式 Update；恢复项目版本不会恢复 Bolt/Supabase 数据库。[Bolt 生命周期][bolt-lifecycle] [版本历史][bolt-history] [发布][bolt-publish] [Git 定位][bolt-git] | 内建版本历史服务普通用户，Git 服务专业协作；草稿与线上快照分离；代码和数据库回滚分离。 |
| Lovable | Project 包含 Chat、实时 Preview、Code、自动 Version History 和 Settings。Preview 是工作期间启动的临时云环境，已发布应用是只有显式 Publish 才改变的快照；但 Preview 与发布应用共享同一后端和数据。[Lovable Project][lovable-project] [Preview][lovable-preview] [History][lovable-history] [Publish][lovable-publish] | 可借鉴“临时预览 + 稳定发布快照”，但共享数据库意味着预览操作仍可能影响生产数据；本系统应默认隔离 preview/prod 数据或明确提示风险。 |
| v0 | Chat 可一键发布到 Vercel；一个 Project 有一个稳定生产 URL，每次 Publish Changes 创建新 deployment 替换当前生产版本。官方 API 还支持直接从 ZIP 创建 chat，再访问预览和部署，无需先入 Git。[v0 Deployments][v0-deployments] [ZIP 创建 Chat][v0-zip] | AI 会话/生成版本不应直接等于生产；Project 维持稳定地址，Deployment 是可替换、可回退的快照。 |

OpenAI 官方站点用例同样把“从 repo/截图/设计生成或修改应用”“本地构建检查”“默认部署 preview”“用户明确要求才上 production”串成一条链路。[OpenAI：部署应用或网站][openai-deploy-usecase] 目标系统的核心因此不是 ZIP，而是：

```text
Project（长期上下文、文件、数据绑定、对话）
  → Generation / Edit（一次 AI 修改任务）
  → WorkspaceVersion（自动保存，可预览、可恢复）
  → PreviewSession（临时运行环境，可分享、可过期）
  → ReleaseCandidate（构建与检查通过）
  → Deployment（显式发布到稳定 URL）
```

### 3.2 托管静态/前端平台

| 产品 | 输入方式 | 构建与版本方式 | Python / SQLite 边界 | 可借鉴点 |
|---|---|---|---|---|
| Netlify | Git 持续部署、CLI 手动部署、拖放目录、API 文件摘要或 ZIP | 每次创建完整 deploy，完成后原子切换；支持 Deploy Preview | 适合静态/前端和平台函数，不是常驻 Python + 本地可写 SQLite 主机 | 同时服务普通上传用户和 Git 用户；deploy 是一等实体，不是目录覆盖。[创建部署][netlify-create] |
| Vercel | Git 集成、CLI、预构建输出部署 | Git commit 对应 deployment；也可将本地 `vercel build` 结果用 `--prebuilt` 上传 | Python 以 Functions runtime 运行，不等价于任意常驻进程；本地文件系统不应作为持久数据库 | 源码构建与预构建制品是两条入口，但统一为 deployment。[Git 部署][vercel-git] [预构建部署][vercel-prebuilt] |
| Cloudflare Pages | Git 集成，或 Direct Upload（Wrangler / 拖放 ZIP 或目录） | 每次上传产生新 deployment，可发生产或预览 | 拖放方式不能编译 `functions`；Pages Functions 是 Workers 运行模型，不是传统 Python 容器 | Direct Upload 与 Git 是项目创建时的两种路径；CLI 比网页拖放能力更完整。[Direct Upload][cf-direct] |
| GitHub Pages | Git 仓库分支/Actions artifact | 从仓库中的 HTML/CSS/JS 构建并发布 | 只提供静态站点托管，不能运行 Python 或可写 SQLite | 适合把“站点源码协作”和静态发布绑定。[GitHub Pages][github-pages] |
| GitLab Pages | Git 仓库 + GitLab CI/CD，发布目录通常为 `public` | Pipeline 产出 Pages deployment，可设置过期 | 官方明确不支持 PHP/ASP 等动态服务端处理；Python 只能用于构建静态结果 | 自建 GitLab 时可复用权限、CI、制品和 Pages，但不是动态应用 PaaS。[GitLab Pages][gitlab-pages] |

这些产品共同说明：**ZIP/目录直传和 Git 并不冲突，它们是不同用户的入口；真正统一的是 deployment/release 模型。**

### 3.3 可自建 PaaS / 容器平台

| 产品 | 官方模式 | 适合本场景的程度 |
|---|---|---|
| Coolify | 从源码用 build pack 生成 Docker 镜像，或部署预构建镜像；应用最终都运行在容器中；可配置专用 build server，将构建与生产服务器分离。[Coolify Applications][coolify-apps] | 适合快速验证 Git/Python 容器部署和管理后台；若面向互不信任的外部用户，仍需在其前面补上传审查、更强沙箱和租户安全控制。 |
| Dokku | 典型入口是 `git push`；默认 Heroku buildpack，也支持 Dockerfile 和现有 Docker image。[Dokku 部署][dokku-deploy] | 适合小团队、可信开发者和单机 PaaS，不适合直接把公网用户任意上传当作安全边界。 |
| CapRover | CLI 部署、网页上传 TAR、Git Webhook 自动部署；官方把网页 TAR 上传定位为通常仅用于测试；镜像版本可一键回滚，但环境变量和持久目录不会回滚。[CapRover 部署方式][caprover-deploy] | 很接近需要的产品流程，可参考其入口与镜像回滚语义；仍需自建上传隔离、审核和租户配额。 |
| Portainer | 可通过网页编辑 Compose、上传 Compose 文件、Git 仓库或模板部署 stack；Git 模式会克隆整个仓库。[Portainer Stack][portainer-stack] | 更像容器运维控制台，不是面向普通用户的站点产品；可作为内部运维层，不宜直接暴露给租户。 |
| Cloud Native Buildpacks | 生命周期执行 analyze/detect/restore/build/export 等阶段，把源码转换为 OCI 镜像。[CNB Lifecycle][cnb-lifecycle] | 可作为 Python 等受支持语言的标准构建内核，避免为每个框架手写 Dockerfile；仍需在沙箱中执行。 |

**选型判断：** Coolify/CapRover 可以缩短内部 MVP，但“让外部用户上传并执行 Python”已经跨入多租户代码执行平台。不能因为底层用了 Docker，就默认获得了 Vercel/Heroku 等公有 PaaS 的安全等级。

## 四、按站点类型拆成三条产品通道

### 4.1 A 类：纯静态站点

允许 HTML、CSS、JS、图片和只读 JSON。流程如下：

1. 用户上传 ZIP/目录到隔离区对象存储；
2. 校验后安全解包；
3. 可选执行平台内置、固定版本的静态构建器；
4. 输出按内容哈希存储，部署到对象存储/CDN；
5. 域名原子指向新 release。

这是最适合作为一期的范围。即使不执行服务端代码，用户 HTML/JS 仍是不可信主动内容，应使用独立站点域名，避免与管理后台共享 Cookie、Service Worker 作用域和 CSP。GitLab Pages 官方专门提示共享子域 Cookie 风险，并提供 unique domains 规避。[GitLab Pages 安全说明][gitlab-pages]

### 4.2 B 类：受控 Python 模板

平台只支持明确约定，例如：

- `requirements.txt` / `pyproject.toml`；
- Flask、FastAPI、Django 等有限框架；
- 固定启动约定和 Python 版本；
- 禁止自定义 Dockerfile、特权参数、宿主挂载；
- 构建时默认无生产密钥，外网访问使用白名单或依赖代理。

使用 Buildpacks/Nixpacks 或平台维护的 Dockerfile 生成 OCI 镜像。这样仍然需要强隔离，但攻击面明显小于允许用户提交任意 Dockerfile 和 Compose。

### 4.3 C 类：高级容器应用

允许 Dockerfile/Compose 相当于允许用户定义构建命令、基础镜像、网络访问和运行拓扑，只应面向经过审核的团队或专属租户。它需要：镜像扫描、签名/来源策略、独立 build node、网络策略、秘密管理、运行时准入控制以及更强的容器沙箱。

## 五、SQLite、JSON 与上传文件怎么管理

### 5.1 SQLite

| 类型 | 是否随源码上传 | 是否进 Git | 发布时处理 |
|---|---|---|---|
| 初始化/演示/只读数据库 | 可以 | 小且稳定时可选，更推荐 SQL dump/迁移 | 复制进制品，运行时只读 |
| Schema / migration | 应该 | 应该 | 在受控迁移阶段执行 |
| 线上可写 SQLite | 不应作为新版本源码 | 不应 | 挂载独立本地持久卷，发布不覆盖 |
| 多实例共享数据 | 不适合 SQLite 文件 | 不适用 | 改用 PostgreSQL/MySQL 或专门数据库服务 |

SQLite 官方说明其同一数据库文件任一时刻只能有一个 writer；如果数据库与应用被网络隔开，或需要很多并发写者，应选择 client/server 数据库。[SQLite 适用场景][sqlite-when] 对网络文件系统，SQLite 还明确警告锁和 `fsync` 语义因实现而异，错误可能导致数据库损坏。[SQLite 网络文件系统注意事项][sqlite-network]

回滚时只回滚代码/镜像，**不自动回滚 SQLite 数据**。CapRover 的一键回滚同样只恢复镜像，不恢复环境变量和持久目录。[CapRover 部署方式][caprover-deploy] 数据变更需用向前兼容迁移；需要数据回退时，走单独、显式的快照恢复流程。

### 5.2 JSON 与附件

- 小型、人工维护的配置 JSON：随源码版本化；
- 构建时生成的 JSON：属于制品，不回写源码；
- 在线业务数据 JSON：进入数据库或对象存储，不通过重新发布更新；
- 图片/附件：对象存储，数据库仅保存对象 key、哈希、大小、MIME 和所有者；
- 对象存储开启版本控制和生命周期规则。S3 Versioning 的设计即是在同一 key 下保留多个对象版本，用于恢复意外覆盖或删除。[S3 Versioning][s3-versioning]

## 六、平台数据模型与状态机

不要用“仓库目录是否存在”表达业务状态。建议至少有以下实体：

| 实体 | 关键字段 | 作用 |
|---|---|---|
| `Project` | `id, owner_id, type, quota_policy` | 用户站点 |
| `Conversation/Task` | `id, project_id, prompt, input_refs, status` | 一次 AI 生成/修改任务及其输入上下文 |
| `SourceRevision` | `id, source_type, object_key/repo, commit_sha, sha256` | 一次不可变源码输入 |
| `WorkspaceVersion` | `id, project_id, parent_id, task_id, source_ref, manifest_digest` | 自动保存的完整项目版本，可形成版本树 |
| `PreviewSession` | `id, version_id, url, status, expires_at, runtime_policy` | 与生产分离、可回收的交互预览 |
| `Build` | `id, version_id, status, builder, log_key, started_at` | 可重试的构建执行 |
| `Artifact` | `id, build_id, type, digest, registry/object_key` | 静态制品或 OCI 镜像 |
| `Release` | `id, project_id, artifact_id, environment, status` | 某环境的发布记录 |
| `Route` | `domain, active_release_id` | 原子切流指针 |
| `DataBinding` | `project_id, volume/database/bucket` | 与代码发布独立的数据资源 |

状态可采用：

```text
UPLOADING → QUARANTINED → VALIDATING → READY → QUEUED
    → BUILDING → BUILT → DEPLOYING → ACTIVE
                         └→ FAILED
ACTIVE → SUPERSEDED；旧 Release 仍保留，可再次激活
```

每个阶段都应使用稳定 ID 和幂等键。相同 `project_id + manifest_digest + build_config_hash` 可复用成功制品，但**不同租户的构建缓存默认隔离**，避免缓存投毒和数据泄露。AI 每次修改先生成新的 `WorkspaceVersion`，预览和构建都引用确定版本，不能直接读取仍在变化的共享目录。

## 七、上传、解包与执行安全

OWASP 对上传服务的基线建议包括扩展名白名单、不能信任 `Content-Type`、随机化存储名、大小限制、授权、存到不同主机或 Web Root 外、杀毒/沙箱和最小文件权限；还明确列出 ZIP bomb、覆盖文件和客户端主动内容等威胁。[OWASP 文件上传][owasp-upload]

对 ZIP/TAR 还必须检查：

- 解压后的规范化路径必须仍在临时根目录内，拒绝 `../` 和绝对路径；
- 拒绝符号链接、硬链接、设备文件、命名管道和异常权限位；
- 限制压缩包大小、解压总大小、文件数、单文件大小、目录深度和压缩比；
- 文件名统一 Unicode/大小写规则，拒绝重复规范化路径；
- 解包在一次性、无宿主挂载、低权限沙箱中完成；
- 静态文件发布前设置准确 MIME、`nosniff`，站点与平台控制台分域。

Zip Slip 的典型成因就是归档成员使用 `../../` 逃出目标目录，进而覆盖可执行或配置文件；该问题不仅影响 ZIP，也影响 TAR/JAR/CPIO 等归档格式。[Snyk Zip Slip 研究][zip-slip]

Python 构建和运行至少应执行：

- 非 root 用户、只读根文件系统、临时目录限额；
- drop Linux capabilities，启用 seccomp/AppArmor/SELinux；
- CPU、内存、磁盘、PID、运行时间和日志大小限制；
- build/runtime 网络分离，默认禁止访问云元数据地址和内网；
- 不向不可信构建注入部署密钥，不挂载 Docker Socket；
- 每次构建使用干净 worker，结束后销毁；
- 多租户外部用户优先 gVisor/Kata/Firecracker 等更强边界。

预览页面本身也要隔离。v0 的公开接入指南把生成代码明确视为不可信代码，要求 iframe 使用不同 registrable domain 的隔离 origin，不能只使用主站的普通子域，并过滤 Cookie、Authorization 与 Set-Cookie。[v0 预览隔离][v0-preview] 这比仅设置 iframe `sandbox` 更完整，适合作为本系统预览网关的基线。

Docker 官方说明 namespaces 和 cgroups 分别提供进程隔离与资源限制，但也强调 Docker daemon 的高权限攻击面、应只允许可信用户控制，并建议最小化 capabilities。[Docker 安全][docker-security] gVisor 在容器与宿主内核间增加用户态应用内核；Firecracker 则以 microVM 为多租户容器/函数提供虚拟机边界。[gVisor][gvisor] [Firecracker][firecracker]

## 八、构建队列与发布/回滚

### 8.1 构建队列

建议每个 build 都是一次性任务：取不可变源码、产生不可变制品、写日志后退出。Kubernetes Job 的官方语义就是运行至完成的一次性任务，并支持失败重试、完成计数和并行度，适合作为规模化后的 worker 调度基础。[Kubernetes Job][k8s-job]

一期即应具备：

- 全局与租户并发上限；
- 排队超时、构建超时、取消和有限重试；
- 日志流式查看与对象存储归档；
- webhook/上传事件去重；
- 失败不影响当前线上 release；
- build worker 与 runtime node 分离。

Coolify 也明确建议资源密集的镜像构建可放到专用 build server，而不是生产服务器。[Coolify Applications][coolify-apps]

### 8.2 不可变发布

静态站点：

```text
artifacts/{project_id}/{sha256}/...
routes/{domain} -> release_id -> artifact_prefix
```

动态站点：

```text
registry/site/{project_id}@sha256:<digest>
release_id -> image_digest + config_version + data_bindings
```

先部署到预览 URL，健康检查通过后再原子更新 `active_release_id`。回滚同样只更新这个指针或重新部署旧 image digest，不重新构建旧源码。数据卷、环境变量、域名和证书应各自版本化/审计，不能假设代码回滚等于完整系统回滚。

## 九、GitHub 与 Stack Overflow 社区经验

以下属于社区经验，不作为产品能力的一手证据，但与官方资料方向一致：

- Stack Overflow 高票讨论建议把数据库 schema/data dump 作为可 diff 文本纳入版本控制，而不是直接跟踪运行中的数据库文件。[数据库纳入 Git][so-database-git]
- SQLite schema 版本讨论指出，直接提交 SQLite 二进制会降低 diff 可读性；可使用 `.schema`/`.dump` 生成文本，尤其适合只读、单一更新源的数据集。[SQLite schema 版本控制][so-sqlite-schema]
- Docker 中 SQLite 持久化问题的社区答案把数据库目录挂载到宿主/volume，印证了“数据独立于镜像和容器生命周期”的做法。[Docker 持久化 SQLite][so-sqlite-volume]
- 关于在 Docker 运行不可信代码的讨论认为，仅以 non-root 运行只是增加一道提权障碍，仍应结合 user namespace、网络隔离和 SELinux/AppArmor；这与 Docker 官方对 daemon、高权限和 capabilities 的警告一致。[Docker 不可信代码讨论][so-untrusted-docker]
- Coolify 曾报告“首次贡献者的预览构建被意外触发”的问题，随后以阻止 fork PR 的修复关闭；这类真实问题说明来自 fork/PR/上传的构建不能自动获得生产秘密或可信网络权限。[Coolify issue #10342][coolify-issue]
- Portainer 官方文档链接到其 Git submodule 支持讨论，反映“从 Git 部署”还有 clone 深度、子模块、凭据和仓库大小等实现细节，不能仅等同于一次 `git clone`。[Portainer discussion #9767][portainer-submodules]

## 十、推荐落地路线

### 一期：AI 静态站点生成与发布系统

1. 创建持久 `Project`，让对话、附件、生成任务和数据绑定归属同一项目；
2. 支持从提示词生成或用预签名 URL 把 ZIP 直传 S3/MinIO；
3. 每次 AI 修改产生新的 `WorkspaceVersion`，ZIP 则同时保留不可覆盖的 `SourceRevision`；
4. 队列触发安全校验/解包/受控生成，不执行用户自定义构建命令；
5. 在独立域名的一次性沙箱中生成 `PreviewSession`，允许审阅后再发布；
6. 输出不可变静态制品到对象存储/CDN，提供版本历史、显式发布和一键回滚；
7. SQLite 仅允许作为只读种子文件；每站预览域与控制台、生产域完全隔离。

这一期不需要自建 Git 服务，也不需要 FTP。MinIO + PostgreSQL + 队列 + 静态文件网关/CDN 即可形成可演进内核。

### 二期：Git 与受控 Python

1. 接入 GitHub/GitLab/Gitea OAuth 与 webhook；
2. ZIP 和 Git 共用 `SourceRevision → Build → Artifact → Release`；
3. 引入 Buildpacks/Nixpacks，只支持有限 Python 模板；
4. 独立 build node，镜像仓库，容器运行平台；
5. 可写 SQLite 使用每项目单机持久卷、备份和单副本约束；需要扩容时迁移 PostgreSQL。

### 三期：完整多租户 PaaS

1. 支持审核后的 Dockerfile/Compose；
2. 使用 Kubernetes Jobs/专用调度器管理构建；
3. 引入 gVisor/Kata/Firecracker、网络策略、镜像签名与准入；
4. 增加组织、角色、配额、计费、审计、域名证书和数据服务；
5. FTP/SFTP 只在客户确有遗留集成需求时增加为 ingestion adapter。

## 十一、最终建议

面向类似 ChatGPT Sites/Artifacts 的产品，最佳起点不是 FTP，也不是强制 Git，而是：

> **持久 Project + 自动 WorkspaceVersion + 隔离 PreviewSession + 显式 Deployment；ZIP 与 Git 只是项目的两种输入。**

底层仍采用“原始输入进对象存储、生成版本不可变、构建与预览进沙箱、发布原子切换”的内核。Git 作为技术用户入口后加；FTP 作为遗留兼容后加；Python 作为高风险能力分层开放；SQLite 运行数据永远与源码和 release 分离。这样一期能以较小复杂度上线 AI 静态站点生成，后期再演进成可协作、容器化、多租户的应用生成/PaaS 系统。
