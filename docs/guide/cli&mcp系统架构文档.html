项目总览

理解 opscli 的定位、技术栈与设计哲学，是看懂后续所有模块的前提。

opscli 的本质是一个多模块可扩展的运营能力网关。它本身不直接持有业务数据，而是统一封装"认证 → 取数/采集 → 结果产出"的完整链路，并把每一项能力同时投射到两个消费端：

$

入口 opscli，基于 Typer 构建命令树。面向运营同事手动执行，以及 Shell 脚本/CI 自动化调用。默认输出 JSON，便于脚本消费。

{ }
MCP 形态

入口 opscli-mcp，基于 FastMCP 把同样的能力暴露为 MCP Tools。面向 Claude / ChatGPT 等 AI Agent，支持 stdio 与远程 HTTP/SSE 部署。

01

整体架构

两个入口、一套内核、统一凭证——这是理解 opscli 的关键心智模型。

无论是 CLI 命令还是 MCP Tool，最终都收敛到同一套业务管理器（Manager），再经由统一的 AuthClient 与凭证存储访问后端。这种"双前端、单内核"的设计，保证了能力一致、凭证统一、维护成本最低。

▲ 双前端单内核：CLI 与 MCP 收敛到同一业务内核，共享 AuthClient 与凭证存储
关键洞察：新增一个模块时，只需在 cli.py 追加一行 add_typer，并在 mcp/server.py 调用一次 register()，业务逻辑写在 services/ 即可被两端复用。这是模块化扩展的核心契约（铁律 1）。

03

auth · 认证授权内核

整个工具集的安全地基：OAuth2 设备流登录、多系统 JWT 管理、双层凭证存储、双层并发锁。

登录：OAuth2 Device Flow（RFC 8628）

CLI 无法承载浏览器登录页，因此采用设备授权流：CLI 拿设备码 → 用户在浏览器确认 → CLI 轮询换取 session。MCP 模式下，轮询节奏交给 AI Agent 用 poll_once() 单次查询控制。

sequenceDiagram autonumber participant U as 用户 participant C as opscli CLI participant O as OPS 后端 participant B as 浏览器 C->>O: POST /v1/cli/device/code O-->>C: device_code + user_code + verification_url C->>U: 显示验证 URL 与验证码 U->>B: 打开 URL 输入 user_code 确认授权 loop 每 interval 秒轮询(最长 5 分钟) C->>O: GET /v1/cli/device/poll?device_code=... O-->>C: status: pending end O-->>C: status: authorized + session_id + expires_at C->>C: CredentialStore.save_session() 持久化 Note over C: 切换账号时自动清空旧 JWT
▲ Device Flow 时序：授权成功后落地 session，登录态切换会清空旧系统 Token
状态机分支：poll_once() 返回 5 种状态——authorized（成功落库）/ pending（继续轮询）/ expired（设备码超时，不可重试）/ denied（用户拒绝）/ error（含 retryable 标志，区分网络超时与服务不可达）。

Token 三态生命周期

每个系统的 JWT 都有三种状态，由 REFRESH_THRESHOLD = 300s（提前 5 分钟刷新）与过期时间共同决定。MAX_JWT_TTL = 86400s 防止后端返回异常超长 TTL（铁律 7）。

双层并发锁（铁律 6）

多个 CLI 进程、多个线程可能同时发现 Token 过期而并发去换取，造成对后端的重复请求。TokenManager.get_token() 用双层锁 + 双重检查解决：

LAYER 1
threading.Lock

进程内线程锁，按 system_key 隔离。防止同进程多线程并发换取。进锁后先做一次"是否已有效"的双重检查。

LAYER 2
fcntl.flock()

跨进程文件锁 .lock_<system_key>。防止多个 CLI 进程并发换取。Windows 无 fcntl 时自动跳过。进锁后再次双重检查。

# 层1：进程内线程锁，防止同进程多线程并发重复换取
with thread_lock:
    td = data.get("tokens", {}).get(system_key)
    if td and self._is_valid(td): return td["jwt"]  # 双重检查
    # 层2：跨进程文件锁，防止多个 CLI 进程并发重复换取
    with open(lock_path, "w") as lf:
        fcntl.flock(lf, fcntl.LOCK_EX)
        td = ...  # 再次双重检查：其他进程可能已完成刷新
        if td and self._is_valid(td): return td["jwt"]
        return self._fetch_token(system_key, url, endpoint)

05

mcp · 无状态 MCP 服务

把 opscli 能力暴露给 AI Agent。核心是"服务器不存凭证"的无状态设计与按 API Key 隔离的多用户安全。

MCP Server 基于 FastMCP，不保存任何用户 OAuth 凭证：所有认证信息由调用方（AI Agent）传入 session_id/jwt。这从根本上规避了远程共享部署时的"用户 session 串用"风险。

四种传输协议

stdio
stdio（默认）

标准输入输出，本地 AI 工具集成。无需 API Key。

sse
sse

GET /sse 事件流 + POST /messages/。兼容 Cursor、Claude Desktop。

http
http

Streamable HTTP，统一走 POST /mcp。ChatGPT / OpenAI Apps SDK 推荐。

both
both（推荐远程）

同时暴露 /sse 与 /mcp，链式生命周期合并到一个 Starlette 应用。

三个精巧的工程设计

① 遥测代理

_TelemetryMcpProxy 拦截 mcp.tool() 装饰器，注册时自动包裹遥测——零侵入，无需改任何 tools/ 代码。

② contextvar 双读

SSE 模式下 contextvar 传播链复杂易丢失。context.py 优先读自定义 mcp_request_ctx，降级读 MCP 框架的 request_ctx scope。

③ 客户端识别

从 MCP initialize 握手读 clientInfo.name，识别是哪个 AI 工具在调用，用于按 Agent 隔离与统计。

开发铁律精选

23 条铁律是 opscli 长期可维护的护栏。以下为架构相关的核心条目。

铁律 1 · 模块接入

新模块只在 cli.py 追加一行 add_typer，配置必须用 CONFIG_DIR，禁止硬编码路径。

铁律 2 · 导入方向

config.py 只依赖标准库，绝不反向导入子模块，避免循环导入。

铁律 3 · 双 SDK 导入

顶层 re-export 与子模块直导两种 AuthClient 导入方式必须同时可用。

铁律 5 · Keychain 服务名

opscli-auth 不可改，否则全部用户凭证失效需重登。

铁律 6 · 双层并发锁

线程锁 + 文件锁不可删减任意一层。

铁律 7 · Token 常量

REFRESH_THRESHOLD=300s / MAX_JWT_TTL=86400s 调整需评估影响。

铁律 8 · 测试隔离

测试用 base_dir=tmp_path 跳过 Keychain，用 respx mock 网络。

铁律 9 · 统一凭证

CLI 与 MCP 共用 CredentialStore，禁止 MCP 引入独立明文存储。

铁律 10 · 内置系统

ops/polaris 受保护不可删除。

铁律 11 · Skill 不直连

所有远端动作必须经 opscli 命令转发。

铁律 13 · ops- 前缀

所有内置 Skill 命名必须以 ops- 开头。

铁律 17/23 · 中文注释 & GBK

代码必须中文注释；终端输出字符必须 GBK 兼容（Windows 安全）。

这些铁律有效的标志：diff 中不必要的减少、因过度复杂导致的重写减少、澄清问题在实现之前而非犯错之后。
