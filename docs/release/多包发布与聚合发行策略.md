# opscli 多包发布与聚合发行策略

> 适用场景：`opscli` 从当前单包发布模式，演进为 `core + 多模块包 + 聚合包` 的发布体系后，统一定义构建、上传、版本、发布顺序与责任边界。
>
> 文档状态：发布策略提案
> 创建时间：2026-04-23

---

## 1. 文档目标

本文档回答五个问题：

1. 后续拆包后，是统一打包上传，还是每个包独立上传
2. `opscli`、`opscli-core`、`opscli-<module>` 各自扮演什么角色
3. 多个包发布时，推荐的上传顺序是什么
4. 版本号应该如何治理，哪些需要联动，哪些可以独立
5. CI / 发布责任如何划分给平台团队和模块团队

一句话结论：

后续应采用“**每个包独立构建、独立上传、独立版本管理**”的发布模式，同时保留一个 `opscli` 聚合包作为默认安装入口。

---

## 2. 当前模式与未来模式

### 2.1 当前模式

当前仓库仍是单包发布：

- 包名：`opscli`
- 构建产物：一个 wheel + 一个 sdist
- 上传目标：PyPI / TestPyPI / 私有 PyPI

这一模式适用于当前 `auth / query / skills` 仍处于同一包内的阶段。

### 2.2 未来模式

未来拆包后，推荐采用如下发布物结构：

```text
opscli-core
opscli-auth
opscli-query
opscli-skills
opscli-deploy
opscli-notify
opscli
```

其中：

- `opscli-core`：最小内核包
- `opscli-<module>`：独立模块包
- `opscli`：默认聚合发行包

注意：

`opscli` 也是一个独立上传的包，但它不再等价于“所有实现都在这个包里”。

---

## 3. 为什么不是“统一打包一次上传”

不推荐未来继续沿用“把所有模块合成一个大包一起上传”的原因如下：

1. 某个模块改动会迫使整个产品一起发版
2. 不同团队无法独立控制发布时间
3. 一个冷门模块故障会拖累整套发行
4. 安装体积会越来越大
5. 无法真正支持按需安装
6. 回滚粒度过粗

所以，未来的正确方向不是“统一打包上传”，而是：

- 统一规范
- 分别构建
- 分别上传
- 由聚合包统一默认安装体验

---

## 4. 发布物角色定义

### 4.1 `opscli-core`

职责：

- 提供 CLI 容器
- 提供插件发现与注册机制
- 提供公共配置、输出、异常、版本、兼容校验
- 提供公共 SDK 接口层

发布特点：

- 是所有模块共同依赖的基础包
- 版本治理需要更严格
- 破坏性变更影响面最大

### 4.2 `opscli-<module>`

职责：

- 承载单个业务模块的 CLI 命令与业务实现
- 通过 `entry_points` 接入 `opscli`

发布特点：

- 独立构建、独立上传
- 可由不同团队独立维护
- 与 `opscli-core` 保持兼容约束

### 4.3 `aukeys-opscli`

职责：

- 作为默认安装入口
- 依赖 `opscli-core` 和一组默认模块

发布特点：

- 仍然要独立构建、独立上传
- 自身可以很轻，主要承担依赖聚合作用
- 用户安装体验保持 `pip install aukeys-opscli`

---

## 5. 推荐发布模式

### 5.1 构建粒度

推荐每个包单独构建：

```text
opscli-core     -> dist/opscli_core-*.whl
opscli-auth     -> dist/opscli_auth-*.whl
opscli-query    -> dist/opscli_query-*.whl
opscli-skills   -> dist/opscli_skills-*.whl
aukeys-opscli   -> dist/aukeys_opscli-*.whl
```

### 5.2 上传粒度

推荐每个包单独上传到仓库：

```bash
twine upload dist/opscli_core-*.whl
twine upload dist/opscli_auth-*.whl
twine upload dist/opscli_query-*.whl
twine upload dist/opscli_skills-*.whl
twine upload dist/aukeys_opscli-*.whl
```

### 5.3 安装体验

对用户暴露的体验仍然可以是：

```bash
pip install aukeys-opscli
```

其实际效果是：

- 安装 `aukeys-opscli`
- 自动拉取 `opscli-core`
- 自动拉取默认模块包

## 6. 推荐依赖关系

### 6.1 默认发行依赖

建议 `aukeys-opscli` 聚合包依赖：

- `opscli-core`
- `opscli-auth`
- `opscli-query`
- `opscli-skills`

示意：

```toml
[project]
name = "aukeys-opscli"
dependencies = [
    "opscli-core>=0.5",
    "opscli-auth>=0.5",
    "opscli-query>=0.5",
    "opscli-skills>=0.5",
]
```

### 6.2 模块包依赖

各模块默认依赖：

```toml
dependencies = [
    "opscli-core>=0.5",
]
```

若业务模块强依赖认证，可进一步声明：

```toml
dependencies = [
    "opscli-core>=0.5",
    "opscli-auth>=0.5",
]
```

是否直接依赖 `opscli-auth`，按实际耦合强度决定，不强制所有模块都这么做。

## 7. 版本治理策略

### 7.1 版本独立原则

推荐每个包有自己的版本号：

- `opscli-core` 有自己的版本
- `opscli-query` 有自己的版本
- `opscli-skills` 有自己的版本
- `opscli` 聚合包也有自己的版本

这样可以做到：

- 模块独立发版
- 模块独立回滚
- 版本含义更清晰

### 7.2 不建议强行全量同版

不建议长期要求所有包始终保持完全同一版本号，例如：

```text
opscli-core   0.5.0
opscli-auth   0.5.0
opscli-query  0.5.0
opscli-skills 0.5.0
opscli        0.5.0
```

原因：

- 看起来整齐，但会牺牲独立发版能力
- 小模块微调也要推动全家桶一起升级
- 版本号会被大量“同步发版”稀释

### 7.3 推荐做法：兼容范围 + 聚合版本

推荐采用：

1. 每个模块独立版本
2. 每个模块声明 `requires_core`
3. `opscli` 聚合包声明一组默认模块依赖范围

例如：

```toml
opscli-core = "0.5.2"
opscli-auth = "0.5.1"
opscli-query = "0.7.0"
opscli-skills = "0.4.3"
opscli = "0.6.0"
```

其中：

- `opscli` 的版本代表“默认发行版组合”的版本
- 不要求其子模块版本完全一致

### 7.4 什么时候需要联动发版

以下场景建议联动：

1. `opscli-core` 公共接口发生破坏性变更
2. 默认模块兼容范围整体调整
3. `opscli` 聚合包默认依赖列表变化
4. 需要发布新的“官方标准工作台组合”

也就是说：

- 并不是每次模块升级都要发 `opscli`
- 只有默认发行版组合发生变化时，才需要更新 `opscli`

---

## 8. 推荐发布顺序

### 8.1 正式顺序

当一次变更涉及多个包时，推荐按以下顺序发布：

1. 发布 `opscli-core`
2. 发布依赖新核心能力的模块包
3. 验证模块兼容性
4. 最后发布 `opscli` 聚合包

原因：

- 聚合包依赖前面的真实可用版本
- 避免用户先装到指向不存在版本的聚合包

### 8.2 示例

假设这次发布涉及：

- `opscli-core 0.6.0`
- `opscli-query 0.8.0`
- `opscli-skills 0.5.0`
- `opscli 0.7.0`

推荐顺序：

```text
1. 发布 opscli-core 0.6.0
2. 发布 opscli-query 0.8.0
3. 发布 opscli-skills 0.5.0
4. 发布 opscli 0.7.0
```

### 8.3 单模块发版

如果只有一个按需模块升级，例如 `opscli-notify`：

- 只发布 `opscli-notify`
- 不需要同步发布 `opscli`

前提是：

- 与当前 `opscli-core` 兼容
- 不影响默认发行版依赖集合

## 9. 构建与上传建议

### 9.1 本地构建原则

每个包都应有自己的构建上下文。

如果后续是单仓多包，建议目录类似：

```text
packages/
├── opscli-core/
├── opscli-auth/
├── opscli-query/
├── opscli-skills/
└── opscli/
```

则构建命令类似：

```bash
cd packages/opscli-core && python -m build
cd packages/opscli-query && python -m build
cd packages/opscli && python -m build
```

### 9.2 上传原则

每个包上传命令独立执行，便于失败重试和审计：

```bash
twine upload packages/opscli-core/dist/*
twine upload packages/opscli-query/dist/*
twine upload packages/opscli/dist/*
```

### 9.3 TestPyPI / 私有仓优先验证

推荐流程保持一致：

1. 先上传测试仓
2. 验证安装
3. 再上传正式仓

只是对象从“一个包”变成“一组相关包”。

## 10. CI/CD 责任边界

### 10.1 平台团队责任

平台团队负责：

- `opscli-core`
- `opscli` 聚合包
- 插件协议和兼容矩阵
- 默认发行版依赖集合
- 跨模块发布协调

### 10.2 模块团队责任

模块团队负责：

- 自己模块包的代码与测试
- 模块版本管理
- 与 `opscli-core` 的兼容声明
- 模块单包发布

### 10.3 联合发布场景

当某次发布涉及：

- 核心接口变更
- 默认模块变化
- 聚合包依赖调整

则应由平台团队牵头，模块团队配合完成联合发布。

---

## 11. 推荐的 CI 流水线模型

### 11.1 单包流水线

每个包建议具备自己的流水线步骤：

1. 单包测试
2. 单包构建
3. 单包元数据校验
4. 上传测试仓
5. 安装验证
6. 上传正式仓

### 11.2 聚合包流水线

`aukeys-opscli` 聚合包的流水线应额外增加：

1. 依赖版本存在性校验
2. 默认安装链路验证
3. `pip install aukeys-opscli` 后命令可用验证

### 11.3 联动发布流水线

如果一次 PR 或一个 release 涉及多个包，可使用发布编排：

```text
构建 core
-> 发布 core 到测试仓
-> 构建 modules
-> 发布 modules 到测试仓
-> 安装验证
-> 发布聚合包到测试仓
-> 全链路验证
-> 正式发布
```

## 12. 用户侧安装语义

### 12.1 默认安装

普通用户：

```bash
pip install aukeys-opscli
```

得到：

- `opscli-core`
- 默认模块包

### 12.2 极简安装

高级用户或平台开发者：

```bash
pip install opscli-core
```

然后再按需装模块：

```bash
pip install opscli-query
pip install opscli-notify
```

### 12.3 全量安装

如果未来需要“官方全家桶”环境，可考虑：

```bash
pip install "opscli[full]"
```

但不建议把它作为默认发布路径。

---

## 13. 对当前项目的建议

基于当前 `opscli` 现状，建议采用以下演进策略：

1. 当前继续保持单包发布
2. 在设计层面先确认未来采用“多包独立上传”
3. 当插件加载基础设施稳定后，再进入单仓多包阶段
4. 拆包后保留 `opscli` 作为默认安装入口
5. 默认模块先固定为：
   - `auth`
   - `query`
   - `skills`

也就是说，当前你们不用马上改发布方式，但未来方向应该提前统一。

---

## 14. 最终结论

关于“上传提交到 PyPI 云端的时候是统一打包上传，还是每个包独立上传”，最终建议是：

- 当前单包阶段：统一打一个 `opscli` 上传
- 未来模块化阶段：每个包独立构建、独立上传
- 同时保留 `opscli` 聚合包，保证用户仍可一条命令安装默认模块集合

一句话总结：

未来的正确模式不是“一个大包上传所有内容”，而是“多个包分别发布，由 `opscli` 负责默认安装体验聚合”。

## 15. 建议的下一步

如果继续推进，后续建议二选一：

1. 输出《模块版本联动与兼容矩阵维护规范》
