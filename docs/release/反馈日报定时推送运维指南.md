# 反馈日报定时推送运维指南

> 内部文档，仅供 `ops-feedback-query` Linux 服务部署和运维人员使用。

## 1. 服务说明

反馈日报使用 systemd `oneshot + timer`，不是常驻 HTTP 服务：

- `ops-feedback-report.service`：查询完整昨日反馈、生成脱敏 Markdown，并调用企业微信群机器人推送摘要。
- `ops-feedback-report.timer`：每天 09:00（Asia/Shanghai）触发服务。
- `Persistent=true`：服务器关机错过执行时间后，恢复时补跑一次。

服务不自动重试。这样可避免企业微信已收到消息但客户端未收到响应时重复推送；失败后由运维人员确认群消息状态再手工补跑。

## 2. 前置条件

1. Linux 使用 systemd，且具备 root 安装权限。
2. 项目为完整 Git 工作区，例如 `/opt/open-opscli`。
3. 项目虚拟环境已安装当前代码，`<venv>/bin/python` 和 `<venv>/bin/opscli` 可执行。
4. 创建不可登录的专用服务账号：

```bash
sudo useradd --system --home-dir /nonexistent --shell /usr/sbin/nologin ops-feedback
```

5. 在以下文件配置真实反馈密钥和企业微信 Webhook：

```text
opscli/skills/templates/ops-feedback-query/data/credentials.json
```

禁止把密钥或 Webhook 放入命令参数、systemd unit、环境变量、日志或工单。

6. 如需启用大模型反馈洞察，参考 Skill 的
   `data/feedback_insight.example.json` 创建 `/etc/opscli/feedback-insight.json`，配置
   OpenAI-compatible Chat Completions 接口的精确 endpoint、API Key 和模型名。模型配置
   不得放入 Git 工作区。

## 3. 安装

在 Skill 目录执行：

```bash
cd /opt/open-opscli/opscli/skills/templates/ops-feedback-query
sudo bash deploy/install_systemd.sh \
  --project-root /opt/open-opscli \
  --venv /opt/open-opscli/.venv \
  --user ops-feedback \
  --insight-config /etc/opscli/feedback-insight.json
```

`--insight-config` 为可选参数。不传时保持原有只读日报；传入后启用当前周期与上一
等长周期对比、大模型模块分类、P0-P4 优先级、建议工作和 P0/P1 群提醒。安装器会校验
`endpoint/api_key/model`，并将模型配置权限收紧为 `0600`。

服务账号主组不是默认组时，可增加：

```bash
--group <服务组>
```

安装脚本会：

1. 校验 root 权限、服务账号、项目、虚拟环境和关键文件。
2. 将凭据文件设为服务账号所有、权限 `0600`。
3. 创建 `output/feedback-query/`，所有者为服务账号、权限 `0700`。
4. 渲染并校验 service，安装 timer。
5. 执行 `systemctl daemon-reload` 和 `systemctl enable --now ops-feedback-report.timer`。

安装过程不会读取或输出凭据内容。

## 4. 首次验证

先确认定时器：

```bash
systemctl status ops-feedback-report.timer
systemctl list-timers ops-feedback-report.timer
```

再手动执行一次真实推送：

```bash
sudo systemctl start ops-feedback-report.service
systemctl status ops-feedback-report.service
journalctl -u ops-feedback-report.service -n 50 --no-pager
```

成功日志为结构化 JSON，包含 `success=true`、报告路径、反馈数量和 `sent=true`。同时确认：

- 企业微信群收到一条脱敏摘要；
- `output/feedback-query/反馈日报-YYYY-MM-DD.md` 已生成；
- 启用洞察时，报告包含“模块问题洞察”，群消息仅突出 P0/P1；
- 日志中没有 API Key、Webhook、邮箱、用户 ID 或原始反馈正文。

## 5. 日常巡检

```bash
systemctl list-timers ops-feedback-report.timer
systemctl status ops-feedback-report.service
journalctl -u ops-feedback-report.service --since today --no-pager
```

重点检查：

- timer 下次触发时间是否为上海时区 09:00；
- service 最近一次结果是否成功；
- 输出目录是否生成对应日期报告；
- 企业微信群是否收到摘要。

## 6. 故障处理

### 6.1 查询失败

检查服务日志中的安全业务码。确认服务器可访问反馈 API，凭据文件存在且仍有效。日志不会展示密钥；不要为排障临时打印请求 Header。

### 6.2 企业微信推送失败

确认机器人仍在目标群、Webhook 未失效，并检查服务器到 `qyapi.weixin.qq.com` 的 HTTPS 连通性。先查看群内是否已经收到消息，再决定是否补跑，避免重复推送。

### 6.3 大模型洞察失败

确认模型 endpoint 可访问、API Key 有效、模型支持 Chat Completions JSON 输出，并检查
配置文件仍为服务账号可读的 `0600` 权限。非本机模型 endpoint 必须使用 HTTPS。日志只返回安全错误类别，不得临时打印
Authorization Header、模型密钥、模型原始请求或含反馈详情的响应。模型不可用时，本次
任务自动生成并推送基础日报，在报告和群消息中标注洞察已降级；不会发布不完整的 AI
分类，也不会丢失原有 Critical/High 提醒。

### 6.4 权限失败

确认：

```bash
sudo stat /opt/open-opscli/opscli/skills/templates/ops-feedback-query/data/credentials.json
sudo stat /opt/open-opscli/output/feedback-query
```

凭据应为服务账号所有且权限 `0600`；输出目录应为服务账号所有且权限 `0700`。项目其余目录可保持只读。

### 6.5 手工补跑

确认当天群内没有对应日报后执行：

```bash
sudo systemctl start ops-feedback-report.service
```

默认始终统计完整昨日。如需指定历史日期，应先停用 timer，再以前台方式显式传入 `--date-from/--date-to --send`，确认完成后恢复 timer。

## 7. 停用与回滚

停用自动推送：

```bash
sudo systemctl disable --now ops-feedback-report.timer
```

完整移除：

```bash
sudo systemctl disable --now ops-feedback-report.timer
sudo rm -f \
  /etc/systemd/system/ops-feedback-report.service \
  /etc/systemd/system/ops-feedback-report.timer
sudo systemctl daemon-reload
```

移除 unit 不会删除凭据和历史 Markdown。若需要清理这些文件，必须先确认保留要求并按内部敏感数据流程处理。

## 8. 安全边界

1. 反馈密钥和企业微信 Webhook 只保存在 Skill 的 `data/credentials.json`。
2. 不向 journal、Shell 历史、截图、工单或聊天复制凭据。
3. 完整日报仅写入权限 `0700` 的专用目录；群消息只包含脱敏摘要。
4. 不修改 service 以输出调试 Header、请求 URL 或完整异常对象。
5. 更新项目后重新运行安装脚本，使 unit 路径和安全配置与当前版本保持一致。
6. 模型只处理白名单脱敏字段；周期次数、影响人数和优先级由本地确定性规则计算，不能用模型自由输出覆盖。
