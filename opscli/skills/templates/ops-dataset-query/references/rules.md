# 查询意图澄清规则

> **适用范围**：AI Agent 通过 `opscli query` 或 `query_*` MCP Tool 执行数据查询前，必须先按本规则逐项检查用户输入。
> **核心原则**：不确定就问，禁止猜测。任何可能产生歧义的情况都必须向用户确认。
> **数据来源**：本文件只描述规则和模式。具体数据集、字段名称、字段含义等数据应从 `data/datasets.csv`、`data/dataset_fields.csv`、`data/dataset_catalog.json` 中动态查询，**禁止将数据硬编码到规则判断中**。
> **结构化提问**：凡本文件写到"确认"、"澄清"、"让用户选择"、"确认后执行"的场景，必须按 `references/ask-user-question-guide.md` 使用 `AskUserQuestion`。纯文本告知不等于用户确认。

---

## 零、AskUserQuestion 结构化澄清总则

### 0.1 必须使用 AskUserQuestion 的场景

以下场景必须使用 `AskUserQuestion`，不得只用纯文本提问：

- 数据集未指定、自然语言匹配到候选数据集、或业务领域词可能对应多个数据集
- 数据集名称模糊匹配到多个相似数据集
- 字段术语精确或模糊匹配到多个字段
- 同一字段或公式指标跨多个数据集且口径不同
- 人员/组织、SKU/ASIN、库存、分类体系、广告类型等存在多个角色、层级或变体
- "最近一个月"、"最近一周"、跨月对比、天数不对等、主周期/对比周期不完整等时间歧义
- 查询前参数摘要需要用户确认
- 查询返回 0 行、主要指标全空/全 0 或用户反馈结果有误，需要进入纠错流程

### 0.2 候选展示规则

- 候选项 ≤4 个：直接用 `AskUserQuestion` 展示全部候选。
- 候选项 >4 个：先文本展示完整候选列表，再用 `AskUserQuestion` 展示最相关的 2~3 个快捷选项和"其他（自定义）"。
- 每次 `AskUserQuestion` 必须保留"其他（自定义）"入口，允许用户输入序号、字段名、数据集别名或自然语言补充。
- 用户确认前，不得把推荐项写入 `query_simple` 参数，更不得执行查询。
- 只有用户明确指定且唯一命中的参数，才可以跳过单独提问；但仍必须在查询前参数摘要中明示。

## 零-A、字段语义解析流程（强制）

> **适用时机**：用户给出字段名称或业务术语（如"库存"、"销售额"、"SP"、"转化率"）时，在构造查询参数前必须执行本流程。

**解析顺序（严格按序）**：

1. **先查 `data/field_semantic_index.yml` 的 `semantic_groups`**
   - 按 `business_domain` 过滤候选字段（不只做字段名关键词匹配）
   - 查 `disambiguation.possible_meanings`：若存在多个含义且无法从上下文判断 → 执行步骤 2

2. **多义词触发 AskUserQuestion**
   - 命中 `disambiguation` 且含义数 ≥ 2 → 按 `disambiguation.possible_meanings` 列出选项，禁止猜测

3. **标记字段特殊属性**
   - `formula_rule=true`（ACOS/ROAS/转化率/平均CPC 等）→ 构造查询时**不传 `aggregation` 参数**，使用字段的 `summary_expression`
   - `snapshot_rule=true`（总库存/海外仓库存/在途库存等）→ 只能用于明细表，禁止在有维度分组的聚合查询中使用

4. **校验字段真实存在**
   - 语义索引只提供候选推荐，仍需通过 `data/dataset_fields.csv`（CLI）或 `query_metadata(dataset=alias)`（MCP）确认字段真实存在

**高风险多义词快查**（必须澄清，不可猜测）：

| 术语 | 可能含义 | 处理 |
|------|---------|------|
| SP | SPU 产品编码 / Sponsored Products 广告 | 广告上下文→SP广告；销售上下文→SPU；不明确→澄清 |
| 销售额 | 账单销售额 / 即时销售额 / 广告销售额 / 总销售额 | 先判断时间口径和平台，再确认数据集 |
| 库存 | 物控库存 / 快照库存（聚合受限）/ 补货计划 / 库龄 | 必须澄清库存类型 |
| 转化率 | 广告转化率（CVR）/ 自然转化率（页面转化率）| 确认口径来源 |
| 部门 | 销售部门（dept_name）/ 物控组织（org_name）| 看数据集类型 |

## 一、时间范围规则

### 1.1 "近 xx 天"是否包含今天

**歧义点**：用户的"近N天"可能指最近N个完整自然日（不含今天），也可能包含今天。

**处理规则**：
- 用户明确说明时 → 遵循用户指定
- 用户未明确时 → 默认理解为**包含今天**，但必须在回复中明示此假设，并告知用户如有异议可以纠正

### 1.1.1 "近 xx 天"日期精确推算（铁律）

> **铁律**：计算"近N天"的起止日期时，**必须使用日期算法精确推算，禁止凭感觉猜测日期**。

**推算公式**：

```
结束日期 = 今天
起始日期 = 今天 - (N - 1) 天
日期范围 = [起始日期, 结束日期]，共 N 天
```

**核心原则**：近N天包含今天，因此起始日期是今天往前推 `N - 1` 天，总跨度恰好为 N 天。

**正确示例**：

| 今天 | "近30天" | 推算过程 | 日期范围 | 天数 |
|------|---------|---------|---------|------|
| 5月11日 | 4月12日 ~ 5月11日 | 5.11 - 29天 = 4.12 | [4.12, 5.11] | 30天 |
| 3月15日 | 2月14日 ~ 3月15日 | 3.15 - 29天 = 2.14 | [2.14, 3.15] | 30天 |
| 1月5日 | 12月7日 ~ 1月5日 | 1.5 - 29天 = 12.7 | [12.7, 1.5] | 30天（跨年） |

**典型错误**：

| 错误写法 | 正确写法 | 错误原因 |
|---------|---------|---------|
| 近30天 = 4.11 ~ 5.11（31天） | 4.12 ~ 5.11（30天） | 多算了一天 |
| 近7天 = 5.4 ~ 5.11（8天） | 5.5 ~ 5.11（7天） | 多算了一天 |
| 近90天 = 往前推3个月 | 精确减去89天 | "3个月"天数不固定（28~31×3） |

**处理规则**：
- 涉及"近N天"的日期计算时，**必须**用代码或工具精确推算（如 Python `datetime.timedelta(days=N-1)`）
- 禁止用"往前推N天"（实际得到 N+1 天），正确做法是"往前推 N-1 天"
- 禁止用"约N天"、"大概N天"等模糊表述
- 回复中必须列出推算后的具体起止日期。若本次还存在数据集、字段、筛选或币种默认值，必须在查询前参数摘要中用 `AskUserQuestion` 一并确认

### 1.2 月份天数不对等

**歧义点**：不同月份天数不同（28/29/30/31），导致月汇总对比时口径不一致。

**处理规则**：
- 完整月对比时，使用**完整自然月**，明确告知用户天数差异。若用户关注趋势，建议使用日均值
- 同期对比（如本月1~N日 vs 上月1~N日）时，使用**相同天数**，不可用完整月
- 本月前N天 vs 上月完整月 → **必须用 AskUserQuestion 澄清**，因为天数严重不对等，给出两个方案让用户选择：A) 用上月同期N天、B) 计算日均值
- 查询月份有30号但对比月份只有31天（无30号对应日）→ **必须用 AskUserQuestion 澄清**对齐方式

### 1.3 "本月" / "上月" 边界定义

| 表述 | 默认理解 | 需澄清的场景 |
|------|---------|------------|
| 本月 | 当前自然月 | 月初时用户可能实际想查上月 |
| 上月 | 上一自然月 | 跨年时需确认年份（1月的"上月"为去年12月） |
| 最近一个月 | 近30天（滚动）还是当月？ | **必须用 AskUserQuestion 确认** |
| 上个月同期 | 上月1日~同日 | 需确认具体日期范围 |

### 1.4 "周"的边界定义

- "本周"默认 = 周一至今天，需确认是否要完整周
- "上周"默认 = 上周一至上周日
- "最近一周" ≠ "上周"（前者是近7天滚动，后者是上周完整周）

### 1.5 缺少查询范围时的默认值规则

| 缺少项 | 行为 |
|--------|------|
| 分析对象（部门/小组/ASIN 等） | 必须追问，禁止取数 |
| 时间范围 | 默认近 30 天（含今天），但必须在回复中写出绝对起止日期 |
| 国家 / 平台 | **直接按默认值执行**：国家=美国，平台=Amazon SC + Amazon VC；在取数状态中写明；**禁止事前追问** |

> 只有取数返回 0 行或数据异常时，才提示用户确认国家/平台范围。
> 用户问部门、项目部、小组、各小组、整体表现时：直接按默认口径（美国，Amazon SC + Amazon VC）取数，在取数状态中写明，不得追问。

### 1.6 上下文继承规则（父级范围约束）

当对话有前文分析记录时，用户后续追问子级维度（小组、店铺、ASIN、广告活动等），必须在最新父级范围内执行。

| 场景 | 是否有父级范围 | 行为 | 取数状态标注 |
|------|-------------|------|------------|
| 首次提问 | ❌ 无 | 全库匹配→唯一时直接取数；多个时追问 | `当前查询范围：XX部` |
| 续问下钻 | ✅ 有 | 父级范围内精确匹配→直接取数（继承父级） | `当前查询范围：父级→子级` |
| 续问下钻 | ✅ 有 | 父级范围内匹配不到 | 反问"父级范围内没有该对象，是否查其他范围？" |

**规则**：
- 父级范围只在用户明确切换到新范围时才重置；模糊说法不得自行切换
- 每次输出报告，取数状态中必须包含 **"当前查询范围"** 字段（格式：`部门→小组` 或 `部门→小组→ASIN`）

## 二、人员/组织意图澄清规则

### 2.1 同名维度存在多个语义角色

**歧义模式**：数据集中存在多组"人员姓名"或"组织名称"维度字段，分别代表不同角色（如销售人员 vs 开发人员、销售小组 vs 开发小组）。当用户只说一个名字时，无法确定是哪个角色。

**检测方法**：
1. 搜索 `dataset_fields.csv` 中 `verbose_name` 或 `field_name` 含"人员"、"姓名"、"用户名"、"小组"、"团队"、"组织"等关键词的字段
2. 确认是否存在 >=2 组同概念但不同语义的维度字段（如 `team_username` / `develop_username`）
3. 存在则触发澄清

**触发条件**：用户查询中包含以下模式：
- 人名 + 指标/数据查询（如"xxx的销售"、"查一下张三"）
- 小组名 + 指标/数据查询（如"xxx组的数据"）
- 任何无法从上下文判断角色身份的人员/组织查询

**澄清模板**：
> "请问'{名称}'属于哪种角色类型？数据集中存在以下同名字段维度：
> 1. `字段A` — 角色A
> 2. `字段B` — 角色B
> 我需要确认按哪个维度过滤。"

### 2.2 组织层级歧义

当数据集中存在多级组织维度（如大组 → 小组 → 个人）时，用户说的"团队"、"组"可能指不同层级。

**处理规则**：搜索 `dataset_fields.csv` 中 `field_type=dimension` 且名称含组织关键词的字段，若存在多级则用 `AskUserQuestion` 向用户确认层级。

### 2.3 team_name 与 dept_name 相互独立（重要！）

**team_name（销售小组）与 dept_name（部门）是两个独立维度，无隶属关系。**

反直觉场景：某部门的销售小组名称可能带有其他部门的前缀（如九部下属小组名为"一部-A组"、"二部-D组"）。小组名中的"一部""二部"**不代表该小组属于一部/二部**，仅是小组标签。

- **判断部门归属的唯一依据**：`dept_name` 字段，而非 `team_name` 前缀
- 诊断报告中遇到小组名称带其他部门前缀时，必须说明"小组名称为独立标签，部门归属以 dept_name 为准"

### 2.4 店铺、渠道、平台维度严格区分

已知错误：问店铺时返回平台维度；问渠道时用平台 + 国家冒充渠道。

| 维度 | 对应字段 | 禁止用以下替代 |
|------|---------|--------------|
| 店铺 | 店铺 / 账号维度字段 | 平台字段 |
| 渠道 | `channel_name` 或渠道同义字段 | 平台 + 国家 |
| 平台 | `Amazon` / `Amazon VC` 等 | — |
| 国家 | `country` 字段 | — |

**规则**：找不到渠道或店铺字段时，**不得**用平台、国家或平台+国家替代；必须说明字段缺失或改查范围。

## 三、产品标识歧义规则

### 3.1 同一概念存在多个变体字段

**歧义模式**：同一业务概念（如 SKU、ASIN）在数据集中可能有多个变体字段（渠道SKU、公司SKU、父公司SKU；子ASIN、父ASIN 等）。

**检测方法**：
1. 从 `dataset_fields.csv` 中搜索用户提到的标识类型关键词（如"SKU"、"ASIN"、"编码"）
2. 若匹配到 >=2 个不同字段 → 触发澄清

**澄清模板**：
> "您提到的'{标识类型}'在数据集中有多个变体，请确认具体类型：
> 1. `字段1` — 含义1
> 2. `字段2` — 含义2
> ..."

### 3.2 产品标识缩写歧义

当用户使用缩写（如"SP"）时，可能指"SPU（产品编码）"也可能指"Sponsored Products（广告类型）"。

**处理规则**：根据查询语境判断——涉及广告指标大概率是广告类型，涉及产品管理大概率是产品编码。无法判断时用 `AskUserQuestion` 向用户确认。

## 四、币种歧义规则

**歧义模式**：广告数据集中大量金额指标同时存在原币（original currency）和人民币（CNY）两个版本，字段名通常以 `_cny` 后缀区分。

**检测方法**：
1. 在 `dataset_fields.csv` 中搜索用户所需的金额指标
2. 若同时匹配到 `xxx` 和 `xxx_cny` 两个版本 → 存在币种歧义

**默认策略**：
- 用户未指定币种时，**默认使用 CNY（人民币）版本**
- 在回复中明示"以下数据均为人民币计价"
- 用户明确提到"美金"、"美元"、"USD"、"原币"时，使用对应版本

## 五、数据集选择规则

### 5.0 数据集必须明确（核心规则）

> **铁律**：用户未明确指定数据集名称时，必须通过以下方式确定目标数据集，**禁止猜一个直接用**。

**处理流程**：
1. **用户明确指定数据集名称** → 在 `datasets.csv` 中精确或模糊匹配，匹配到多个相似名称时列出让用户选
2. **用户未指定数据集** → 从用户查询中提取关键词，检索 `datasets.csv` 的 `dataset_name` 和 `description` 字段：
   - 匹配到 0 个 → 使用 `AskUserQuestion` 请求用户指定数据集、查看全量数据集或改写需求
   - 匹配到 1 个 → 使用 `AskUserQuestion` 确认"使用该数据集 / 查看其他候选 / 自定义"，确认前不得查询
   - 匹配到 >=2 个 → **强制列出所有候选**，分别说明其数据粒度和适用场景，再用 `AskUserQuestion` 让用户选择
3. **catalog intents 可用时** → 优先用 catalog 意图匹配，但仍需用 `AskUserQuestion` 确认匹配结果
4. **业务领域词特殊规则**：当用户只说"广告数据"、"销售数据"、"库存数据"、"物流数据"、"财务数据"等大领域词时，必须搜索数据集列表本身（`datasets.csv` / `query_metadata()` / catalog），不能只根据字段搜索结果集中在某个 table_id 就认定数据集唯一。

### 5.1 数据集名称相似歧义

**歧义模式**：多个数据集的名称高度相似（如同一业务领域的不同粒度、不同合并方式），用户说的名称可能同时匹配多个。

**检测方法**：在 `datasets.csv` 中用用户提到的名称做关键词匹配，若 >=2 个数据集的 `dataset_name` 包含该关键词 → 触发澄清。

**澄清模板**：
> "您的关键词'{关键词}'匹配到以下 {N} 个数据集，请选择一个：
> - **数据集A** — 数据粒度：xxx，适用场景：xxx
> - **数据集B** — 数据粒度：xxx，适用场景：xxx"

执行要求：候选列表文本展示后，必须按 `ask-user-question-guide.md` 使用 `AskUserQuestion` 提供推荐项和"其他（输入序号或数据集名）"。

### 5.2 字段跨数据集存在时必须澄清

**歧义模式**：同一个字段名在多个数据集中存在，但各数据集的计算口径、数据粒度、数据源可能不同，查询结果会不一致。

**检测方法**：
1. 在 `dataset_fields.csv` 中按 `field_name` 搜索目标字段
2. 统计该字段出现在哪些 `table_id` 中
3. 若出现在 >=2 个数据集 → 触发澄清

**处理流程**：
- 用户已指定数据集 → 使用该数据集中的字段
- 用户未指定数据集且字段跨多个表 → **列出每个数据集 + 该字段在该数据集中的含义**，并用 `AskUserQuestion` 让用户选择
- 特别关注：公式字段（如 ACOS、ROAS）跨表时计算口径差异更大

### 5.3 综合 vs 细分数据集选择

**歧义模式**：用户要查的数据在"综合数据集"和"细分数据集"中都存在。综合数据集覆盖面广但粒度粗，细分数据集粒度细但范围窄。

**处理规则**：用 `AskUserQuestion` 询问用户是要"全貌概览"（综合数据集）还是"细分详情"（细分数据集），说明两者的差异。

### 5.4 数据集优先级（经营 vs 广告）

已知错误：经营总览类问题优先用了广告数据集，导致经营口径错位。

| 分析场景 | 优先使用 |
|---------|---------|
| 经营总览、毛利、广告费占总销售、总销售额 | **即时综合数据集** |
| 广告活动、广告类型、关键词、搜索词、ASIN 广告明细 | **广告明细数据集** |

- 跨数据集口径差异必须在"数据注意事项"中说明
- 广告费占比等经营指标优先使用即时综合口径；广告明细用于拆解

## 六、字段名称模糊匹配必须澄清（核心规则）

### 6.0 多字段匹配处理流程

> **铁律**：用户使用的术语在 `dataset_fields.csv` 中匹配到 **>=2 个不同含义的字段**时，**禁止静默选择一个**，必须列出所有候选项让用户明确选择。

**匹配优先级（两级匹配）**：

```
用户说"查 xxx 指标"
  ↓
第一级：精确匹配（verbose_name 或 field_name 完全等于用户术语）
  ↓
精确匹配到 1 个 → 直接使用该字段，跳过模糊匹配
精确匹配到 >=2 个 → 列出精确匹配的候选项，并用 `AskUserQuestion` 让用户选择
精确匹配到 0 个 → 进入第二级
  ↓
第二级：模糊匹配（verbose_name / field_name 包含用户术语，但不是完全相等）
  ↓
模糊匹配到 0 个 → 告知用户无此字段，列出相近字段
模糊匹配到 1 个 → 直接使用（告知用户将使用该字段）
模糊匹配到 >=2 个 → 【强制】列出所有候选项及各自含义，并用 `AskUserQuestion` 让用户选择
```

> **关键区别**：用户说"销售额"且 `verbose_name` 中恰好有字段叫"销售额"时，直接精确命中，**不需要**列出"交易额"、"交易额（自发货）"、"交易额（平台发货）"等模糊匹配字段。只有无精确匹配时才进入模糊匹配阶段。

**澄清模板**：
> "您说的'{术语}'匹配到 {N} 个字段，请确认要使用哪一个：
> 1. `字段名` — 含义说明（所属数据集：xxx）
> 2. `字段名` — 含义说明（所属数据集：xxx）
> ..."

执行要求：字段候选超过 4 个时，先文本展示全部候选，再用 `AskUserQuestion` 展示最相关的 2~3 个字段和"其他（输入字段名或序号）"。

### 6.1 常见多字段匹配模式

以下模式在 `dataset_fields.csv` 中高频出现，是字段歧义的主要来源：

| 歧义模式 | 说明 | 检测方式 |
|---------|------|---------|
| **大类 vs 子类** | 一个汇总字段 + 多个按维度拆分的子字段 | 搜索关键词，观察是否有带括号后缀的变体（如 `xxx(SP)`、`xxx(SD)`） |
| **不同口径同名** | 同一概念在不同数据集中有不同计算口径 | 同一 `field_name` 出现在多个 `table_id` 中 |
| **原币 vs CNY** | 金额字段同时存在原币和人民币版本 | 字段名以 `_cny` 结尾 vs 不以 `_cny` 结尾 |
| **总计 vs 明细** | 一条总计记录 vs 多个按类别拆分的子项 | `verbose_name` 含"总计"、"全部" vs 含具体类别名 |
| **不同语义同名** | 字段名相似但含义完全不同（如 `price`=交易额 vs `original_price`=销售额） | `verbose_name` 不同但 `field_name` 相似 |

### 6.2 库存等"多子类"维度

当数据集中某一概念存在 >=3 个变体字段时（如库存有平台库存/海外仓库存/在途库存/国内库存等多种），用户只说查"库存"时无法确定要查哪种。

**处理规则**：列出所有变体并用 `AskUserQuestion` 让用户选择，不得默认选"总库存"或第一个。

### 6.3 分类体系歧义

当数据集中存在多套分类体系（如内部品类 vs 平台类目），用户说"品类"、"类目"时需用 `AskUserQuestion` 确认用哪套体系。

## 七、术语缩写规则

### 7.1 缩写可能多义

当数据集中存在缩写词（如 SP/SD/SB/SBV），用户使用这些缩写时可能不理解其含义，或缩写本身可能指代不同概念。

**处理规则**：
- 用户正确使用术语缩写 → 直接使用，无需解释
- 缩写可能产生歧义（如 SP 既可能指 SPU 产品也可能指 Sponsored Products 广告）→ 根据查询语境判断，无法判断时用 `AskUserQuestion` 向用户确认
- 用户使用了不存在的缩写 → 告知并列出相近选项

### 7.2 公式指标的口径差异

ACOS、ROAS 等公式指标在多个数据集中存在，但计算口径不同（综合口径 vs 广告类型口径 vs campaign 口径）。

**处理规则**：查询公式指标时，优先使用对应粒度的数据集。若用户未指定粒度，列出各数据集中的该指标及其计算口径差异，并用 `AskUserQuestion` 让用户选择。

## 八、catalog 意图匹配规则

### 8.1 意图匹配优先级

当 catalog 的 `intents` 可用时，按以下优先级选择数据集：
1. 用户明确指定数据集名称 > 所有自动匹配
2. catalog intents 推荐 > 本地关键词检索
3. 关键词精确匹配 > 模糊匹配

### 8.2 多个数据集同时匹配

当用户查询匹配到多个数据集时，**必须列出候选项让用户选择**，不得静默选择第一个。列出时应说明每个数据集的：
- 数据粒度（按产品/按日期/按广告类型/campaign 层级等）
- 适用场景（一句话说明）
- 是否有特殊约束（如需日期过滤）

选择动作必须使用 `AskUserQuestion`。若候选项超过 4 个，先文本展示完整候选，再展示最相关的 2~3 个快捷选项和"其他（输入序号或数据集名）"。

## 九、查询前自检清单

在执行任何查询前，按以下流程检查：

```
□ 【时间】用户的日期范围是否明确？
         → 近xx天含不含今天？月份对比天数是否对等？滚动 vs 自然月？触发歧义时是否已用 AskUserQuestion 确认？
□ 【身份】查询涉及人名/组织名时，是否存在同名多角色维度？
         → 搜索 dataset_fields.csv 中维度字段，确认是否有 >=2 组同概念维度
□ 【产品标识】查询涉及 SKU/ASIN/编码时，是否存在多个变体字段？
         → 搜索 dataset_fields.csv，确认是否匹配到 >=2 个字段
□ 【币种】查询涉及金额指标时，是否同时存在原币和 CNY 版本？
         → 搜索 field_name 是否同时有 xxx 和 xxx_cny
□ 【数据集】是否已明确指定且唯一？
         → 搜索 datasets.csv / query_metadata，确认用户关键词匹配几个数据集；业务领域词不能只靠字段搜索结果判定唯一
□ 【数据集名称】用户说的名称是否匹配多个相似数据集？
         → 模糊匹配 datasets.csv 的 dataset_name；多个候选时是否已用 AskUserQuestion 选择
□ 【字段跨表】目标字段是否存在于多个数据集且含义/口径不同？
         → 在 dataset_fields.csv 中按 field_name 搜索，统计 table_id 去重数
□ 【字段名】用户使用的指标术语是否匹配到 >=2 个字段？
         → 在 dataset_fields.csv 中搜索 verbose_name/field_name；多个候选时是否已用 AskUserQuestion 选择
□ 【公式字段】是否为公式字段？是 → 禁止加 aggregation
         → 检查 summary_expression / detail_expression 是否非空
□ 【查询组件扩展字段】筛选字段不在普通字段列表但在查询组件列表中？
         → CLI：检查 dataset_select_columns.csv；MCP：检查 query_metadata(dataset=alias) 的 select_columns
         → 属于合法筛选条件（见第十二章 12.2），允许作为 filters 使用，不得拒绝
□ 【查询组件权限校验】filters 中是否存在属于查询组件的字段？
         → 是 → 先查询 component_dataset_alias 数据集获取合法枚举值列表，确认用户指定的值存在后再查询
         → 值不在列表中 → 告知无权限，展示合法值列表，用 AskUserQuestion 引导重选
□ 【default_filters】catalog 的 default_filters 是否已验证可用？
□ 【参数确认】本次是否使用了推荐值或默认值？如是，执行前是否已用 AskUserQuestion 展示参数摘要并获得确认？
□ 【输出字段名】输出结果时，列名和指标名称是否使用了数据集原始字段名？
         → 禁止将"广告费"写成"广告花费"、将"订单量"写成"订单数量"等
□ 【取数状态】回答中是否输出了固定格式的取数状态块？（取数结果/当前日期/数据时间/筛选范围/当前查询范围/已取数据集）
□ 【平台过滤】是否在 filters 中强制添加了 Amazon SC + Amazon VC 平台过滤？取到非 Amazon 数据是否已丢弃？
□ 【范围继承】续问子级维度时，是否在最新父级范围内执行？取数状态是否标注了查询范围链（部门→小组）？
□ 【全量展示】用户问"各小组""全部 ASIN""所有渠道""明细"时，是否展示全量而非自动 Top N？
         → 超 50 行须先展示摘要并说明总行数；任何截断都必须写明排序字段、截断数量和总行数
□ 【self_small_cat】使用细分品线字段时，是否确认当前部门为范泰克？非范泰克部门禁止使用该字段
```

## 十、输出结果字段名规范（核心规则）

### 10.0 禁止修改字段名称

> **铁律**：输出查询结果时，**必须原样使用数据集中定义的字段名称**（`verbose_name` 或 `field_name`），禁止自行"优化"、"美化"或"意译"字段名。

**歧义点**：AI Agent 在整理查询结果时，可能下意识将数据集字段名替换为"更通俗"或"更好看"的说法，导致字段名与数据集定义不一致，用户无法对照数据集理解字段含义。

**典型错误示例**：

| 数据集原始字段名 | AI 擅自改写后 | 问题 |
|-----------------|-------------|------|
| 广告费 | 广告花费 | 改变了字段语义，用户可能以为查的是另一个字段 |
| 订单量 | 订单数量 | 虽意思相近，但与数据集定义不一致 |
| 销售额 | 销售金额 | 同上 |
| 退款率 | 退款比例 | 同上 |

**处理规则**：
- 输出表格/列表的列名 → **必须**使用数据集的 `verbose_name`（中文含义名）或 `field_name`（英文字段名）
- 文字描述中提及指标 → **必须**使用数据集的 `verbose_name`
- 即使用户使用了口语化表达（如"帮我看看花了多少钱"），查询到对应字段"广告费"后，输出结果必须写"广告费"，不能写成"花费金额"
- 如果需要解释某个字段的含义 → 用括号或注释说明，但不能替代字段名本身

**正确示例**：
```
| 日期 | 广告费 | 广告销量 | ACOS |
|------|--------|---------|------|
| 2026-05-01 | 1,234 | 56 | 12.3% |
```

**禁止示例**：
```
| 日期 | 广告花费 | 广告销售数量 | 广告成本占比 |
|------|---------|------------|------------|
| 2026-05-01 | 1,234 | 56 | 12.3% |
```
> 上例中"广告花费"、"广告销售数量"、"广告成本占比"均非数据集定义字段名，是 AI 擅自改写的结果。

## 十一、库存数据查询规则

### 11.1 指定产品的库存查询默认不聚合

**核心原则**：当用户查询涉及某个具体产品的库存相关字段时（如可售库存、在途库存、海外仓库存等），该查询的目的是了解当前最新的库存状况，而非历史汇总统计，因此**默认不应做时间聚合**。

**触发条件**（满足任一即触发）：
- 查询中指定了具体产品标识：ASIN、渠道 SKU（渠道SKU）、公司 SKU（公司SKU）、父公司 SKU（父公司SKU）等
- 查询中指定了具体的产品 ID（如 `product_id`、`listing_id` 等）
- 查询意图明显是针对某个已知产品的库存状况

**处理规则**：
- **默认不加时间聚合**：查询库存字段时，维度中不应包含日期聚合字段（如 `年-月`、`年-周` 等），而是直接查最新的明细数据
- **查询最新库存数据**：默认条件应自动匹配最近一次库存快照日期，而非一段历史时间范围
- **用户明确要求历史趋势时例外**：如果用户要求查看库存的历史变化趋势（如"近30天可售库存变化"、"库龄分布"），则按正常的趋势/聚合查询处理
- **用户未指定库存字段类型时按 6.2 规则处理**：如果只说"查库存"而不指定具体库存类型（可售/在途/海外仓等），按 6.2 规则列出所有变体并用 `AskUserQuestion` 让用户选择

**正确示例**—用户说"查 ASIN B0XXXXX 的库存"：
- 维度：ASIN、库存类型
- 指标：库存数量（最新快照值）
- 过滤：ASIN = B0XXXXX
- **不做**：按日期维度聚合（如查"每天的可售库存"）

**正确示例**—用户说"查 ASIN B0XXXXX 近30天的可售库存变化"：
- 维度：日期
- 指标：可售库存数量
- 过滤：ASIN = B0XXXXX，日期范围 = 近30天
- 此时因用户明确要求历史趋势，按正常趋势查询处理

**理由说明**：
- 库存数据通常是"快照型"数据，而非"流水型"数据
- 对指定产品查库存的核心需求是"现在还有多少货"，而非历史上各时间点有多少
- 不加聚合直接查最新快照，避免因时间维度聚合导致结果不直观或数据量过大

## 十二、查询组件权限校验规则

### 12.1 什么是查询组件字段

**定义**：每个数据集都可配置若干"查询组件"（Select Column）。这类字段的合法枚举值由 `component_dataset_alias` 数据集动态提供，代表当前用户可使用的权限范围。

**两种模式下的数据来源不同（必须区分）**：

| 模式 | 数据来源 | 说明 |
|------|---------|------|
| **CLI 模式** | `data/dataset_select_columns.csv` | 本地缓存的平铺 CSV 文件，需按 `current_dataset_alias` 过滤 |
| **MCP 模式** | `query_metadata(dataset="<alias>")` 响应中的 `select_columns` 数组 | API 直接返回，每个 dataset 对象内嵌套 `select_columns` 列表 |

**CLI 模式 CSV 结构**：

| 列名 | 含义 |
|------|------|
| `current_dataset_alias` | 当前查询的数据集 alias |
| `column_name` | 查询组件字段名（筛选维度） |
| `verbose_name` | 中文显示名 |
| `component_dataset_alias` | 枚举值来源数据集 alias |

**MCP 模式响应结构示例**（`query_metadata` 返回的 `datasets` 列表中每个元素）：

```json
{
  "table_id": 1,
  "dataset_alias": "ds_d35ac6f3910c",
  "dataset_name": "即时综合数据集",
  "select_columns": [
    {
      "column_name": "platform_name",
      "verbose_name": "平台",
      "component_dataset_alias": "ds_3d2714e6d40e"
    },
    {
      "column_name": "dept_name",
      "verbose_name": "部门",
      "component_dataset_alias": "ds_1n8a4K0d7yBB"
    }
  ]
}
```

> **MCP 模式注意**：`query_metadata()` 无参数时只返回数据集列表（不含 `select_columns`）；调用 `query_metadata(dataset="<alias>")` 才能获取包含 `select_columns` 的完整数据集信息。

### 12.2 查询组件字段是合法的筛选条件（扩展字段集规则）

> **核心规则**：`dataset_select_columns.csv` 中出现的 `column_name`，即使该字段**不存在于** `dataset_fields.csv` 的对应数据集字段列表中，也是该数据集的**合法筛选条件**，可以直接作为 `filters` 参数传入查询。

**典型场景**：广告数据集本身没有 `dept_name`（部门名称）字段，但 `dataset_select_columns.csv` 记录了该广告数据集关联了 `dept_name` 查询组件，则 `dept_name` 可以作为广告数据集的筛选条件使用。

**处理规则**：
- 校验筛选字段是否合法时，必须同时检查 `dataset_fields.csv` **和** `dataset_select_columns.csv`
- 只要字段出现在 `dataset_select_columns.csv` 中对应数据集（`current_dataset_alias`）的 `column_name` 列，就允许作为 `filters` 使用
- 不得因字段不在 `dataset_fields.csv` 中就拒绝该筛选条件

### 12.3 权限校验流程（枚举值来源验证）

当用户提供的筛选值涉及查询组件字段时，**必须先验证该值在用户权限范围内**，再构造查询。

**校验步骤**：

```
第一步：获取当前数据集的查询组件列表
  - CLI 模式：读取 data/dataset_select_columns.csv，过滤 current_dataset_alias = 当前数据集
  - MCP 模式：调用 query_metadata(dataset="<alias>")，读取响应中的 select_columns 数组
  筛选字段（如 platform_name）是否出现在 column_name 列表中？
  ↓ 否 → 按普通字段处理，跳过权限校验
  ↓ 是 → 继续以下步骤

第二步：获取 component_dataset_alias（枚举值来源数据集）

第三步：查询 component_dataset_alias 数据集
  - CLI 模式：
    ① 先从 datasets.csv 查出 component_dataset_alias 对应的整数 table_id（--table-id 只接受整数，不接受 alias）：
       python3 -c "
       import csv
       with open('data/datasets.csv', encoding='utf-8-sig') as f:
           rows = list(csv.DictReader(f))
       row = next((r for r in rows if r['dataset_alias'] == '<component_dataset_alias>'), None)
       print(row['table_id'] if row else 'NOT FOUND')
       "
    ② 用整数 table_id 执行查询（注意：--json 传参，不支持 --dimensions 独立参数）：
       opscli query simple --table-id <integer_table_id> \
         --json '{"dimensions":[{"field":"<column_name>","alias":"f_col"}],"limit":100}' \
         --run --pretty
  - MCP 模式：query_simple(table_id="<component_dataset_alias>", dimensions=["<column_name>"])
  不传 filters，目的是获取该用户下的合法枚举值列表

第四步：检查用户指定的筛选值是否在合法值列表中
  ↓ 在列表中 → 有权限，继续构造原始查询
  ↓ 不在列表中 → 无权限，执行 12.4 无权限处理流程
```

### 12.4 无权限时的处理

- **明确告知用户**：该筛选值（如 "Amazon"）在当前账号的权限范围内不存在
- **展示合法值列表**：即 `component_dataset_alias` 查询返回的枚举值，供用户选择
- **停止原始查询**：禁止继续构造或执行原始查询
- **引导用户**：使用 `AskUserQuestion` 让用户从合法值列表中选择，或告知其联系管理员获取权限

**示例流程**：

```
用户请求：查询 Amazon 平台的广告数据

第一步：读取 dataset_select_columns.csv
→ ads_dataset 数据集的 platform_name 查询组件，component_dataset_alias = platform_component

第二步：查询 platform_component 数据集获取合法平台列表
→ CLI 模式：先从 datasets.csv 查出 platform_component 对应的整数 table_id，再执行：
   opscli query simple --table-id <integer_id> \
     --json '{"dimensions":[{"field":"platform_name","alias":"f_platform"}],"limit":100}' \
     --run --pretty
→ MCP 模式：query_simple(table_id="platform_component", dimensions=["platform_name"])
→ 返回：["Temu", "TikTok Shop", "Walmart"]

第三步：用户指定 "Amazon" 不在列表中
→ 无权限，告知用户：当前账号不包含 Amazon 平台的数据权限
→ 通过 AskUserQuestion 展示可用平台列表，建议选择其一
→ 停止原查询，等待用户重新确认筛选条件
```

### 12.5 本章规则与其他规则的优先级

- 本章权限校验优先于字段匹配（第六章）执行 — 即使字段确认无歧义，也必须先过权限校验
- 本章扩展字段集规则（12.2）与第六章字段存在性校验并列适用 — 两个来源都算合法字段
- 本章规则不影响 `dataset_fields.csv` 中的维度/指标字段的正常聚合逻辑

## 十三、取数状态强制输出格式

每次取数后，回答必须按以下顺序输出，且取数状态块必须固定位于回答开头：

1. **取数状态**（固定格式，见下）
2. 核心结论与动作方向
3. 关键数据
4. 诊断依据
5. 动作清单

**取数状态固定格式（每次取数必须输出）**：

```markdown
## 取数状态
- 取数结果：成功 / 部分成功 / 失败
- 当前日期：YYYY-MM-DD
- 数据时间：YYYY-MM-DD 至 YYYY-MM-DD
- 筛选范围：（平台/部门/小组/国家等）
- 当前查询范围：（部门→小组，继承链）
- 已取数据集：（alias 列表）
- 未取到或缺失：（或"无"）
- 数据注意事项：（跨数据集口径差异，或"无"）
```

**处理规则**：
- 取数失败时必须说明失败原因，**不能假装取数成功**
- 部分成功（某数据集失败）时，必须注明哪个数据集未取到
- 不得使用训练知识、截图猜测、历史记忆或其他未验证来源补数字

## 十四、平台过滤强制规则

本 Skill 范围为 Amazon SC 和 Amazon VC，**不得返回其他平台数据**。

| 场景 | 规则 |
|------|------|
| 每次取数 | 必须强制添加平台过滤条件，限定为 Amazon SC 和 Amazon VC，不得省略 |
| 数据集没有平台字段 | 通过渠道名称、店铺名称等可用字段确保结果仅含 Amazon 数据 |
| 取数返回 0 行 | 不得改查其他平台或跳过平台过滤；如实报告"该范围在 Amazon SC/VC 下无数据"，建议用户确认范围 |
| 取到非 Amazon 数据（Temu/TikTok 等） | 必须丢弃，报告"取到了非目标平台数据，已过滤，实际可用数据为 0 行" |

**禁止行为**：
- ❌ 省略平台过滤条件
- ❌ 将非 Amazon 平台数据当作 Amazon 数据展示或参与计算
- ❌ 取数 0 行时改查其他平台

## 十五、内部口径常识映射

取数前必须先做以下口语映射，避免字段误用。

### 15.1 平台映射

| 用户说 | 实际查询 |
|--------|---------|
| 亚马逊 | Amazon SC + Amazon VC（同时查） |
| Amazon / 亚马逊SC | Amazon SC（仅SC） |
| Amazon VC / 亚马逊VC | Amazon VC（仅VC） |

### 15.2 部门映射

- 常见部门说法：`X部`、`项目X部`
- `范泰克`、`宁波`、`ohwill`、`傲家` 默认代表**部门字段**，不要误映射为渠道、品牌、店铺或小组

**部门名称三步匹配规则（铁律）**：

1. **精确匹配**：按用户原词精确匹配 `dept_name` 字段 → 匹配成功则直接取数，不得追问
2. **标准化重试**：精确匹配返回 0 行时，做阿拉伯数字 ↔ 中文数字互换后重试（"9部"→"九部"，"3部"→"三部"）  
   **严禁**在互换过程中增减文字（"九部"与"项目九部"是两个不同部门，不可互换）
3. **仍有歧义才追问**：标准化后仍匹配不到，或命中多个部门，才追问用户确认

### 15.3 小组与人员映射

| 用户说 | 实际使用字段 |
|--------|------------|
| 小组 / 销售小组 / 运营小组 / 各小组 | 销售小组字段（如 `team_name`） |
| 人名 | 销售人员字段（如 `team_username`） |
| 开发小组 / 开发人员（明确说） | 开发小组/开发人员字段 |

### 15.4 币种口径

- 字段名**不含"原币"**的金额字段 → 按**人民币**口径理解
- 字段名**含"原币"**的金额字段 → 按**当地币种**理解
- 输出金额时必须说明币种；跨币种数据不得直接相加

## 十六、部门/项目部分析下钻规则

当分析对象为部门或项目部时：

- 默认同时执行两个层级的取数与诊断：
  - ① **部门汇总层面**（整体花费、销售额、ACOS 等核心指标）
  - ② **按销售小组下钻明细**（各小组花费、销售额、ACOS 对比）
- 下钻为**默认行为**，不需要用户额外要求
- 用户明确说"只要汇总"或"不需要看小组明细"时，才可跳过下钻

## 十七、`self_small_cat` 使用限制

- `self_small_cat`（细分品线）**仅范泰克部门可用**
- 其他部门不得使用该字段筛选、分组或解释
- 用户未说明部门是否为范泰克时，不使用该字段；如确需细分品线，先确认部门

## 十八、典型用例防错补充

以下用例是 ops-dataset-query 中高频翻车场景，补充至防错清单：

| 用户问题 | 高风险错误 | 正确做法 |
|---------|----------|---------|
| 看部门广告表现 | 未加平台过滤或事前追问范围 | 直接按美国 Amazon SC+VC 取数，取数状态写明 |
| 取数返回 Temu/TikTok 等非 Amazon 数据 | 当作 Amazon 数据展示或参与计算 | 必须过滤丢弃，报告"取到了非目标平台数据，已过滤" |
| 取数返回 0 行 | 改查其他平台或跳过过滤 | 如实报告"该范围在 Amazon SC/VC 下无数据"，建议用户确认范围 |
| 查范泰克表现 | 误当品牌或渠道 | 默认范泰克代表**部门**字段 |
| 查某渠道广告 | 用平台+国家冒充渠道 | 使用 `channel_name` 字段，找不到则说明字段缺失 |
| 查某店铺广告 | 返回平台维度数据 | 匹配店铺/账号维度，找不到则说明 |
| 看各小组表现 | 命中开发组 / 只展示 Top 小组 | 用销售小组字段，全量展示 |
| 查金额字段 | 混用人民币与原币 | 不含"原币"为人民币，含"原币"为当地币种，跨币种不直接相加 |
| 查近 30 天 | 不同工具日期不一致 | 统一含今天，输出当前日期和绝对起止日期 |
| 细分品线分析 | 非范泰克部门使用 `self_small_cat` | 仅范泰克使用，其他部门换维度 |
| 明确指定数据集 | 直接照用但结果不对 | 校验字段、粒度、口径，必要时补数 |
