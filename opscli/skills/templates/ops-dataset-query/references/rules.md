# 查询意图澄清规则

> **适用范围**：AI Agent 通过 `opscli query` 或 `query_*` MCP Tool 执行数据查询前，必须先按本规则检查用户输入。
> **核心原则**：不确定就问，禁止猜测。所有"可能歧义"的情况都必须向用户确认。

---

## 一、时间范围规则

### 1.1 "近 xx 天"是否包含今天

| 用户表述 | 歧义点 | 澄清问题 |
|---------|--------|---------|
| 近7天 / 最近一周 | 是否包含今天？ | "请问'近7天'是指最近7个完整自然日（如 5/4-5/10），还是包含今天（如 5/5-5/11）？" |
| 近30天 / 最近一个月 | 同上 | 同上模板 |
| 近3天 / 近15天 | 同上 | 同上模板 |

**默认策略**：若用户未明确说明，默认理解为**包含今天**（以 `date_id <= 今天` 为右边界），但必须在回复中明示此假设，并告知用户如有异议可以纠正。

### 1.2 月份天数不对等

| 场景 | 歧义点 | 处理规则 |
|------|--------|---------|
| 本月 vs 上月完整月对比 | 月份天数不同（如 3月31天 vs 4月30天） | 月汇总对比时使用**完整自然月**，明确告知用户天数差异；若用户关注的是月趋势，建议使用日均值 |
| 本月1日~N日 vs 上月1日~N日（同期对比） | 天数对等时对比才有意义 | dataComparison 必须使用**相同天数**的同期对比（如 4.1-4.22 vs 3.1-3.22），不可用完整月 |
| 本月1日~N日 vs 上月完整月 | 天数严重不对等 | **必须向用户确认**："本月1-22日只有22天，上月有31天，直接用汇总值对比会有偏差。建议方案：A) 用上月同期1-22日对比，B) 计算日均值后对比，您选哪种？" |
| 查询月份有30号但上月只有31天（没有30号） | 同期天数对不齐 | **必须澄清**："上个月只有31天没有30号对应的同期数据，请问对比上月的30号用的是上月最后一天的数据吗？还是调整为同天数（如都取1-30号）？" |

### 1.3 "本月" / "上月" 边界定义

| 表述 | 默认理解 | 需澄清的场景 |
|------|---------|------------|
| 本月 | 当前自然月（5.1-5.31） | 用户月初问"本月"可能实际想查上月数据 |
| 上月 | 上一個自然月（4.1-4.30） | 跨年时（1月说"上月"指去年12月）需确认年份 |
| 这个月 | 同"本月" | 同上 |
| 最近一个月 | 近30天（滚动）还是当月？ | **必须确认**："是指近30天（滚动），还是当月（5月1日到今天）？" |
| 上个月同期 | 上月1日到同日 | 如今天是5.11，上月同期为4.1-4.11，需确认 |

### 1.4 "上周" / "本周" / "下周"

| 表述 | 默认理解 | 需澄清 |
|------|---------|--------|
| 本周 | 周一至今天 | 是否需要包含完整周？周一至周日？ |
| 上周 | 上周一至上周日 | 跨月时注意归属 |
| 最近一周 | 近7天 | 与"上周"不同，需区分 |

## 二、人员/组织意图澄清规则

### 2.1 人员身份歧义（核心规则）

> **数据集中同时存在"销售"和"开发"两个人员维度，用户只说"xxx"时无法判断是销售还是开发。**

| 字段 | 含义 | 字段名 |
|------|------|--------|
| 销售 | 销售人员姓名 | `team_username` |
| 开发 | 开发人员姓名 | `develop_username` |

**触发条件**：用户查询中包含以下模式时，必须澄清：
- "xxx 的数据" / "xxx 的广告情况" / "xxx 的销售额"（xxx 是人名）
- "查一下张三" / "李四的业绩" / "王五的广告"
- 任何人名 + 指标/数据查询（无法通过上下文判断是销售还是开发）

**澄清模板**：
> "请问'{用户名}'是销售人员还是开发人员？数据集中有'销售'和'开发'两个人员维度，我需要确认按哪个维度过滤。"

### 2.2 小组身份歧义

> **数据集中同时存在"销售小组"和"开发小组"两个组织维度。**

| 字段 | 含义 | 字段名 |
|------|------|--------|
| 销售小组 | 销售团队分组 | `team_name` |
| 开发小组 | 开发团队分组 | `dev_team_name` |

**触发条件**：
- "xxx 小组的数据" / "xxx 组的广告" / "xxx 组的业绩"
- "我们组的" / "团队的数据"

**澄清模板**：
> "请问'{小组名}'是销售小组还是开发小组？数据集中有'销售小组'和'开发小组'两个维度。"

### 2.3 "大组"字段说明

| 字段 | 含义 | 字段名 |
|------|------|--------|
| 大组 | 比销售/开发小组更大的组织单元 | `large_team_name` |

用户提到"大组"时，一般在销售或开发小组上层，无需额外澄清，但需确认是否为大组维度。

## 三、产品标识歧义规则

### 3.1 SKU 类型歧义

> **数据集中至少有 4 种 SKU 标识，用户说"SKU"时无法确定指哪个。**

| 字段 | 含义 | 适用场景 |
|------|------|---------|
| `sell_sku` | 渠道SKU | 平台销售层面，Amazon 上的 SKU ID |
| `ed_sku` | 公司SKU | 公司内部编码 |
| `parent_ed_sku` | 父公司SKU | 变体父级的公司SKU |
| `pmc_code` | 物控编码 | 供应链/物控管理 |

**触发条件**：
- 用户说"查一下 SKU xxx" / "某个 SKU 的数据"
- 用户提供了看起来像 SKU 编码的字符串

**澄清模板**：
> "您提供的'{SKU编码}'是哪种 SKU？数据集中支持：渠道SKU（Amazon 上显示的 SKU）、公司SKU（内部编码）、物控编码。请确认类型。"

### 3.2 ASIN 歧义

| 字段 | 含义 |
|------|------|
| `asin` | 子ASIN（单个变体） |
| `parent_asin` | 父ASIN（变体组） |

**触发条件**：用户提到"ASIN"未明确是父还是子。

**澄清模板**：
> "请问是子ASIN还是父ASIN？（子ASIN = 单个变体，父ASIN = 整个变体组）"

### 3.3 产品型号 / SPU / UPC 等唯一标识

| 字段 | 含义 | 备注 |
|------|------|------|
| `model` | 产品型号 | |
| `spu` | SPU | 注意与 SP(Sponsored Products广告类型) 区分 |
| `upc` | UPC码 | |
| `product_name` | 产品名称 | 模糊匹配 |

**SPU vs SP 歧义**：用户说"SP"时，可能指"SPU"也可能指"Sponsored Products(SP广告)"，取决于语境。若查询内容涉及广告，大概率是SP广告类型。

## 四、币种歧义规则

> **广告数据集中大量指标同时存在原币和人民币(CNY)两个版本。**

| 常见原币字段 | 对应 CNY 字段 |
|------------|-------------|
| `ads_total_spend` (广告费原币) | `ads_total_spend_cny` (广告费) |
| `sales` (广告销售额原币) | `sales_cny` (广告销售额) |
| `cost` (花费原币) | `cost_cny` (花费) |
| `cpc_avg` (平均CPC原币) | `cpc_avg_cny` (平均CPC) |

**触发条件**：用户查询的是广告数据集（table_id: 15, 20, 27-31）的金额指标。

**默认策略**：
- 用户未指定币种时，**默认使用 CNY（人民币）版本**
- 在回复中应明示"以下数据均为人民币计价"
- 如果用户是海外团队或明确提到"美金"、"美元"、"USD"，则使用原币版本

## 五、数据集选择规则

### 5.1 "查广告数据"时的数据集选择

| 用户意图 | 推荐数据集 | table_id |
|---------|-----------|---------|
| 按产品/部门/小组看广告总览 | 广告费数据集 | 15 (inner_where_enabled) |
| 按SP/SD/SB类型看广告花费 | 广告类型花费数据集 | 20 |
| 查SP广告详细指标 | SP广告数据集 | 27 |
| 查SD广告详细指标 | SD广告数据集 | 28 |
| 查SB广告详细指标 | SB广告数据集 | 29 |
| 综合对比SP+SD | SP+SD广告数据集 | 30 |
| 综合对比SP+SD+SB | SP+SD+SB广告数据集 | 31 |
| 查销售+广告+库存全貌 | 即时综合数据集 | 1 |

**触发条件**：用户说"查广告数据"但未指定粒度时必须确认：
> "有多个广告数据集可用：A) 产品维度的广告总览（含ACOS/点击率等）、B) 按广告类型（SP/SD/SB）细分、C) SP广告详细数据。您需要哪种？"

### 5.2 "查销售数据"时的数据集选择

用户说"查销售"时可能指：
- 即时综合数据集 (table_id=1) 的订单销售数据（`price`, `order_qty`, `gross_profit` 等）
- 广告数据集中的广告销售额（`ads_sales_cny`, `sales_cny`）

**默认策略**：若语境中有"广告"关键词→广告销售额；若为通用"销售数据"→即时综合数据集。

## 六、指标含义歧义规则

### 6.1 销售额相关歧义

| 字段 | 含义 | 备注 |
|------|------|------|
| `original_price` | 销售额（销售价×销量） | 原始售价 |
| `price` | 交易额（实际成交额） | 折扣后金额 |
| `ads_sales_cny` | 广告销售额 | 广告带来的销售额 |

**触发条件**：用户说"销售额"。

**默认策略**：默认使用 `price`（交易额），因为反映真实收入。如果用户说"原价销售额"则用 `original_price`。

### 6.2 广告费相关歧义

| 字段 | 含义 |
|------|------|
| `advertising_fee` | 广告费（即时综合数据集中） |
| `ads_total_spend_cny` | 广告费（广告数据集中） |

两者数据源不同，值可能有差异。应优先使用对应数据集来源的字段。

### 6.3 库存相关歧义

| 字段 | 含义 |
|------|------|
| `platform_qty` | 平台库存（FBA仓） |
| `total_qty` | 总库存 |
| `transfer_qty` | 海外仓库存 |
| `transfer_available_qty` | 海外仓可售库存 |
| `local_qty` | 国内库存 |
| `intransit_qty` | 在途库存 |
| `coming_qty` | 采购库存 |
| `destroy_qty` | 待销毁库存 |

**触发条件**：用户说"查库存"时。**必须确认**用户要查哪种库存。

### 6.4 品类 / 类目歧义

| 字段 | 含义 | 适用场景 |
|------|------|---------|
| `category` | 品类（内部分类） | 公司内部品类体系 |
| `amazon_cat` | 平台类目（Amazon类目） | Amazon 平台的分类 |

**触发条件**：用户说"查某个品类/类目"时需确认用哪个分类体系。

## 七、广告类型术语规则

### 7.1 广告类型缩写

用户可能不熟悉广告类型缩写：

| 缩写 | 全称 | 说明 |
|------|------|------|
| SP | Sponsored Products | 商品推广广告 |
| SD | Sponsored Display | 展示型推广广告 |
| SB | Sponsored Brands | 品牌推广广告 |
| SBV | Sponsored Brands Video | 品牌视频推广广告 |

**规则**：用户提到广告类型时，不用解释缩写，但需确保选择了正确的数据集。

### 7.2 ACOS / ROAS 歧义

数据集 1（即时综合）和多个广告数据集（15, 20, 27-31）都有 ACOS/ROAS 指标，但计算口径可能不同：
- 数据集 1 的 ACOS = `广告费 / 广告销售额`（全局口径）
- 数据集 27-31 的 ACOS = `花费 / 广告销售额`（按广告层级口径，如 campaign/ad_group）

**规则**：查询 ACOS/ROAS 时，优先使用对应的广告数据集（而非即时综合数据集），选择理由需告知用户。

## 八、catalog 意图匹配规则

### 8.1 意图匹配优先级

当 catalog 的 `intents` 可用时，按以下优先级选择数据集：
1. 关键词精确匹配 > 模糊匹配
2. 用户明确提到某数据集名称 > intents 推荐
3. intents 推荐 > 本地关键词检索

### 8.2 多个数据集同时匹配

当用户查询匹配到多个数据集时（如"查广告"匹配到 6 个广告数据集），**必须列出候选项让用户选择**，不得静默选择第一个。

## 九、查询前自检清单

在执行任何查询前，AI Agent 必须完成以下检查：

```
□ 【时间】用户的日期范围是否明确？（近xx天是否含今天？月份对比是否天数对等？）
□ 【人员】查询涉及人名/小组名时，是否已确认是销售还是开发？
□ 【产品】查询涉及 SKU/ASIN 时，是否已确认具体是哪种标识？
□ 【币种】查询广告金额指标时，是否已默认使用 CNY（或用户明确指定了币种）？
□ 【数据集】用户意图匹配到多个数据集时，是否已让用户选择？
□ 【指标】用户提到的指标是否可能存在多义（如"销售额"有 original_price vs price）？
□ 【公式字段】查询 ACOS/ROAS/毛利率等公式字段时，是否加 aggregation？（→ 不加！见铁律九）
□ 【子查询】目标数据集 inner_where_enabled=true 时，是否至少加了日期过滤？（→ 必须！见铁律四）
□ 【default_filters】是否检查了 catalog default_filters 的可用性？（→ 见铁律八）
```

## 十、常见歧义速查表

| 用户表述 | 可能的歧义 | 处理方式 |
|---------|-----------|---------|
| "查一下张三" | 销售张三 vs 开发张三 | 确认身份 |
| "A组的广告" | 销售A组 vs 开发A组 | 确认组织类型 |
| "SKU ABC123" | 渠道SKU vs 公司SKU vs 物控编码 | 确认SKU类型 |
| "这个ASIN" | 子ASIN vs 父ASIN | 确认ASIN级别 |
| "近7天" | 含今天 vs 不含今天 | 默认含，明示 |
| "和上月比" | 完整月 vs 同期天数 | 确认对比方式 |
| "广告费" | 原币 vs CNY | 默认CNY |
| "销售额" | 交易额 vs 销售价×销量 | 默认交易额 |
| "库存" | 平台库存/总库存/海外仓/在途等8种 | 确认库存类型 |
| "品类" | 内部品类 vs Amazon类目 | 确认分类体系 |
| "SP" | SPU产品 vs Sponsored Products广告 | 根据语境判断 |
| "等级" | 产品的什么等级？(sku_type / pmc_type / level_name) | 确认等级含义 |
| "部门" | 具体哪个部门？（dept_name） | 如用户未指定，按全部部门查询 |
