# 运营流程共建成 Skill

## 目标

和运营同事一起把正在使用的工作流程、判断规则和交付标准整理成明确、可复用的 Skill/技能包。交付这些结果：

- `流程地图`：记录触发场景、输入、流程、判断规则、例外、质量标准、案例和待确认问题。
- `Skill 草案`：生成一个 Skill 文件夹或 `SKILL.md`，让另一个 AI Agent 不需要重新听访谈也能照着执行。
- `试运行问题`：至少两个真实工作里会出现的测试 prompt，用来验证 Skill 是否真的有帮助。
- `数据方案`：当工作流需要内部数据时，给出数据意图、候选数据集、字段/聚合、过滤/对比方式和实际取数方案。
- `取数预检`：生成或更新 Skill 前模拟未来使用者的真实提问，验证 ops 查询条件、字段、过滤、对比和空结果处理是否可执行；流程固化后，日常执行默认直接使用已验证取数规则。
- `评测闭环`：设计 with-skill / baseline 对比、断言、反馈和迭代优化步骤。
- `跨工具方案`：说明当前 AI 工具的专属能力如何替换为其他 AI 工具可执行的通用方案。
- `脚本固化清单`：识别哪些流程步骤应沉淀为 Python 脚本，减少每次 AI 重新理解。
- `HTML 展示`：需要可视化或汇报时，输出可打开的 HTML 报告或审阅页。
- `发布治理`：需要团队共享时，补版本、变更记录、回归评测、负责人和更新分发方案。
- `执行日志`：需要持续迭代时，设计执行记录、失败案例沉淀和自我改进的评测兜底。
- `内测提交`：运营同事用新 Skill 多次执行有效后，能按门槛生成脱敏候选提交包，进入团队候选库。
- `统一框架`：新建 Skill 和已有 Skill 改造都按轻量 `SKILL.md`、按需 `references/`、稳定 `scripts/` 的结构交付，内容不减少但默认加载更少。
- `执行分层`：生成的 Skill 默认先按已固化流程直接执行；只有缺参数、取数失败、字段/权限变化、用户要求测试/优化/发布或需要解释流程时，才展开预检、测试、治理和详细说明。

默认用中文协作访谈、中文整理、中文编写 Skill。只有在用户明确要求英文或其他语言时，才改用对应语言。技术标识符、文件名、字段名、脚本名、工具名和 YAML `name` 仍按生态要求使用英文或原文。保留业务原话、缩写、平台术语、指标名、表名和工具名；如果是团队黑话，补一句简短解释。

## 公司背景

默认面向 Aukeys 跨境电商运营场景。公司业务以跨境电商为主，Amazon 是最大份额平台；因此访谈和 Skill 草案要优先覆盖 Amazon SC/VC、广告、Listing、库存、评论、竞品、利润、渠道、部门、ASIN、类目、国家和平台等常见运营对象。

不要把 Skill 写成泛泛的“运营常识”。如果任务涉及 Amazon 或跨境电商，要主动追问站点、平台、账号/渠道、部门、ASIN、类目、广告类型、时间周期、币种口径、利润口径和业务目标。

## 资源

- 用户要创建或更新 Skill 时，先读 `references/guided-six-gates.md`。这份文档是阶段 0 的执行脚本：按“交互式提问优先、聊天选项降级、表单/HTML 兜底 + 短简答 + 逐题检查”顺序问实业务 6 维信息，不是面向运营同事的一次性表单。
- 需要判断“案例复盘 + 六维信息检查”是否适合当前用户时，读 `references/interview-method-analysis.md`。
- 工作流可能需要内部数据时，读 `references/ops-data-intake.md`，按“识别意图 → 推荐数据集 → 推荐字段和聚合 → 明确数据用途 → 获取数据”的流程推进。
- 需要设计测试、基准对比、评分和迭代时，读 `references/testing-benchmark-loop.md`。
- 生成的 Skill 需要复用到其他 AI 工具时，读 `references/cross-tool-portability.md`。
- 需要判断哪些流程步骤可固化为脚本时，读 `references/script-automation-guide.md`。
- 用户需要可视化交付、审阅页或管理层展示时，读 `references/html-output-guide.md`。
- 需要团队发布、版本管理、变更审查或共享给多工具用户时，读 `references/release-governance.md`。
- 需要让 Skill 基于使用反馈持续改进时，读 `references/self-improvement-loop.md`。
- 需要让内测运营提交多次执行有效的 Skill 时，读 `references/skill-submission-governance.md`。
- 需要给目标 Skill 设计运行摘要、学习日记或日志 schema 时，读 `references/execution-log-schema.md`。
- 新建或改造任何运营 Skill 前，读 `references/skill-framework-standard.md`，按统一框架设计 `SKILL.md`、`references/` 和 `scripts/`。
- 用户要求调整已有 Skill、统一历史 Skill、降低旧 Skill token 负担或对比新旧版时，读 `references/existing-skill-retrofit.md`。
- 六维信息、阶段 1 技术细节和流程地图经用户确认后，读 `references/skill-creator-handoff.md`，再使用当前 AI 工具可用的 skill-creator/技能创建能力生成或更新 Skill。
- 需要访谈问题、对方答得太抽象、或对话卡住时，读 `references/interview-playbook.md`。
- 要整理结构化流程简报或让用户补模板时，读 `references/flow-brief-template.md`。
- 简报填好且用户要生成确定性的 Skill 草案目录时，运行 `scripts/brief_to_skill.py`。脚本会把执行日志、候选提交规范和提交脚本复制到目标 Skill 草案中；生成的是初稿，之后仍要按当前环境的 Skill 写作和校验标准精修。

## 工作流

1. 先判断任务类型。用户要新建 Skill 时进入阶段 0 访谈；用户要改造已有 Skill 时，先按 `references/existing-skill-retrofit.md` 建立基线、盘点文件和保护已有行为，再把现有材料映射回 Q1-Q6。已有文件能回答的问题可以代答，但要展示“我问 → 我从现有 Skill 代答 → 内部检查”，缺口再问用户。

2. 新建 Skill 进入阶段 0：业务 6 维确认。必须打开并执行 `references/guided-six-gates.md`。按 `Q1 业务目标 → Q2 当前做法 → Q3 具体步骤 → Q4 方法论 → Q5 调用方式 → Q6 期望输出` 顺序推进，一题一题问实；每题使用低负担选项题开场，再用短简答补细节；如果当前 AI 工具有按钮式/结构化提问能力且已开启，优先使用它；否则用聊天里的选项题继续推进，不得因为没有交互式 UI 中断流程。每题结束都做内部质量检查，不够具体就继续追问，不得跳到写文件。对用户表达时使用“还差一块信息”，不要说“你没通过”。如果用户更适合讲故事，先请他讲最近真实案例，再把案例拆回 Q1-Q6 补齐。

3. 阶段 0 没确认前，不要创建或更新 Skill 文件。可以做临时笔记、流程地图草稿或待确认清单，但不要生成看似完整的 `SKILL.md`、脚本或目录，避免把空泛假设固化成团队资产。改造已有 Skill 时，允许先建立 git 基线和只读盘点，但不要开始重排内容。

4. 如果用户要求“测试这个 Skill”或“你代替我回答”，仍然要逐条显示阶段 0 的问题、代答内容和内部检查结果。只有展示完 Q1-Q6、阶段 1 技术补充和复述确认后，才允许生成目标 Skill。

5. 聚焦一个任务，不要覆盖整个岗位。问清目标场景、负责人/团队、预期交付物、未来用户会在什么情况下调用这个 Skill。如果用户说不清范围，先让他讲一个最近真实案例，再从案例里反推范围。

6. 用案例复盘整理判断。让运营讲一个最近处理成功的案例：触发点是什么，第一眼看到了什么，打开了哪些数据/工具，检查了什么，做了什么选择，忽略了什么，怎么知道处理完成。

7. 阶段 0 结束后，必须向用户复述 6 维答案并等待确认。复述内容包含业务目标、当前做法、数据/步骤、判断方法、触发话术、输出规范和待确认项。用户确认后，才进入阶段 1。

8. 进入阶段 1：补 4 个技术细节。参照 `guided-six-gates.md` 的阶段 1 补问，确认是否要做测试、优先数据入口/可复用工具或脚本、调用频率、目标使用人群。若用户已经在阶段 0 回答过，就复述并请用户确认，不要重复逼问。

9. 判断是否需要内部数据。只要任务涉及部门、渠道、ASIN、广告、销售、利润、库存、排名、评论、预算、趋势、对比或报表，就启动数据取数检查：识别业务意图，推荐数据集，推荐字段和聚合方式，明确数据用途，再用 `ops-dataset-query` / opscli 正式获取数据。不要凭印象猜字段或伪造数据。

10. 生成 Skill 前做取数可执行性预检。凡是未来 Skill 会用 ops 内部数据，都必须在落地文件前模拟 2-3 个“分享给同事后真实会问的问题”，把自然语言转成查询计划，并按 `references/ops-data-intake.md` 做 `catalog 匹配 → metadata 字段校验 → dry-run/query_build 验证 → 小样本 smoke query`。如果无法构造查询、字段不存在、过滤口径不清、结果为空或权限失败，不要继续写成正式取数流程；先补问用户或把该数据路径标为 `[待确认]`，并给出 Excel/CSV 降级方案。

11. 设计跨工具替代方案。不要假设运营同事一定使用当前 AI 工具。凡是使用当前工具专属服务、MCP、Skill、子 agent、app connector 或内置文件/浏览器能力的地方，都要给出其他 AI 工具可执行的替代路径：Python 脚本、CLI、CSV/Excel 导出、HTML 文件、通用 prompt 或 API 调用。必要时先用当前工具生成高质量参照，再用替代方案复现，并对比校验差异。

12. 抽取隐藏判断。对每个重要决策追问：

- 注意到的信号
- 使用的阈值或对比口径
- 会改变规则的例外
- 新人容易犯的错
- 确认或否定判断的证据

13. 识别脚本固化点。分析哪些步骤稳定、重复、可参数化、对格式或数值准确性要求高；这些优先写成 Python 脚本，减少每次让模型重新理解和重写，降低 token 消耗。

14. 补对比案例。至少问一个失败/返工案例、一个边界案例、一个“看起来相似但应该不同处理”的案例，用来挖边界、升级规则和误判点。

15. 生成流程地图。把访谈结果整理为：

- 触发话术和使用场景
- 必要输入和来源系统
- 工作流步骤
- 判断规则和操作启发
- 例外与升级规则
- 内部数据取数方案
- 取数预检结果和失败降级方案
- 跨工具替代方案
- 可脚本化步骤
- HTML 展示需求
- 输出约定
- 质量标准
- 案例
- 需保留术语
- 待确认问题

16. 生成流程地图后，先套用统一框架。读取 `references/skill-framework-standard.md`，确定主 `SKILL.md` 只放执行路由、快速开始、必要参数、日常工作流、默认执行策略、按需加载资料、错误处理、输出规范、日志和候选提交；完整业务背景、数据方案、判断规则、测试、跨工具和案例放入 `references/`。内容不减少，但默认执行不要加载全部资料。

17. 交给当前 AI 工具可用的 skill-creator/技能创建能力落地。不要把本 Skill 当成完整替代品。本 Skill 负责把已确认的业务 6 维、数据方案、取数预检结果、测试方案、统一框架要求和流程地图整理成结构化 brief；正式创建/更新 Skill 时，按当前环境的 Skill 创建规范处理目录结构、`SKILL.md` frontmatter、progressive disclosure、`references/` / `scripts/` / `assets/` 划分、界面元数据和校验。

18. 起草 Skill。默认中文编写 `SKILL.md` 正文、引用文档、用户提示和输出模板。`SKILL.md` 要简洁、可执行，并优先包含 `快速开始/使用示例`、`必要参数`、`日常工作流`、`默认执行策略`、`按需加载资料`、`错误处理`、`输出规范`。长案例、问题库、字段说明、取数 recipes、取数预检记录、评测用例、跨工具替代方案和输出模板放入 `references/`；稳定重复的格式化、取数后处理、规则计算、报告生成、HTML 渲染和校验动作放入 `scripts/`，脚本语言优先使用 Python。运营类 Skill 默认带执行日志、内测提交门槛和脱敏打包脚本；如果只是个人草稿，可把提交状态标为 `personal_draft`。不要编造阈值、政策或业务规则，缺口标为 `[待确认]`。**草案完成后，必须继续执行步骤 25 的强制发布确认门禁。**

19. 设计测试和基准对比。为草案 Skill 创建至少 2-3 个真实测试 prompt，给每个测试写可检查的断言。新建 Skill 的 baseline 是“不使用 Skill”；更新已有 Skill 的 baseline 是旧版本。涉及当前工具专属服务替代时，必须增加“当前工具参照输出 vs 通用替代方案输出”的对比校验。涉及 ops 取数时，测试断言必须覆盖“能构造查询计划、字段存在、过滤条件有效、结果为空时有解释或降级”。改造已有 Skill 时，公共数据集更新、字段修复、依赖升级应先作为共同前置修正同步到新旧对照版本，不作为新版优劣证据。环境允许且用户授权时可用独立 agent 跑 with-skill / baseline；否则用本地模拟和人工审阅做轻量对比。

20. 补执行日志。目标 Skill 需要被内测、复用或提交时，按 `references/execution-log-schema.md` 设计 `runs/YYYY-MM.jsonl` 执行摘要和 `diary/YYYY-MM-DD.md` 学习日记。日志只记录摘要、口径、状态、断言和反馈，不记录 token、cookie、密码、账号或原始明细。

21. 设计内测提交。只同步多次执行有效的 Skill，不收灵感草稿。按 `references/skill-submission-governance.md` 设定状态、候选门槛、提交包结构和用户确认流程；默认门槛是最近 14 天执行至少 3 次、成功率至少 70%、至少 1 次真实业务输入、无 critical 失败、无敏感信息、运营本人确认提交。

22. 补发布治理。只要 Skill 会给团队、项目部或其他 AI 工具复用，就按 `references/release-governance.md` 补齐版本、CHANGELOG、负责人、回归评测、跨平台冒烟、安全检查和更新分发说明。把 Skill 当成会被别人执行的代码包，而不是一次性文档。

23. 优化上下文负担。内容不减少，但要通过 progressive disclosure 控制默认加载：日常执行只加载 `SKILL.md` 和本次必要的 0-2 个 reference，优先直接运行已固化脚本或已验证取数规则；测试、发布、跨工具迁移、流程解释、错误排查或用户明确要求优化时，再加载完整资料。改造已有 Skill 时，估算旧版和新版常规执行 tokens；新版若高出 25% 以上，必须先压缩主文件、合并重复 reference 或把固定流程脚本化。

24. 迭代优化。根据测试输出、断言结果、执行日志和用户反馈修改 Skill。每轮都记录修改点、提升点、仍未解决的问题。需要持续运行的 Skill，按 `references/self-improvement-loop.md` 记录失败案例和候选改进；只有经过断言复测和人工确认的反复失败，才沉淀为正式规则。直到用户确认满意，或测试反馈不再暴露有意义的问题。**迭代优化完成后，必须继续执行步骤 25 的强制发布确认门禁。**

25. **[强制] 发布到技能广场确认门禁。** 无论通过哪条路径到达（新建 Skill 草案完成、已有 Skill 改造完成、迭代优化完成、或用户说"好了"/"完成"/"收工"），只要本次会话中创建或修改了 Skill 目录的内容，就**必须**执行此步骤，不得跳过：

    使用 `AskUserQuestion` 向用户确认是否发布到技能广场：

    ```
    AskUserQuestion({
      questions: [
        {
          question: "Skill 工作已完成。是否将「<skill_name>」发布到技能广场？",
          header: "发布确认",
          multiSelect: false,
          options: [
            { label: "发布到技能广场（全员可见）", description: "调用 ops-skills 完成认证、版本号检查和发布" },
            { label: "发布到技能广场（仅部门可见）", description: "仅部门内成员可见与安装" },
            { label: "暂不发布", description: "稍后用 opscli skills publish 手动发布" }
          ]
        }
      ]
    })
    ```

    用户选择"发布到技能广场"时，按以下流程执行：

    a. **调用 `ops-skills` Skill**，先执行认证门禁（`opscli auth token status`，未登录则调用 `ops-auth`）

    b. **版本号准备**（按 ops-skills 版本号铁律）：
       - 新建 Skill：确认 `data/VERSION.json` 存在（缺失则创建 `{"name": "<skill-name>", "version": "0.0.1"}`），确认 `SKILL.md` frontmatter 包含 `version: v0.0.1`（缺失则补全）
       - 改造/优化已有 Skill：按铁律递增 `data/VERSION.json` 中的 `version`（如 `0.1.0` → `0.1.1`），同步更新 `SKILL.md` frontmatter 的 `version`（如 `v0.1.1`）
       - 确保 VERSION.json 的 version（无 v 前缀）与 SKILL.md frontmatter 的 version（有 v 前缀）数值一致

    c. **执行发布命令**：
       - 全员可见：`opscli skills publish --dir <skill-dir> --share-type company --changelog "<变更摘要>"`
       - 部门可见：`opscli skills publish --dir <skill-dir> --share-type department --changelog "<变更摘要>"`

    d. **发布成功后**向用户报告：identifier（如 `pengjianchao@ops-xxx`）、版本号、可见范围

    用户选择"暂不发布"时，告知用户：`后续可通过 opscli skills publish --dir <skill-dir> --share-type company --changelog "版本说明" 手动发布`

## [强制] 技能广场发布确认门禁

> **【强制】每次创建或优化 Skill 后，必须执行发布确认，不得跳过。**

无论本次任务走了哪条路径（新建 Skill / 改造已有 Skill / 迭代优化），只要在本次会话中创建或修改了 Skill 目录中的文件，就必须在工作完成后立即使用 `AskUserQuestion` 向用户确认是否发布到技能广场。

**触发条件（满足任一即执行）：**
- Skill 草案首次生成完成（步骤 18 结束）
- 已有 Skill 改造/优化完成（步骤 24 结束，用户确认满意）
- 用户明确表示"好了"、"完成"、"收工"、"就这样"等结束信号
- 本次会话中使用了 Edit/Write 工具修改了目标 Skill 目录中的任何文件

**执行方式：** 参见步骤 25 的详细流程。核心是 `AskUserQuestion` 三选一（全员发布 / 部门发布 / 暂不发布），选择发布时调用 `ops-skills` Skill 完成认证门禁 + 版本号准备 + `opscli skills publish`。

**禁止行为：**
- 工作完成后直接结束对话，不询问发布意愿
- 仅在对话文本中口头提及"你可以发布"，不使用 `AskUserQuestion` 工具
- 假设用户下次会自己发布而跳过确认

## 默认中文规则

以后制作或更新 Skill 时，默认使用中文：

- YAML `description` 默认中文，必须写清“做什么 + 什么时候用”。
- `SKILL.md` 正文默认中文，标题优先使用 `## 目标`、`## 工作流`、`## 判断规则`、`## 输出规范` 等中文标题。
- `references/` 中面向 AI 或用户阅读的资料默认中文。
- `agents/openai.yaml` 的 `display_name`、`short_description`、`default_prompt` 默认中文。
- 只有以下内容保留英文或原文：Skill 文件夹名、YAML `name`、脚本/函数/字段/数据表/指标/工具/API 的真实名称、用户提供的原始术语。

## 六维信息映射

把六维信息映射进最终 `SKILL.md`。这是内部检查清单，不要原样丢给运营同事填写：

| 维度 | 需要采集 | 写入位置 |
| --- | --- | --- |
| Q1 业务目标 | 目标结果、不做的代价 | `## 目标` 或 `## 业务背景` |
| Q2 当前做法 | 人工基线、工具、耗时、痛点 | `## 当前工作流（人工版）` |
| Q3 具体步骤 | 每步的动作、输入、输出、判断 | `## 工作流` 或 `## Skill 工作流（自动版）` |
| Q4 方法论 | 阈值、优先级、例外、判断规则 | `## 判断规则` 或 `## 核心原则 / 踩坑规避` |
| Q5 调用方式 | 真实触发话术、业务入口 | YAML `description` 和 `## 触发场景` |
| Q6 期望输出 | 文件/报告/消息格式、落点、命名、完成信号 | `## 输出规范` |

## 内部数据检查

当 Skill 需要使用公司内部数据时，必须按以下顺序推进：

1. `识别意图`：把用户问题翻译成业务对象、时间范围、平台/国家/部门/渠道/ASIN/类目、指标和决策用途。
2. `推荐数据集`：使用 `ops-dataset-query` 的 catalog 优先流程，按 intents 匹配候选数据集。不能跳过 catalog 直接猜 dataset。
3. `推荐字段和聚合`：列出维度、指标、聚合方式、过滤条件、排序、limit 和是否需要环比/同比/周期对比。
4. `明确数据用途`：说明数据用于访谈举例、规则阈值校准、Skill 测试样本、报告生成，还是正式业务判断。
5. `取数预检`：模拟未来使用者的真实提问，至少验证 2 个查询计划能通过字段、过滤、排序、limit 和日期对比检查；需要正式业务判断时再做小样本 smoke query。
6. `实现获取数据`：按 `ops-dataset-query` 规则完成认证、字段校验、轻量探查和正式查询；保存原始结果，并在 Skill 草案里写清数据口径和限制。

如果用户只说“查一下数据”或“拿内部数据看看”，先推荐可选数据方案，让用户确认用途和范围，再执行查询。

## 跨工具兼容原则

生成的 Skill 默认要能迁移到其他 AI 工具中使用。设计时必须区分：

- `当前工具专属能力`：当前 AI 工具的 Skill/技能系统、MCP 工具、子 agent、app connector、内部文件链接、浏览器或内置文档/表格/演示能力。
- `通用替代能力`：Python 脚本、命令行、CSV/Excel 输入输出、HTML 静态页、Markdown prompt、公开 API 或公司标准导出文件。

如果某一步只能在当前 AI 工具内部完成，必须写清替代方案或降级路径。可先用当前工具能力生成一份高质量参照，再用替代方案生成同类结果，并用断言或人工审阅对比校验。

写作时遵守跨平台“干净指令”：

- 正文不用某个平台专属的触发符号当执行命令；必须提及时只作为例子说明。
- 工具写能力，不写死工具名，例如写“调用命令行执行脚本”，不要假设所有平台都叫同一个工具。
- 路径用相对路径或占位符，不硬编码某个 AI 工具的本地目录。
- 平台专属增强放入清楚标注的独立段落或 HTML 注释，并提供默认降级路径。

## 脚本固化原则

优先把以下动作固化为 Python 脚本：

- 稳定重复的数据清洗、字段映射、聚合计算。
- ACOS、ROAS、CTR、CVR、毛利率、环比等确定性指标计算。
- 报告、Excel、CSV、JSON、HTML 的固定格式生成。
- 阈值规则、异常标记、输出校验。
- 多 AI 工具都需要复用的中间转换。

不要把高度依赖运营判断、需要解释业务背景、或规则仍未稳定的内容过早脚本化。脚本的作用是减少重复理解和降低 token 消耗，不是掩盖未确认的业务规则。

## HTML 展示原则

当输出需要给运营、主管或多人审阅时，优先考虑额外生成 HTML：

- 诊断报告：适合用 HTML 展示摘要、指标卡、异常表、趋势图和行动建议。
- 评测审阅：适合用 HTML 并排展示 baseline、with-skill、替代方案输出和断言结果。
- 培训交接：适合用 HTML 展示流程图、案例、常见错误和检查清单。

HTML 默认生成静态文件，使用本地 CSS/JS，不依赖某个 AI 工具的内置浏览器。需要图表时优先用轻量、可离线的方案；不要为了展示引入复杂前端工程。

## 测试与迭代闭环

每个正式 Skill 草案都要带测试方案：

- `测试用例`：至少 2-3 个真实 prompt，覆盖正常案例、边界案例、错误/缺数据案例。
- `基准对比`：新 Skill 对比不使用 Skill 的输出；改旧 Skill 对比旧版本输出。
- `断言`：尽量写成可检查标准，例如必须包含哪些字段、必须识别哪些异常、不能给出哪些高风险建议。
- `评分`：记录通过/失败、证据和原因。主观型输出用人工审阅，数据型输出优先脚本化检查。
- `迭代`：根据失败断言和用户反馈更新 Skill，再重跑同一批测试，避免只凭一次感觉交付。
- `回归门槛`：团队共享前，同一批核心用例不能比旧版或 baseline 更差。
- `执行日志`：持续使用的 Skill 记录 prompt、输入摘要、输出路径、断言结果、用户反馈和修复建议。
- `内测提交`：多次执行有效后，使用候选门槛判断是否提交团队候选库；未经用户确认不自动提交。

不要为了测试而编造业务事实。测试数据可模拟，但必须标注为模拟；正式结论必须来自用户提供文件或 ops 内部数据。

## 执行日志

目标 Skill 只要会被持续使用、内测或提交给团队候选库，就默认设计轻量执行日志。日志不是聊天全文存档，而是帮助团队判断“这个 Skill 是否真的被用过、是否有效、哪里需要改”的证据。

默认采用 `references/execution-log-schema.md` 的结构：

- `runs/YYYY-MM.jsonl`：每次执行记录一行摘要，包含时间、使用人、运行环境、Skill 名称/版本、业务意图、输入摘要、数据来源、执行状态、断言结果、错误分类和用户反馈。
- `diary/YYYY-MM-DD.md`：记录可复用经验、错误案例、功能建议和复盘结论，使用 `[LRN]`、`[ERR]`、`[FEAT]`、`[REF]` 标记。

隐私和安全优先。日志只记录摘要和判断证据，不记录 token、cookie、密码、账号、客户隐私、供应商报价、原始明细数据或未经脱敏的内部链接。

## 内测提交

目标 Skill 默认先是个人草稿，只有多次执行有效后才建议提交。不要把一次灵感、一次试跑或尚未验证的访谈稿同步到团队候选库。

默认按 `references/skill-submission-governance.md` 处理状态和门槛：

- `personal_draft`：个人草稿，可继续试用和修改。
- `candidate`：最近 14 天执行至少 3 次，成功率至少 70%，至少 1 次真实业务输入，无 critical 失败，无敏感信息，且运营本人确认提交。
- `team_beta`：经过团队小范围复用、反馈和回归测试。
- `standard`：成为团队推荐或标准 Skill。

需要提交时，优先使用目标 Skill 中复制的 `scripts/qualify_candidate.py` 判断是否达标，再用 `scripts/package_submission.py` 生成脱敏提交包。提交包至少包含 Skill 压缩包、提交说明、执行摘要、资格判断和安全检查结果；未经用户确认，不自动提交。

## 访谈规则

提问要具体、低负担。避免“把你所有方法都讲一下”这种大问题。优先这样问：

- "最近一次你判断得很准的案例，从接到问题开始讲。"
- "你第一眼看哪个指标？为什么不是另一个指标？"
- "什么情况看起来像这个问题，但其实不能按这个方法处理？"
- "新人最容易漏掉哪一步？"
- "如果 AI 只能问你三个字段，你希望它先问什么？"

每轮问题控制在 7 个以内，并按目的分组。每轮结束后，简短总结已确认内容、缺口和下一轮只问什么。

使用柔性的内部质量检查。如果答案为空、抽象、前后矛盾、只有动作没有判断，或只说“看情况”却没有阈值/例子，不要急着写 Skill。对外表达要友好：引用对方的原话，说明“这里 AI 还不知道该怎么执行”，再问一个最小的具体问题。

不要对运营同事使用这些表达：

- “你这个没通过”
- “必须按模板填完”
- “你的回答太敷衍”

改成：

- “这块我帮你翻译成 AI 能执行的规则，还差一个判断标准。”
- “你不用写完整 SOP，讲最近一次怎么做的就行。”
- “这个地方如果交给新人，你会提醒他先看什么？”
- “我们先用一个案例跑通，后面再补边界。”

## 起草前最低信息

起草 Skill 前，必须确认或标记 `[待确认]`：

- 目标用户和目标任务
- 应触发 Skill 的真实话术
- 必要输入及来源
- 如需内部数据：候选数据集、字段、聚合、过滤和用途
- 如需内部数据：取数预检是否通过、失败原因和降级方案
- 当前 AI 工具专属能力及其通用替代方案
- 可固化为 Python 脚本的步骤
- 是否需要 HTML 展示
- 统一框架与加载策略：主 `SKILL.md` 放什么，哪些 reference 日常读取，哪些只在测试/发布时读取
- 如果是改造已有 Skill：旧版基线、保留行为、共同基础设施修正和同源对比方案
- 是否需要执行日志和内测提交；如需要，确认日志位置、候选门槛、提交人、审核人和同步位置
- 正常工作流路径
- 至少 3 条判断规则或操作启发
- 至少 2 条例外或升级条件
- 期望输出格式
- 质量检查或审核标准
- 至少 1 个真实案例
- 至少 2 个测试 prompt 和对应验证点

如果缺这些信息，继续访谈，不要产出看似完整但实际空泛的 Skill。

## 交付格式

交付时包含：

- `流程地图`: 已确认的触发场景、输入、流程、判断规则、例外、质量标准、案例和待确认问题
- `Skill 草案`: 已创建/更新的文件，或拟定的 `SKILL.md`
- `数据方案`: 涉及内部数据时，说明意图、数据集、字段、聚合、过滤、用途和取数状态
- `取数预检`: 涉及内部数据时，说明模拟问题、查询计划、字段校验、dry-run/smoke query 结果和降级方案
- `跨工具方案`: 当前工具专属能力和替代实现路径
- `脚本固化`: 建议沉淀为 Python 脚本的步骤
- `HTML 展示`: 是否生成 HTML 及展示内容
- `统一框架`: 主文件、references、scripts 的拆分结果，日常加载策略和 token 负担估算
- `待确认`: 仍不确定的业务规则、阈值、工具或责任人问题
- `试运行问题`: 用于前向测试的真实 prompt
- `评测结论`: baseline 对比、断言结果、用户反馈和下一轮优化建议
- `发布治理`: 团队共享时的版本、负责人、CHANGELOG、回归门槛、跨平台冒烟和更新方式
- `迭代日志`: 需要持续运行时的执行记录位置、失败案例沉淀方式和人工审核规则
- `内测提交`: 候选门槛、提交包内容、脱敏检查结果和是否已获用户确认

本地 Skill 完成后，如果有校验脚本，运行校验并报告结果。
