# 内部数据取数检查

当用户要把跨境电商/Amazon 运营流程做成 Skill，且流程涉及指标、报表、部门、渠道、ASIN、广告、销售、利润、库存、评论、Listing 或周期对比时，使用本流程。目标不是直接“查个数”，而是帮助运营把数据需求讲清楚，并通过 ops 正式入口拿到准确数据。

必须配合 `ops-dataset-query` 使用。查询数据时遵循它的规则：catalog 优先、字段校验、轻量探查、简化接口优先，不直接调用后端 HTTP，不伪造字段。

## 1. 识别意图

先把用户口头需求翻译成数据意图：

- 业务对象：部门、项目部、大组、小组、渠道、平台、国家、ASIN、类目、广告类型、活动、关键词、搜索词等。
- 时间范围：当前期、对比期、同比/环比、最近完整自然月、最近 7/14/30 天。
- 指标目标：销售额、订单、广告花费、ACOS、ROAS、CTR、CVR、CPC、毛利、毛利率、库存、排名、评论等。
- 决策用途：诊断问题、校准阈值、生成报告、整理案例、构造测试样本、验证 Skill 输出。
- 输出粒度：总览、部门、渠道、ASIN、活动、搜索词、日期趋势。

如果用户没有说清楚周期，Amazon 运营分析默认建议“最近一个完整自然月 + 上一个完整自然月对比”；广告搜索词/活动动作类任务可建议最近 7/14/30 天，由用户确认。

## 2. 推荐数据集

使用 `ops-dataset-query` 的 catalog 优先流程：

1. 调用远程 catalog，读取 intents。
2. 按用户意图匹配 `use_cases`、`keywords` 和 `scenario_description`。
3. 提取候选数据集的 `table_id`、`dataset_alias`、`default_filters`、`comparison_strategy`。
4. 如果 catalog 失败，再使用本地缓存或关键词搜索兜底。

向用户说明候选数据集时，用业务语言：

```markdown
我建议先用这类数据：
- 广告明细：看广告花费、曝光、点击、订单、ACOS/ROAS。
- 经营/利润明细：看总销售、订单、毛利、广告费占比。
- 活动层数据：看 campaign/ad type 的结构问题。

用途：先确认问题在哪一层，再决定这个 Skill 的规则和测试样本。
```

## 3. 推荐字段和聚合

按“维度 + 指标 + 聚合 + 过滤 + 对比”给方案。

常见维度：

- `date_id`
- `platform_name`
- `country_name`
- `dept_name`
- `channel_name`
- `large_team_name`
- `team_name`
- `asin`
- `product_name`
- `amazon_cat`
- `category`
- `ads_type` / `ad_type`
- `campaign_name`

常见指标与聚合：

- 广告花费：`SUM`
- 广告销售额：`SUM`
- 广告订单：`SUM`
- 曝光：`SUM`
- 点击：`SUM`
- 销售额：`SUM`
- 订单量：`SUM`
- 毛利：`SUM`
- Sessions / Page Views：`SUM`
- ACOS、ROAS、CTR、CVR、CPC：优先用基础指标本地计算或使用数据集已提供的口径，避免直接平均比例。

推荐表达：

```markdown
建议字段：
- 维度：平台、国家、渠道、ASIN、广告类型
- 指标：广告花费 SUM、广告销售额 SUM、广告订单 SUM、点击 SUM、曝光 SUM
- 派生：ACOS = 广告花费 / 广告销售额；CVR = 广告订单 / 点击
- 过滤：date_id 在当前周期；platform_name in ["Amazon", "Amazon VC"]
- 对比：如果用户要环比，当前期 filters + dataComparison 同时传
```

## 4. 明确数据用途

查询前必须问清楚数据用途。不同用途会影响粒度和口径：

- `访谈举例`：可以小样本，重点帮助运营讲清判断。
- `规则阈值校准`：需要较完整周期和足够样本，不能只查一两行。
- `Skill 测试样本`：需要正常、边界、异常三类数据。
- `正式业务判断`：必须确认周期、口径、过滤条件和数据完整性。
- `报告生成`：需要输出结构、排序、原始底稿保存位置。

如果用途不清，不要直接查询。

## 5. 生成 Skill 前的取数可执行性预检

只要未来 Skill 会使用 ops 内部数据，在生成或更新 Skill 文件前，必须先做预检。目标是验证“未来使用者的一句话”能不能稳定转成可执行查询，而不是等 Skill 安装后才发现字段、过滤条件或日期对比不可用。

### 5.1 模拟分享场景

根据 Q5 触发话术和目标用户，写出 2-3 个真实使用 prompt。覆盖：

- 一个常规场景：用户参数比较完整。
- 一个缺参场景：缺项目部、国家、周期、平台、ASIN、数据入口中的至少一项。
- 一个边界场景：需要环比/同比、跨广告类型、ASIN + campaign、利润/库存辅助判断，或可能返回 0 行。

示例：

```markdown
模拟问题 1：帮我看下宁波部门上周 Amazon SP 和 SD 哪些 ASIN 广告浪费。
模拟问题 2：识别最近 7 天广告花费高但没订单的 campaign，需要按负责人分组。
模拟问题 3：对比本月和上月，找出广告费占比升高但销售没增长的 ASIN。
```

### 5.2 查询计划检查

每个模拟问题都要整理成查询计划：

- 业务对象：部门/负责人/国家/平台/ASIN/广告类型/campaign。
- 时间范围：明确起止日期；相对日期必须转成绝对日期或写明转换规则。
- 数据集候选：`table_id`、`dataset_alias`、选择理由、不能覆盖的场景。
- 维度：字段名、别名、是否必需。
- 指标：字段名、聚合方式、是否需要本地派生。
- 过滤条件：字段、操作符、值、默认值来源。
- 排序和 limit：用于预览、Top N 或输出完整明细。
- 对比方式：是否使用 `dataComparison`，主周期和对比周期如何设置。

### 5.3 字段和 dry-run 校验

按以下顺序验证：

1. 用 catalog 匹配候选数据集，不直接猜 dataset。
2. 拉取 metadata，确认字段存在、字段类型适合过滤或聚合。
3. 用 `query_build` / `query_simple(dry_run=True)` 或等价 CLI 构造 payload，确认维度、指标、过滤、排序和日期对比能通过。
4. 如果 dry-run 通过，再按需要做 `limit 3-10` 的 smoke query，验证过滤条件不会稳定返回 0 行。
5. 如果数据为空，先判断是业务事实为空、默认过滤过窄、字段口径不对，还是权限/数据延迟问题。

### 5.4 预检结论

预检结果必须写进流程地图和交接 brief：

```markdown
## 取数预检

- 模拟问题：
- 推荐数据集：
- 查询计划：
- 字段校验：通过 / 失败，原因：
- dry-run：通过 / 失败，原因：
- smoke query：通过 / 空结果 / 未执行，原因：
- 可写入 Skill 的取数规则：
- 不能写死的口径：
- 降级方案：用户上传 Excel/CSV、减少过滤、改用备用数据集、人工确认字段。
```

如果预检失败，不要把失败查询写成正式工作流。只能写成 `[待确认]` 或降级路径，并继续补问用户。

## 6. 获取数据

执行查询时：

1. 按 `ops-dataset-query` 判断 CLI/MCP 模式。
2. 需要远端数据时先确认认证。
3. 先做字段校验，不猜字段。
4. 对 catalog 的 `default_filters` 做轻量探查，避免默认过滤导致 0 行。
5. 普通聚合优先使用 `query_simple` / `opscli query simple`。
6. 涉及环比/同比时，同时传主周期日期 filters 和 `dataComparison`。
7. 原始结果保存到工作区，例如 `data/<skill-name>/<intent>-current.json`。
8. 在流程地图和 Skill 草案里写明数据集、字段、过滤条件、对比方式和口径限制。

## 7. 写入 Skill 的方式

如果未来 Skill 需要每次都取数，在 `SKILL.md` 写：

- 何时需要取数。
- 用哪个数据集或如何通过 catalog 选择数据集。
- 必要维度、指标、聚合和过滤。
- 生成 Skill 前通过了哪些模拟问题和 dry-run/smoke query。
- 取数失败、字段缺失、数据为空时如何处理。
- 数据仅作参考还是可直接形成业务建议。

同时必须区分两件事：

- `生成/更新前的取数预检`：用于验证未来同事的一句话能否稳定转成查询计划，结果写入 reference。
- `日常执行的取数动作`：流程固化后默认直接使用已验证数据集、字段、过滤和脚本，不重复做完整预检。

只有在字段不存在、权限失败、结果为空、业务对象超出固化范围、数据集变更、口径不清或用户明确要求“重新检查取数方案”时，才重新展开 catalog/metadata/dry-run/smoke query。

如果只是本次创建 Skill 时用数据校准规则，把取数过程放入 `references/data-recipe.md` 或 `references/eval-data-notes.md`，不要把一次性细节塞进主 `SKILL.md`。
