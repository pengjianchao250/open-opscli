# 测试、基准对比与迭代闭环

每个正式 Skill 草案都要设计测试。目标不是证明它“看起来能用”，而是找到它相对不用 Skill 或旧版 Skill 的真实改进点。

## 1. 测试用例

至少准备 2-3 个真实 prompt：

- `正常案例`：用户提供足够信息，Skill 应稳定完成。
- `边界案例`：数据不足、口径不完整、规则例外或需要人工确认。
- `失败/返工案例`：过去容易误判、漏步骤或输出不合格的场景。

每个测试包含：

```json
{
  "id": "case-1",
  "prompt": "用户真实会说的话",
  "files": [],
  "expected_behavior": "希望 Skill 怎么处理",
  "assertions": []
}
```

## 2. 基准对比

根据任务类型选择 baseline：

- 新建 Skill：baseline 是不使用 Skill，直接让 AI 处理同一个 prompt。
- 更新已有 Skill：baseline 是旧版 Skill。
- 数据型 Skill：baseline 输出必须使用同一批输入文件或同一份查询结果，避免口径变化。

比较时看：

- 是否更少追问无关问题。
- 是否更准确识别输入和数据口径。
- 是否执行了关键判断规则。
- 是否正确处理例外和升级。
- 输出是否更接近运营真实交付物。

## 3. 断言设计

优先写可检查的断言：

- 输出必须包含某些章节或字段。
- 必须使用指定周期、平台、国家或部门过滤。
- 必须识别某个异常、例外或风险。
- 必须在数据缺失时停止并追问，不能编造。
- 不得给出某类高风险建议，例如低样本直接停投、品牌词直接否定。

主观型输出也要有评审标准，例如“老板能否直接看懂”“行动建议是否可执行”“是否标注假设”。

## 4. 执行方式

环境允许且用户授权时，可用独立 agent 跑 with-skill 和 baseline。否则用本地模拟：

1. 用草案 Skill 跑一遍测试 prompt。
2. 不用 Skill 或用旧版 Skill 跑一遍同样 prompt。
3. 把两个输出放在一起评审。
4. 记录断言通过/失败和证据。

不要让测试泄漏答案。测试 prompt 应像真实用户请求，而不是把 Skill 的规则完整贴进去。

## 5. 评分记录

每个测试记录：

```json
{
  "case_id": "case-1",
  "run": "with_skill",
  "assertions": [
    {
      "text": "输出必须标注数据周期和平台过滤条件",
      "passed": true,
      "evidence": "报告摘要写明 2026-04-01 至 2026-04-30，platform_name in Amazon/Amazon VC"
    }
  ],
  "summary": "通过 4/5，主要缺口是未解释毛利口径"
}
```

## 6. 回归门槛

团队共享前，建议把核心断言写成二元结果：

- `pass`：符合断言，有证据。
- `fail`：不符合断言，或证据不足。

发布或更新时至少满足：

- 新建 Skill：with-skill 输出要明显优于不用 Skill 的 baseline，或至少更稳定、更少漏问、更少编造。
- 更新 Skill：新版不能比旧版少执行关键检查。
- 数据型 Skill：不能在字段缺失、过滤不清或结果为空时给正式结论。
- 跨工具 Skill：当前工具参照输出和通用替代输出的关键字段、指标和风险判断一致。

失败断言要写清证据和修复建议，不要只写“效果不好”。

## 7. 执行日志

需要长期使用的 Skill，把真实执行记录写入 `runs/` 或 `diary/`，用于后续迭代：

```json
{
  "case_id": "run-20260518-001",
  "skill_version": "0.1.0",
  "prompt": "用户真实请求",
  "input_summary": "数据周期、站点、部门、文件",
  "assertions_passed": 4,
  "assertions_total": 5,
  "user_feedback": "需要补毛利口径",
  "fix_suggestion": "输出规范增加毛利口径说明"
}
```

日志只保留必要摘要。涉及账号、token、cookie、客户信息或内部明细时先脱敏。

## 8. 迭代

每轮迭代只改真正暴露问题的地方：

- 如果 Skill 漏问关键字段，把触发追问加到工作流。
- 如果输出结构不稳定，增加输出模板。
- 如果反复写同样代码，沉淀到 `scripts/`。
- 如果长规则挤占主文件，把细节拆到 `references/`。
- 如果 description 没触发，优化 YAML `description` 的触发场景。

修改后重跑同一批测试。停止条件：

- 用户确认满意。
- 核心断言稳定通过。
- 新一轮反馈没有暴露有意义的问题。

同类失败出现 2-3 次，或单次失败风险很高时，才把修复建议沉淀为正式规则。沉淀前先补测试用例，再修改 Skill，最后回归验证，避免为单个案例过拟合。

## 9. 交付时说明

最终交付要包含：

- 测试 prompt 列表。
- baseline 类型。
- with-skill 相比 baseline 的改进。
- 仍未覆盖的场景。
- 建议下一轮新增的测试。
