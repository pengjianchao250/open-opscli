## 一、项目概述

〈一句话说明这个服务是做什么的〉

- **技术栈**：Python 3.12 + FastAPI + SQLAlchemy 2.0（异步，`aiosqlite` 驱动）+ Alembic + Pydantic v2 + SQLite；依赖管理 uv + `pyproject.toml` + `uv.lock`
- **入口**：`app/main.py`，容器内端口 `8000`；CLI 入口 `cli.py`
- **请求流**：浏览器 → 前端 Nginx `/api/` 代理 → `api/v1` 路由 → `services/` 业务层 → `models/` ORM → SQLite（容器内 `/data/app.db`）
- **探针**：`/health` 存活（不查依赖），`/ready` 就绪（检查数据库），Compose healthcheck 用 `/ready`
- **前端与部署**：由仓库根目录 `frontend/`、`deployment/` 与 `ops-app.config` 承担，本文件只管 `backend/`

**目录结构**

```
backend/
├── cli.py                    唯一 CLI 入口（click group，只做命令聚合，不写业务）
├── app/
│   ├── main.py               应用装配：中间件、异常处理器、路由注册、lifespan
│   ├── config.py             Settings 单例（唯一配置入口，禁止 os.getenv）
│   ├── database.py           引擎 / sessionmaker / get_db 依赖 / PRAGMA 注入
│   ├── core/                 横切：鉴权、响应信封、异常、日志、分页、加解密
│   ├── models/               ORM，一表一文件；聚合导出只在 __init__.py
│   ├── schemas/              Pydantic 出入参
│   ├── api/v1/               对外接口（/api/v1）
│   ├── api/internal/         内部接口（/internal，独立鉴权）
│   ├── services/             业务逻辑（API 与后台任务共用）
│   ├── scheduler/            定时任务：声明式注册表 + 统一注册器 + 包裹层
│   ├── cli/                  CLI 命令实现，按组分文件（jobs / migrate / ops）
│   └── tasks/                后台任务（按需创建）
├── migrations/versions/      Alembic 迁移，唯一 DDL 入口（render_as_batch）
├── tests/
├── scripts/
├── docs/
│   ├── 开发指南/             通用规范全文（来自 Skill，只读，不在项目内修改）
│   ├── API规范/openapi.json  接口契约（由应用生成，禁止手工编辑）
│   └── CHANGELOG.md          变更记录，随代码同 commit
├── AGENTS.md                 只做指向本文件
├── pyproject.toml / uv.lock  依赖清单与锁文件
└── .env.example              配置示例（三处同步之一）
```

## 二、环境准备与常用命令

```bash
# ===== 环境（在 backend/ 目录内执行）=====
uv sync                                          # 创建 .venv 并按 uv.lock 安装依赖（含 dev）
cp .env.example .env                             # 首次初始化后按注释填写实际值
# SQLite 无需基础设施容器；本地库路径由 .env 的 SQLITE_PATH 指定

# ===== 启动 =====
uv run alembic upgrade head                      # 首次启动前把本地库升到最新
uv run uvicorn app.main:app --reload --port 8000

# ===== 测试 =====
uv run pytest -m "not db"                        # 快速回归，日常用这个
uv run pytest -m "not db" -k "关键字"             # 快速档 + 相关面收窄（最常用）
uv run pytest -m db                              # 只跑真实依赖用例（慢，不可并发）
uv run pytest                                    # 全量（仅限三种情形，见铁律十九）
uv run pytest tests/test_xxx.py -v               # 按文件跑

# ===== 数据库迁移 =====
uv run alembic revision --autogenerate -m "变更简述"   # 独占 SQLite 允许 autogenerate，但必须逐行审查（见铁律六）
uv run alembic upgrade head
uv run alembic current

# ===== 定时任务（手动执行）=====
uv run python cli.py jobs list                   # 列出全部任务及调度、开关、责任人
uv run python cli.py jobs run <job_id> --参数=值  # 手动执行
uv run python cli.py jobs run <job_id> --dry-run  # 只看会做什么，不写入

# ===== 运维 =====
uv run python cli.py ops backup --dst <备份路径>   # 在线备份 SQLite（Connection.backup），禁止 cp 库文件

# ===== API 契约 =====
uv run python scripts/gen_openapi.py             # 写入 docs/API规范/openapi.json，API 一改就要跑，见铁律十五

# ===== 静态检查 =====
uv run ruff format . && uv run ruff check . && uv run mypy app/
```

**环境约束**：

- **必须在虚拟环境中开发和测试**（`uv sync` 创建的 `.venv`），禁止污染系统 Python。
- **未明确要求时不得用容器启动业务服务**；本地开发直接 `uvicorn`，Compose 只用于发布检查。
- **任何时候不得清空容器旧数据与卷**；`/data` 卷中的 SQLite 是唯一数据副本。
- 本地开发 `SCHEDULER_ENABLED=false`，需要调试任务时用 `cli.py jobs run` 手动执行，不在本地开启调度器。
- worktree / 隔离环境工作时，**必须把所有不入库的本地配置一并复制过去**（`.env`、`*.ini`、本地证书），详见第八章。

## 三、架构要点

### 3.1 分层与依赖方向（严格单向）

```
api/  →  schemas/
 ↓
services/  →  core/（横切，任意层可依赖）
 ↓
repositories/  →  models/
```

- `services/` 不得 import `api/`；`models/` 不得 import `services/`；`core/` 不得 import 业务层。
- **事务边界**：service 只 `flush` 不 `commit`，提交由 API handler / 任务入口收口，**一个请求只有一个提交点**。
- **关系加载**：响应需要的关系必须在查询阶段 `selectinload` 预加载；写后要返回关系集合必须**重新查询**（`expire_on_commit=False` 下旧集合不刷新；序列化阶段首次触碰惰性关系会抛 `MissingGreenlet` 直接 500）。

### 3.2 数据库

- 数据库为本应用独占的 SQLite，容器内路径 `/data/app.db`，本地路径由 `SQLITE_PATH` 指定；ORM 基类 `app/models/base.py` 的 `Base`，Alembic 只管理该 metadata。
- 表名蛇形复数，无前缀；主键 `id`；软删除统一用 `〈deleted_at / status〉`。
- 引擎 `sqlite+aiosqlite` + `NullPool`，`app/database.py` 在 `connect` 事件注入 PRAGMA 基线（WAL、`foreign_keys=ON`、`busy_timeout=5000`），写事务 `BEGIN IMMEDIATE`；每个参数都有取值依据注释。
- SQLite 任何时刻只有一个写者：Compose 固定单副本，事务必须短，禁止事务内网络调用。需要多副本或高并发写时停止并联系 IT，不得硬扛。
- 类型规则以《SQLite 数据库使用通用规范》为准：金额 `INTEGER` 最小单位、时间 UTC 单一表示、`STRICT` 表、JSON 列 `json_valid`。
- 迁移 `render_as_batch=True`；改列类型、约束、主键外键必须走 batch 重建，并显式重建索引与触发器。

### 3.3 业务口径单一事实来源

任何被两处以上引用的口径（枚举、可见性过滤、计数规则）必须提升为**模型层常量**，禁止散写字面量。

```python
ORDER_STATUSES = (...)                      # 全项目唯一白名单
ORDER_VISIBLE = Order.deleted_at.is_(None)  # 读侧统一过滤
```

## 四、代码规范

### 4.1 通用

- **注释与 docstring 一律中文**；每个方法必须有 docstring；关键行注释解释**「为什么」**而非「做了什么」。
- 每个模块首行 `from __future__ import annotations`。
- ORM：SQLAlchemy 2.0 异步风格（`Mapped` / `mapped_column` / `select()`），禁止 1.x `Query` API。
- Schema：Pydantic v2，禁止 v1 写法（`@validator` / `.dict()` / 内部 `Config` 类）。
- 命名：模型文件蛇形单数 / 路由文件蛇形复数 / Schema 后缀 `Create|Update|Out|List` / 布尔 `is_|has_` / 时间 `_at`。
- 单文件体量：路由 ≤500 行、服务 ≤800 行、函数 ≤80 行、路由函数体 ≤40 行；超出即拆分。

### 4.2 API

- 【必须】显式 `response_model` + 返回类型标注 + 鉴权依赖 + 归属校验。
- 【必须】每个 `Query`/`Path`/`Body` 带中文 `description`（这是前端契约）。
- 【必须】列表接口分页（`page` / `page_size` 带 `le` 上限）+ **显式 `ORDER BY`**（含唯一列兜底，否则分页会重复/遗漏）。
- 【必须】排序字段、枚举过滤值**走白名单校验**，禁止把用户输入拼进 SQL。
- 【必须】「无权限访问他人资源」与「资源不存在」**统一返回 404**，不区分。
- 【必须】有外部副作用的 POST（支付、扣款、发消息）**必须幂等**（唯一约束或 `Idempotency-Key`）。
- 【禁止】路由函数里写业务逻辑；【禁止】用 `dict`/`Any` 当 `response_model`。

### 4.3 数据库 / ORM

- 【必须】一表一文件；字段**必须带中文 comment**（说明含义 + 取值范围/枚举值）。
- 【必须】新增 NOT NULL 列同时给 `default`（ORM 侧）与 `server_default`（存量行），缺一即失败。
- 【必须】金额用 `INTEGER` 存最小单位（分/厘，列名带 `_cent` 等后缀，禁 `REAL` / `Float`）；时间统一存 UTC 且全项目只用一种表示；需过滤/排序的字段独立成列（不塞 JSON）。
- 【必须】被两处以上引用的业务口径提升为模型层常量（见 3.3）。
- 【禁止】N+1 查询；【禁止】循环里单条写；【禁止】裸 SQL 字符串拼接。

### 4.4 异步

- 【禁止】异步路由中调用阻塞 IO；必须用 `asyncio.to_thread` 卸载。
- 【必须】fire-and-forget 任务用集合持有引用（见铁律十六）。
- 【必须】所有外部调用显式设置超时；重试只对幂等操作开启，带次数上限 + 指数退避。
- 【必须】后台任务的失败判定基于**真实活性信号**（心跳/租约/状态转移），**不得仅按记录年龄**。

### 4.5 定时任务

见铁律二十六。要点：声明式注册表、`max_instances=1`、统一包裹层做超时与异常兜底、tick 轮询、`python cli.py jobs run` 手动执行。

### 4.6 错误处理与日志

- 【禁止】`except Exception: pass`；至少 `logger.warning(..., exc_info=True)`，并捕获具体异常类型。
- 【必须】业务失败抛业务异常（带稳定错误码），由统一处理器映射；service 层不抛 `HTTPException`。
- 【必须】错误响应不含堆栈/SQL/内部路径/连接串；日志不含密码、token、身份证、完整卡号。
- 【必须】新增的失败路径要有可观测出口（指标/落库/告警），**不得只有日志**，更不得静默。

### 4.7 配置与依赖

- 【必须】配置统一走 Settings；**禁止业务代码里 `os.getenv`**。
- 【必须】新配置项三处同步（见铁律十四）；`.env` 中**禁止同名变量重复定义**（后值静默覆盖前值，是密钥漂移类事故的常见根因）。
- 【必须】代码 import 的三方包必须写进依赖清单并注明用途与版本约束理由（见铁律十三）。
- 【必须】新特性带**默认关闭的功能开关**，关闭时行为与上线前完全一致。

### 4.8 opscli 接入

- 【必须】只导入 `opscli` 包根导出的符号；服务端一律显式传入 `session_id` / `jwt` 构造 Manager，**每请求构造**，禁止模块级单例、禁止缓存凭证、禁止落盘。
- 【必须】对外鉴权统一走 `app/core/auth.py` 的 `get_current_user`：从 cookie `polarisUserToken` 或 `X-Session-Id` 取会话，用 `AuthClient().get_me(session_id=...)` 解析，`AuthError` 一律 401。
- 【必须】按 `AuthError` / `QueryError` 等模块基类捕获并保留错误码；日志与异常文本只留凭证前 6 位摘要。
- 【禁止】手拼 `Authorization` 头、读取 `credentials.bin` 或 Keychain、用环境变量偷传 JWT、手写查询 payload 的 `userEmail` / `from.table` / `from.permission`。
- 详见 `docs/开发指南/OPSCLI_SDK调用规范.md`、`OPSCLI_API调用规范.md`。

## 五、开发铁律

> 违反即评审打回。完整解释见开发规范对应章节。

### 铁律一：改代码前必须先分析（开发规范 §18.1）
理解代码 → 定位根因 → 列出方案 → **等待确认**。禁止未读代码就改、未分析根因就猜着改、未说明方案就擅自改。对方只是描述现象、未要求修改时，不得直接改代码。明确说「直接改」时可跳过确认，但前三步不可省。

### 铁律二：只改指定范围（开发规范 §18.2）
需求方指定了文件/模块，就只改那里。确需扩大范围**必须先说明原因并取得确认**。范围内的工作要全部做完；有阻塞就把其余做完并明确说明未做部分。

### 铁律三：不确定就问，不猜（开发规范 §18.3）
不确定意图 → 直接问；不确定方案 → 列选项让对方选；不确定细节 → 追问。同时保持独立判断：对方说的不一定对，不合理的要求要指出；被重申后视为其决策，说明风险后按完整要求执行。

### 铁律四：每个 ORM 模型独立文件（开发规范 §2.3 §6.2）
`models/` 保持「一表一文件，一文件一模型类」；禁止创建 `models.py` 式聚合定义文件；聚合导出只放 `models/__init__.py`。

### 铁律五：数据库变更必须通过迁移（开发规范 §7.1）
禁止手工 DDL 作为正式变更方案。模型改动与迁移文件、测试必须在同一次提交中。

### 铁律六：共享数据库禁用 `--autogenerate`（开发规范 §7.2）
autogenerate 对整库 diff，会为不属于本服务的表生成 `op.drop_table()`，一执行就是不可逆数据丢失。共享库一律 `alembic revision -m "..."` 生成空白迁移后手写。本应用的 SQLite 是独占库，允许 `--autogenerate`，但 `migrations/env.py` 必须配置 `include_object` 只放行本项目 `Base.metadata` 的表，生成后逐行审查；一旦数据库改为与其他系统共享，立即禁用。

### 铁律七：迁移必须先合主干，再应用到共享/生产库（开发规范 §7.5）
共享库 `alembic_version` 一旦记录了主干上不存在的 revision，主干上的**任何** alembic 命令都会硬失败并全阻断。
配套禁令：禁止删 `alembic_version` 孤儿行「消错」；多 head 只能用 `alembic merge` 收敛，**禁止改 `down_revision` 做线性化**。

### 铁律八：迁移必须对称且带 comment（开发规范 §7.3）
`upgrade()` / `downgrade()` 都要实现且对称；每个 `sa.Column` 必须带中文 comment；DML 回填必须幂等；含方言特有 SQL 要做方言分支；**迁移中不得 import ORM 模型**。

### 铁律九：表字段必须带中文 comment（开发规范 §6.2）
新建或修改任何字段，同一次改动中同步写入中文 `comment`，说明含义 + 取值范围/枚举值；禁止英文或空串敷衍。新增 NOT NULL 列必须同时给 `default`（ORM 侧）与 `server_default`（存量行）。

### 铁律十：严禁直接对数据库执行破坏性操作（开发规范 §18.7）
禁止以任何方式对生产/共享库直接执行 UPDATE/DELETE/DROP 作为变更手段。结构变更走迁移；数据修复须先确认影响范围、留备份、经确认。

### 铁律十一：完成实现后必须自审并验证（开发规范 §15.2 §18.8）
改完先自审，再跑**相关面测试**。相关面 ≠ 全量：`git diff --name-only` → 用改动的模块/类/函数/路由名 grep 反查测试 → 按改动类型追加。没有审查和测试，不得说「完成」。

### 铁律十二：方法必须补中文注释（开发规范 §4.5）
所有新增或修改的方法都要有中文 docstring；关键行注释解释「为什么这样做」；踩坑修复处注明**日期 + 现象 + 根因**。

### 铁律十三：新依赖必须同步依赖清单（开发规范 §9）
禁止代码 import 了三方包而 `requirements.txt` / `pyproject.toml` 未声明（含原本靠传递依赖引入的）。声明时注明用途与版本约束理由。

### 铁律十四：新配置项必须三处同步（开发规范 §8.2）
`config.py`（字段 + 中文 description）+ `.env`（实际值）+ `.env.example`（脱敏示例 + 中文注释说明用途、取值范围、默认行为）。删除或重命名同样三处同步。禁止 `.env` 中同名变量重复定义。

### 铁律十五：API 变更必须同步 OpenAPI（开发规范 §5.9）
新增/删除/修改任何路由、请求体、响应体、状态码、参数后，同一次改动中重新生成契约文件。必须从当前 app 生成，禁止手工拼接或局部编辑。新增接口必须显式声明 `response_model`；非 JSON 响应用 `responses={...}` 标注；必须挂鉴权依赖。

### 铁律十六：fire-and-forget 任务必须持有引用（开发规范 §10.2）
禁止裸调 `asyncio.create_task(coro())` 而不保存返回值——GC 会在协程执行前回收，任务静默丢失且不报错。
```python
_background_tasks: set[asyncio.Task] = set()
task = asyncio.create_task(coro())
_background_tasks.add(task)
task.add_done_callback(_background_tasks.discard)
```

### 铁律十七：技术方案先查框架/SDK 原生能力（开发规范 §1.4）
涉及方案选型或架构调整，动手前先查所依赖框架/SDK 的文档与源码，确认是否已原生提供（FastAPI 的 `Depends`/`BackgroundTasks`/`lifespan`、SQLAlchemy 的关系加载/事件、Pydantic 的校验器、Alembic 的 `merge`）。已有官方方案必须优先采用，禁止造轮子。确认不支持才允许自定义，并写明「已确认 X 不支持」的查证结论与查证位置。
本项目关键 SDK：FastAPI、SQLAlchemy、Alembic、APScheduler 官方文档；opscli SDK 参考 `docs/开发指南/OPSCLI_SDK使用文档.md`。〈补充本项目其他关键 SDK 源码路径〉

### 铁律十八：真实连库/连外部依赖的测试必须打标记（开发规范 §15.1）
文件顶部 `pytestmark = pytest.mark.db`。判定标准：真的拿去建连接或建 session（仅用于 `patch()` 打桩的、只出现在注释/字符串里的不算）。新测试**优先不连真实依赖**，能用依赖覆盖或内存库解决的一律不连。禁止对这批用例开 `pytest-xdist`。

### 铁律十九：按相关面回归，禁止把全量当默认动作（开发规范 §15.2）
默认只跑相关面。**必须跑全量的三种情形（只有这三种）**：① 改动触及公共基础设施（`core/`、`config.py`、`conftest.py`、`models/__init__.py`、`main.py`、框架/依赖升级）；② 合入主干前 / push 前；③ CI。
相关面为空 = 该改动无测试覆盖，**必须补测试**，不得拿「跑了全量」当替代验证。

### 铁律二十：commit 前必须更新变更记录并随同提交（开发规范 §16.4）
任何 commit 之前，先把本次改动写入 `docs/CHANGELOG.md`：为什么改、改了哪些文件/模块、具体做了什么、验证方式与结果、影响范围、回滚方式。**必须与代码在同一次 commit 中提交**，禁止代码已入库而记录游离在工作区。

### 铁律二十一：commit message 使用中文描述（开发规范 §16.2）
遵循 Conventional Commits，类型前缀（`feat`/`fix`/`refactor`）与 emoji 可为英文，**冒号之后的描述必须中文**，写清「改了什么、为什么改」。
示例：`feat(orders): 订单列表支持按状态过滤并返回聚合计数`

### 铁律二十二：跨系统共享契约必须双向同步（开发规范 §18.5）
被两个及以上系统共同读写的接口/数据表，任一侧修改参数、响应体、业务码、权限语义，必须在同一改动周期内同步另一侧代码与两份契约文档。既有的可观测行为（哪怕看起来不合理）是强约束，**不得单侧"修正"**。共享表结构变更须双端评审。

### 铁律二十三：他方资产不得擅改（开发规范 §18.6）
禁止为修正本系统行为而修改用户上传内容、业务方编写的配置/脚本/文档、第三方仓库代码、他团队维护的模块——即使本地有副本。问题收敛在自己这一侧解决；确需调整须告知所有者由其自行修改。

### 铁律二十四：环境操作红线（开发规范 §18.7）
- 允许本地 `git commit`；**禁止主动 `git push`**，推送必须由需求方明确指令。
- 未明确要求时**不得用容器启动业务服务**（数据库等基础设施除外）。
- **任何时候不得清空容器旧数据与卷**。
- Python 开发测试必须在虚拟环境中进行。
- 本地连共享环境时，启动前必须关闭全部后台任务（定时调度、清扫、失败恢复）。

### 铁律二十五：对外标识与访问控制（开发规范 §5.6 §5.7）
- 【必须】访问控制**永远由归属字段（`user_id`/`tenant_id`）兜底**，不得依赖「id 不可猜」；【禁止】用客户端可控字段判权（典型提权漏洞）。
- 【必须】「无权限访问他人资源」与「资源不存在」对外**统一返回 404**，不区分——否则 id 可被用于探测资源存在性。
- 【应当】对外**不直接暴露自增主键**：UUIDv7 主键 / 业务编号 / 可逆加密，三选一并全项目统一。
- 采用可逆加密方案时：出入参统一用类型注解自动加解密（不在每个接口手工调用）；**非 Pydantic 响应（裸 dict）必须手动加密回填**（最易漏）；流式事件、回调、外链中的同一标识同样用密文；**解密失败降级为永不命中的哨兵值**让归属校验自然 404，不得抛 422 泄漏 id 合法性。

### 铁律二十六：定时任务四件套（开发规范 §19）
- 【必须】任务声明集中在**声明式注册表**（`SCHEDULED_JOBS`），禁止一长串 `if enabled: add_job(...)`。
- 【必须】每个 Job 显式给出 `id` / `max_instances=1` / `coalesce=True` / `misfire_grace_time` / `replace_existing=True`，禁止依赖默认值。
- 【必须】任务函数**必须 `async def`**、自持 DB 会话、**必须幂等**（重复执行结果一致）、单轮处理量有上限。
- 【必须】统一包裹层负责**超时 + 异常兜底 + 指标 + 告警**——APScheduler 里未捕获的异常不会冒泡，不兜底即静默失败；无超时的任务卡死会占住 `max_instances` 名额导致**此后永不再执行**。
- 【必须】告警覆盖「**没跑**」而不只是「跑失败」：监控 `now - last_success_at > 预期间隔 × 2`。
- 【必须】多实例靠**分布式锁 + 幂等**，禁止拿「只部署一个实例」当保证（扩容/滚动发布即破产）。
- 【必须】用户可配置的定时任务走 **tick 轮询**（DB 的 `next_run_at` 为唯一事实来源），禁止逐条注册成 Job。
- 【必须】**每个任务同时可手动执行**，且与调度**共用同一任务函数、同一包裹层、同一参数模型**：
  ```bash
  python cli.py jobs list                                    # 列出全部任务
  python cli.py jobs run <job_id> --参数=值                   # 手动执行
  python cli.py jobs run <job_id> --dry-run                  # 只看会做什么，不写入
  ```
  CLI 入口是根目录 `cli.py`（极薄，只做命令聚合），`main.py` 不承载 CLI 逻辑；CLI 选项由 Pydantic 参数模型**自动生成**，禁止两处各写一份。
- 【禁止】为手动执行另写脚本——两份实现必然漂移，且只在故障需要补跑时才暴露。一次性运维任务也进注册表（`manual_only=True`），复用锁/超时/审计。
- 【必须】写操作任务支持 `--dry-run`；退出码规范 0=成功 / 1=业务失败 / 2=参数错误；手动执行记录操作者与参数。
本项目调度器位置：`app/scheduler/`；CLI：`uv run python cli.py jobs ...`；任务清单见 `app/scheduler/registry.py` 的 `SCHEDULED_JOBS`。SQLite 维护（`PRAGMA optimize`、`wal_checkpoint`、在线备份）也作为注册表任务实现，与手动执行共用同一函数。

## 六、测试指引

### 6.1 分层与执行

| 层 | 特征 | 占比 |
|---|---|---|
| 单元测试 | 不连任何外部依赖，毫秒级 | ≥70% |
| 集成测试 | 连内存库或容器化真实依赖 | ~25% |
| 端到端测试 | 连共享环境，慢且不可并发 | ≤5% |

连接真实/共享依赖的测试必须打 `pytestmark = pytest.mark.db`（铁律十八）；执行入口见第二章。

### 6.2 相关面回归（日常默认档）

按序做，不凭感觉：

1. `git diff --name-only` 列出改动文件；
2. 用改动的**模块名/类名/函数名/路由路径**在测试目录 grep 反查：
   ```bash
   grep -rl "OrderService\|/api/v1/orders" tests/
   ```
3. 按改动类型追加：改路由/schema → 该路由测试 + OpenAPI 校验；改 ORM/迁移 → 模型测试 + 迁移测试；改公共工具 → 全部调用方测试；
4. **相关集为空 = 该改动无测试覆盖，必须补测试**。

### 6.3 必须有测试的场景

每个接口的成功路径 + 至少一个失败路径；每个状态机流转（含非法流转被拒）；每个迁移（DDL 序列 + 对称性）；每个幂等实现；**每次修 bug 必须补一个能复现该 bug 的回归测试**。

### 6.4 验收纪律

- **禁止**只看「流程跑通 / 没报错」就判定通过——必须核对**最终产出的实际内容**；降级、兜底、拦截都发生在「无报错」的执行里。
- **禁止**核对产出时做任何截断（SQL `LEFT/RIGHT`、日志切片）——被截掉的尾部往往正是问题所在。
- 除 error 外，还要检查**不以 error 形态出现的异常信号**（降级/重试/回退/兜底分支）。
- 故意制造失败的验收数据必须**显式标注**，避免在共享环境遗留误导性数据。

## 七、数据库迁移指引

```bash
uv run alembic revision --autogenerate -m "订单表新增状态列"   # 独占 SQLite：允许 autogenerate，生成后逐行审查
uv run alembic revision -m "订单表新增状态列"                  # 需要手写 batch 重建或 DML 回填时用空白迁移
```

SQLite 专项：`env.py` 必须 `render_as_batch=True`；`ADD COLUMN` 的非空列必须给常量默认值；重建表迁移显式重建索引与触发器，并在提交后跑 `PRAGMA foreign_key_check`。

| 规则 | 说明 |
|---|---|
| **共享库禁用 `--autogenerate`** | 它对整库 diff，会为不属于本服务的表生成 `op.drop_table()`，执行即不可逆数据丢失 |
| **`upgrade` / `downgrade` 都要实现且对称** | 每次变更都要有回滚路径 |
| **每个 `sa.Column` 带中文 comment** | 与模型共用同一份文案常量，避免两处漂移 |
| **DML 回填必须幂等** | 带 `WHERE ... IS NULL` 等守卫；大表分批（每批 1000~5000 行） |
| **迁移中不得 import ORM 模型** | 模型会随代码演进，历史迁移会因此失效；用 `sa.table()/sa.column()` 就地声明 |
| **`down_revision` 接主干当前 head** | 不能接尚未合入的分支上的迁移 |
| **一个迁移只做一件事** | 不要「加列+改索引+迁数据+删表」塞一起 |

**上线顺序（不可颠倒）**：

```
功能分支自测（本地库 / 独立 schema）
        ↓
   合入主干
        ↓
在主干上 alembic upgrade head → 写共享库
        ↓
核对 alembic current 与实际字段/索引
        ↓
      共享环境 E2E
```

**禁止**：从未合入主干的分支把迁移应用到共享/生产库；删 `alembic_version` 孤儿行「消错」；改 `down_revision` 做线性化（多 head 只能 `alembic merge` 收敛）。

**环境口径必须诚实**：本地库/镜像/独立 schema 上的验证只能说「本地隔离验证通过」「合入前预验收通过」，**不得**说成「测试环境验收通过」。

## 八、隔离环境（worktree）规范

> 详见开发规范 §18.4

### 8.1 环境准备
创建 worktree 后，**必须把所有不入库的本地配置一并复制过去**（`.env`、`*.ini`、本地证书等）。漏拷会让客户端回落到打包的默认（常为生产）配置，产生极难定位的权限/环境错误。
本项目需要复制的文件清单：`.env`、本地 SQLite 库文件（`SQLITE_PATH` 指向的 `*.db` 及伴生 `-wal` / `-shm`，或改用独立库路径）〈补充其他不入库的本地配置〉

### 8.2 提交粒度
同一模块「验证通过 + 已知缺陷修完」后才提交；禁止把试错过程逐条提交；拆分维度只能是模块/关注点，不能是时间/试错轮次；分支 commit 数不超过涉及的模块数。

### 8.3 收尾处置

| 类型 | 合并回原分支 | 删除 worktree + 临时分支 | 决策方 |
|---|---|---|---|
| **fix** | 自动执行 | 自动执行 | 自行完成 |
| **feat** | 由需求方决定 | 由需求方决定 | 必须先汇报再询问 |

feat 收尾汇报须含：worktree 路径、分支名、commit 清单与说明、验证结果、目标合并分支、预估冲突范围；并**分开询问**「是否合并」与「是否删除」，不得捆绑代答。

commit 前写入变更记录并随代码同 commit（铁律二十）。

- [ ] 迁移 upgrade/downgrade 对称、DML 幂等、未 import ORM 模型

- [ ] 无裸 `create_task`、无阻塞调用、无 `except: pass`、无散写口径字面量

- [ ] 有对应测试（含失败路径），且能给出实际执行结果

- [ ] OpenAPI 契约已重新生成
- [ ] 变更记录已写入并随同提交

## 十一、工作方式

### 11.1 分析先行（改代码前的强制流程）
1. **理解问题** —— 完整读完相关代码，弄清现有逻辑与上下文；
2. **定位根因** —— 找根本原因而非表面现象；
3. **列出方案** —— 至少一个具体方案，写明改动点、理由、影响面、备选与取舍；
4. **等待确认** —— 告知需求方，**得到确认后再动手**。

**禁止**：未读代码就改 / 未分析根因就猜着改 / 未说明方案就擅自改 / 对方只是描述现象未要求修改就直接改。
**例外**：对方明确说「直接改」「帮我修复」时可跳过第 4 步，前三步不可省。
**排查报错时先检索既有经验/历史记录再重试**，禁止盲目重试同一操作。

### 11.2 不确定就问，不猜
不确定意图 → 直接问；不确定方案 → 列选项及取舍让对方选；不确定细节 → 追问明确后再执行。

### 11.3 独立判断，不迎合
对方说的不一定对，以代码与数据为准；不合理的要求要指出并说明原因；提出质疑后若对方重申，**视为其决策**，说明已知风险后按完整要求执行。

### 11.4 先查框架原生能力
见铁律十七。

### 11.5 范围完整性
完成范围内**全部**工作；某部分被阻塞时，把其余做完，并**明确说明哪部分未做、为什么**。缩小交付范围是需求方的决定。

### 11.6 汇报口径
必须写明：**跑了哪些测试、通过多少条、筛选条件、在什么环境**。
- ✅ 「相关面回归 182 条通过（筛选：`pytest -m "not db" -k "order"`）」
- ❌ 「测试通过」/「应该没问题」/ 未跑全量却写「全量通过」/ 隔离环境却写「测试环境验收通过」

### 11.7 完成的定义（DoD）
功能实现完整 ✓ 自审完成 ✓ 相关测试通过且给出数据 ✓ 核对了实际产出内容 ✓ 文档同步（API 契约 / 配置示例 / 变更记录）✓ 明确回滚方式 ✓
—— **全部满足才可称「完成」**。
