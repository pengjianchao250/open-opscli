# 业务取数编排

在 Codex 中把复合业务取数目标拆成有限、互不重复的数据问题，逐项使用现有通用取数 Skill 获取真实结果，再按原始业务目标汇总。

本 Skill 只负责编排，不实现底层查询，不创建看板，也不分析当前看板。

## 触发边界

使用本 Skill：

- 用户要求为后续搭建看板准备多组数据。
- 用户提出经营复盘、业务诊断或其他需要多个查询共同回答的取数主题。
- 一个请求同时需要总览、趋势、对比、排名、结构、风险或明细中的多种结果。
- 用户要求先梳理需要查哪些数据，再逐项执行并汇总。
- 多个查询之间存在业务顺序或结果依赖。

典型触发：

- “帮我准备销售经营看板需要的数据。”
- “做库存健康分析，需要总览、趋势和风险商品明细。”
- “最近销售下降，帮我拆成几个数据问题并查出来。”

不要使用本 Skill：

- 单个查询且信息完整：直接使用 `$ops-dataset-query`。
- 单个查询但关键范围、指标或维度不清晰：直接使用 `$ops-query-wizard`。
- 用户指出已有查询的数据集、字段、条件、排序或结果有误：直接使用 `$ops-query-wizard` 纠错模式。
- 用户要求创建、修改或删除当前看板图表：使用对应的 Dashboard 页面编辑 Skill。
- 用户要求分析当前已绑定仪表盘：使用对应的 Dashboard 数据分析 Skill。

“为看板准备数据”只表示提供后续搭建看板所需的真实数据，不表示操作 Dashboard 页面。

## 前置条件

- 当前运行环境是 Codex。
- `$ops-dataset-query` 和 `$ops-query-wizard` 已安装且可加载。
- 不要求存在 Dashboard 页面上下文。

任一依赖 Skill 不可用时，停止对应问题并提示安装依赖；不得降级为直接调用查询命令或自行猜测结果。

## 依赖路由

- 清晰的数据问题使用 `$ops-dataset-query`。
- 模糊、缺参或有歧义的数据问题使用 `$ops-query-wizard`。
- 已有结果被用户判定有误时，仅将对应问题及其查询上下文交给 `$ops-query-wizard` 纠错。

“使用”或“委托”现有 Skill 仅表示按其入口和规则完成当前数据问题；不得修改、复制或覆盖它们的文件和规则。

## 硬边界

- 不直接调用 `opscli query` 或查询 MCP Tool 绕过现有 Skill。
- 不选择或猜测数据集、字段、聚合、公式、筛选值和查询参数。
- 不保存固定数据集 ID、字段 ID、凭证或认证信息。
- 不修改 `ops-dataset-query` 和 `ops-query-wizard`。
- 不依赖 `dashboard_session_get_context` 或任何 Dashboard 页面工具。
- 不读取、分析、创建或修改当前看板。
- 不考虑已废弃的 `codex-custom-builder`。
- 不创建站点代码、接口、数据库、同步任务、定时任务或部署配置。
- 不把用户只要求的取数扩展成未要求的业务域或完整分析项目。
- 没有真实查询结果时，不生成数值、结论或伪造的结果摘要。

## 工作流

### 1. 识别业务目标

提取用户要解决的问题、数据用途、主要业务对象、已确认范围和明确要求的结果类型。

### 2. 判断单一或复合请求

- 能由一次明确查询回答：使用 `$ops-dataset-query` 并停止业务层编排。
- 只是一次查询但信息不完整：使用 `$ops-query-wizard` 并停止业务层编排。
- 需要多个独立业务判断：继续拆解。

不得为了触发本 Skill，把一个单查询人为拆成多个问题。

### 3. 拆解数据问题

读取 `references/orchestration-contract.md`，按其中的任务结构记录每个问题。

- 先按业务问题拆，不按数据集拆。
- 一个问题只回答一个主要业务判断。
- 同一范围和粒度可一次回答的问题不要重复拆分。
- 先覆盖用户明确要求，再判断是否存在必要依赖。
- 原因诊断先确认现象；只有真实结果支持时，才提出用于验证明确假设的补充查询。
- 此阶段只描述业务问题，不推断底层数据集和字段。

### 4. 展示查询计划并控制范围

复合请求开始执行前，简要展示业务目标、数据问题清单及用途、预计查询数量、执行顺序和待确认范围。

不设置机械的查询数量阈值。出现以下任一情况时，必须先等待用户确认：

- 关键业务范围仍有歧义。
- 计划跨入用户未明确要求的其他业务域。
- 新增查询会显著改变用户明确要求的范围或交付量。
- 后续查询依赖用户对前序结果的业务判断。

如果拆解完全来自用户明确列出的结果，且没有上述情况，可以展示计划后继续执行。

### 5. 逐项委托并记录结果

按依赖顺序处理每个问题：

1. 问题足够清晰时，显式使用 `$ops-dataset-query`。
2. 问题存在关键缺参或歧义时，显式使用 `$ops-query-wizard`。
3. 向依赖 Skill 传递业务问题、业务用途、用户已确认的范围和必要上下文。
4. 接受依赖 Skill 的数据集、字段、查询参数、反馈和错误处理结果，不在本层重复实现。
5. 按编排契约记录状态、实际数据范围、结果摘要、限制和警告。

仅能根据依赖 Skill 的真实返回内容填写结果记录。

### 6. 处理阻塞与纠错

- 单个问题失败时，遵循被调用 Skill 的失败处理；业务层不自行重试底层查询。
- 保留已成功的问题结果，继续执行无依赖且可安全执行的问题。
- 前置问题阻塞时，暂停依赖它的后续问题并标记为 `not_run`。
- 用户指出某项结果有误时，只纠正该问题；其他成功结果保持不变。
- 最终结果必须区分 `success`、`blocked`、`needs_confirmation` 和 `not_run`。

### 7. 汇总并停止

按 `references/orchestration-contract.md` 的输出模板交付原始业务目标、各问题状态、数据范围、真实结果摘要、限制和未完成事项。

只汇总多个结果共同支持的业务现象，不得把相关变化表述为已证明的因果关系。完成原始业务目标后立即停止，不为“多展示一些数据”继续增加查询。

## 输出原则

- 默认在 Codex 对话中输出，不自动生成文件。
- 用户明确要求时，可以把同一真实结果整理为 Markdown 或 JSON；不得为此改变查询范围。
- 用户只要求取数时，交付数据范围和结果摘要，不主动扩写成长篇业务分析报告。
- 必须说明截断、缺失、失败、口径限制和未执行项。

## 本地开发闭环

- 静态评估：`python scripts/skill_dev_loop/run_eval.py --skill ops-business-data-orchestrator --pretty`
- 契约测试：`pytest tests/skills/test_ops_business_data_orchestrator_skill.py -q`
- 改动触发边界、依赖路由或输出契约后，必须同时运行上述两项校验。

## 完成信号

- 用户明确要求的数据问题均已成功、明确阻塞或等待确认。
- 每项结论都能追溯到真实查询结果。
- 最终汇总回答了原始业务目标。
- 没有读取或操作 Dashboard 页面。
- 没有修改依赖 Skill，也没有扩展到站点、接口、数据库或发布工作。
