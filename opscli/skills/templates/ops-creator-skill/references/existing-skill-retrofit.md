# 旧 Skill 改造流程

旧 Skill 改造不是直接覆盖。目标是先理解现有能力，再判断本次改造会影响哪些地方，只确认实际受影响项，最后用同源测试证明没有破坏旧能力。

不要把某个示例里的确认项固定成所有改造的必问项。是否需要确认适用范围、名称、触发、输出、数据、脚本、安装兼容，取决于本次改造实际影响什么。

## 改造前硬门槛

开始改文件前必须完成：

1. `只读盘点`：读取旧 `SKILL.md`、`agents/openai.yaml`、`references/`、`scripts/`，记录触发、输入、输出、脚本、测试和已知能力。
2. `保留行为`：列出必须保留的触发话术、输出格式、脚本能力和业务规则。
3. `影响点扫描`：逐项判断本次改造是否影响下面内容；只对受影响项追问或请求确认。
4. `同源对比`：新旧版本使用同一批输入、同一批数据、同一套断言比较；不能用字段修复或依赖升级证明新版更好。
5. `不覆盖原则`：没有用户确认前，不直接删除旧行为、不直接覆盖关键规则、不自动安装替换。

## 影响点扫描

```markdown
## 改造影响点
- 触发话术：不变 / 会变，需确认：
- 适用对象：不变 / 会变，需确认：
- 输入来源：不变 / 会变，需确认：
- 判断规则：不变 / 会变，需确认：
- 输出格式：不变 / 会变，需确认：
- 数据口径：不变 / 会变，需确认：
- 脚本或依赖：不变 / 会变，需确认：
- 名称与展示：不变 / 会变，需确认：
- 安装兼容：不变 / 会变，需确认：
- 旧能力保留：必须保留：
```

判断方法：

- 如果用户要求扩大或收缩适用对象，确认实际新增/删除的对象，以及未确认对象是否只标为 `[待扩展]`。
- 如果旧名称、展示名或触发描述会误导新范围，建议调整名称或增加兼容说明；若不影响理解，不强制改名。
- 如果输出接收人、落点或完成信号变化，确认新输出规范。
- 如果数据来源、字段或过滤变了，先做取数预检。
- 如果脚本输入输出会变，补同源测试。

## 改造步骤

1. 建立旧版基线。目录不是 git 仓库时，至少记录文件清单和关键摘要。
2. 把旧 Skill 内容映射回 Q1-Q6。已有文件能回答的可以代答，但必须标明来源；缺口继续问用户。
3. 做影响点扫描，只确认本次受影响项。
4. 按统一框架重排：主 `SKILL.md` 只放执行路由和硬边界；长规则、案例、数据方案、测试放 `references/`；稳定动作放 `scripts/`。
5. 运行同源测试。至少包含正常、边界、旧能力保留、受影响项缺参四类。
6. 通过后再安装或打包；失败则列问题，不上线。
