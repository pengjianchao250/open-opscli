# 已有运营 Skill 归一化流程

当用户说“把已有 Skill 按 ops-creator-skill 规范调整”“统一历史 Skill 框架”“优化旧 Skill token 负担”时，使用本流程。

## 原则

旧 Skill 改造不是重写。先保护已验证能力，再统一框架。

- 不静默覆盖用户已完成版本。
- 不把数据集更新、依赖修复、字段改名当作新版框架优劣证据。
- 不删除已有业务知识；通过拆分 references、加载路由和脚本固化降低默认上下文。
- 先做同源对比：旧版和新版使用同一批输入、同一批数据、同一套校验。

## 步骤

1. `建立基线`
   - 检查是否已有 git 仓库。
   - 若没有，创建本地 git，并提交当前版本为 baseline。
   - 若已有仓库，记录当前 tag、branch 和 dirty status。

2. `盘点触发和产物`
   - 读取 `SKILL.md`、`agents/openai.yaml`、references、scripts。
   - 记录现有触发描述、用户话术、输入参数、输出文件、脚本命令和测试方式。

3. `识别公共基础设施问题`
   - 数据集 alias/table_id、字段、认证、依赖、脚本 bug、路径问题属于共同基础设施。
   - 这些问题应先同时修到旧版对照和新版草案，或明确作为共同前置修正。
   - 不能用“旧版字段过期”证明“新版框架更好”。

4. `按统一框架重排`
   - 主 `SKILL.md` 改成轻量执行路由。
   - 六维信息、案例、完整判断、数据方案、测试和跨工具方案拆到 references。
   - 保留原有脚本，必要时只补校验、日志、候选提交脚本。

5. `运行同源对比`
   - 同一批输入 prompt。
   - 同一批原始数据或文件。
   - 同一套阈值和脚本版本。
   - 同一套断言和校验脚本。

6. `比较三类结果`
   - 执行过程：是否更早发现缺参、字段、口径、空结果。
   - 上下文负担：估算默认加载 tokens、references 数量、脚本固化程度。
   - 业务结论：核心指标、问题归因、行动建议是否一致或更准确。

7. `交付建议`
   - 如果新版结论一致但流程更稳，建议作为候选标准版。
   - 如果新版 token 明显更高，先做 progressive disclosure 压缩。
   - 如果新版改变业务结论，必须解释是数据差异、规则差异还是脚本差异导致。

## 合格标准

- 新版不丢失旧版已验证能力。
- 日常执行上下文不应比旧版高出 25% 以上；若超过，必须说明原因并优化加载策略。
- 团队复用版必须有日志、测试、候选提交和跨工具降级。
- 基础设施修正应记录为共同修正，不混入框架优劣判断。
