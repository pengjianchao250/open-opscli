# 访谈方法分析：案例复盘 + 六维信息检查

## 结论

“运营流程共建 → 六维信息检查”是默认方法。它的目标不是要求运营同事写完整 SOP，而是让 AI 用更轻的提问方式，把真实工作里的目标、步骤、判断、例外和交付标准问清楚。

推荐执行方式：

1. 用户已经有明确需求时，直接按 Q1-Q6 用“选项题 + 短简答”一题一题推进。
2. 用户表达比较散时，先请他讲一个最近真实案例，再把案例拆回六维信息。
3. 每题结束做内部检查；如果答案还不能指导 AI 执行，就补一个最小问题。
4. 阶段 0 没有复述并获得确认前，不生成 `SKILL.md`、脚本、目录或完整草案。
5. 对外用轻松、具体的表达，不说“不通过”“敷衍”。

## 为什么这个方法有效

- 能避免 Skill 写成行业常识。运营流程里的阈值、例外、优先级和禁忌，通常要从真实案例里追出来。
- 六维信息和 `SKILL.md` 结构天然对应：目标、当前做法、步骤、判断规则、触发场景、输出规范。
- 对跨境运营尤其有用，因为 Amazon 广告、Listing、库存、利润和活动分析都高度依赖口径、周期、样本量和例外条件。
- 能提前暴露数据需求：哪些要用户文件，哪些要 ops 内部数据，哪些只是人工复核判断。

## 提问设计原则

1. **低负担**：先给可选方向，再让用户补一句，避免要求用户凭空组织长答案。
2. **节奏稳定**：Q1-Q6 顺序清晰，AI 不跳步。
3. **检查点明确**：每题都有“够不够写进 Skill”的内部标准。
4. **过程透明**：当用户要求 AI 代答或测试流程时，也要逐条展示“问什么、答什么、还缺什么”。
5. **支持案例入口**：运营专家有时更容易讲真实案例，而不是按表单回答。
6. **补齐数据口径**：跨境电商 Skill 不能只停在文字流程，必须追数据集、字段、聚合、过滤和用途。
7. **考虑迁移复用**：不要写死某个平台的创建器或专属连接器；能脚本化的稳定步骤优先沉淀为 Python。

## 六维引导方式

| 内部维度 | 对运营的说法 |
| --- | --- |
| 业务目标 | “这件事最后要帮你省时间、少亏钱，还是帮新人少犯错？” |
| 当前做法 | “你现在从哪里开始做？打开哪个表或系统？” |
| 具体步骤 | “按你上次处理那个案例，从第一步讲到最后一步。” |
| 判断方法 | “当时哪个指标让你决定这么处理？” |
| 调用方式 | “以后你会怎么跟 AI 说这件事？” |
| 期望输出 | “结果给谁看？他第一眼最关心什么？” |

## 推荐话术

开场：

> 不用先写 SOP，也不用一次讲完整。你讲一个最近真实处理过的案例，我来帮你追问、整理，最后把它翻译成 AI 能照着做的 Skill。

当用户说“看情况”：

> “看情况”没问题，我们就把这个判断拆小一点。你当时第一眼看的是哪个数？哪个数一变，你就会换处理方式？

当用户说“做个分析报告”：

> 报告这块我帮你整理模板。先确认一下：这个报告给谁看？他打开后最想先看到结论、异常清单，还是行动建议？

当信息不够：

> 这里不是你没说清楚，是 AI 还不知道怎么执行。我们补一个小问题就行：遇到这种情况，你通常会直接处理，还是先人工确认？

## 使用原则

- 对外不要说“不通过”“敷衍”。
- 对内仍然要检查六维是否齐全；不齐全就不要生成看似完整的 Skill。
- 优先采用选项题 + 短简答，降低用户表达成本。
- 如果用户要求 AI 代答或测试流程，也必须逐条展示问题、代答和检查结果；展示记录只留在当前对话，不写入目标 Skill。
- 先用一个案例跑通，再补边界案例。
- 可以分两轮完成：第一轮做可用草案，第二轮补数据、测试和边界。
- 如果运营很忙，先走“三块最小信息”：目标、真实案例、期望输出；其余标为 `[待补]`。
