# 执行日志与自我迭代

Skill 可以根据真实使用反馈变得更好，但不能让它因为一次失败就随意改规则。尤其是运营 Skill，单个案例的修复可能会伤害其他场景。正确做法是：先记录，再评测，再人工确认，最后沉淀。

本文件处理“如何把反馈沉淀成更好的 Skill”。如果目标是判断一个内测 Skill 是否值得提交团队候选库，先读 `references/skill-submission-governance.md`；如果目标是记录每次执行摘要，先读 `references/execution-log-schema.md`。

## 1. 适用场景

当 Skill 会被长期使用、多人使用或定期巡检时，建议加执行日志。一次性草案可以不加。

适合记录的 Skill：

- 周报、月报、巡检、异常监控。
- 广告诊断、库存风险、利润异常、竞品跟踪。
- 需要持续修正阈值、字段、例外和输出模板的流程。
- 已经出现“这个情况上次处理错了”的重复反馈。

## 2. 记录什么

每次执行后，先按 `references/execution-log-schema.md` 记录到 `runs/YYYY-MM.jsonl`。当出现用户纠正、错误、功能需求或复盘时，再写入 `diary/YYYY-MM-DD.md`：

```json
{
  "time": "2026-05-18T10:00:00+08:00",
  "skill_version": "0.1.0",
  "prompt": "用户真实请求",
  "input_summary": "输入文件/时间范围/站点/ASIN/部门",
  "output_paths": ["outputs/report.html"],
  "assertions": [
    {"text": "必须标注数据周期", "passed": true}
  ],
  "user_feedback": "哪里有用，哪里不对",
  "failure_reason": "",
  "fix_suggestion": ""
}
```

不要把账号密码、token、cookie、客户个人信息或未经授权的原始明细写入日志。需要保留样本时，先脱敏。

## 3. 失败案例沉淀

当一次执行失败时，不要马上改 `SKILL.md`。先写入失败日记：

```markdown
## 2026-05-18 / case-001

- 触发请求：
- 输入摘要：
- 失败表现：
- 影响范围：
- 初步原因：
- 建议修复：
- 需要用户确认：
```

把失败分成几类：

- 触发失败：该用 Skill 时没触发，或不该用时触发。
- 输入失败：漏问关键字段、文件、周期、站点、币种。
- 数据失败：字段不存在、过滤不清、权限失败、结果为空。
- 判断失败：误判异常、漏掉例外、阈值不适合。
- 输出失败：格式不稳定、老板看不懂、行动建议不可执行。
- 跨工具失败：当前工具能做，替代方案做不到或结果不一致。

## 4. 什么时候改成正式规则

满足以下条件，才把失败建议写入正式 Skill：

- 同类失败至少出现 2-3 次，或单次失败风险很高。
- 能写成清晰的判断规则、追问条件、脚本校验或输出约束。
- 不会与已有正常案例冲突；如可能冲突，先加入例外而不是覆盖原规则。
- 已补充或更新测试用例。
- 重跑核心回归用例后没有退化。
- 业务负责人或用户确认。

## 5. 自我迭代的安全边界

可以让 AI 提出修复建议，但不要让它在没有评测兜底时自动改正式 Skill。

允许：

- 自动整理失败日志。
- 自动生成候选 patch。
- 自动补测试用例草案。
- 自动对比新版和旧版输出。

不允许：

- 没有用户确认就改变关键业务阈值。
- 没有回归测试就删除原有例外。
- 把单个 case 的特殊处理写成全局规则。
- 把临时数据、个人信息或内部明细写进 Skill。

## 6. 交付格式

需要持续迭代的 Skill，在交付时补：

```markdown
## 执行记录与迭代

- 日志位置：
- 记录字段：
- 失败分类：
- 进入正式规则的条件：
- 人工审核人：
- 回归测试用例：
- 最近一次迭代结论：
```
