# 交给当前 AI 工具的 skill-creator

本 Skill 不替代 skill-creator/技能创建器。推荐分工：

- `ops-creator-skill`：负责跨境运营访谈、业务 6 维确认、ops 数据方案、测试意图和流程地图。
- 当前 AI 工具可用的 `skill-creator` 或同类技能创建能力：负责正式创建或更新 Skill，保证目录结构、frontmatter、资源拆分、界面元数据和校验符合该工具规范。

不要写死某一个平台的内置创建器。在 Codex、Claude、Cursor、Dify、Coze、飞书智能伙伴或公司内部 Agent 中，都按当前环境实际可用的 Skill 创建方式落地。

## 交接前必须准备

在调用 skill-creator/技能创建能力前，先整理出：

- Skill 名称候选：英文小写连字符，描述动作，不超过当前工具要求的长度。
- 中文展示名和中文简介。
- YAML/frontmatter `description` 草案：中文，写清“做什么 + 什么时候触发”。
- 触发描述检查：避免“处理运营问题”这类泛描述，加入真实触发话术、业务对象和关键词；需要跨工具复用时不要绑定某一个 AI 平台名。
- 目标用户和目标任务。
- 触发话术。
- 快速开始示例：1-2 条真实用户输入，以及 Skill 应该如何起步。
- 必要参数表：参数名、是否必需、来源、默认值和缺失时怎么追问。
- 必要输入、来源系统和数据口径。
- 工作流步骤。
- 判断规则、例外、升级条件。
- 错误处理：缺输入、缺权限、数据为空、字段不存在、脚本失败、跨工具能力不可用时的处理方式。
- ops 数据取数方案。
- 取数预检结果：模拟问题、查询计划、字段校验、dry-run/smoke query、失败降级方案。
- 跨 AI 工具兼容方案：当前工具专属能力、通用替代路径和对比校验方式。
- 可固化为 Python 脚本的步骤。
- HTML 展示需求。
- 输出规范。
- 测试 prompt 和断言。
- 版本、CHANGELOG、负责人、回归门槛和更新分发方式。
- 执行日志、学习日记和失败案例沉淀方式。
- 内测提交方案：状态、候选门槛、提交包内容、脱敏检查、提交人、审核人和团队候选库位置。
- 统一框架方案：主 `SKILL.md` 日常执行内容、按需加载 references、稳定脚本、默认上下文预算和 token 优化方式。
- 如果是改造旧 Skill：旧版基线、保留的触发话术、保留的脚本/输出、共同基础设施修正、同源对比方案。
- 待确认问题。

## 推荐交接提示

```markdown
请使用当前 AI 工具可用的 skill-creator/技能创建能力，根据下面的运营流程地图创建或更新一个可复用 Skill。

要求：
- 默认中文编写 `SKILL.md` 正文、references、输出模板和 UI 文案。
- YAML/frontmatter `name`、文件夹名、脚本名和字段名保留英文或原文。
- 使用 progressive disclosure：主 `SKILL.md` 放核心流程，长规则/案例/数据取数/测试放 `references/`。
- 按 `ops-creator-skill` 统一框架生成：主 `SKILL.md` 必须包含快速开始、必要参数、日常工作流、按需加载资料、错误处理、输出规范、执行日志与候选提交；完整业务资料拆到 `references/`。
- 内容不减少但默认加载更少：日常执行只加载 `SKILL.md` 和本次必要的 0-2 个 reference；测试、发布、跨工具迁移、错误排查或用户明确要求优化时再加载完整资料。
- 必须写清默认执行策略：已固化流程默认直接执行，只追问缺失参数；不要在日常执行中重复做取数预检、baseline 测试、发布治理或长篇流程介绍。
- 涉及 ops 内部数据时，把生成/更新前的取数预检结果放入 reference；日常执行默认使用已验证取数规则，只有字段变化、权限失败、空结果、新场景或用户要求时才重新展开预检。
- 主 `SKILL.md` 优先包含：快速开始/使用示例、必要参数、工作流、默认执行策略、错误处理、输出规范；测试与基准对比只保留按需加载入口，详细内容放 reference。
- `description` 要写得积极且具体：说明做什么、何时触发、常见业务关键词和真实话术；跨工具复用时不要写死当前 AI 工具名。
- 涉及 ops 内部数据时，必须写入生成前取数预检结果：模拟问题、候选数据集、字段校验、dry-run/smoke query 和失败降级方案。
- 需要兼容其他 AI 工具；当前工具专属能力必须写替代方案，可先用当前工具输出作为参照，再用替代方案输出做对比校验。
- 如有稳定重复的数据清洗、报告生成、HTML 渲染或校验动作，优先用 Python 放入 `scripts/`；脚本应提供 `--help`、结构化 JSON 摘要、明确退出码和中文错误信息。
- 团队共享时，补 `CHANGELOG.md` 或发布说明、版本、负责人、回归测试结果和更新方式。
- 需要持续迭代时，补执行日志和失败案例沉淀规则；自我改进建议必须经过断言复测和人工确认后才能写入正式规则。
- 参与运营内测的 Skill 默认带 `references/execution-log-schema.md`、`references/skill-submission-governance.md`、`scripts/qualify_candidate.py` 和 `scripts/package_submission.py`；多次执行有效后才提交候选库，未经用户确认不得自动提交。
- 如当前工具支持界面元数据、默认 prompt、图标或校验脚本，请按该工具规范生成并校验。

流程地图：
[粘贴流程地图]
```

## 交接后检查

skill-creator/技能创建能力生成草案后，回到本 Skill 做业务检查：

- 是否还保留运营原话和关键术语。
- 是否把“看情况”拆成了可执行规则。
- 是否有快速开始示例、必要参数和错误处理，而不是只写泛流程。
- 是否有默认执行策略，且不会在日常运行时重复解释流程、预检取数或执行测试治理。
- 是否写清 Amazon/跨境电商口径。
- 是否写清内部数据来源和用途。
- 是否写清生成前取数预检结果，避免未来调用时无法构造查询条件。
- 是否写清当前工具专属能力的替代方案。
- 是否识别并固化了可脚本化步骤。
- 是否在需要时提供 HTML 展示方案。
- 是否有测试 prompt、baseline 和断言。
- 是否有版本、变更记录、负责人和团队共享前的回归门槛。
- 是否有执行日志和失败案例沉淀方式，且没有允许无评测自改正式规则。
- 是否写清内测候选门槛和脱敏提交包，且默认不提交个人草稿。
- 是否符合统一框架：轻量主文件、按需 references、稳定 scripts、日常 token 预算和框架合规说明。
- 如果是旧 Skill 改造，是否先保留基线、共同修正数据/字段/依赖、再用同一批输入和数据比较新旧输出。
- 是否存在编造阈值、字段或政策。
- 是否是在业务 6 维和阶段 1 技术细节确认后才开始落地文件。

如果业务检查不通过，先补访谈或补数据，再让 skill-creator/技能创建能力更新草案。
