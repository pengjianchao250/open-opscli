# Skill 发布治理

当 Skill 只是个人试验，可以轻量交付；当它会被运营团队、项目部、跨团队或其他 AI 工具复用时，要把它当成一个小型代码包治理。目标是避免“一个看似像文档的东西，被多人反复执行，却没有版本、测试和负责人”。

## 1. 什么时候需要发布治理

出现以下任一情况，就启用本清单：

- Skill 会发给其他同事安装或复制。
- Skill 会进入团队仓库、共享盘、内部 Skill 市场或自动化流程。
- Skill 会调用内部数据、脚本、API、文件写入或外部系统。
- Skill 会影响广告预算、库存、价格、利润、选品、绩效或对外消息。
- Skill 已经被使用过多次，并且开始出现更新、分支或旧版本问题。

内测运营提交的 Skill 先按 `references/skill-submission-governance.md` 判断是否达到 `candidate` 门槛。只有从 `candidate` 升级到 `team_beta` 或 `standard` 时，才执行完整发布治理。

## 1.1 发布状态

| 状态 | 含义 | 发布治理要求 |
| --- | --- | --- |
| `personal_draft` | 个人试验 | 不发布，只保留本地 |
| `candidate` | 多次执行有效，已生成候选包 | 做安全检查、运行摘要和人工初审 |
| `team_beta` | 内测团队可用 | 需要版本、CHANGELOG、测试和负责人 |
| `standard` | 公司标准流程 | 需要回归门槛、发布说明、升级路径和稳定负责人 |

## 2. 元数据

生成或更新 Skill 时，尽量补齐这些信息。不同平台支持字段不同；不支持的内容放到 `references/release-notes.md` 或 `CHANGELOG.md`。

```yaml
metadata:
  version: "0.1.0"
  owner: "业务负责人或团队"
  reviewer: "审核人"
  category: "operations"
  tags:
    - amazon
    - ads
```

版本建议使用语义化版本：

- `0.x`：试点中，规则还在调整。
- `1.x`：团队稳定使用。
- `x.y.z` 中 `z`：修错字、补边界、修脚本。
- `x.y.z` 中 `y`：新增场景、字段、输出。
- `x.y.z` 中 `x`：可能影响旧用法的重大变更。

## 3. CHANGELOG

团队共享的 Skill 默认维护 `CHANGELOG.md`。最小格式：

```markdown
# CHANGELOG

## 0.1.0 - 2026-05-18

- 新增：创建初版 Skill。
- 数据：使用 [数据集/导出文件]，口径为 [口径]。
- 测试：通过 [N/M] 个回归用例。
- 风险：仍待确认 [问题]。
```

每次更新必须写清：

- 改了什么。
- 为什么改。
- 影响哪些场景。
- 是否需要运营同事调整用法。
- 回归测试结果。

## 4. 发布前检查

发布前按这份清单检查：

| 检查项 | 通过标准 |
| --- | --- |
| 基础校验 | `SKILL.md` frontmatter 合法，`name` 和 `description` 可被平台识别 |
| 触发描述 | 写清“做什么 + 什么时候触发”，包含真实业务话术和关键词 |
| 渐进加载 | 主 `SKILL.md` 只放核心流程，长规则/案例/字段/测试放 `references/` |
| 脚本契约 | 脚本有 `--help`、明确输入输出、退出码、中文错误信息和结构化结果 |
| 内部数据 | 写清数据来源、字段、聚合、过滤、权限限制和失败降级 |
| 跨平台 | 平台专属能力都有通用替代方案，至少跑过一次冒烟测试 |
| 回归评测 | 核心测试用例不低于旧版或 baseline |
| 安全 | 不包含 token、cookie、密码、个人敏感信息或越权指令 |
| 负责人 | 有业务负责人和审核人，知道谁能批准规则变更 |

## 5. 回归门槛

建议用简单的二元断言作为发布门槛：

- `pass`：必须包含/必须识别/必须停止/必须降级。
- `fail`：缺字段、伪造数据、错误触发、输出不可执行、高风险建议。

团队共享前，核心用例至少满足：

- 正常案例全部通过。
- 边界案例能主动追问或降级。
- 错误/缺数据案例不能编造结论。
- 新版不能比旧版少执行关键检查。

## 6. 分发与更新

按团队实际情况选择一种方式：

- 仓库分发：适合需要版本、评审和回滚的团队。
- zip 分发：适合少量同事试用。
- 平台市场：适合公司内大范围共享。
- 项目级目录：适合某个业务项目固定使用。

更新时告诉使用者：

- 当前版本号。
- 如何安装或替换。
- 是否兼容旧用法。
- 是否需要重跑某些测试或重新授权。
- 如何反馈问题。

如果旧版本不应继续使用，在 `SKILL.md` 靠前位置写清弃用原因和升级建议。

## 7. 本地开发循环

为了减少“改一行、重启一次、复测一次”的低效循环，可以采用：

- 支持热加载的平台：直接在 Skill 目录编辑，再用同一批测试 prompt 复测。
- 不支持热加载的平台：保持 dev/prod 两份目录，用同一批测试 prompt 对比。
- 仓库开发：用软链把开发目录指向平台 Skill 目录，避免复制错版本。
- 每次改动后至少跑一次基础校验和核心冒烟用例。

不要因为平台支持自动更新，就跳过人工审阅和回归评测。
