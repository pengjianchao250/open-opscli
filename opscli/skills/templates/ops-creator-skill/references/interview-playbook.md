# 访谈问题库

使用这份问题库，从运营专家的真实案例里整理出流程、判断规则和交付标准，而不是一上来要求对方写正式 SOP。默认用中文提问、中文总结、中文生成 Skill。

## 访谈姿态

把运营同事当领域专家，不要把他当文档撰写者。先问真实案例、决策、错误和交付物，不要先问抽象原则。

好的访谈方式：

- 每次只问一小组问题。
- 先复盘真实案例，再提炼规则。
- 用结构化方式复述运营原话。
- 保留本地术语和缩写。
- 不确定的规则标为 `[待确认]`，不要替对方圆过去。

避免：

- "请完整描述你的所有方法"
- "这个流程的 SOP 是什么"
- "有没有其他补充"
- 对方说“看情况”时替他编阈值

## 开场话术

可直接使用或微调：

> 我们先不写 SOP。你只要讲一个最近真实发生的案例，我来负责追问和整理。目标是把你平时做判断的步骤，变成 AI 以后能照着做的 Skill。

接着问：

1. 这个 Skill 最想帮谁做什么事？
2. 最近一次你处理得比较准的案例是什么？
3. 这件事最后交付了什么结果？

如果对方担心麻烦，补一句：

> 不用一次讲完整，我们先用一个案例跑通。缺的信息我会一点点问，不需要你自己整理成文档。

## 模块 A：范围

目标模糊时使用。

- 这个流程主要用于哪个团队、账号、平台、渠道、品类或业务场景？
- AI 应该在用户说什么话时触发这个 Skill？
- 这个 Skill 最终应该输出什么：诊断、报告、表格、操作建议、复盘、告警、SOP、邮件草稿？
- 哪些事情不属于这个 Skill，遇到后应该拒绝、转交或另开流程？
- 哪些工具、系统、数据表、模板或文件是必须用的？

## 模块 B：案例复盘

尽量优先使用这个模块。

- 这次案例的触发点是什么？谁发现的？用户原话大概是什么？
- 你第一步打开了什么工具或数据？为什么先看它？
- 你最先看的 3 个信号是什么？
- 哪个信号让你觉得方向变了？
- 你当时排除了哪些看似可能的原因？
- 中间有没有一个关键判断点？你怎么判断的？
- 最后输出了什么？谁看？怎么用？
- 怎么知道这次处理是对的？

## 模块 C：判断规则

运营讲完案例后使用。

- 这一步有没有固定阈值、范围、排序、同比/环比、预算比例、转化漏斗或优先级？
- 如果没有固定阈值，你通常拿什么做参照？
- 什么情况下这个规则不成立？
- 哪些指标必须一起看，不能单独看？
- 哪些信号只是噪音，通常可以忽略？
- 新人看到同样数据时最容易误判什么？
- 你会怎么向新人解释这个判断？

## 模块 D：对比案例

用于挖出边界条件。

要求对方提供三类案例：

1. 一个失败或返工案例。
2. 一个边界案例。
3. 一个看起来相似但处理方式完全不同的案例。

每个案例都追问：

- 它和正常案例最像的地方是什么？
- 关键区别在哪里？
- 如果 AI 按正常流程处理，会错在哪里？
- 哪个信号应该触发升级、暂停或人工确认？

## 模块 E：材料与数据

当 Skill 会处理报告、表格、看板、广告、Listing 或内部系统时使用。

- 输入文件或数据长什么样？字段名是什么？
- 数据口径有没有坑：时间区间、币种、站点、归因、退货、税费、广告口径、自然/付费拆分？
- 输出有没有固定模板、字段、排序或命名规则？
- 有没有截图、历史报告、优秀样例、差样例可以作为 reference？
- 数据缺失、异常、重复、延迟时怎么处理？

## 模块 F：质量与审核

起草 Skill 前使用。

- 你怎么判断 AI 的结果是靠谱的？
- 哪些错误是小问题，哪些错误会造成业务风险？
- 交付前必须检查哪几项？
- 哪些建议不能直接给，必须标注假设或需要人工确认？
- 谁拥有最终解释权？

## 模块 G：Skill 封装

流程信息已经足够后使用。

- Skill 名称应该描述什么动作？
- 触发描述里必须包含哪些场景词？
- 哪些内容应该放在 `SKILL.md` 的核心流程里？
- 哪些长例子、字段说明、模板或术语表应该放进 `references/`？
- 有没有稳定重复的转换、清洗、格式化动作值得写成 `scripts/`？

## 每轮总结模板

每轮访谈后这样总结：

```markdown
## 已确认
- ...

## 暂定规则
- ... [待确认: 需要运营确认阈值/例外/口径]

## 还缺
- ...

## 下一轮只问
1. ...
2. ...
3. ...
```
