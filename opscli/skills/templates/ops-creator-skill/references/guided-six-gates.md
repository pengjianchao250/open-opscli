# 六维引导式访谈脚本

本文件是阶段 0 的硬门槛。目标是把用户脑子里的真实流程问成可执行规则，而不是让 AI 直接猜一个 Skill。

## 总协议

1. 必须顺序推进 `Q1 → Q6`，一个主题完成并通过内部检查后再进入下一个主题。
2. 每题用“低负担选项 + 一段短简答”推进；有结构化提问 UI 时可用，没有时用聊天选项降级。
3. 阶段 0 没有复述并获得用户确认前，不得创建或更新 `SKILL.md`、脚本、目录、压缩包或看似完整的草案。
4. 用户说“别问了，你代答”时，只能输出 `我问 → AI 代答 → 内部检查 → 待用户确认`。代答内容不得写入正式 Skill 文件。
5. 用户贴长文时，先抽取已回答内容，再按缺口回到对应 Q；不要把长文等同于确认完成。
6. 如果任务被判断为“不值得创建 Skill”，停止访谈，给更轻替代物。

## Q1 业务目标

问：

> 这个 Skill 主要解决什么业务问题？如果不做，一次大概浪费多少时间、多少钱、机会或返工成本？

内部通过标准：

- 有明确业务目标。
- 有重复使用价值。
- 至少有时间、金额、销量、风险、机会或返工成本中的一种代价。

不通过时补问：

> “提升效率”还不够落成 Skill。现在一次要花多久？最想省掉哪一步？

## Q2 当前做法

问：

> 现在怎么做？是纯手动、用工具但要串联、半自动，还是全新流程？最烦或最容易错的是哪一步？

内部通过标准：

- 有当前基线。
- 说明了工具、耗时、痛点或风险。
- 不是只说“看一下”“整理一下”。

## Q3 具体步骤

问：

> 请按第 1 步到第 N 步写。每一步用：
>
> ```text
> 第 X 步：[动作]
>   输入：[来自哪里]
>   输出：[产出什么]
>   判断：[如果 xxx 则 yyy，否则 zzz；没有就写无]
> ```

内部通过标准：

- 至少 3 步，最好 5-8 步。
- 每步有输入和输出。
- 非线性流程有明确 if/else。
- 涉及数据时能说出来源系统或文件。

## Q4 方法论

问：

> 这个流程最关键的判断是什么？最好写成“如果……则……”。没有阈值也可以说没有，我会标成待校准。什么情况看起来像但不能按常规处理？

内部通过标准：

- 至少一条可执行判断。
- 至少一个例外、升级或人工复核条件。
- AI 不得自行编造阈值、政策、平台规则或补偿方案。

## Q5 调用方式

问：

> 以后你或同事会怎么叫起这个 Skill？给 2-3 句真实话术，不要写说明书。

内部通过标准：

- 有触发方式。
- 有业务入口。
- 至少两句真实触发话术。

## Q6 期望输出

问：

> 跑完后要交付什么？落到哪里？文件怎么命名？什么信号代表完成？

内部通过标准：

- 有输出类型。
- 有落点或接收人。
- 有命名规则或完成信号。
- 不把“生成本地文件”当成唯一完成条件。

## 阶段 0 复述确认

Q1-Q6 全部通过后，必须先复述并等待用户确认：

```markdown
## 阶段 0 已确认
- Q1 业务目标：
- Q2 当前做法：
- Q3 具体步骤：
- Q4 方法论：
- Q5 调用方式：
- Q6 期望输出：

## AI 假设，待用户确认
- ...

## 暂不能写入正式 Skill 的内容
- ...
```

用户确认后，才进入阶段 1。

## 阶段 1 技术补充

阶段 0 确认后，再确认：

1. 是否要做测试：至少 2-3 个真实 prompt 和断言。
2. 数据入口优先级：ops/BI、CSV/Excel、API、飞书或其他；涉及 ops 数据时给 2-3 句未来真实提问用于取数预检。
3. 调用频率：每天、每周、固定巡检、一事一议。
4. 使用人群：自己、运营、客服、产品、广告团队、跨团队或全公司。

阶段 1 确认后，才能进入流程地图、数据预检、脚本固化、测试方案和 Skill 文件生成。

## 代答规则

如果用户要求 AI 代答：

- 可以根据场景生成一版代答草案。
- 每条代答都必须标 `[AI 假设，待用户确认]`。
- 输出后停下来请求用户确认。
- 不得创建、覆盖、安装或打包正式 Skill。

## 停止创建规则

如果发现需求只是一次性通知、单条消息、临时文案、没有复用场景、没有明确输入输出，直接停止创建。输出：

```markdown
不建议创建 Skill。
原因：
更合适的交付：
如未来要做成 Skill，需要补充：
```
