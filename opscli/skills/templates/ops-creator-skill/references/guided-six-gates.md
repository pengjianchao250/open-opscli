# 六维引导式访谈脚本

本文件是 `ops-creator-skill` 阶段 0 的执行脚本。目标是用分层问题和低负担选项，把跨境电商运营流程、判断规则和交付标准问实，再进入 Skill 文件生成阶段。

不要把整份文档发给用户填写。AI 要按下面脚本一层一层问，记录答案，逐题检查。对用户保持轻松表达；内部检查可以严格，但不要对用户说“不通过”“敷衍”。

## 总协议

1. 必须顺序推进 `Q1 → Q6`，一个主题完成后再进入下一个主题。
2. 每个主题用“选项题/低负担选择 + 一段短简答”的方式推进；当前工具有结构化提问 UI 时优先用 UI，否则用聊天列选项。
3. 每题结束都做内部检查；如果答案为空、抽象、矛盾、只有动作没有判断、只有“看情况”没有规则，就当场补问。
4. 阶段 0 没有复述并获得用户确认前，不要创建 `SKILL.md`、脚本、目录或完整草案。
5. 如果用户要求 AI 代答或使用已有材料代替回答，仍然要逐条显示：`我问 → 我代答 → 内部检查`。展示内容只放在当前对话，不写入目标 Skill 文件或 references；展示完整过程后再生成文件。
6. 如果用户贴长文，先抽取已回答的信息，再按缺口回到对应 Q，不要直接判定完成。
7. 如果用户说“先快速试试”，可只问 `Q1 + Q3 + Q6`，但要明确说明这是低保真草案，团队复用前必须补 Q2/Q4/Q5。

## 交互式提问与降级

把结构化提问当作增强体验，不当作硬依赖。优先级如下：

1. `结构化提问 UI`：当前 AI 工具有按钮式选项、表单卡片或类似交互能力，且当前会话模式允许使用时，优先用它问本主题的 L1 低负担选择题。
2. `聊天选项降级`：当前工具没有结构化提问 UI、模式未开启、用户中断卡片、或其他 AI 工具不支持时，直接在聊天里列出 3-5 个业务选项，并允许用户自由补充。
3. `表单/HTML 兜底`：需要多人异步补充、运营不方便连续对话、或要收集多个同事经验时，可生成 Markdown 表单或静态 HTML 表单；回收后再按 Q1-Q6 做内部检查。

使用结构化提问 UI 时遵守：

- 一次只问一个主题，不要把 Q1-Q6 全部塞进一张卡片。
- 选项必须互斥或含义清楚，默认推荐项放第一位，并用运营能看懂的话表达。
- 每题保留自由补充入口，避免运营经验被选项限制住。
- 结构化 UI 只负责降低表达成本；真正的通过标准仍看答案是否具体、有数据来源、有判断规则、有例外和输出标准。
- 如果工具要求切换特定模式才能使用结构化 UI，不要强迫用户切换；除非用户明确想要按钮式体验，否则自动用聊天选项继续。

聊天选项降级示例：

```markdown
先定一下这个 Skill 的业务类型，你可以直接选，也可以补充自己的说法：

1. 自动化：固定周报、数据整理、模板填写、批量检查
2. 风险监控：库存告急、差评暴增、排名暴跌、广告失控、利润异常
3. 决策支持：广告调价、补货、选品、定价、Listing 改版、预算分配
4. 团队交付：给运营、供应链、项目部、老板输出报告或异常清单
5. 培训交接：把资深同事的流程变成新人可照做的 SOP/Skill

选完后再补一句：如果不做这个 Skill，现在最浪费时间或最容易出错的是哪里？
```

## Q1 业务目标

### L1 业务类型

问：

> 这个 Skill 主要帮你解决什么类型的业务问题？可以多选或直接说你的答案：自动化、风险监控、决策支持、团队交付、培训交接。

跨境电商常见选项：

- 自动化：固定周报、数据整理、模板填写、批量检查。
- 风险监控：库存告急、差评暴增、排名暴跌、广告失控、利润异常。
- 决策支持：广告调价、补货、选品、定价、Listing 改版、预算分配。
- 团队交付：给运营、供应链、项目部、老板输出报告、异常清单、飞书消息。
- 培训交接：把资深同事的流程变成新人可照做的 SOP/Skill。

### L2 不做的损失

继续问：

> 如果不做这个 Skill，会损失什么？尽量给一个量化感受，比如每次多花几小时、每月多浪费多少钱、错过什么机会，或者新人会在哪里返工。

### Q1 内部检查

通过标准：

- 说清业务类型。
- 说清不做的代价。
- 至少有时间、钱、销量、风险、机会、返工成本中的一个量纲。

补问示例：

> “提升效率”还不够落成 Skill。你现在一次要花多久？最想省掉哪一步？

## Q2 当前做法

### L1 自动化程度

问：

> 你现在做这件事处于什么状态？选最接近的一类：纯手动、用专业工具但还要串联、已经半自动、全新流程。

常见选项：

- 纯手动：Excel、肉眼对比、复制粘贴。
- 用专业工具但还要串联：内部系统、ERP、BI、飞书表格、Amazon 后台、第三方工具之间要搬数据。
- 已经半自动：有 Python 脚本、Excel 模板、宏、BI 图表或工作流，但还要人工触发和复核。
- 全新流程：以前没有系统做过，只是偶尔临时处理。

### L2 卡点

继续问：

> 现在做一次大概花多久？最烦、最容易出错、最容易拖延，或者新人最容易漏掉的是哪一步？

### Q2 内部检查

通过标准：

- 说明当前状态。
- 如果不是全新流程，说明至少一个耗时、痛点或风险点。
- 不能只说“用 Excel 看一下”。

补问示例：

> “用 Excel 看一下”太粗了。你打开 Excel 后先看哪一列，接着怎么判断？

## Q3 具体步骤

这是最关键的一题，分三层问。

### L1 数据来源

问：

> 这个流程会用到哪些数据来源？可以多选：内部系统/ops、Amazon 后台报表、Amazon 业务报表、广告 API/BI 已同步数据、本地 Excel/CSV、飞书表格、人工粘贴、其他。

跨境电商常见数据：

- 内部系统/ops：订单、利润、库存、负责人、项目部、渠道、ASIN 归属。
- Amazon 后台报表：广告活动、搜索词、投放 ASIN、Business Report、库存、Listing。
- 广告 API/BI：campaign、ad group、ASIN、广告类型、花费、销售额、订单。
- 本地 Excel/CSV：运营导出的临时文件或固定模板。

### L2 流程复杂度

问：

> 这个流程的判断分支有多复杂？线性流程、少量分支，还是复杂判断？

### L3 逐步骤描述

继续问：

> 请按第 1 步到第 N 步写出来。每一步用这个格式，不用追求完美：
>
> ```text
> 第 X 步：[动作]
>   输入：[来自哪里？文件/系统/上一步结果]
>   输出：[产出什么？]
>   判断：[如果 xxx 则 yyy，否则 zzz；没有判断就写“无”]
> ```

### Q3 内部检查

通过标准：

- 已知主要数据来源。
- 至少 3 步，最好 5-8 步。
- 每一步至少有输入和输出。
- 非线性流程必须出现至少一个明确判断分支。

补问示例：

> 你刚才说“复杂判断”，但步骤里还没有 if/else。哪一步会改变处理方式？比如什么指标一高就要降价，什么情况只观察？

## Q4 方法论

### L1 判断框架

问：

> 这个流程主要靠哪些判断框架？可以多选：阈值判断、趋势对比、优先级排序、异常归因、例外排除、样本量、业务阶段、广告占比异常、利润/毛利约束、库存约束。

### L2 关键规则

继续问：

> 从这些方法里挑最关键的 1-3 条，最好写成“如果……则……”或“超过/低于多少就算异常”。如果目前没有明确阈值，也直接说“没有”，我会把它标成默认起点 + 待校准。

### L3 例外条件

继续问：

> 什么情况看起来像这个问题，但不能按常规规则处理？比如新品、大促、断货、Buy Box、价格刚调整、品牌防守等。

### Q4 内部检查

通过标准：

- 至少有一个判断框架。
- 至少有一条可执行规则，或明确说明“暂无规则，需要默认建议并待校准”。
- 至少有一个例外、升级条件或人工复核条件。

补问示例：

> “看情况”没问题，我们把判断拆小一点：你通常在比哪两个数？哪个数一变，你就会换处理方式？

## Q5 调用方式

### L1 触发方式

问：

> 你希望这个 Skill 平时怎么被触发？一句话直接跑、先问参数、上传文件后自动识别、几种都要，还是定期触发？

### L2 业务入口

继续问：

> 它最常从哪些业务入口被叫起？比如内部系统/ops、Amazon 后台、Excel/CSV、飞书、老板临时问题、团队周会、项目部复盘。

### L3 真实话术

继续问：

> 给我 2-3 句你真的会说出口的话，不要写说明书，按你平时跟 AI 或同事说话的口气写。

### Q5 内部检查

通过标准：

- 已知触发方式。
- 已知至少一个业务入口。
- 至少两句真实触发话术。

补问示例：

> 请按你平时真的会说的话写一句，比如“帮我看下上周哪个广告活动在浪费钱”，不要写“运行本 Skill”。

## Q6 期望输出

### L1 产物类型

问：

> 这个 Skill 跑完后，你最希望拿到什么？Markdown 简报、Excel/CSV、HTML 页面、异常清单、行动建议、飞书消息、操作步骤，还是其他？

### L2 落点

继续问：

> 结果应该落到哪里？当前对话、本地目录、飞书群/文档/表格、共享盘、内部系统，还是只要直接回复？

### L3 命名规则和完成信号

继续问：

> 文件怎么命名？完成后怎么告诉你算交付完成？

### Q6 内部检查

通过标准：

- 已知输出类型。
- 已知落点。
- 有命名规则或完成信号。

补问示例：

> “给我一个报告”还不够。报告给谁看？他打开第一屏必须看到什么？

## 阶段 0 复述确认

Q1-Q6 全部通过后，必须先复述并等用户确认：

```markdown
## 阶段 0 已确认
- Q1 业务目标：
- Q2 当前做法：
- Q3 具体步骤：
- Q4 方法论：
- Q5 调用方式：
- Q6 期望输出：

## 待确认
- ...

## 我将写入 Skill 的核心规则
- ...
```

用户确认后，进入阶段 1。

## 阶段 1 技术补充

阶段 0 确认后，再问这 4 个技术细节。若前面已回答，复述并请用户确认。

1. 是否要做测试？建议正式团队 Skill 都要有 2-3 个真实 prompt 和断言。
2. 数据入口优先级是什么？内部 ops/BI、用户上传 Excel/CSV、API、飞书、还是其他？有没有现成工具/脚本可复用？如果会用 ops 数据，请补 2-3 句未来同事真实会问的问题，用来做取数预检。
3. 调用频率是什么？每天、每周、固定巡检，还是一事一议？
4. 谁来用？自己、项目部运营、广告团队、跨团队，还是全公司共享？

阶段 1 确认后，再进入流程地图、数据方案、取数预检、脚本固化、测试方案和 Skill 文件生成。
